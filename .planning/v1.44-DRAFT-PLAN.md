# Milestone v1.44 — Human-in-the-Loop Workflows (Draft Plan)

**Status:** Draft — not yet opened as a milestone. Awaits `/gsd:complete-milestone` (v1.43.0) and `/gsd:new-milestone` (v1.44) before phases formally exist.
**Captured:** 2026-07-03
**Source:** Design synthesis of three independent HITL proposals (runtime-first, DSL-ergonomics-first, product/operations-first), reconciled against the actual v1.43 codebase. The competing proposals and the reasoning that selected between them are preserved in the "Alternatives Considered" appendix.

## Why This Milestone Exists

Skytime can now run durable workflows, trigger them from webhooks and cron, and demonstrate crash recovery (v1.43). But every flow to date is **fully automated** — the DAG runs start-to-finish with no place for a person to intervene. Real integration work is full of gates that a machine cannot close:

1. **Approvals.** "Hold the refund until a manager approves." "Don't ship until the release owner signs off." "Revoke access unless the reviewer confirms it's still needed." These are the single most common request for any orchestration tool, and Skytime has no way to express them.
2. **Human-supplied data.** Sometimes the workflow needs a value only a person has — a tax ID, a budget code, a triage severity — before it can continue.

Today a flow author who needs this has to leave Skytime: split the process into two flows joined by hand-rolled correlation state, stand up their own callback endpoint, invent their own token scheme, and give up the "the flow reads like the business process" property that is the whole pitch. The framing question from the field is exactly right: *how do we represent a human in Starlark, how does the workflow wait, and how does it resume when the person does their part?*

This milestone answers all three. It also inherits — and finally **must** solve — a hazard v1.43 could tolerate: the lambda re-parse / content-hash footgun (`FlowNotInRegistry` when a `.star` file is edited while a workflow is in flight). At v1.43's minutes-long timescales that window is narrow. HITL waits are measured in days and weeks, so an unrelated edit to a repo while an approval is pending would strand it. The content-addressed flow archive (Phase 8.4) closes that class of failure.

## Milestone Definition of Done

A flow author can:

1. Write `human_task(...)` in a `.star` flow body — declaring *who* must act, *what typed data* they must return, and *what happens if they don't* — and have `skytime validate` type-check it and downstream `ctx.<alias>.<field>` accesses at parse time.
2. Run that flow on `skytime server`; the workflow **parks** at the gate as a pure Temporal wait (durable timer + signal channel), consuming no worker-side state.
3. Have the assignee receive a notification through an ordinary extension (Slack/email/HTTP) — no notifier code ships in Skytime core.
4. Have the assignee click a signed link, land on a stdlib-rendered form, submit a decision, and **watch the workflow resume exactly once** — recording who decided, when, and via which channel — *even if the worker was down at the moment of the click.*
5. Test the whole thing under `skytime test` with a mocked human response on the virtual clock, passing the run-twice replay-determinism check.
6. Demonstrate the load-bearing demo: open an approval, **kill the server, click Approve while it is down**, restart the server, and watch the flow branch on the decision and complete — then read `decided_by` in the dashboard.

## Locked Design Decisions

These were settled during synthesis and do not need to be re-litigated. Where the three source designs disagreed, the reason for the choice is given.

| Decision | Choice | Reason |
|----------|--------|--------|
| Human representation | New body-level DAG node `human_task(...)` — a genuine 7th primitive | A human gate is a new *effect class* (durable wait on an external principal) that no composition of the six existing primitives can express. Modeling it as a `step` breaks the "step = one `ExecuteBatch` activity" contract; modeling it as a second `trigger`-launched flow shatters "the flow reads like the process." |
| **Wait mechanism** | **Temporal Signal** (`workflow.GetSignalChannel` + `Selector` + `workflow.NewTimer`) — *not* Update | This is the milestone's crux. Signals are durably appended to history **by the Temporal server regardless of worker liveness**; a human clicking Approve during a worker redeploy must never get an error or a lost decision. Workflow Update requires a live polling worker to accept the decision (down-worker click → block → 503 → lost). Durability-through-worker-death is Skytime's entire v1.43 identity, and month-long HITL waits make "worker down at click time" routine, not an edge case. The synchronous-verdict UX that Update offers is exactly nullified when the worker is down. See Alternatives Considered §A and Open Item 1 (the reserved Update upgrade path). |
| Completion ingress | `GET/POST /tasks/{token}` mounted on the existing `skytime server`, a cousin of `pkg/extension/receiver` (webhook receiver) — **not** a reuse of it | The receiver's 9-step pipeline, locked `error_class` taxonomy, and `REJECT_DUPLICATE` semantics are about *starting* workflows. Resuming a *running* workflow is a different contract and gets its own package (`pkg/extension/humantask`) and its own locked taxonomy. |
| Approver authn (v1) | Per-assignee HMAC-signed capability token; signing key is a credential ID resolved JIT via the existing `extension.CredentialHandler` | No new credential machinery — same JIT-resolution and `Secret` redaction discipline as webhook signing secrets in v1.43. Possession of an unexpired signed token = authorization; the token subject is the recorded `decided_by`. Honest capability model, documented as such (same trust stance as the v1.43 no-auth dashboard carve-out). |
| Token minting | Minted **inside the single `ExecuteBatch` activity** via a `${task.url}` sentinel + an IDs-only grant on the dispatched `ActionRef`; substituted activity-side from `activity.GetInfo` | Preserves the load-bearing **WORK-01 invariant** (exactly one workflow + one activity registered, pinned by firewall tests). The token thus appears only in the outbound notification payload — never in workflow state, DAG JSON, or Temporal history. A second `NotifyHumanTask` activity was the runner-up (see Alternatives §B); rejected to avoid amending WORK-01. |
| Typed response | `form = {...}` source-level dict literal using the existing type mini-language + a `choice:`/`enum:` extension, feeding `pkg/parser/state_schema.go` | Makes `ctx.<alias>.decision` parse-time-checked and keeps expression-mode `if_cond` typing intact. Free-form JSON payloads would kill both. |
| Notification | Author-supplied arity-2 lambda `notify = lambda ctx, task: [ActionRef...]` returning ordinary extension actions, dispatched through `ExecuteBatch` | Zero provider code in Skytime core (two-tier model). The arity-2 lambda mirrors the v1.43 `trigger(map=...)` precedent and gives typed access to the `task` struct (`task.url`, `task.title`, `task.expires_at`). |
| Timeout | **Required kwarg, no default** | A silent default on "how long may this block production" is exactly the magic Skytime avoids. One explicit line (`timeout="72h"`) is cheap. `on_timeout="fail"` (loud, non-retryable) is the default disposition; `"continue"`/`"default"`/`"escalate"` are opt-in. |
| Stale-file hazard | Content-addressed **flow archive** (server snapshots parsed `.star` bytes; boot re-parses the archive too) + a boot-time drain report | Byte-identical re-parse rehydrates the exact lambdas (lambda IDs hash whole-file bytes), so a workflow pinned to a 3-month-old hash still resolves. Build IDs remain the mechanism for *behavioral* migration; the archive kills the "someone edited a comment and stranded 40 approvals" class. |
| `for_each_parallel` nesting | **Rejected in v1** — parse error for `human_task` inside `for_each_parallel` | Per-branch task-instance keying, per-branch tokens, and update routing are a design of their own. Punt with a clear error; revisit on demand. (Design C sketched an `id@stepPath` scheme — captured in Open Items, not committed.) |
| Continue-as-new | **Not in v1** | A 30-day wait with daily reminders is ~200 history events; the ceiling is ~10K/50MB. Cap reminders at parse time (lint error if `timeout/remind_every` exceeds ~500) and CAN is unnecessary. CAN mid-DAG would need a resumable walker position — a milestone of its own. |

## Phase Breakdown

Five phases, in execution order. Proposed requirement prefix `HITL-`.

### Phase 8 — `human_task` foundation (primitive + park + test harness)

**Goal:** Establish the Starlark primitive, the DAG node, all parse-time validation, and the interpreter wait mechanic — with **timeout only** (no notifications, no HTTP ingress yet). Gates are silent; completion happens via `temporal workflow signal` by hand, which is itself proof the wait is pure Temporal. The test harness ships in the foundation phase because the wait loop is the highest replay-risk code in the milestone and "quality > speed" is a stated project constraint.

**Deliverables:**
- `human_task(id=, title=, assignee=, form=, output_alias=, timeout=, on_timeout=)` parser builtin (`pkg/parser/builtins.go`, new `builtinHumanTask` modeled on `builtinTrigger`)
- `dag.HumanTask` node type + JSON marshaling (`pkg/dag/human_task.go`); `FormKeys []string` insertion-order determinism contract mirroring `dag.Result.Keys`
- New ordered `finalize()` pass validating: literal `id` (unique per flow), `form` as source-level dict literal with the type mini-language + `choice:`, required `output_alias` feeding `stateSchema` with injected `decided_by/decided_at/timed_out` fields, duration literals with `on_timeout ∈ {fail, continue}` (the richer `default`/`escalate` dispositions arrive in 8.2), and the `for_each_parallel`-nesting rejection
- An arm for `HumanTask` in **every** hand-rolled body walker (~10 — the `walkBodyForLogSteps` comment contract lists them); `HumanTask` counts as a non-log sibling for the `[N/M]` step counter
- Interpreter: one signal channel + router coroutine + `skytime.tasks.v1` query handler registered at `NewWorkflow`; new `walkHumanTask` (`pkg/interpreter/walk_human_task.go`) with the timer/selector wait loop and workflow-authoritative payload validation + first-valid-wins dedup
- `tester.human_response(task=, response=, by=, after=)` Tier-3 builtin (`pkg/testing`) via `RegisterDelayedCallback` → `SignalWorkflow` on the virtual clock; unmocked-gate diagnostics; run-twice replay pins
- Valid/invalid fixtures (`tests/fixtures/`), regenerated goldens, docgen markers + `go generate ./pkg/parser/` for `docs/reference/builtins.md`

**Verify:** a flow with a gate parses, golden-matches, blocks under `skytime run`, completes via `temporal workflow signal --name skytime.task.complete.v1`, times out correctly with a named `HumanTaskTimeout` non-retryable error, survives kill/restart of the worker mid-wait, and passes the full `skytime test` matrix including replay-determinism. **Requirements (proposed):** HITL-01..06

### Phase 8.1 — Completion ingress (token + HTTP resume path)

**Goal:** The signed-token round trip from "manager clicks" to "workflow resumes," durable even with the worker down.

**Deliverables:**
- New temporal-free package `pkg/extension/humantask`: token mint/verify (`skt1.<b64url(claims)>.<b64url(HMAC-SHA256)>`, claims `{wid, rid, flow, hash, task, sub, exp, nonce}`), shared by activity (mint) and web handler (verify); `hmac.Equal` only, JIT credential resolution, `Secret` redaction — extend the `tests/receiver_hmac_only_test.go` and `tests/firewall_credential_redaction_test.go` grep gates to the new package
- `${task.url}` sentinel substitution inside `ExecuteBatch` (`pkg/activity/execute_batch.go`) + an IDs-only grant field on `dag.ActionRef` (JSON-safe under the marshal rules) — the WORK-01-preserving mint path
- `GET /tasks/{token}` (read-only stdlib `html/template` form rendered from the boot registry's `FormSpec` — enum→radio, bool→checkbox; mail-scanner-safe: **GET never mutates**) and `POST /tasks/{token}` (verify → pre-validate against registry → `SignalWorkflow`), mounted in `pkg/cli/server.go` after `receiver.Mount`
- New locked ingress taxonomy (do **not** grow the receiver's D-7.1-15-locked `error_class` strings): `ok, bad_token, task_expired, payload_invalid, task_unknown, already_completed, worker_unavailable`
- Idempotency ladder: double-click / replayed link / post-timeout click all resolve safely via workflow-side dedup (authoritative) + best-effort ingress query (UX only)
- Firewall test pinning the new `SignalWorkflow`/`QueryWorkflow` client call sites to exactly this seam, in the spirit of `tests/firewall_execute_workflow_test.go`
- Redacted audit rows into the existing deliveries ring buffer (token never stored)

**Verify:** curl/`gh`-driven E2E — mint via a test flow, approve via link, double-click dedup, expired-token 401, closed-gate friendly page, and the **worker-down click** case (signal accepted, processed on restart). **Requirements:** HITL-07..11

### Phase 8.2 — Notifications, reminders, escalation, defaults

**Goal:** Close the loop so a human actually learns a task awaits them, with the full lifecycle policy set.

**Deliverables:**
- `notify = lambda ctx, task: [ActionRef...]` (arity-2 capture via `captureLambdaWithArity`; a `task`-walk validator modeled on `pkg/parser/req_walk.go` pinning `task.<attr>` to the fixed struct)
- Reminder loop (`remind_every`, re-fires `notify` with `task.reminder=True`) and single-stage escalation (`on_timeout="escalate"` + `escalate_to`/`escalation_timeout`, fresh tokens for the escalated round)
- `on_timeout="default"` with a parse-time-type-checked `default={...}` payload (`decided_by="skytime:timeout"`, `timed_out=True`)
- Reminder-count cap lint (parse-time error)
- An example `smtp` extension under `examples/` (two-tier reference, like the `github` extension) and an approval flow in `examples/http-github-webhook`

**Verify:** `skytime test` scenarios asserting notify-mock kwargs at t=0, reminder at t=24h, escalation at t=48h under virtual time; replay pins for the timer-loop event stream. **Requirements:** HITL-12..15

### Phase 8.3 — Dashboard tasks page + operator actions

**Goal:** Make pending human tasks visible and completable from the teaching dashboard.

**Deliverables:**
- "Pending Tasks" panel on the stdlib dashboard, populated by `client.QueryWorkflow(..., "skytime.tasks.v1")` over running Skytime workflows (queries are read-only and replay-free), riding the existing 2s poller and SSE broadcaster; gate name, assignee, deadline, local form link
- Operator complete/reassign via the same signal path with `channel="dashboard"` and the operator string as `decided_by` (same no-auth teaching-dashboard trust boundary as v1.43)
- `skytime task list|complete` CLI (a no-HTTP completion path; also the Phase 8 smoke tool)
- A "pinned to non-live hash" badge for workflows waiting on an archived flow version

**Verify:** browser UAT per the dashboard-walkthrough house style (pinned H2 headings, golden regen via `GSD_UPDATE_GOLDEN=1`); the kill-server-mid-approval durability demo. **Requirements:** HITL-16..18

### Phase 8.4 — Flow archive + docs + hardening

**Goal:** Close the stale-`.star` hazard and ship the documentation set.

**Deliverables:**
- Content-addressed flow archive: at boot, `skytime server` snapshots each parsed source file to `<rootdir>/.skytime/archive/<sha256>.star` (write-once); `bootRegistry` re-parses the archive and registers historical `(flow, hash)` pairs (the `ErrDuplicateFlow` path gains an idempotent same-bytes carve-out); `skytime archive prune --older-than=` for retention (prunes only hashes with no open workflows)
- Boot-time drain report: after `worker.Start`, list open Skytime executions and WARN for any whose `(name, hash)` is absent from the registry, at the moment the operator can still fix it
- `docs/for-flow-authors/human-tasks.md`; `docs/walkthroughs/human-approval.md` + smoke script (the crash-mid-wait demo; mind the heading-pin and `dev-server`-grep gates)
- PROJECT.md updates: the Locked Decisions (Signal-not-Update; capability-token trust model; no CAN in v1) and a carve-out amendment for the dashboard tasks page

**Verify:** edit-the-`.star`-while-parked E2E resumes and completes against archived bytes; docs drift/heading gates green. **Requirements:** HITL-19..20

## Surface Changes (Final)

```
skytime run <file.star>            # one-shot (existing) — human_task hard-errors unless --base-url set
skytime validate <file.star>       # tier 1 (existing) — now type-checks human_task + form schema
skytime test <dir>                 # tier 3 (existing) — now supports tester.human_response
skytime server --rootdir=...       # existing — now mounts /tasks/{token}; new flags below
skytime task list                  # NEW: list pending human tasks across running workflows
skytime task complete --workflow-id=... --task=... --input='{...}' --by=...   # NEW: no-HTTP completion
skytime archive prune --older-than=...                                        # NEW: archive retention
```

New `skytime server` flags: `--base-url=` (for task links; `human_task` under `skytime run` hard-errors without it), `--task-signing-credential=<id>`, `--flow-archive=<dir>` (default `<rootdir>/.skytime/archive`).

New Starlark builtin: `human_task(...)`. Existing flows are unaffected — this is purely additive.

## Load-Bearing Demo (the point of v1.44)

```bash
$ temporal server start-dev &
$ extbin server --rootdir=./flows --task-queue=demo --base-url=http://localhost:8080 &
# Trigger the refund flow (webhook or manual dashboard trigger).
# The flow runs "hold funds", then PARKS at human_task "manager_approval".
# A Slack/email notification arrives with a signed link. Open the dashboard — the task is listed as pending.

# Now demonstrate durability — the whole reason for Signal-over-Update:
$ kill %2                              # kill the server WHILE the approval is pending
# Click "Approve" on the link. The decision is accepted by the Temporal server (200), worker or no worker.
$ extbin server --rootdir=./flows --task-queue=demo --base-url=http://localhost:8080 &   # restart
# Watch the dashboard:
#   - the parked workflow replays, re-arms its timer, consumes the queued signal
#   - it branches on ctx.approval.decision == "approve" and completes
#   - the dashboard shows decided_by / decided_at / channel
```

That the approval **survives a click against a dead worker** is the load-bearing paragraph — and the concrete reason the wait is a Signal, not an Update.

## Migration Path for Existing Users

- `human_task(...)` is additive; no existing flow changes behavior.
- Two new architectural facts get PROJECT.md decisions rather than silent scope creep: (a) the wait mechanism introduces the first Signal/timer usage in `pkg/` (new determinism surface, new firewall-pinned client calls); (b) WORK-01 is *preserved* (single activity) via the sentinel-mint approach — no invariant is amended, which is itself the reason that approach was chosen.
- The flow archive changes boot behavior (a new `.skytime/archive/` dir appears under `--rootdir`); document it and the `--flow-archive` override.

## Open Items for `/gsd:discuss-phase 8`

1. **Reserved Update upgrade path.** When a live worker *is* present, Update would give a synchronous "Approved ✓ / already decided by Alice" without the best-effort query. Do we freeze the signal name + payload shape now so a v1.45 dual-protocol (Update-first, Signal-fallback) is wire-compatible? Recommend yes — reserve the contract, ship Signal-only.
2. **`base_url` derivation.** New `--base-url` flag vs. deriving from the `Host` header (fragile per the `sanitizeOriginFromAddr` LAN-IP lesson). Recommend the flag, and hard-error `human_task` under `skytime run` when it is unset.
3. **`human_task` inside `for_each_parallel`.** Banned in v1. Design C sketched `id@stepPath` instance keying with per-branch tokens; is the "each regional manager approves their region" demand real enough to pull into 8.2? Needs a dedicated replay test before committing.
4. **Quorum / multi-approval** (2-of-3 signers). First-valid-response-wins is v1; quorum changes the wait predicate and output shape. New `quorum=` kwarg vs. compose-with-fan-out-and-`script`-tally? Recommend compose for v1.
5. **Dashboard task listing at scale.** Per-open-workflow `QueryWorkflow` is O(running workflows) per poll tick and first-page-only; a `SkytimePendingTasks` search attribute scales but needs cluster-level registration (ops friction for the teaching story). v1 = query; when does the search-attribute pressure win?
6. **Notify-failure policy.** Default is fail-loud (a silent, undelivered approval request is the worst failure mode). Worth a `notify_failure="fail"|"continue_waiting"` knob in 8.2, given the CLI/dashboard completion paths still work when delivery broke?
7. **Token expiry vs. task timeout coupling.** `exp = min(remaining, 7d)` means a 30-day no-reminder task has a dead link after a week. Force `remind_every` when `timeout > 7d`, lengthen default expiry, or document-and-accept?
8. **SDK/server floor.** Signals need nothing new, but the reserved Update path (Open Item 1) needs Temporal server ≥ 1.21. Do we document a hard minimum server version and have `skytime server` probe it at boot?
9. **Form richness ceiling.** `choice:` covers approve/reject; multi-select, file upload, and markdown are plausible asks and all stdlib-page scope-creep vectors. Recommend a *locked* decision: "one page, one form, hints only; anything richer is the deployer's own UI posting to the same endpoint."

## Alternatives Considered

Three independent designs were produced (runtime-first "A", DSL-ergonomics-first "B", product/operations-first "C"). All three converged on the same primitive (`human_task` as a 7th body node), the same typed-`form`→`stateSchema` integration, the same two-tier extension-based notification, the same mint-token-inside-an-activity discipline, and the same content-addressed flow archive for the stale-file hazard. They split on two decisions:

### A. Wait mechanism: Update (designs A, B) vs. Signal (design C) — **Signal chosen**

Designs A and B argued for Temporal **Workflow Update** on UX grounds: a validator rejects bad input *before* it pollutes history, the approver's click gets a synchronous verdict in one RPC, and double-clicks dedup server-side by `UpdateID`. These are real advantages — **when a worker is polling.** Both designs explicitly conceded the failure: Update requires a live worker to accept a decision, so a click during a redeploy blocks and 503s (design B's own comparison table: "Works while worker is down: No").

Design C argued for **Signal**: the Temporal server durably records a signal independent of worker liveness, so the decision is never lost. The cost is no synchronous validation — handled by pre-validating the token, form schema, and choices at the *ingress* (which needs only the in-memory registry, no worker) and degrading the one worker-dependent check ("already decided by someone else") to a best-effort query.

Signal wins because the tie-breaker is the project's own stated identity: the v1.43 milestone's load-bearing demo and DoD item 5 are both "kill the worker, it still completes." HITL waits of days-to-months make "worker down at click time" a routine occurrence, not an edge case — precisely the condition under which Update's advantages evaporate and its failure mode (lost human decision) is most damaging. The synchronous UX gap is small and gracefully covered by ingress-side pre-validation. The Update path is not discarded — it is reserved as a forward-compatible v1.45 dual-protocol upgrade (Open Item 1).

### B. Token minting: single-activity sentinel (design A) vs. second activity (designs B, C) — **single-activity chosen**

All three designs solve "the token must never touch workflow history" by minting inside an activity. Design A did it *inside the existing `ExecuteBatch`* via a `${task.url}` sentinel plus an IDs-only grant on the `ActionRef`, preserving the WORK-01 "exactly one activity" invariant. Designs B and C added a second `NotifyHumanTask`/`humantask.mint` activity — conceptually cleaner (mint-and-send is genuinely a different effect from batch-execute) but requiring an amendment to WORK-01, which is a deep invariant with firewall tests. Given "quality > speed / correct boundaries are hard to fix retroactively," the surgical sentinel approach was chosen; the second-activity option is the documented fallback if sentinel substitution proves too invasive during `/gsd:discuss-phase 8.1`.

## Beyond v1.44

Candidate directions surfaced during this synthesis and from `.planning/ROADMAP.md` / `RETROSPECTIVE.md`, not committed:

1. **Update-based synchronous completion (v1.45).** Ship the reserved dual-protocol: Update-first when a worker is live, Signal-fallback otherwise — the best of both wait mechanisms once the wire contract is frozen here.
