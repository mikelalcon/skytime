# Milestone v1.43 — Draft Plan (Durability + Triggers)

**Status:** Draft — not yet opened as a milestone. Awaits `/gsd:complete-milestone` (v1.42.0) and `/gsd:new-milestone` (v1.43) before phases formally exist.
**Captured:** 2026-05-08
**Source:** Design conversation following Phase 6 completion + v1.42.0 audit.

## Why This Milestone Exists

Two real gaps in v1.42.0 that the example project surfaced but did not close:

1. **No long-running worker mode.** `skytime run` is a one-shot embedded transient worker. The CLI starts, executes the flow, exits. There is no host process for Temporal to call back into when retrying or replaying after a worker crash. The example project can claim "Temporal handles replay" but cannot *show* it. That is the load-bearing durability promise — and the demo can't demonstrate it.
2. **No triggering primitive.** Skytime has zero opinions about how external events become workflow invocations. Customers writing real integrations have to roll their own HTTP server, idempotency, signature validation, and event-to-flow mapping per source. The example project hardcodes `skytime run` invocations because that's all that exists.

Plus accumulated tech debt from v1.42.0 that naturally folds into this work: `extbin` has too much boilerplate, `pkg/cli` lacks `WithBuildID` / `WithCredentialHandler`, and there's no auth-integration documentation for production Temporal connections.

## Milestone Definition of Done

A consultant can:
1. Run `skytime server --rootdir=...` against a Temporal cluster and have a long-running worker that survives crash-and-restart.
2. Declare triggers (HTTP webhook, cron) directly in `.star` files alongside flows; both register at server boot.
3. View workflows running on the server through a built-in dashboard (live workflow list + manual trigger form + recent webhook deliveries).
4. Authenticate to Temporal Cloud, self-hosted clusters, and dev-server with credentials sourced from cloud-native chains (WIF → GSM, IRSA → Secrets Manager, mTLS reload) — documented with working snippets.
5. Demonstrate replay-after-crash: open the dashboard, trigger a flow via GitHub webhook, kill the server mid-execution, restart it, watch the workflow complete.

## Locked Design Decisions

These were settled during discussion and do not need to be re-litigated.

| Decision | Choice | Reason |
|----------|--------|--------|
| Trigger primitive shape | Top-level `trigger(...)` builtin (separate from `flow()`) | Decouples flow from triggers; one flow can be triggered from many sources without rewriting |
| Trigger sources | Extension-based, return new `TriggerSource` value type | Composes with existing extension SDK; customers add their own (Stripe, Slack, custom) without parser changes |
| Cron engine | Temporal Schedules (server-side, durable) | In-process polling loses durability the moment the single `server` instance crashes; Temporal Cloud uses Schedules natively |
| Credentials | Reuse existing `extension.CredentialHandler.Resolve()` for webhook signing secrets | Same JIT resolution, same `Secret` wrapping, no new credential machinery |
| Single binary | Worker + HTTP receiver + dashboard in one process | Simpler demo; production deployments can split if they want |
| New CLI subcommand | `skytime server --rootdir=...` | Verb form parallels `validate`/`run`/`test` |
| Rename | `skytime dev-server` → `skytime dev-temporal` | Clearer (the thing it spins up is *Temporal's* server, not Skytime's). Pre-1.0; no deprecation alias needed. |
| Manual trigger UI | JSON textarea (not schema-aware form fields) | Form fields per input type is creep; JSON is enough for v1 |
| Boot path | `--rootdir=...` walks recursively for `*.star`, skips `*_test.star`, registers flows + triggers from same files | Mirrors Phase 5 worker bootRegistry pattern; one source of truth |

## Phase Breakdown

Six phases, in execution order.

### Phase 7 — Trigger primitive + server shell (foundation)

**Goal:** Establish the Starlark trigger primitive, the `TriggerSource` extension return type, the DAG node, parse-time validation, and the `skytime server` subcommand shell. Rename `dev-server` → `dev-temporal`. No HTTP receiver yet — the server just runs the worker, registers flows and triggers, prints what it would mount, and shuts down gracefully on signal.

**Why a foundation phase first:** Adding a new Starlark primitive touches parser, dag, boot, and a new lambda evaluation surface. Bundling that with HTTP routing makes the phase too big to verify cleanly.

**Deliverables:**
- `trigger(flow=, source=, map=, idempotency_key=, credential=)` parser builtin
- `dag.Trigger` node type + JSON marshaling
- New `TriggerSource` interface in `pkg/extension`
- Boot registry walks dir/pattern, registers flows AND triggers from same `.star` files
- `skytime server --rootdir=... --task-queue=... --temporal=... --credfile=...` subcommand
- Rename `dev-server` → `dev-temporal` across code + docs + CI smoke script
- Graceful drain on SIGTERM with in-flight workflow handling

**Requirements (proposed):** TRIG-01..05, SERVER-01..03, RENAME-01

### Phase 7.1 — HTTP webhook receiver + GitHub source

**Goal:** Ship the HTTP listener, the `triggers` extension exposing `github_webhook` and `generic_http_webhook` sources, idempotency via Temporal `WorkflowIDReusePolicy=REJECT_DUPLICATE`, and signature validation via the existing `CredentialHandler`. Add `gh webhook forward` walkthrough to README so the demo runs without tunnels.

**Deliverables:**
- HTTP listener mounted by `skytime server` (default `:8080`, configurable)
- `triggers.github_webhook(events=[...], secret_credential=...)` source
- `triggers.generic_http_webhook(path=..., method=..., secret_credential=...)` source
- HMAC signature validation for GitHub (sha256, X-Hub-Signature-256 header)
- Idempotency mapping (X-GitHub-Delivery → WorkflowID) with REJECT_DUPLICATE policy
- README walkthrough section: `gh webhook forward` invocation, expected output, kill-the-server-and-restart durability demo
- Updated walkthrough_smoke.sh covers webhook trigger path (or new smoke for it)

**Requirements:** TRIG-06..10, EX-05

### Phase 7.2 — Cron triggers backed by Temporal Schedules

**Goal:** Cron source backed by Temporal Schedules. Schedule lifecycle managed at server boot — register/update/delete on registry changes. Expose backfill, overlap, and reconciliation policies as Starlark kwargs.

**Open design questions to resolve in `/gsd:discuss-phase 7.2`:**
1. **Cron syntax.** Standard 5-field POSIX, robfig 6-field (with seconds), or both? Recommend 5-field only (most familiar; matches Temporal Schedules default).
2. **Backfill / catch-up policy.** If worker is down at scheduled time and recovers later, replay or skip? Temporal Schedules has `CatchupWindow` + `Overlap` policies. Defaults matter; recommend exposing as kwargs.
3. **Overlap policy.** If 09:00 run takes 65 minutes and 10:00 fires while it's still running: skip, buffer-one, buffer-all, cancel-other?
4. **Schedule reconciliation on boot.** If a `.star` file removes a `cron(...)` trigger, do we delete the corresponding Temporal Schedule? Recommend yes (registry is authoritative). Customer concern: typo deletes production schedules. Possible flag: `--reconcile=strict|preserve|dry-run`.

**Deliverables:**
- `triggers.cron(schedule=, timezone=, overlap=, catchup_window=)` source
- Temporal Schedules client integration in `pkg/cli/server`
- Reconciliation logic at boot (create/update/delete Schedules to match parsed registry)
- `--reconcile` flag for safety
- Documented examples for common patterns (daily digest, hourly poll, weekday-only)

**Requirements:** TRIG-11..14, SCHED-01..03

### Phase 7.3 — Dashboard + manual trigger page

**Goal:** Stdlib-only HTML dashboard. Live workflow list (auto-refreshing), recent webhook deliveries (in-memory ring buffer, last 100), manual trigger form (dropdown of registered flows + JSON textarea + "Run" button). Same `executeFlow` code path as webhook ingress, minus signature validation and idempotency mapping.

**Constraint:** Stdlib only — `net/http` + `html/template`. No JS framework, no external CSS. Lives entirely under `pkg/cli/server/web/` (or similar). Pre-existing PROJECT.md "Web UI / dashboard" Out-of-Scope entry needs an explicit carve-out: this is a *teaching* dashboard for the customer integration pattern, not a Skytime product feature. If we let it grow a Vue/React frontend we've changed what Skytime is.

**Deliverables:**
- Single dashboard page (`GET /`) — live workflow list via `client.ListWorkflow`
- Recent webhook deliveries section (ring buffer)
- Manual trigger form (`POST /api/trigger`)
- Schema-aware *only* in the dropdown (knows registered flows); input is plain JSON textarea
- Polling refresh (no WebSocket complexity)

**Requirements:** UI-01..04

## Crash Recovery Demo Flow

The whole point of v1.43. Reader's path:

```bash
$ temporal server start-dev &
$ extbin server --task-queue=demo &
$ gh webhook forward --events=issues --repo=me/test --url=http://localhost:8080/webhook/github
# Open http://localhost:8080 in browser
# Open an issue in the GH repo → workflow appears in dashboard, runs to completion

# Now demonstrate durability:
$ kill %2     # kill extbin server mid-flow
# Open another issue → gh webhook forward queues the delivery
$ extbin server --task-queue=demo &     # restart server
# Watch dashboard:
#   - queued webhook gets processed
#   - any in-flight workflow from before the kill resumes from event history
#   - both complete cleanly
```

That last paragraph is the load-bearing demo.

## Open Items for `/gsd:discuss-phase 7`

When we get to phase planning, the discuss step should surface:

1. **Lambda evaluation surface for trigger map functions.** The map lambda runs at HTTP request time, *before* `ExecuteWorkflow`. It is neither parse-time nor workflow-time. What predeclared globals does it get? Recommend the same locked 20-key `lambdaTimeGlobals` set (no time, no random, no I/O), plus payload struct injection, but with no determinism requirement (it runs once at ingress).
2. **`TriggerSource` value semantics.** Frozen Starlark value? Wrapped Go type with reflective access? Probably the latter — the parser stores it as an opaque payload on the `dag.Trigger` node, and the runtime's HTTP server unpacks it via type-switch.
3. **Idempotency key lambda signature.** `lambda payload, headers: str` or `lambda req: str`? Headers are commonly needed (`X-GitHub-Delivery`); two-positional is more explicit.
4. **Credential ID resolution timing.** At trigger ingress, the secret is resolved JIT (fine). But for cron, there are no per-trigger headers — credentials would need a different resolution pattern. Recommend: cron triggers don't take a `credential` kwarg in the trigger declaration; their flows resolve credentials normally inside steps.
5. **Server signal handling.** SIGTERM should drain in-flight workflows up to a configurable timeout, then SIGKILL. Default? 30s? 60s? Match Kubernetes default (`terminationGracePeriodSeconds: 30`).
