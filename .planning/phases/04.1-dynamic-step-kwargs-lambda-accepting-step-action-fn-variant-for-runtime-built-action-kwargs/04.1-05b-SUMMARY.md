# Phase 04.1 Plan 05b: Workflow-side action_fn / block_fn dispatch + name resolution + replay determinism Summary

**`walkStep` now evaluates `step.ActionFn` and `step.BlockFn` lambdas via `i.evalLambda`, type-asserts the return (`*ActionRef` or `[]*ActionRef`) into a uniform `[]*ActionRef` batch, explicitly `Freeze()`'s lambda-returned refs (W8 — bypasses parser freeze), runs `resolveKwargs` from Plan 05a to flatten interpolated string kwargs, and dispatches `ExecuteBatch` — empty `block_fn` returns short-circuit with `step_complete summary="empty batch"` (no activity dispatched). `flow.NameFn` and `step.NameFn` resolve once at the right emit point and feed the slog event labels. `bridge.CallLambda` walks `*starlark.EvalError.CallStack` to surface the user's `fail()` callsite (skipping `<builtin>` and synthetic frames) so `:line:col:` of the actual `fail("...")` call appears in the workflow's NonRetryableApplicationError message. `ActionRef.UnmarshalJSON` sorts kwarg keys before `SetKey` so the rebuilt `*starlark.Dict`'s `Items()` order matches the wire JSON across every activity-boundary round-trip — closes the last replay-determinism hazard.**

## Accomplishments

- **pkg/interpreter/walk_step.go::buildStepActions** — switchboard that returns `step.Actions` for static steps, evaluates `step.ActionFn` for single-action dynamic steps (asserts `*dag.ActionRef` return), and evaluates `step.BlockFn` for batch steps (asserts `*starlark.List` whose every element is `*dag.ActionRef`). Wrong types surface as `temporal.NewNonRetryableApplicationError` with a distinct error type per branch (`ActionFnFailed`, `ActionFnTypeMismatch`, `BlockFnFailed`, `BlockFnTypeMismatch`) and the lambda's def-site `Pos` embedded.
- **Empty-batch short-circuit (D4.1-09)** — when `block_fn` returns `[]`, `walkStep` emits `step_complete` inline with `summary="empty batch"`, `status="ok"`, then sets `deferEmit=false` so the post-ExecuteActivity defer skips its emission. No activity dispatched, no fake "0 ok" history event, observable to the renderer.
- **W8 explicit Freeze pass** — lambda-returned `*ActionRef` instances are `Freeze()`'d explicitly inside `walkStep` before `resolveKwargs` runs. Static actions are already frozen by the parser; `Freeze()` is idempotent so re-freezing them is a no-op. The invariant that activity-side `Items()` iteration is stable across replays now holds for both the static and dynamic paths.
- **resolveKwargs wiring** — `walkStep` calls `i.resolveKwargs(ctx, ref)` per-action AFTER `Freeze()` and BEFORE `ExecuteActivity`. The Plan 04.1-05a fast path returns the frozen original dict when no `*StarlarkLambda` values are present; only interpolated/dynamic kwargs pay the rebuild cost.
- **pkg/bridge/lambda_call.go CallStack walker (D4.1-08, B6)** — when `starlark.Call` returns a `*starlark.EvalError`, `CallLambda` now walks `ee.CallStack` from innermost (`len-1`) toward outermost (`0`), skipping frames whose `Pos.Filename()` is `"<builtin>"` or `""` (synthetic). The first user-source frame found is wrapped via `fmt.Errorf("%s: %w", fr.Pos, ee)`. Composed with `evalLambda`'s lambda-position prefix and `buildStepActions`'s outer wrap, the final error chain reads top-down as `action_fn lambda failed (defined at <lambda-def>): lambda <id> @ <lambda-def>: <user-fail-line>: fail: <reason>`.
- **pkg/interpreter/workflow.go::resolveFlowName + flow_start emission (D4.1-16)** — flow.NameFn evaluates ONCE inside the workflow goroutine before `flow_start` fires; the resolved string surfaces as the `flow_name` attr. Defensive fallbacks (eval error, non-string return) emit a warn-level `flow_name_lambda_error` / `flow_name_lambda_type_error` event and use the literal `flow.Name` — display-only attribute, must not fail the workflow.
- **pkg/interpreter/walk_step.go::stepDisplayLabel (D4.1-15)** — `i.stepDisplayLabel(ctx, step)` resolves `step.NameFn` (lambda eval), then `step.Name` (literal), then falls back to the existing `stepActionLabel(step)` helper. Same defensive fallback shape as `resolveFlowName`. Used at the `step_dispatch` emit site in `walkStep`, replacing the direct `stepActionLabel(step)` call.
- **pkg/dag/marshal.go::ActionRef.UnmarshalJSON deterministic rebuild** — sorts kwarg keys before `SetKey` so the rebuilt `*starlark.Dict`'s insertion order (and therefore `Items()` iteration order) matches the wire JSON. Without this, Go map range randomization made `TestWalkStep_ActionFn_ReplayFrozenKwargs` flaky (~30% failure rate) even though the wire JSON is canonical (encoding/json sorts on Marshal). Tracked as Auto-fixed Rule 1.

## Decisions Made

- **CallStack walking convention.** Rather than trust `CallStack.At(0)` (which the prior uncommitted code used), we walk the slice from `len-1` (innermost) toward `0` (outermost), skipping frames whose `Pos.Filename()` is `"<builtin>"` or `""`. This is robust against future starlark-go changes that might add or remove implicit frames around the user code; the user-source frame is always the deepest non-builtin frame.
- **Activity-boundary marshal determinism is in scope.** `TestWalkStep_ActionFn_ReplayFrozenKwargs` asserted byte-equal kwargs `Items()` order across two runs. The fix had to land here (not deferred) because the test is part of Plan 05b's verification — the activity-boundary round-trip is what re-built the dict, and Plan 05a's workflow-side determinism could not by itself save the test. Tracked as Auto-fixed Rule 1.
- **Defensive name resolution does NOT fail the workflow.** `resolveFlowName` and `stepDisplayLabel` swallow lambda eval errors and non-string returns, falling back to the literal `Name`. Reasoning: typos surface at parse time (D4-02), and the name is for display only. Failing a workflow over a label would be a poor UX trade-off vs. surfacing a warn event.
- **Single combined commit for Task 1 GREEN.** Strict TDD would split into three commits (impl + bridge fix + marshal fix). All three are necessary for the RED tests to pass (CallStack walk for `:2:`, marshal sort for `Items()` byte-equality, dispatch impl for the rest). Split commits would leave the working tree in intermediate states where some tests pass and others fail — uninformative for `git bisect`. Combined commit cited each fix line-by-line in its message.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 — Bug] ActionRef.UnmarshalJSON used Go map range over kwargs**

- **Found during:** Task 1 GREEN — `TestWalkStep_ActionFn_ReplayFrozenKwargs` was flaky (sometimes passing, sometimes failing with `run1=[m z a]` vs `run2=[z a m]`).
- **Issue:** `pkg/dag/marshal.go::ActionRef.UnmarshalJSON` iterates `raw.Kwargs` (a `map[string]any`) with `for k, v := range raw.Kwargs` and `SetKey`s each into a fresh `*starlark.Dict`. Go map range is randomized, so the rebuilt Dict's insertion order varied across activity-boundary round-trips. The wire JSON is canonical (encoding/json sorts map keys on Marshal), but the Unmarshal side dropped that property.
- **Fix:** Collect `raw.Kwargs` keys into a slice, `sort.Strings`, then iterate in sorted order when calling `SetKey`. The rebuilt `*starlark.Dict`'s `Items()` now matches the wire JSON.
- **Files modified:** `pkg/dag/marshal.go` (added `sort` import + key sort before `SetKey` loop).
- **Verification:** Ran `TestWalkStep_ActionFn_ReplayFrozenKwargs` 10 times — 10/10 pass. `TestReplayDeterminism_DynamicKwargs` (Task 2) confirms the property generalizes.
- **Committed in:** `8cd7055` (Task 1 GREEN — bundled with the dispatch impl).

**2. [Rule 1 — Bug] bridge.CallLambda CallStack indexing surfaced `<builtin>` instead of user-source frame**

- **Found during:** Task 1 GREEN — `TestWalkStep_ActionFn_LambdaPanic` failed with the surfaced error containing `<builtin>: fail: oops` instead of `actionfn_panic.star:2:13: fail: oops`.
- **Issue:** The prior uncommitted code used `ee.CallStack.At(0).Pos`. Per `go.starlark.net/starlark/eval.go:215`, `CallStack` is "outermost first" and `CallStack.At(i)` returns `stack[len-1-i]` — so `At(0)` IS the innermost frame, but the innermost frame for `fail("...")` is the `<builtin>` fail frame, not the user's `.star` callsite. The user-source frame is one step further out.
- **Fix:** Walk the slice from `len-1` (innermost) toward `0` (outermost), skipping frames whose `Pos.Filename()` is `"<builtin>"` or `""`. The first user-source frame found is wrapped into the error.
- **Files modified:** `pkg/bridge/lambda_call.go`.
- **Verification:** `TestWalkStep_ActionFn_LambdaPanic` now passes; the error message contains both `oops` and `:2:13`.
- **Committed in:** `8cd7055` (Task 1 GREEN — bundled with the dispatch impl).
