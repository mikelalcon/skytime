### Demo-Driving Question (Goal Achievement)

**Question:** Can a consultant write `step(name="Get repo info ${ctx.input.repo}", action_fn=lambda ctx: gh.get(path="/repos/${ctx.input.repo}"))` and have it work end-to-end on Temporal — `${ctx.input.repo}` resolves at the right point, ActionRef is built at workflow time, the live block renders the named step?

**Answer:** YES (with one path-shape note: this codebase exposes input fields directly as `ctx.<field>`, not `ctx.input.<field>`. The actual demo corpus uses `${ctx.repo}`, which is the path consultants will write per the inputs={"repo": "string"} declaration).

The exact pattern appears verbatim in examples/skeleton/simple_check.star line 28-30:
```
step(
    name = "Get repo ${ctx.repo}",
    action = gh.get(path = "/repos/${ctx.repo}"),
),
```

End-to-end flow:
1. **Parse time:** desugarInterpolation rewrites both interpolated strings to lambdas; the step name lambda lands in step.NameFn; the path kwarg lambda is wrapped as *StarlarkLambda inside ActionRef.Kwargs.
2. **Workflow start:** flow.NameFn (none here) is resolved once for display.
3. **Step dispatch:** stepDisplayLabel evaluates step.NameFn → "Get repo octocat/Hello-World" — emitted in the step_dispatch event the live block consumes.
4. **Pre-activity:** resolveKwargs walks ActionRef.Kwargs in insertion order, evaluates the *StarlarkLambda for path → "/repos/octocat/Hello-World" → builds a new frozen *Dict.
5. **Activity:** ExecuteBatch dispatches gh.get with the resolved path kwarg, hits the real URL.
6. **Live block:** the same step_dispatch / step_complete events that drive the static renderer drive the live renderer's active list — the named step appears in the redraw region, gets the ✓ on completion.

For block_fn, parallel_fanout.star line 32-37 demonstrates the equivalent batch path with three idempotent gh.get calls built per-item from `ctx.repo`.
