# Phase 04.1 Plan 04: block_fn parse-time idempotency lint + runtime fallback Summary

**`step(block_fn = lambda ctx: [...])` now ships a parse-time best-effort idempotency lint (D4.1-11): the AST-walking classifier recognizes `<ext>.<op>(...)` CallExprs at the outermost level (kwargs not walked, per the locked D-11 boundary), looks up each op's declared Idempotent via the registry, and rejects mixed-typed batches at parse with the same fix-suggestion shape as D2-05 (`Suggestion: split into separate steps with action_fn each.`). Opaque shapes (helper functions, indirect dispatch) defer to the runtime fallback in `pkg/activity/validate_batch.go`, which already enforces D2-05/06/07 — Plan 04 closes the dynamic-block_fn loop with new tests that prove the existing gate rejects BEFORE any per-action OperationDispatch invocation.**

## Accomplishments

- **`pkg/parser/block_fn_lint.go::classifyBlockFn`** walks the body of a captured block_fn lambda via syntax.Walk and classifies each outermost CallExpr. Recognized `<ext>.<op>(...)` calls — where the op is declared on a registered extension — record an `extOp` with the declared Idempotent. Bare-ident calls (`helper(x)`), unknown receivers, and dotted calls into non-extensions mark `HasOpaque=true`. Sub-expressions inside kwargs of recognized extension calls are NOT walked — `return false` from the visitor stops syntax.Walk's descent into Args/Kwargs, exactly per D4.1-11 amendment.
- **`pkg/parser/block_fn_lint.go::lookupOpSpec`** is the two-step extension recognition heuristic: try `p.registry.Get(receiverName)` first; on miss, scan all registered extensions for a unique op-name match. This handles both `fake_ext.echo(...)` (direct registered name) and `gh.get(...)` where `gh = http.endpoint(...)` (rebound receiver) without static assignment-chain analysis. Ambiguous matches conservatively return ok=false → caller marks opaque.
- **`pkg/parser/block_fn_lint.go::lintBlockFnIdempotency` + `walkLintBlockFnIdempotency`** mirror lintMixedIdempotency's recursion shape (descends into IfCond.Then/Else, ForEachParallel.Steps). For each step with BlockFn populated, runs classifyBlockFn; if any opaque call is present, defers to runtime; otherwise asserts homogeneity across the typed calls and rejects mixed-idempotency batches at parse time with the canonical message.
- **`pkg/parser/finalize.go`** wires lintBlockFnIdempotency between lintMixedIdempotency and lintBlockSize. The pass-chain doc comment grew a §2.5 entry describing the new lint and its runtime-fallback handoff to D4.1-12.
- **`pkg/activity/validate_batch_test.go`** adds 6 new tests under the Plan 04.1-04 Task 3 banner. The runtime fallback path requires NO production change — `validateBatch` already enforces every D2-05/06/07 invariant with the canonical errType constants. The new tests pin the gate's behavior under the dynamic-block_fn lens, including TestValidateBatch_RuntimeBlockFnReachesGate which uses per-Func counters to prove validateBatch rejects BEFORE any OperationDispatch.Func runs.
- **13 new tests** — 7 classifier (AllHomogeneous / MixedTyped / OpaqueHelper / StrInsideKwarg_NotWalked / HelperCallTrulyOpaque / ConditionalExtCalls / EmptyListLiteral); 5 finalize-chain (HomogeneousPasses / MixedRejected / OpaqueDefers / RecursesIntoIfCondAndForEachParallel / FinalizeChainOrder); 6 activity-side (MixedIdempotency_RuntimeReject / OversizedBlock_RuntimeReject / HomogeneousIdempotent_OK / SingleNonIdempotent_OK pinned twice / EmptyBatch / RuntimeBlockFnReachesGate). ## Decisions Made

- **lookupOpSpec heuristic (Rule 2 — critical functionality).** The plan's literal `p.registry.Get(extIdent.Name)` algorithm only matches when the user wrote the extension's registered name directly (`fake_ext.echo`). The canonical fixtures use `gh = http.endpoint(...)` then `gh.get(...)`; without two-step lookup, the classifier would mark every fixture call opaque and the parse-time lint would never fire end-to-end. The heuristic stays best-effort: ambiguous matches (multiple extensions sharing an op name) conservatively defer to runtime.
- **`return false` from the AST-walk visitor enforces the kwarg boundary.** The D4.1-11 amendment requires the classifier to walk only outermost CallExpr nodes, not their kwargs. Implementation: the visitor function returns `false` on every recognized typed call AND every opaque call. starlark-go's syntax.Walk treats `false` as "do not recurse into this node's children" — so kwargs are never visited. This is the load-bearing pin for Test 4 (str(p) inside a recognized kwarg → not classified as opaque).
- **parseBlockFnSource bypasses finalize() for classifier-level tests.** Mixed-typed shapes (TestClassifyBlockFn_MixedTyped, TestClassifyBlockFn_ConditionalExtCalls before normalization) cannot reach the classifier through the full parse path because lintBlockFnIdempotency rejects them upstream. The test helper invokes starlark.ExecFileOptions directly (mirroring the parse() body sans finalize) so classifier-level pinning is possible. End-to-end coverage stays in TestLintBlockFnIdempotency_*.
- **TestClassifyBlockFn_ConditionalExtCalls uses two homogeneous-idempotent calls** instead of the plan's example (echo + post mixed). The classifier doesn't care about idempotency mixing — it just records what it finds. Using two `echo` calls keeps the test focused on "both branches of a CondExpr get classified" without re-testing what TestClassifyBlockFn_MixedTyped already covers.
- **Tests-only contribution to pkg/activity (Scenario A confirmed).** Reading `pkg/activity/validate_batch.go` confirmed the plan's Scenario A: every D2-05/06/07 invariant the runtime fallback needs is already enforced via the existing errType constants. New tests (TestValidateBatch_*) pin the gate's behavior under the dynamic-block_fn lens; TestValidateBatch_RuntimeBlockFnReachesGate uses per-Func counters to prove validateBatch rejects BEFORE any OperationDispatch.Func runs.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 2 - Critical functionality] lookupOpSpec heuristic added beyond the plan's literal algorithm**

- **Found during:** Task 2 (TestLintBlockFnIdempotency_MixedRejected against block_fn_invalid_mixed.star)
- **Issue:** The plan's classifier shape uses `p.registry.Get(extIdent.Name)` to recognize `<ext>.<op>(...)` calls. This works only when the user's source text uses the extension's registered Name() directly (e.g., `fake_ext.echo`). The fixtures (block_fn_*.star) use `gh = http.endpoint(...)` with `gh.get(...)` / `gh.post(...)`. With the plain literal algorithm, `extIdent.Name == "gh"` → `p.registry.Get("gh")` returns nothing → classifier marks opaque → lint defers to runtime → TestLintBlockFnIdempotency_MixedRejected would NEVER fire on the fixture. Direct contradiction with the plan's success criterion.
- **Fix:** Added `lookupOpSpec(receiverName, opName)` two-step heuristic. Step 1: try `p.registry.Get(receiverName)` — keeps the literal-name path working for cases like `fake_ext.echo`. Step 2: scan all registered extensions for a unique op-name match — handles the rebound-receiver case (`gh.get` where `gh = http.endpoint(...)`). Ambiguous matches conservatively return ok=false. Best-effort lint stays best-effort; no false rejections introduced.
- **Files modified:** pkg/parser/block_fn_lint.go (lookupOpSpec helper)
- **Commit:** 4bf1342

**2. [Rule 1 - Bug] TestClassifyBlockFn_MixedTyped + TestClassifyBlockFn_ConditionalExtCalls couldn't reach classifyBlockFn through the full parse path**

- **Found during:** Task 2 GREEN (after wiring lintBlockFnIdempotency into finalize)
- **Issue:** Once lintBlockFnIdempotency is wired into finalize, ParseSource on a source with `step(block_fn = lambda ctx: [echo, post])` (mixed) rejects upstream — the classifier-level test never gets a chance to call `p.classifyBlockFn` on the captured lambda. The first symptom was `parseBlockFnSource: parse must succeed before classifyBlockFn runs`.
- **Fix:** Refactored parseBlockFnSource to bypass finalize(): inline the parse path's lazy parseTimeGlobals init + fileBytes cache + thread setup + ExecFileOptions, omitting the `if ferr := p.finalize(); ferr != nil` step. The test helper now produces the same parser state ExecFileOptions would yield right before finalize. End-to-end finalize coverage stays in TestLintBlockFnIdempotency_* via ParseFile.
- **Files modified:** pkg/parser/block_fn_lint_test.go (parseBlockFnSource refactor)
- **Commit:** ec82650

**3. [Rule 1 - Polish] TestClassifyBlockFn_ConditionalExtCalls used two homogeneous-idempotent calls (echo + echo) instead of the plan's mixed-idempotency example**

- **Found during:** Task 2 GREEN
- **Issue:** The plan's example for Test 6 used `gh.create_issue(...) if cond else gh.delete_issue(...)`. Translating to fakeExtension shape: `fake_ext.echo(...) if cond else fake_ext.post(...)` — but echo is idempotent and post is not, which would have been rejected by lintBlockFnIdempotency upstream of the classifier-level test (same root cause as the parseBlockFnSource issue, but here the test bypass alone wouldn't be enough — the test goal is "both branches classified", not "mixed batch behavior").
- **Fix:** Changed the test fixture to use two `fake_ext.echo` calls in the conditional. The test assertion still verifies "both branches of the CondExpr are classified" — which is what the test was always after; the idempotency mix was incidental scenery in the plan's example. Comment updated to call out the focus.
- **Files modified:** pkg/parser/block_fn_lint_test.go (TestClassifyBlockFn_ConditionalExtCalls)
- **Commit:** ec82650
