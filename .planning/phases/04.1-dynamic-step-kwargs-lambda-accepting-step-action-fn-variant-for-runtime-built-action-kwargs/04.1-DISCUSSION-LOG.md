## Pre-discussion arc (in main conversation, before discuss-phase invoked)

### User's original ask
"I want to add you also String interpolation. For example, steps should be able to have a name, like 'Get repo info'. The beauty is that then we can do 'Get repo info ${input.repo_name}'. I also want the progress for one step to be in the same line. You can do [1/3] Get repo info TIME. Where time keeps increasing until finish and then you put the last time and the tick of correct or the X if it failed and the next line has the error."

### Initial pushback (string interpolation collision)
PROJECT.md explicitly forbids string-expression languages:
> CEL or string-based expressions — explicitly rejected; lambdas only
> "String-expression languages (CEL, JSONPath, Jinja) — Re-introduces parse-time evaluation surface that lambdas eliminate; explicitly forbidden by spec"

Initial recommendation was to use lambda form (`name_fn=lambda ctx: ...`) instead.

### User's pivotal insight
"Cannot you generate a lambda on the fly?"

This reframed the entire design: instead of a runtime template engine, **desugar `${...}` at parse time into native Starlark lambdas**. The runtime evaluation surface stays unchanged; the desugaring is purely syntactic sugar over the existing lambda machinery.

### Result of the reframe
- No new runtime evaluation surface → PROJECT.md amendment becomes a one-line clarification rather than a foundational change
- Validator (D4-02 ctx.<name> walker) catches typos for free on the synthesized lambdas
- Free dot-chains, indexing, len(), or/and/%-formatting — all of Starlark expression power
- Implementation cost ~50 LOC for the desugarer vs ~200 LOC for a string-template engine

### Long form vs short form decision
Long form `${ctx.foo}` chosen over short form `${foo}` (with implicit ctx. prepending):
- Implementation: ~50 LOC vs ~150+ LOC with edge cases (D-20 builtin filtering, source rendering of mutated AST)
- Consistency: every other ctx.foo reference is explicit; no special rule inside `${...}`
- Self-documenting: `${ctx.input.repo}` makes "this reads from workflow state" obvious
- Cost: 4 chars per use — negligible

## Area 1: Interpolation grammar + scope

### Q1.1 — Grammar for `${...}`?

| Option | Description | Selected |
|--------|-------------|----------|
| Bare identifier only | `${repo}` resolves to ctx.repo. No dots, methods, filters. ~30 LOC parser. | |
| Dot-access (one level) | `${input.repo}` allowed. ~80 LOC. Maps cleanly to ctx.<top>.<field>. | |
| Full dot-chains (no methods/filters) | `${input.repo.default_branch}` and arbitrary chains. More CEL-shaped. | ✓ (initially) |

**User's initial choice:** Full dot-chains.

### Reframing to desugar approach
After "Cannot you generate a lambda on the fly?" the question changed from "what grammar do we invent?" to "Starlark IS the grammar — we just need to decide implicit-ctx vs explicit-ctx."

### Q1.1-revised — Implicit `ctx.` prepending or explicit?

| Option | Description | Selected |
|--------|-------------|----------|
| Short form `${foo}` (implicit ctx.) | ~150 LOC, edge cases | |
| Long form `${ctx.foo}` (explicit) | ~50 LOC, dead-simple desugar | ✓ |

**User's choice:** Long form (explicit `${ctx.foo}`).
**Reasoning:** "If you think it is not difficult, we can do the short version, but I wouldn't be horrified if you do ${ctx.foo} to ease the translation." Picked long form for implementation simplicity + consistency with ctx.foo references everywhere else.

### Q1.2 — Scope: where is `${ctx.foo}` allowed?

| Option | Description | Selected |
|--------|-------------|----------|
| step.name + flow.name | Tightest carve-out, only naming fields | |
| step.name only | Smallest possible scope | |
| Anywhere a string kwarg appears | step names, action kwargs, script ids, etc. | ✓ |

**User's choice:** Anywhere a string kwarg appears.
**Implementation note:** Action kwargs becoming lambdas means the workflow walker must `resolveKwargs` before activity dispatch (D4.1-14), and D-11 schema validation widens to accept `string OR *CapturedLambda` (D4.1-05). ~100-150 LOC additional.

### Q1.3 — PROJECT.md amendment shape?

| Option | Description | Selected |
|--------|-------------|----------|
| Locked carve-out + 'requires new ADR to extend' | Strong language to prevent future expansion | |
| One-line clarification | Note that desugaring isn't string compilation | ✓ |
| No amendment | Argue desugaring isn't covered by the rule | |

**User's choice:** One-line clarification. User notes: "umm but we can validate the lambda, right?" — confirmed yes (D4-02 catches typos for free), so the amendment is purely documentary.

### Q1.4 — Validator behavior for `${ctx.typo}`?

| Option | Description | Selected |
|--------|-------------|----------|
| Parse error with position | Free via D4-02 | ✓ |
| Runtime error only | Skip static check | |

**User's choice:** Parse error (free).

## Area 2: DSL surface

### Q2.1 — Ship block_fn alongside action_fn?

| Option | Description | Selected |
|--------|-------------|----------|
| Ship both | block_fn for batched dynamic actions; mixed-idempotency moves to runtime | ✓ |
| Defer block_fn | Only action_fn in 4.1 | |
| Require explicit idempotency | step(block_fn=..., idempotent=True) | |

**User's response:** "I need more context about this" — led to detailed explanation of static `block` semantics (Phase 2 batch optimization) and the trade-off (block_fn = 1 activity for N actions; without it, for_each_parallel = N activities).
**User's final choice:** "I like a lot block_fn." Ships in 4.1.

### Q2.2 — Naming for the lambda-accepting kwargs?

| Option | Description | Selected |
|--------|-------------|----------|
| action_fn / block_fn | Mirrors Phase 1 `script(fn=...)` convention | ✓ |
| dynamic_action / dynamic_block | More verbose; doesn't match `fn` convention | |
| action / block accept both | Same kwarg, type-discriminate | |

**User's choice:** action_fn / block_fn.

### Q2.3 — name + name_fn coexistence?

| Option | Description | Selected |
|--------|-------------|----------|
| Just name (with interpolation) | Desugarer handles dynamic via ${...} | ✓ |
| name AND name_fn | Both available | |
| Just name_fn | Drop interpolation | |

**User's choice:** Just name with interpolation.

### Q2.4 — Lambda return contract?

| Option | Description | Selected |
|--------|-------------|----------|
| Strict: ActionRef / []ActionRef | Runtime error on wrong type | ✓ |
| Coerce common shapes | Build ActionRef from dict | |

**User's choice:** Strict.

## Area 4: Failure semantics + corpus

### Q4.1 — action_fn wrong return type?

| Option | Description | Selected |
|--------|-------------|----------|
| NonRetryableErrResult with position | Surfaced as *dag.ValidationError | ✓ |
| Workflow-level panic | Breaks Starlark-first error rendering | |

**User's choice:** NonRetryableErrResult with position.

### Q4.2 — block_fn mixed-idempotency?

| Option | Description | Selected |
|--------|-------------|----------|
| Activity-side runtime check | Mirrors D2-05 message at runtime | |
| Auto-split | Subverts D2-06 | |
| Reject at parse: explicit idempotency | step(block_fn=..., idempotent=True) | |

**User's response:** "can we detect it on load (static validation)?" — led to detailed explanation that static analysis works for SIMPLE cases (direct extension factory calls in comprehensions) but NOT for complex cases (helper functions, indirect dispatch, opaque calls).

### Q4.2-revised — Static + runtime split?

| Option | Description | Selected |
|--------|-------------|----------|
| Best-effort static + runtime fallback | Walk the lambda AST; static-validate when possible; fall back to runtime check otherwise | ✓ |
| Runtime-only check | Simpler implementation | |
| Static-only (reject opaque) | Most restrictive | |
| Require user-declared idempotency | step(block_fn=..., idempotent=True) | |

**User's choice:** Best-effort static + runtime fallback.

### Q4.3 — Lambda panic / Starlark eval error?

| Option | Description | Selected |
|--------|-------------|----------|
| NonRetryableErrResult with Starlark traceback | The error is in .star code, not transient | ✓ |
| RetryableErrResult | A buggy lambda would retry forever | |

**User's choice:** NonRetryableErrResult with traceback.

### Q4.4 — Corpus migration scope?

| Option | Description | Selected |
|--------|-------------|----------|
| Rewrite simple_check.star to use everything | Showcase the new features | ✓ |
| Keep static + add new corpus files | Two ways shown side-by-side | |
| Defer corpus update to Phase 6 | 04.1 ships features without demo | |

**User's choice:** Rewrite simple_check.star.
