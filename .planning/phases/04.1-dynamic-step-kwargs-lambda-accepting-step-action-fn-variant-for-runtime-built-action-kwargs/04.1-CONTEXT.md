# Phase 04.1: Dynamic step kwargs + named steps + live progress block - Context

**Gathered:** 2026-05-02
**Status:** Ready for planning

<domain>
## Phase Boundary

Three coupled DSL/UX changes, urgent insertion between Phase 4 and Phase 5:

1. **Dynamic action kwargs via lambdas** — `step(action_fn=lambda ctx: ext.op(...))` and `step(block_fn=lambda ctx: [ext.op(...) for ...])` so consultants can build entire ActionRefs from runtime state.

2. **String interpolation in string kwargs via parser-time desugaring** — `"...${ctx.expr}..."` desugars at parse time into `lambda ctx: "..." + str(ctx.expr) + "..."`. The runtime evaluation surface is unchanged (lambda-only). Interpolation is purely an ergonomic shortcut over `name_fn`-style lambdas.

3. **Multi-line live progress block** — the CLI's renderer upgrades from per-line static output to a redrawing in-progress section with spinner, per-step timer, and Bazel-style "[N/M] step name" format.

**The trigger:** Phase 4's `simple_check.star` corpus had hardcoded URLs that demonstrably ignored `--input`. Without dynamic kwargs, every real consultant flow (Phase 6 example, customer specializations) is forced into `.star` file forks per customer. This is a missed v1 requirement, not a v1.x nice-to-have.

**Required before:** Phase 5 (E2E test harness — needs to test dynamic flows) and Phase 6 (real example project — every flow takes input).

</domain>

<decisions>
## Implementation Decisions

### Interpolation (parser-time desugaring)

- **D4.1-01: `${ctx.expr}` desugars to a Starlark lambda at parse time.** When the parser encounters a string literal containing `${...}` markers in any allowed position (D4.1-02), the parser scans the string for `${...}` segments, extracts each inner expression, and synthesizes an equivalent Starlark lambda:
  ```python
  "Get repo info ${ctx.input.repo}"
  # desugars at parse time to:
  lambda ctx: "Get repo info " + str(ctx.input.repo)
  ```
  The synthesized lambda flows through the existing `bridge.CallLambda` machinery — no new runtime evaluation surface. Implementation: `pkg/parser` adds a desugarer (`pkg/parser/template.go` or similar) that uses `syntax.ParseExpr` to validate each inner expression, then constructs the synthesized lambda via `syntax.LambdaExpr` AST construction → resolve → starlark.Function.

- **D4.1-02: Interpolation is allowed ANYWHERE a string kwarg appears.** Concretely:
  - `step(name = "...")` — step display names
  - `flow(name = "...")` — flow display names (visible in Temporal UI)
  - Action kwargs: `gh.get(path = "/repos/${ctx.input.repo}")` — runtime-built URLs, paths, headers, etc.
  - `script(id = "...")` — script identifiers (rare but consistent)
  - Any other future string-typed DSL kwarg
  Excluded: kwargs whose declared type is non-string (e.g., `inputs={...}` dict literal).

- **D4.1-03: Validator catches `${ctx.typo}` at parse time for free.** The synthesized lambda is treated identically to any other captured lambda — D4-02's `ctx.<name>` walker (Phase 4) inspects the body, validates every dot-path against the lexically-visible state schema. Typos surface as `*dag.ValidationError` with the position of the opening `${`. No new validator code needed.

- **D4.1-04: `${...}` syntax rules.** Single-line expressions only (no `${\n  ctx.foo\n}`). Escape via doubled `$` — `"$${not interpolated}"` produces literal `${not interpolated}`. Empty `${}` is a parse error. Mixed: `"a${ctx.x}b${ctx.y}c"` desugars to `"a" + str(ctx.x) + "b" + str(ctx.y) + "c"`. The `str()` wrapper is unconditional for safety (handles int, bool, None, float gracefully).

- **D4.1-05: When a string kwarg becomes a lambda via desugaring, downstream machinery handles it.**
  - For `step.name` / `flow.name`: the dag node carries `Name string` (literal, no `${}`) OR `NameFn *CapturedLambda` (set by desugarer when interpolation was detected); never both.
  - For action kwargs: the `ActionRef.Kwargs` map's value type widens from "any" to "any | *CapturedLambda" — the workflow walker (D4.1-12) evaluates lambda-valued kwargs against `ctx` BEFORE dispatching to the activity.
  - D-11 reflection-based kwarg validation (Phase 1) extends to accept `string OR *CapturedLambda` for any kwarg whose declared schema type is `string`.

### action_fn / block_fn (lambda-driven action construction)

- **D4.1-06: New step variants `action_fn` and `block_fn`.** Both kwargs are mutually exclusive with `action`/`block`/each other. Naming follows Phase 1's `fn` convention (`script(fn=lambda ctx: ...)`).
  ```python
  step(action_fn = lambda ctx: gh.create_issue(repo=ctx.input.repo, title=ctx.input.title))
  step(block_fn  = lambda ctx: [gh.add_label(issue=ctx.input.issue, label=l) for l in ctx.input.labels])
  ```
  Lambda evaluates inside the workflow (deterministic, locked predeclared globals D-20). Cancellation watchdog D3-21 wraps the call. MaxExecutionSteps D-22 bounds it.

- **D4.1-07: Strict return contract.** `action_fn` MUST return a single `ActionRef` (the result of calling an extension factory). `block_fn` MUST return `[]ActionRef`. Wrong type → step fails at runtime via `NonRetryableErrResult` carrying the lambda position and a message like `"action_fn returned <actual_type>, expected ActionRef"`. The wrapper around `bridge.CallLambda` (in `pkg/interpreter/walk_step.go`) does the type assertion and surfaces the typed error.

- **D4.1-08: Lambda panic / Starlark eval error → NonRetryableErrResult with traceback.** Existing `bridge.CallLambda` returns Starlark eval errors as Go errors with the .star callsite preserved. The interpreter wraps these as `NonRetryableErrResult` (the bug is in .star code, not transient). Renderer shows `✗ lambda panic: <msg> (at <file>:<line>:<col>)`. `fail("reason")` calls in lambdas produce the same shape with the user's reason string.

- **D4.1-09: Parse-time validation of action_fn / block_fn lambdas.** Same checks as existing lambdas:
  - D-19 free-var lint (no mutable closures; only module-level constants)
  - D-20 lambda-time globals (locked 20-key subset)
  - D4-02 ctx.<name> attribute access against state schema
  - NEW: best-effort idempotency analysis for `block_fn` (D4.1-11)

### block_fn idempotency: best-effort static + runtime fallback

- **D4.1-10: D2-05's parse-time mixed-idempotency check still applies to static `step(block=[...])`.** The Phase 2 lint (`pkg/parser/linter.go::lintMixedIdempotency`) is unchanged for static blocks.

- **D4.1-11: For dynamic `step(block_fn=...)`, use best-effort static analysis with runtime fallback.** Implementation in `pkg/parser` (new file, e.g., `pkg/parser/block_fn_lint.go`):
  1. Walk the block_fn lambda body via `syntax.Walk`.
  2. For each `*syntax.CallExpr`, attempt to classify the callee:
     - If callee is `<ext>.<op>` where `ext` is a registered extension and `op` has a declared `Idempotent *bool` → record as a typed call.
     - If callee is opaque (helper function, indirect dispatch, conditional, comprehension over unknowns) → mark as "needs runtime check" and stop.
  3. If ALL paths produce homogeneous typed calls → static-validated (no runtime check needed for THIS block_fn).
  4. If ANY path is opaque OR if typed calls are heterogeneous in idempotency → defer to runtime.
- **D4.1-12: Runtime fallback for block_fn.** Activity (`pkg/activity`) re-runs the mixed-idempotency check on the actual `[]ActionRef` returned by block_fn. Mirrors D2-05's parse-time message:
  ```
  block_fn returned mixed-idempotency batch:
    - github.create_issue (idempotent)
    - slack.post_message (NOT idempotent)
  Suggestion: split into separate steps with action_fn each.
  ```
  Returns `NonRetryableErrResult` for every action in the batch. Same error spine as parse-time D2-05 errors.

- **D4.1-13: D2-07 block size cap (50 actions) extends to block_fn at runtime.** Activity-side check rejects oversized batches with a clear `NonRetryableErr`.

### Workflow-side kwarg resolution

- **D4.1-14: `pkg/interpreter/walk_step.go` evaluates lambda-valued kwargs before activity dispatch.** New helper `resolveKwargs(ctx, ref *ActionRef)`:
  1. Walk `ref.Kwargs` map.
  2. For each value: if it's a `*CapturedLambda`, call `bridge.CallLambda(ctx, captured, state)`, replace with the resolved string.
  3. Otherwise leave as-is.
  Runs once per ActionRef before scheduling `ExecuteActivity`. The activity sees a fully-resolved `ActionRef.Kwargs` map (string-typed for interpolated cases). Backward-compatible: static kwargs still work with no lambda resolution overhead.

### Step naming

- **D4.1-15: `step(name=...)` is optional and supports interpolation.** New optional `Name string` field on `dag.Step` (literal name) plus `NameFn *CapturedLambda` (set by the desugarer when interpolation present). The renderer prefers `Name` (or resolved `NameFn`) over the auto-derived `<kind>(<label>)` when present.
  ```python
  step(name = "Get repo info ${ctx.input.repo}", action_fn = lambda ctx: gh.get(path = "/repos/" + ctx.input.repo))
  ```
  No separate `name_fn` kwarg — interpolation covers all dynamic-name use cases.

- **D4.1-16: `flow(name=...)` similarly supports interpolation.** Optional. Visible in Temporal UI. Same desugaring path as step names.

### Live progress block (multi-line redrawing)

- **D4.1-17: Renderer upgrades to a multi-line live block.** `pkg/cli/progress.go` (Phase 4) handles per-step lines today. Phase 4.1 extends:
  - Static (completed) lines accumulate at the top.
  - In-progress steps render as a redrawing block at the bottom:
    ```
    [skytime] in-progress  3 active
      [2/4] step Get repo octocat       ⠋ 0.4s
      [3/4] step Get repo torvalds      ⠹ 1.2s
      [4/4] step Get repo someone-else  ⠼ 0.8s
    ```
  - On completion, the step's row finalizes (✓ or ✗ with duration + summary), is removed from the in-progress block, and printed as a static line above the redrawing region.

- **D4.1-18: Spinner cadence = 100ms.** Standard for terminal spinners (npm, cargo, bazel). Balances visual smoothness (10 fps) with CPU (negligible). Timer precision = 0.1s.

- **D4.1-19: Truncation when active > visible.** Show top N (default 10) active rows + a `... and M more` summary line when total active exceeds the cap. As visible steps complete, the next pending takes their slot. Predictable terminal footprint.

- **D4.1-20: `--verbose` disables the live block.** When `--verbose` is on, SDK INFO/DEBUG lines stream to stderr and would constantly break the live region's redraw. Solution: `--verbose` forces static line-per-event mode (no spinner, no overwriting). Reasoning: `--verbose` is for debugging; the live block is for demos. Cleanest separation.

- **D4.1-21: Non-TTY → static lines, no ANSI.** Detected via `golang.org/x/term.IsTerminal(stdout)`. Pipe / CI / file redirect: each step prints a `[N/M] step ... starting...` dispatch line, then a `[N/M] step ... ✓ 234ms` completion line below. No carriage returns, no escape codes, no spinner. Greppable.

### PROJECT.md amendment

- **D4.1-22: Add a one-line clarification to the "no string compilation" rule.** Append the following text to PROJECT.md's existing "No string compilation" entry (in both the Constraints and Out of Scope sections):
  > *Parser-time syntactic sugar that desugars to native Starlark lambdas (e.g., `${ctx.expr}` → `lambda ctx: str(ctx.expr)`) is not string compilation. The runtime evaluation surface remains lambda-only. This carve-out exists for ergonomic step naming and string kwargs; runtime template engines (CEL, Jinja, etc.) remain forbidden. Extending this carve-out beyond parser-time desugaring requires a new ADR.*

  Documents the design discipline so future contributors understand why CEL is still off-limits.

<specifics>
## Specific Ideas

- **Desugar example:** the user's motivating case `step(name = "Get repo info ${ctx.input.repo}", action_fn = lambda ctx: gh.get(path = "/repos/" + ctx.input.repo))` should Just Work end-to-end. Demo target.
- **Live block visual:** use the standard braille spinner pattern `⠋ ⠙ ⠹ ⠸ ⠼ ⠴ ⠦ ⠧ ⠇ ⠏` (used by npm, cargo, etc.). Charm-log is already a dependency; use whatever spinner primitive it offers, otherwise inline.
- **Truncation message format:** `... and N more` — keep simple. Don't try to summarize what those N steps are doing; the user can grep the static log for details after the run.
- **Documentation:** the rewritten `examples/skeleton/simple_check.star` should have a docstring explaining the new patterns (`${ctx.input.repo}` interpolation, `action_fn` for dynamic kwargs). Phase 6 readme will reference this as the canonical introduction.
- **block_fn empty-list behavior:** when `block_fn` returns `[]`, skip the activity entirely (no point dispatching an empty batch) but emit a `step_complete` event with `summary="empty batch"` so the renderer shows the step happened. Cheaper than dispatching a no-op activity; observable.
- **Synthesized lambda IDs (D-18):** use the position of the opening `${` for line+col. File-bytes hash already covers any text change. Stable across re-parse of unchanged file content (the deployment property D-18 was designed for).
- **Interpolation outside the workflow context:** `${ctx.foo}` only makes sense where `ctx` is bound (i.e., inside lambdas the workflow evaluates). For top-level `flow(name="...")`, the desugarer still produces a `lambda ctx: ...` — the workflow evaluates this once at flow start time using the initial state.

</specifics>

<deferred>
## Deferred Ideas

- **`name_fn` lambda variant** — explicitly NOT in Phase 04.1 (D4.1-15). `${...}` interpolation handles all dynamic-name use cases via Starlark expressions. If a future case truly needs lambda logic that doesn't fit in a single expression (multi-statement name building), add `name_fn` then. v1.x add at most.
- **Filters / pipes inside `${...}`** — e.g., `${ctx.foo | upper}` Jinja-style. NOT in v1; would require a real expression parser and re-opens the slippery slope. Use Starlark string methods instead: `${ctx.foo.upper()}`.
- **Multi-line `${...}`** — explicitly rejected. Single-line expressions only. Multi-line use cases should use `script` or `name_fn` (when added).
- **Custom spinner per step kind** — use the same braille spinner everywhere. Custom spinners (e.g., HTTP-specific animation) belong in v2 if at all.
- **Live block on Windows** — Windows terminal handling is fragile (especially around ANSI in cmd.exe). Phase 04.1 ships live block on Unix only via the existing `//go:build !windows` pattern from quick-260501-p7c. Windows fallback is the static line mode (D4.1-21).
- **Auto-fitting truncation cap to terminal height** — Phase 04.1 hardcodes the visible-rows cap at 10. v1.x: query terminal height and adapt.
- **block_fn auto-split into sequential static blocks** — when block_fn returns a heterogeneous batch, the activity COULD auto-split into N homogeneous sub-batches and dispatch them sequentially. Not in v1 — D2-06 says splitting lives in the interpreter, not the activity. Re-evaluate if customer feedback shows the runtime rejection is too noisy.
- **Step output streaming for long-running activities** — the live block updates only on completion. For a 5-minute HTTP call, the timer ticks but no intermediate progress is visible. v2: optional `progress_attr` callback the activity can heartbeat.
- **Validator hint for "did you mean ${...}?"** — when a user writes `"$ctx.foo"` (forgot braces) or `"${ctx,foo}"` (typo), produce an actionable suggestion. Polish for v1.x.
- **Reviewed Todos (not folded)** — none; no pre-existing todos matched this scope.
