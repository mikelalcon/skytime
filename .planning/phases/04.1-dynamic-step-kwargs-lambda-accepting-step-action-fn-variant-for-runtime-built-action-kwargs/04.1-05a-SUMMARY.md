# Phase 04.1 Plan 05a: Workflow-side resolveKwargs Summary

**`i.resolveKwargs(wfctx, ref *ActionRef)` walks `ref.Kwargs` via `*starlark.Dict.Items()` (insertion-order, NOT randomized), evaluates `*StarlarkLambda` values through the existing `evalLambda` path (D-20 globals, D-22 step budget, D3-21 cancellation watchdog), and returns a NEW frozen `*starlark.Dict` with all lambda values replaced by their resolved `starlark.String` values; `ref.Kwargs` containing zero lambdas takes an allocation-free fast path (returns the original frozen dict unchanged) so Phase 1/2/3 static action paths remain zero-cost.**

## Accomplishments

- **pkg/interpreter/resolve_kwargs.go::resolveKwargs** — the workflow-side helper that consumes a `*dag.ActionRef` whose `Kwargs *starlark.Dict` may contain `*dag.StarlarkLambda` values (produced by the parser-side desugarer in Plan 04.1-03 / 04.1-02). For each lambda-valued entry, the function calls `i.evalLambda(ctx, captured.ID)` (the same primitive `walk_script.go` / `walk_ifcond.go` / `walk_foreach.go` use), type-asserts the return as `starlark.String`, and stores the resolved string in a new dict. Non-lambda entries copy verbatim. Output dict is frozen before return.
- **Allocation-free fast path** — first pass scans every value via `dag.UnwrapStarlarkLambda`; if zero lambdas are present, returns `ref.Kwargs` unchanged (the original frozen dict pointer). Static-kwarg actions pay no allocation cost.
- **Determinism comment block** — both iteration sites (the pre-scan and the rebuild walk) carry an inline comment pointing at RESEARCH §Pattern 4: `*starlark.Dict.Items()` is insertion-order by spec; workflowcheck does not flag it; do NOT add a sort.
- **Cancellation propagation** — each `evalLambda` call honors the workflow watchdog through `makeCancelChannel(ctx)` (D3-21). A long-running kwarg lambda is interruptible.
- **Strict return-type contract** — when a lambda returns anything other than `starlark.String`, the helper surfaces `resolveKwargs: kwarg %q: lambda returned %s, expected string` with the kwarg name and actual `Type()` filled in. Defensive against hand-built ActionRefs that skip the parser-side D4.1-04 `str()` wrap.
- **Error spine** — evalLambda failures wrap via `fmt.Errorf("%w")`, preserving the lambda position string the evalLambda wrapper already attaches (`lambda <id> @ <pos>: ...`); the kwarg name layer adds `resolveKwargs: kwarg %q:` in front. Two-layer error message reads top-down as `resolveKwargs: kwarg "path": lambda <id> @ <pos>: <starlark error>`.
- **kwargKeyString helper** — small package-private helper that returns the Go string for a `starlark.String` kwarg key (or `key.String()` as a defensive fallback). Used by both error branches (evalLambda failure + non-string return) so the error wording stays consistent.
- **6 new tests** — `TestResolveKwargs_NoLambdas_ReturnsOriginalShape` (fast path returns same pointer), `TestResolveKwargs_SingleLambda_ResolvesToString` (`lambda ctx: "x"+str(ctx.r)` against `{r:"VAL"}` → `"xVAL"`), `TestResolveKwargs_LambdaReturnsNonString_Errors` (lambda returns `5` → error mentions `"path"`, `int`, `expected string`), `TestResolveKwargs_NilKwargs_ReturnsNil` (`Kwargs == nil` → `(nil, nil)`), `TestResolveKwargs_DeterministicOrder` (kwargs inserted as `[z, a, m]` evaluate as `[z, a, m]` across 5 runs — proves `*starlark.Dict.Items()` insertion order), `TestResolveKwargs_LambdaErrorPropagates` (`fail("custom reason")` propagates with the user's string preserved + kwarg name attribution).
- **Test scaffolding** — `helperBuildParsedFlowWithLambdas` accepts a slice of `(name, src)` pairs and registers each compiled `f = lambda ctx: ...` snippet as a CapturedLambda with a unique ID. Mirrors `lambda_eval_test.go::helperBuildParsedFlowWithLambda` (singular) but supports multi-lambda flows needed by the determinism + multi-kwarg fixtures. ID disambiguation appends the source name suffix to handle two test lambdas with identical compiled bodies.

## Decisions Made

- **`*starlark.Dict.Items()` is the iteration surface; no key sort needed.** RESEARCH §Pattern 4 line 388 explicitly notes that workflowcheck does not flag `*starlark.Dict.Iterate()` because it is not a Go map iteration. The comment block at both iteration sites in `resolve_kwargs.go` makes this distinction load-bearing for any future maintainer who might "add a sort" thinking determinism requires it.
- **Allocation-free fast path on the no-lambda case.** Phase 1/2/3 ship with all-string kwargs (no `*StarlarkLambda` values); rebuilding the dict on every action would impose a per-action allocation cost on every static action workflow already in flight. Two-pass (scan + conditional rebuild) avoids that cost while still allowing the dynamic path to allocate cleanly.
- **Strict `starlark.String` type assertion on the resolved value.** D4.1-04 says the parser-side desugarer always wraps the inner expression in `str()` so user-authored interpolation never returns a non-string. The strict assertion guards against hand-built ActionRefs that bypass the desugarer (test fixtures, future extension authors). The error message is precise enough (`kwarg "path": lambda returned int, expected string`) that the failure mode is unambiguous.
- **Output dict frozen before return.** Temporal replay determinism: the activity input has to be immutable from the workflow's perspective so per-replay the same bytes flow to ExecuteBatch. Freezing the new dict mirrors the static path's already-frozen kwargs invariant.
- **kwargKeyString helper instead of inline `if ks, ok := key.(starlark.String)` branches.** Two error sites (evalLambda failure + non-string return) both need the kwarg-name layer; centralizing the conversion keeps the wording consistent and avoids the temptation to inline a different fallback (`%v` vs `%s` vs `String()`).
- **No REFACTOR step.** The implementation shape on first pass is already clean — single helper, single file, comment block already in place, 97 lines total. A REFACTOR commit would be cosmetic-only and add no value.
