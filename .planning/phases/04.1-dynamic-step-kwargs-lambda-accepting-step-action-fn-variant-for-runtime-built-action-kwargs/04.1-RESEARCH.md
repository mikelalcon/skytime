# Phase 04.1: Dynamic step kwargs + named steps + live progress block — Research

**Researched:** 2026-05-02
**Domain:** Starlark AST synthesis · Temporal workflow determinism · terminal live-redraw UI
**Confidence:** HIGH (CONTEXT.md has 25 locked decisions; research narrows the open AST-construction and terminal-mechanics questions only)

## Summary

Phase 04.1 splices three coupled changes between Phase 4 and Phase 5: lambda-built `ActionRef` kwargs (`action_fn` / `block_fn`), parser-time `${ctx.expr}` desugaring of string kwargs, and a redrawing live-progress region in the CLI renderer. The CONTEXT.md author has already locked the architectural shape — single lambda evaluation surface, parser-time desugaring (NOT runtime templating), best-effort static idempotency analysis with runtime fallback, Unix-only live block, charm-log unaffected. The remaining open questions are all execution details. This research validates them.

**Primary recommendation:** Use **synthesized-source-string + re-parse** for the desugarer (vs. hand-built `*syntax.LambdaExpr`). The reasons are concrete: `go.starlark.net` resolves and compiles whole files via `(*syntax.FileOptions).Parse` + `starlark.ExecFileOptions`; a synthesized lambda needs to flow through `*starlark.Function` (which only `compile` produces from `*syntax.LambdaExpr` *as part of a parsed File*), and there is no public `starlark.FunctionFromAST(...)` API. Synthesizing source text places the lambda inside the same compile/resolve path the rest of the parser already uses — zero new code paths.

For the live block: emit lines from a single render goroutine driven by a `chan event`, redraw via cursor-up + line-clear (NOT alternate-screen — preserves scrollback per `cli/cli` precedent), 100 ms tick, ignore SIGWINCH (truncate to a hardcoded 10-row cap; v1.x adds adaptive height). Detect non-TTY via `golang.org/x/term.IsTerminal` (already used by `pkg/cli/render.go::setupLogging`). `--verbose` pre-empts the live block (locked, D4.1-20).

For workflow-side `resolveKwargs`: use `workflow.DeterministicKeys(ref.Kwargs)` to walk the kwargs map. Lambdas resolve via `bridge.CallLambda` on the workflow goroutine (no `workflow.Go`); each lambda is independent, so order doesn't actually affect history events, but deterministic iteration is cheap insurance against future changes that add side effects.

## Project Constraints (from CLAUDE.md)

- **Tech stack:** Go + Starlark + Temporal. No alternative DSLs / expression languages / orchestrators.
- **Architectural separation:** parse-time generates a deterministic DAG; execute-time walks it. Parser-time desugaring stays inside this rule (D4.1-22 amends PROJECT.md to make this explicit).
- **No string compilation at runtime:** CEL, Jinja, runtime template engines remain forbidden. `${ctx.expr}` desugar is parser-time only.
- **Quality > speed:** Foundational infrastructure; correct boundaries are hard to fix retroactively.
- **Determinism:** Workflow code (and lambdas) must produce the same decisions on replay.
- **Security:** Credentials never enter workflow state. (Out of scope for this phase but applies to action_fn / block_fn — lambdas may not produce ActionRefs that smuggle credential strings into kwargs; existing CredentialID field is the only legal path.)
- **Compatibility:** Temporal Cloud + self-hosted both work. `workflow.DeterministicKeys` is in the standard SDK (v1.42), supported on both.

### Locked Decisions

**Interpolation (parser-time desugaring):**
- **D4.1-01:** `${ctx.expr}` desugars at parse time to `lambda ctx: "..." + str(ctx.expr) + "..."`. Implementation in `pkg/parser` (e.g., `pkg/parser/template.go`); `syntax.ParseExpr` validates each inner expression; synthesized lambda flows through existing `bridge.CallLambda` machinery — no new runtime evaluation surface.
- **D4.1-02:** Interpolation allowed anywhere a string kwarg appears: `step(name=...)`, `flow(name=...)`, action kwargs (`gh.get(path="/repos/${ctx.input.repo}")`), `script(id=...)`, future string kwargs. Excluded: kwargs whose declared type is non-string (`inputs={...}` dict literals).
- **D4.1-03:** Validator catches `${ctx.typo}` at parse time for free — synthesized lambda runs through D4-02's `ctx.<name>` walker. No new validator code needed.
- **D4.1-04:** Single-line expressions only; doubled `$` escapes (`"$${not interpolated}"`); empty `${}` is a parse error; mixed `"a${ctx.x}b${ctx.y}c"` desugars to `"a" + str(ctx.x) + "b" + str(ctx.y) + "c"`. `str()` wrap is unconditional.
- **D4.1-05:** When a string kwarg becomes a lambda via desugaring: `step.Name` / `flow.Name` carries `Name string` OR `NameFn *CapturedLambda`, never both. `ActionRef.Kwargs` value type widens from `any` to `any | *CapturedLambda`. ### Pattern 1: Synthesize Source String + Re-Parse for Desugarer

**Decision:** Render synthesized source text and call `(*syntax.FileOptions).Parse` + `starlark.ExecFileOptions`. Do NOT hand-build `*syntax.LambdaExpr` AST.

**Why:** Three concrete reasons.
1. There is no public `starlark.FunctionFromAST(...)` API. `*starlark.Function` is produced from a `*syntax.LambdaExpr` only via the internal `compile` package, which the public surface invokes through `starlark.ExecFileOptions`. Hand-rolling a `*syntax.LambdaExpr` would require us to either re-export internals or duplicate `compile`'s logic — both unsafe and unsupported.
2. Synthesized source flows through the same `(*syntax.FileOptions).Parse` path that the rest of the parser already uses. D4-02's `ctx.<name>` walker (Phase 4) re-parses cached file bytes and matches by position; if our synthesized lambda lives in source, position matching works the same way.
3. Synthesized source can be cached in `Parser.fileBytes` under a synthetic filename (e.g., `<file>:interp:<line>:<col>`) so D4-02 + D-19 free-var validation work unchanged.

**Implementation skeleton (verified against go.starlark.net pkg.go.dev):**
```go
// Source: https://pkg.go.dev/go.starlark.net/syntax#FileOptions.Parse
// Source: https://pkg.go.dev/go.starlark.net/starlark#ExecFileOptions
package parser

import (
    "fmt"
    "go.starlark.net/starlark"
    "go.starlark.net/syntax"
)

// desugarInterpolation converts a string with ${...} markers into a
// CapturedLambda. The synthesized source is "lambda ctx: ..." which the
// parser exec()s in a sub-thread to obtain a *starlark.Function.
func (p *Parser) desugarInterpolation(thread *starlark.Thread, raw string, openPos syntax.Position) (*dag.CapturedLambda, error) {
    parts, err := scanInterpolation(raw, openPos)
    if err != nil {
        return nil, err
    }
    if !parts.hasInterpolation {
        return nil, nil // no ${...} found → caller stores literal string
    }
    src := buildLambdaSource(parts) // "lambda ctx: \"a\" + str(ctx.x) + \"b\""
    synthFilename := fmt.Sprintf("<interp:%s:%d:%d>", openPos.Filename(), openPos.Line, openPos.Col)

    // Validate each inner expression with ParseExpr first — surfaces
    // syntax errors with the user's position, not the synthesized one.
    for _, expr := range parts.expressions {
        // Source: https://pkg.go.dev/go.starlark.net/syntax#ParseExpr
        if _, err := syntax.ParseExpr(synthFilename, expr.text, 0); err != nil {
            return nil, &dag.ParseError{Pos: expr.pos, Msg: fmt.Sprintf("interpolation expression: %v", err)}
        }
    }

    // Cache synthesized source under the synthetic filename so D4-02's
    // ctx.<name> re-parse path (pkg/parser/ctx_walk.go) finds it.
    p.fileBytes[synthFilename] = []byte(src)

    // Compile via ExecFileOptions on a sub-thread that imports nothing.
    // The synthesized "result = lambda ctx: ..." lets us pluck the
    // *starlark.Function out of the resulting StringDict.
    fullSrc := "result = " + src
    opts := defaultFileOptions()
    subThread := &starlark.Thread{Name: "skytime-desugar:" + synthFilename}
    globals, err := starlark.ExecFileOptions(opts, subThread, synthFilename, fullSrc, lambdaTimeGlobals)
    if err != nil {
        return nil, err
    }
    fn, ok := globals["result"].(*starlark.Function)
    if !ok {
        return nil, fmt.Errorf("internal: synthesized lambda did not produce *starlark.Function")
    }
    // Position the lambda at the opening ${, NOT the synthesized source's
    // line 1 — D4-04 requires user-facing attribution.
    return p.captureLambdaAtPosition(fn, openPos)
}
```

**Key insight:** The synthesized lambda's `Function.Position()` will point at line 1, col 1 of the synthetic file. We override it for D-18 ID computation (`captureLambdaAtPosition` uses `openPos`, not `fn.Position()`). The `pkg/parser/lambda_capture.go::captureLambda` function would need a small extension to accept an override position — that's a one-parameter addition to its signature.

### Pattern 2: Position Attribution for Synthesized Lambdas

**Problem:** A synthesized lambda's natural position (`fn.Position()`) is line 1, col 1 of the synthetic file. ValidationError attribution must instead point at the user's source: the opening `${` in the original file.

**Mechanism:**
- `dag.CapturedLambda.Pos` already holds an arbitrary `syntax.Position`. Set it to the open-`${` position from the source scan, NOT the synthesized lambda's natural position.
- `dag.ComputeLambdaID(fileBytes, pos)` (Phase 1) takes the file bytes hash + line + col. Use the **original** file's bytes hash (covers the template string changes) and the open-`${` line+col. This yields a stable ID matching D-18's deployment property: a cosmetic edit to the template invalidates the ID exactly as for a hand-written lambda.
- D4-02's `findCtxAccesses` (in `pkg/parser/ctx_walk.go`) already takes a `lambdaPos` parameter and re-parses the file bytes for that filename. It needs to use the **synthetic** filename here (`<interp:...>`), because that's where the lambda body actually lives. Adjustment: extend `Parser.FileBytes()` to expose the synthetic-source map, OR pass the synthetic filename through `CapturedLambda.Pos.Filename()` as today and have `findCtxAccesses` look up `p.fileBytes[lambdaPos.Filename()]`.

**Concrete file-byte routing:**
```go
// CapturedLambda for an interpolated string:
//   ID:  "abc123ef:42:18"  -- hash from ORIGINAL file, line 42, col 18 (opening ${)
//   Pos: syntax.MakePosition(<original.star>, 42, 18)
//   Fn:  *starlark.Function compiled from the SYNTHETIC source

// To validate ctx.* accesses, the existing D4-02 path needs to walk the
// synthetic source's AST. Two options:
//   A) Store ALSO a synthetic-filename Pos on CapturedLambda for AST walks.
//   B) Have findCtxAccesses fall back to the synthetic file bytes when
//      lambdaPos.Filename() isn't found.
// Recommendation: A. Add CapturedLambda.SyntheticPos *syntax.Position
//                 (nil for hand-written lambdas; set for synthesized).
```

The simpler path: keep `Pos` pointing at the original source (for error reporting), AND add a `BodyPos syntax.Position` field whose value is the synthetic-file position (used by D4-02 walker). Hand-written lambdas have `BodyPos == Pos`. The walker reads `BodyPos`, errors report `Pos`.

### Pattern 3: `syntax.Walk` for `block_fn` Idempotency Classification

**Goal (D4.1-11):** Walk the body of a `block_fn` lambda. For each `*syntax.CallExpr`, classify whether the callee is a known `<ext>.<op>` whose `Idempotent *bool` is declared. Mixed/opaque → defer to runtime check (D4.1-12).

**Concrete pattern (verified against pkg.go.dev/go.starlark.net/syntax):**
```go
// Source: https://pkg.go.dev/go.starlark.net/syntax#Walk
// Source: https://pkg.go.dev/go.starlark.net/syntax#CallExpr
// Source: https://pkg.go.dev/go.starlark.net/syntax#DotExpr

type blockFnClassification struct {
    typedCalls   []extOp // each {ExtName, OpName, Idempotent bool}
    opaqueCalls  []syntax.Position // calls we couldn't statically classify
    hasOpaque    bool
}

func (p *Parser) classifyBlockFn(fn *starlark.Function, ownerFile string) (blockFnClassification, error) {
    // Re-parse the file (mirror pkg/parser/ctx_walk.go::findCtxAccesses).
    src := p.fileBytes[ownerFile]
    file, err := defaultFileOptions().Parse(ownerFile, src, 0)
    if err != nil {
        return blockFnClassification{}, err
    }

    var lambdaBody syntax.Expr
    var lambdaStmts []syntax.Stmt
    syntax.Walk(file, func(n syntax.Node) bool {
        if le, ok := n.(*syntax.LambdaExpr); ok && positionsEqual(le.Lambda, fn.Position()) {
            lambdaBody = le.Body
        }
        if ds, ok := n.(*syntax.DefStmt); ok && positionsEqual(ds.Def, fn.Position()) {
            lambdaStmts = ds.Body
        }
        return true
    })

    var c blockFnClassification
    classify := func(n syntax.Node) bool {
        call, ok := n.(*syntax.CallExpr)
        if !ok {
            return true
        }
        // Recognize <ident>.<ident>(...) — that's an extension factory call.
        dot, isDot := call.Fn.(*syntax.DotExpr)
        if !isDot {
            // Could be a comprehension generator, helper function, etc.
            // Mark opaque only when this looks like it would build an
            // ActionRef — heuristic: any call whose callee is NOT a
            // recognized ext.op is treated as "might emit ActionRef" if it
            // appears at a "list-element" position.
            c.hasOpaque = true
            c.opaqueCalls = append(c.opaqueCalls, call.Lparen)
            return true
        }
        extIdent, ok := dot.X.(*syntax.Ident)
        if !ok {
            c.hasOpaque = true
            c.opaqueCalls = append(c.opaqueCalls, call.Lparen)
            return true
        }
        opName := dot.Name.Name
        // Look up extension+op in the parser registry.
        ext, ok := p.registry.Get(extIdent.Name)
        if !ok {
            // Could be a Starlark helper module loaded via load(); not an
            // extension. Treat as opaque — runtime check fires.
            c.hasOpaque = true
            return true
        }
        spec, ok := ext.Operations()[opName]
        if !ok || spec == nil || spec.Idempotent == nil {
            c.hasOpaque = true
            return true
        }
        c.typedCalls = append(c.typedCalls, extOp{extIdent.Name, opName, *spec.Idempotent})
        return true
    }
    if lambdaBody != nil {
        syntax.Walk(lambdaBody, classify)
    }
    for _, stmt := range lambdaStmts {
        syntax.Walk(stmt, classify)
    }
    return c, nil
}
```

**Termination:** `syntax.Walk` is finite (no cycles in a parsed AST). Comprehensions like `[gh.get(path=p) for p in paths]` have a `*syntax.Comprehension` node that contains the `*syntax.CallExpr` as its element expression — the walk descends through `Body` automatically. Conditionals (`gh.create_issue(...) if cond else gh.delete_issue(...)`) appear as `*syntax.CondExpr` with two `CallExpr` children — both get classified.

**Heuristic warning:** the classifier marks "any non-ext-call CallExpr in the body" as opaque. This is correct for safety (better to defer to runtime than to skip a check) but pessimistic — `len(...)`, `str(...)`, etc. are not ActionRef-producing but still classify as opaque and force the runtime check. That's fine: the runtime check is cheap and the parse-time path is best-effort.

### Pattern 4: Workflow-Side `resolveKwargs` with Deterministic Iteration

**Goal (D4.1-14):** Walk an `ActionRef.Kwargs` *starlark.Dict; for each `*CapturedLambda`-valued entry, call `bridge.CallLambda` and replace with the resolved string. Activity sees a fully-resolved Kwargs.

**Determinism:**
- `*starlark.Dict` iteration order: starlark-go's `*Dict.Iterate()` returns insertion order (NOT randomized). This is unlike Go's native `map`. Verified by reading `pkg/bridge/struct.go` — the existing struct conversion already relies on this.
- However, kwargs is built from a `starlark.Tuple` of `(key, value)` pairs at parse time, and then frozen. Iteration is deterministic out of the box.
- **Action:** Use `dict.Items()` (deterministic) for the resolveKwargs walk. This composes with `workflowcheck` which only flags Go-native `range map`.
- **Why mention `workflow.DeterministicKeys`?** It's the recommended pattern for Go maps in workflow code per the Temporal SDK docs. Our case uses a `*starlark.Dict` not a Go `map[string]any`, so we don't need it for this specific code path. Document this distinction in the implementation comment so a future maintainer doesn't "add a sort" that's already covered.

**Concrete shape:**
```go
// pkg/interpreter/resolve_kwargs.go

// resolveKwargs walks a frozen *starlark.Dict and replaces every
// *CapturedLambda value with the result of bridge.CallLambda. The
// returned dict is a NEW frozen dict — the caller (walk_step) hands it
// to the activity.
//
// Determinism: *starlark.Dict.Items() is insertion-order (NOT randomized
// like Go map iteration), so a sort is unnecessary. workflowcheck does
// not flag *starlark.Dict.Iterate() because it is not Go map iteration.
//
// Cancellation: each bridge.CallLambda invocation receives the existing
// makeCancelChannel(ctx) per D3-21. A long-running kwarg lambda is
// interruptible.
func (i *interpreter) resolveKwargs(ctx workflow.Context, ref *dag.ActionRef) (*starlark.Dict, error) {
    if ref.Kwargs == nil {
        return nil, nil
    }
    out := starlark.NewDict(ref.Kwargs.Len())
    for _, item := range ref.Kwargs.Items() { // deterministic — see comment above
        key, value := item[0], item[1]
        if cl, isLambda := value.(*starlarkCapturedLambda); isLambda {
            // The *CapturedLambda was wrapped at parse time as a Starlark
            // value so it could survive Dict storage. Unwrap and evaluate.
            val, err := i.evalLambda(ctx, cl.captured.ID)
            if err != nil {
                return nil, fmt.Errorf("kwarg %s: %w", key.String(), err)
            }
            // The synthesized lambda always returns a string (D4.1-04
            // unconditional str() wrap). Defensive type-check.
            sv, ok := val.(starlark.String)
            if !ok {
                return nil, fmt.Errorf("kwarg %s: lambda returned %s, expected string", key.String(), val.Type())
            }
            value = sv
        }
        if err := out.SetKey(key, value); err != nil {
            return nil, err
        }
    }
    out.Freeze()
    return out, nil
}
```

**Wrapping CapturedLambda as a Starlark value:** `*dag.CapturedLambda` is a Go struct, not a `starlark.Value`. To store it in `*starlark.Dict.Kwargs`, the desugarer wraps it in a thin `starlarkCapturedLambda` shim implementing `starlark.Value` (mirrors `pkg/parser/builtins.go::nodeValue`). The shim is package-private to `pkg/parser` AND `pkg/interpreter` — recommend defining it in `pkg/dag/lambda.go` so both packages can import it without circular deps.

### Pattern 5: Live-Block Render Goroutine with Single-Writer Channel

**Goal (D4.1-17..21):** Multi-line redrawing region at terminal bottom; static lines accumulate above. Concurrent step events from interpreter go-routines feed a single render goroutine.

**Decision:** Single render goroutine + buffered channel; events are immutable values; render goroutine owns the writer.

**Why:**
- The interpreter is single-goroutine (workflowcheck enforces no native `go`); but `for_each_parallel` uses `workflow.Go` which produces concurrent slog events. The slog handler runs whichever goroutine emitted the record — so `Handle()` is called concurrently.
- Rather than serialize with a mutex inside `Handle()`, push events into a `chan progressEvent` and let one render goroutine pop, update state, and redraw. This makes redraw atomic and isolates the ANSI escape sequencing.
- The render goroutine is a normal Go goroutine living in `pkg/cli/progress_live.go` — NOT a workflow goroutine. It reads from a channel fed by the slog handler's `Handle()` method, AND from a `time.Ticker` for spinner cadence (100 ms).

**Skeleton:**
```go
//go:build !windows

package cli

import (
    "fmt"
    "io"
    "sync"
    "time"
)

type liveRenderer struct {
    out      io.Writer
    events   chan progressEvent
    done     chan struct{}
    wg       sync.WaitGroup

    // State owned exclusively by the render goroutine.
    active   []*activeStep // ordered: first to complete is at top
    cap      int           // D4.1-19 default 10
    drawn    int           // number of lines currently drawn in the redraw region
}

func newLiveRenderer(out io.Writer) *liveRenderer {
    r := &liveRenderer{
        out:    out,
        events: make(chan progressEvent, 64),
        done:   make(chan struct{}),
        cap:    10, // D4.1-19
    }
    r.wg.Add(1)
    go r.run() // single render goroutine
    return r
}

func (r *liveRenderer) run() {
    defer r.wg.Done()
    tick := time.NewTicker(100 * time.Millisecond) // D4.1-18
    defer tick.Stop()
    for {
        select {
        case ev, ok := <-r.events:
            if !ok {
                r.flushFinal()
                return
            }
            r.applyEvent(ev)
            r.redraw()
        case <-tick.C:
            r.tickSpinner()
            r.redraw()
        case <-r.done:
            r.flushFinal()
            return
        }
    }
}

// redraw clears the previous redraw region (cursor up + line clear) and
// writes the current active rows. Static lines (completed) are NOT in
// the redraw region — they were emitted as immutable lines on completion
// before redraw.
func (r *liveRenderer) redraw() {
    // 1. Move cursor up by r.drawn lines, clear each line.
    for i := 0; i < r.drawn; i++ {
        fmt.Fprint(r.out, "\x1b[1A\x1b[2K") // ESC[1A: up 1; ESC[2K: clear line
    }
    // 2. Write header + active rows + (... and N more) if needed.
    n := len(r.active)
    visible := n
    if visible > r.cap {
        visible = r.cap
    }
    fmt.Fprintf(r.out, "[skytime] in-progress  %d active\n", n)
    drawn := 1
    for i := 0; i < visible; i++ {
        s := r.active[i]
        fmt.Fprintf(r.out, "  %s %s  %s %s\n", s.counter, s.label, s.spinnerFrame(), s.elapsed())
        drawn++
    }
    if n > r.cap {
        fmt.Fprintf(r.out, "  ... and %d more\n", n-r.cap)
        drawn++
    }
    r.drawn = drawn
}
```

**ANSI choice — cursor-up + line-clear vs alternate-screen-buffer:**

Verified against precedent (`cli/cli` PR #5681 explicitly chose alternate-screen for `gh run watch`; cargo, npm, kubectl all use cursor-up). The trade-off:

| Approach | Pros | Cons |
|----------|------|------|
| **Cursor-up + line-clear** (`\x1b[1A\x1b[2K`) | Preserves scrollback. Static lines stay visible. Works in any terminal. Greppable scrollback after run. | Brief flicker on slow terminals during multi-line redraw. |
| **Alternate-screen-buffer** (`\x1b[?1049h` / `\x1b[?1049l`) | Atomic full-screen redraws. No flicker. | Loses scrollback when entering AltBuf; users CANNOT scroll back to see early steps after the run completes. Requires reliable cleanup (signal handler) or tmux/screen leaves user in altbuf. |

**Recommendation: cursor-up + line-clear.** Two reasons:
1. Demos: a consultant running `skytime run` on a customer call wants to scroll up after completion to point at specific steps. AltBuf hides them.
2. CI: CI logs benefit from the static lines persisting in the scrollback (even though we already detect non-TTY and disable live block). Being friendly to PTY-emulating CI runners that report TTY=true is a nice property.

Cargo, npm, kubectl, bazel all chose cursor-up. We follow precedent.

**ANSI sequences used:**
- `\x1b[1A` — cursor up 1 line (CUU)
- `\x1b[2K` — erase entire line (EL with parameter 2)
- `\x1b[?25l` / `\x1b[?25h` — hide / show cursor (DECTCEM)
- We do NOT need: `\x1b[s` / `\x1b[u` (save/restore cursor — flaky across terminals).

### Pattern 6: SIGWINCH Handling (Recommended: Ignore in v1)

**Concern:** When the user resizes the terminal during a live render, the active rows could exceed terminal width and cause line-wrap that the cursor-up math gets wrong.

**Investigation:**
- The truncation cap (D4.1-19, default 10 visible rows) is a hardcoded line count, not a fraction of terminal height. So a vertical resize doesn't break the redraw region's height calculation.
- A horizontal resize CAN cause a single row to wrap into 2 visible lines, throwing off `r.drawn`. This is the actual hazard.

**Trade-off:**
- **Handle SIGWINCH:** Re-query terminal width via `golang.org/x/term.GetSize`, recompute, redraw. ~30 LOC, plus a goroutine listening on `signal.Notify(SIGWINCH)`. Risk: extra moving part, possible cursor confusion if the resize happens mid-redraw.
- **Ignore SIGWINCH:** Truncate row labels to `min(termWidth-20, 80)` characters at first render; never expand. Resize-during-render produces a transient cosmetic glitch that resolves on the next redraw tick. Risk: glitch visible on resize.

**Recommendation: Ignore in v1, document as known limitation.** The live block is for short-running flows (the demo pitch); resize-during-flow is rare in practice. v1.x can add SIGWINCH if a user complains. Keep the code simple.

If SIGWINCH IS handled: `signal.Notify(ch, syscall.SIGWINCH)` → forward to render goroutine via the events channel as a synthetic `eventResize`. Don't query terminal size from a goroutine other than the render goroutine (race with active redraw).

### Anti-Patterns to Avoid

- **Don't sprinkle `mu.Lock()` inside `Handle()`** — race on writer state. The single-render-goroutine pattern is cleaner.
- **Don't use `\033[H\033[J` (clear-screen + home)** — wipes the entire terminal including pre-existing static lines. We only want to clear OUR redraw region.
- **Don't share mutable `progressEvent` values across the channel** — make events fully-owned values; the slog Handler creates the event, ships it, never touches it again.
- **Don't call `bridge.CallLambda` with `workflow.Go`** — the existing pattern (Phase 3 `evalLambda`) calls CallLambda directly on the workflow goroutine. CallLambda's *internal* watchdog uses a native goroutine (Phase 1 design), but the `bridge.CallLambda` invocation itself runs on the workflow goroutine. This is correct because CallLambda blocks (synchronously waits for the lambda) and `workflow.Go` would create a non-deterministic concurrency point.
- **Don't do parser-time scanning with regex for `${...}`** — nested braces (`${ctx.foo[ctx.bar]}` — the `[` and `]` inside don't matter, but `${ctx.foo()}` is fine) are easy. But `${ctx.dict["x"]}` puts a `]` inside `${}`. And expressions like `${ctx.foo("}")}` put a `}` inside a string inside `${}`. Regex won't get this right. Use a state-machine scanner that tracks string-literal mode and bracket depth (see Pitfall #3 below).

## Common Pitfalls

### Pitfall 1: Synthesized Lambda Position Confusion

**What goes wrong:** Error messages report `<interp:simple_check.star:42:18>:1:18: ctx has no attr 'tyop'` — user has no idea what `<interp:...>` means.

**Why it happens:** The synthesized lambda's natural `Function.Position()` is line 1, col 1 of the synthetic file. If we use that for D4-04 attribution, errors leak the synthetic filename.

**How to avoid:** `dag.CapturedLambda.Pos` MUST point at the user's source position (opening `${`). The synthetic filename + position is internal-only — used by `findCtxAccesses` to walk the lambda body's AST, but never surfaced in error messages.

**Warning signs:** Tests showing `<interp:...>` in expected output strings. ValidationError.String() ever returning a synthetic filename.

### Pitfall 2: ${...} Scanner Bracket-Counting Bugs

**What goes wrong:** `"${ctx.foo("}")}` is a valid Starlark expression — `ctx.foo("}")` is a function call with a string literal argument that contains `}`. A naive scanner counts braces and terminates `${...}` at the inner `}`, producing nonsense.

**Why it happens:** Starlark string literals can contain any char including `{` and `}`. A bracket-counting scanner that doesn't track string-literal state breaks.

**How to avoid:** State-machine scanner tracks 4 modes:
1. **text** — scanning normal characters; on `$$` emit literal `$`; on `${` enter expr mode.
2. **expr** — scanning a `${...}` body; track nested `{}/[]/()` depth; track string-literal mode (started by `"`, `'`, `"""`, `'''`); the closing `}` is the one that brings depth back to 0 outside any string.
3. **expr-string** — inside a string literal in an expression; honor `\` escapes; `}` inside is literal.
4. **end** — final state.

```go
// Concrete scanner (≤80 LOC). Emits a list of {literal, lambda-expr-text, position}.
//
// Pre-conditions: input is a Starlark string literal's CONTENT (after
// unquoting). The parser already unquoted it via starlark.UnpackArgs.
//
// Post-conditions: returns ScannedTemplate{parts, hasInterpolation}, OR
// *dag.ParseError on:
//   - empty ${} (D4.1-04)
//   - unterminated ${ (no closing } before EOF)
//   - multi-line ${... with embedded newline (D4.1-04 single-line only)
```

**Warning signs:** Tests for `"${ctx.s.replace(\"}\", \"X\")}"` (synthetic but valid) failing or producing wrong output.

### Pitfall 3: Synthesized Lambda + D-19 Free Var Lint Reporting Wrong File

**What goes wrong:** D-19 free-var lint (validateFreeVars in `pkg/parser/linter.go`) checks that every free variable's binding is at column 1 of the **owning file**. For a synthesized lambda, the "owning file" is the synthetic file. Module-level constants from the user's source are NOT module-level in the synthetic file — they appear as undefined names.

**Why it happens:** D-19's `isModuleLevelBinding` uses `binding.Pos.Filename() == filename`. For a synthesized lambda, the binding's filename would be the original file but the lambda's owning file is synthetic.

**How to avoid:** The synthesized lambda has NO free variables — `${ctx.foo}` references `ctx` (the lambda's parameter) and accesses an attribute. There are no closed-over constants in interpolation desugaring. The `validateFreeVars` call returns immediately (zero free vars) and the bug never fires for interpolation lambdas.

For `action_fn` / `block_fn` (which are user-written, not synthesized), free-var lint runs against the original file — exactly as today.

**Warning signs:** A synthesized lambda having `NumFreeVars() > 0`. If this ever fires, a desugarer regression introduced a closure where there shouldn't be one.

### Pitfall 4: `block_fn` Lambda Returning a Mutable List

**What goes wrong:** `block_fn = lambda ctx: result_list` where `result_list` is a module-level `[]` accumulator that mutates between flow runs. Two replays produce different ActionRefs.

**Why it happens:** Replay determinism requires the same lambda to produce the same output on every replay. A free variable referencing a mutable list breaks this.

**How to avoid:** D-19 free-var lint already catches mutable closures (Phase 1). The synthesized desugarer lambda has no free vars, so it's safe. The user-written `block_fn` flows through `validateFreeVars` exactly as today and any mutable-closure capture errors out at parse time.

**Warning signs:** A `block_fn` capturing a free var. Test fixtures should include a NEGATIVE case: `block_fn = lambda ctx: [gh.get(path=p) for p in some_module_level_list]` where `some_module_level_list` is a (non-frozen) `[]`. The parser must reject — current Phase 1 lint already does, but Phase 04.1 should add a fixture-level test to pin the behavior.

### Pitfall 5: Interpolation in Non-String Kwargs

**What goes wrong:** Consultant writes `step(retry={"max_attempts": "${ctx.attempts}"})`. `retry` is a typed kwarg whose value is a dict, not a string — the interpolation makes no sense there.

**Why it happens:** D4.1-02 says interpolation is allowed "anywhere a string kwarg appears". The parser must NOT desugar interpolation inside non-string kwargs.

**How to avoid:** The desugarer is invoked from the kwarg-unpacking path for each kwarg. Whitelist: `name` (step + flow), action kwargs (driven by extension schema's string fields), `script(id=...)`. Anything else: leave the string literal alone.

**Warning signs:** A test case `step(retry={"max_attempts": "${ctx.x}"})` should produce a literal-string `"${ctx.x}"` in the retry dict (NOT a desugared lambda). The error surfaces at kwarg-shape validation when `"${ctx.x}"` fails to parse as an int.

### Pitfall 6: Live Block Race with Final Flow Output

**What goes wrong:** Render goroutine still has active rows in the redraw region when `flow_complete` arrives. Final summary line gets prepended above the redraw region; cursor positions go wrong on next event.

**Why it happens:** Active rows haven't been cleared because the render goroutine is mid-redraw or hasn't received the `step_complete` for the final step yet (channel buffering).

**How to avoid:** On `flow_complete`, the render goroutine: (1) flushes any pending events, (2) clears the redraw region completely, (3) emits the final summary line as a static line. The flow's slog handler closes the events channel after emitting `flow_complete`; the render goroutine drains and exits.

**Warning signs:** Test output containing duplicate or interleaved lines from active rows + flow summary.

### Pitfall 7: Differential Test Drift from Lambda-Built ActionRefs

**What goes wrong:** Phase 4's `tests/differential_test.go` parses `examples/skeleton/*.star` and dry-run-interprets them. After the corpus rewrite (D4.1-23/24), the static `validator.Validate` accepts but the dryrun path crashes because it doesn't know how to handle `*CapturedLambda` kwargs.

**Why it happens:** The dryrun's `AlwaysOkDispatch` shallow-copies OperationSpec and replaces only `Func`. The activity-side path now needs to handle pre-resolved kwargs (which at runtime are real strings) but at dryrun time the workflow walker hasn't resolved them yet.

**How to avoid:** D4.1-25 — the dryrun activity needs to handle `*CapturedLambda`-valued kwargs by treating them as opaque ("any string") when validating shape. Path:
1. `pkg/interpreter/walk_step.go::resolveKwargs` runs in the dryrun workflow exactly as in production.
2. The dryrun version of `bridge.CallLambda` (or a shim) is needed: the lambda's body might reference `ctx.input.repo` — the dryrun seeds `InitState` from `flow.Inputs` via `stubInitState` (already exists) so the lambda eval succeeds.
3. The lambda's resolved string is whatever `stubInitState` produces (e.g., "" for type "string"). The dispatched activity returns `OkResult{}` and the differential test passes.
4. For `action_fn` / `block_fn`: the workflow walker calls the lambda; the result is `*ActionRef` / `[]*ActionRef` against the `stubInitState`-seeded ctx. Activity-side path is unchanged.

**Warning signs:** `TestDifferentialCorpus` failing after corpus rewrite with a panic from the dryrun's reflection-based decoder hitting `*CapturedLambda` instead of a primitive type.

### Example 2: Workflow-Side Resolution (D4.1-14)

```go
// Source: pkg/interpreter/walk_step.go (Phase 4 pattern), extended for 04.1.

func (i *interpreter) walkStep(ctx workflow.Context, step *dag.Step) (err error) {
    // ... existing dispatch event emission ...

    // 04.1: dispatch action_fn / block_fn lambdas to build actions at workflow time.
    actions, err := i.buildStepActions(ctx, step)
    if err != nil {
        return err
    }

    // 04.1: resolve lambda-valued kwargs on each action.
    for _, ref := range actions {
        if ref.Kwargs != nil {
            resolved, err := i.resolveKwargs(ctx, ref)
            if err != nil {
                return err
            }
            ref.Kwargs = resolved
        }
    }

    // ... rest unchanged: ExecuteActivity, defer step_complete, etc. ...
}

// buildStepActions returns step.Actions if static, OR runs action_fn /
// block_fn lambda to build actions at workflow time.
func (i *interpreter) buildStepActions(ctx workflow.Context, step *dag.Step) ([]*dag.ActionRef, error) {
    switch {
    case step.ActionFn != nil:
        val, err := i.evalLambda(ctx, step.ActionFn.ID)
        if err != nil {
            return nil, err
        }
        ref, ok := val.(*dag.ActionRef)
        if !ok {
            return nil, temporal.NewNonRetryableApplicationError(
                fmt.Sprintf("action_fn returned %s, expected ActionRef (at %s)", val.Type(), step.ActionFn.Pos),
                "ActionFnTypeMismatch", nil)
        }
        return []*dag.ActionRef{ref}, nil
    case step.BlockFn != nil:
        val, err := i.evalLambda(ctx, step.BlockFn.ID)
        if err != nil {
            return nil, err
        }
        list, ok := val.(*starlark.List)
        if !ok {
            return nil, temporal.NewNonRetryableApplicationError(
                fmt.Sprintf("block_fn returned %s, expected list of ActionRef (at %s)", val.Type(), step.BlockFn.Pos),
                "BlockFnTypeMismatch", nil)
        }
        out := make([]*dag.ActionRef, 0, list.Len())
        iter := list.Iterate()
        defer iter.Done()
        var v starlark.Value
        for iter.Next(&v) {
            ref, ok := v.(*dag.ActionRef)
            if !ok {
                return nil, temporal.NewNonRetryableApplicationError(
                    fmt.Sprintf("block_fn batch entry is %s, expected ActionRef (at %s)", v.Type(), step.BlockFn.Pos),
                    "BlockFnTypeMismatch", nil)
            }
            out = append(out, ref)
        }
        return out, nil
    default:
        return step.Actions, nil // static action / block path, unchanged
    }
}
```

```go
// Source: pkg/parser/block_fn_lint.go (NEW)
// Mirrors pkg/parser/linter.go::lintMixedIdempotency pattern.

func (p *Parser) lintBlockFnIdempotency() error {
    for _, flow := range p.flows {
        if err := p.walkLintBlockFn(flow.Name, flow.Body); err != nil {
            return err
        }
    }
    return nil
}

func (p *Parser) walkLintBlockFn(flowName string, body []dag.Node) error {
    for _, node := range body {
        switch n := node.(type) {
        case *dag.Step:
            if n.BlockFn == nil {
                continue
            }
            c, err := p.classifyBlockFn(n.BlockFn.Fn, n.BlockFn.Pos.Filename())
            if err != nil {
                return err
            }
            if c.hasOpaque {
                continue // defer to runtime fallback (D4.1-12)
            }
            // All typed — check homogeneity.
            var hasIdem, hasNonIdem bool
            for _, t := range c.typedCalls {
                if t.idempotent {
                    hasIdem = true
                } else {
                    hasNonIdem = true
                }
            }
            if hasIdem && hasNonIdem {
                return &dag.ValidationError{
                    Pos: n.BlockFn.Pos, Flow: flowName,
                    Msg: fmt.Sprintf("block_fn cannot mix idempotent and non-idempotent operations:\n  - %s.%s (idempotent)\n  - %s.%s (NOT idempotent)\nSuggestion: split into separate steps with action_fn each.",
                        c.typedCalls[0].ext, c.typedCalls[0].op, /* ... pick non-idempotent example ... */),
                }
            }
        // recursion into IfCond / ForEachParallel mirrors lintMixedIdempotency
        }
    }
    return nil
}
```

## Open Questions

1. **Should the synthesized lambda's `BodyPos` field live on `dag.CapturedLambda` or be inferred?**
   - What we know: D4-02's `findCtxAccesses` already takes a `lambdaPos` and re-parses. For a synthesized lambda, the AST lives in the synthetic file, not the original.
   - What's unclear: does adding a `BodyPos` field to `dag.CapturedLambda` ripple through Phase 1 fixtures?
   - Recommendation: Add `BodyPos syntax.Position` (zero value when unset means "use Pos for AST walks too" — backward-compatible). Phase 1 fixtures should be unaffected.

2. **Should the live block emit `[N/M] step ...starting...` lines for non-TTY, OR just emit on completion?**
   - What we know: D4.1-21 says non-TTY → static lines. Phase 4 today emits both `step_dispatch` and `step_complete` events as separate lines.
   - What's unclear: in non-TTY, is `[1/3] step gh.get(...) starting` + `     ✓ 234ms status=200` two lines or merged into one?
   - Recommendation: Keep two-line format for non-TTY (matches Phase 4 behavior; greppable). The CONTEXT example "starting" / "completion" is consistent. CI logs benefit from explicit start/finish.

3. **For `block_fn` returning empty list, should the activity be invoked at all?**
   - What we know: CONTEXT.md recommends skip-with-event ("emit `step_complete` with `summary=\"empty batch\"`").
   - What's unclear: does `pkg/activity/validate_batch.go` reject empty batches today? (Yes — `errTypeEmptyBatch`.) So calling it would surface a confusing error.
   - Recommendation: `walk_step.go::buildStepActions` returns `nil, nil` for an empty `block_fn` result, then `walkStep` skips `ExecuteActivity` and emits `step_complete{status:"ok", summary:"empty batch", duration_ms: <small>}`. Tests pin the behavior.

4. **Should the differential corpus dry-run path call `bridge.CallLambda` for `action_fn` / `block_fn`, or short-circuit with a hardcoded fake ActionRef?**
   - What we know: The differential test seeds `InitState` from `flow.Inputs` via `stubInitState`. The dryrun workflow runs the same `walk_step.go` as production — D4.1-25 says it must.
   - What's unclear: lambda eval over stubInitState may still fail (e.g., `ctx.input.repos` returns "" instead of a list, breaking `[gh.get(path=p) for p in ctx.input.repos]`).
   - Recommendation: Extend `stubInitState` to seed list/dict zero-values that allow comprehensions to run (already does for "list" → `[]`, "dict" → `{}` per Phase 4). For lambdas that depend on richer state, the differential test corpus authors are responsible for ensuring `flow.Inputs` declares appropriate types. If a `block_fn` produces an empty list under stub state, that's fine — Q3 above handles it.

## Closing notes

Phase 04.1's spec is unusually thorough — the CONTEXT.md author has effectively done most of the hard thinking already. The research mostly confirmed paths and surfaced a few execution details:

1. **Synthesized-source-string is the only viable desugarer path.** Don't try to hand-build the AST.
2. **Determinism for `resolveKwargs` is already free** — `*starlark.Dict.Items()` is insertion-order, not randomized. No `DeterministicKeys` needed for this specific path.
3. **`charm-log v2` does NOT ship a spinner.** Inline 10 braille frames; don't pull BubbleTea.
4. **Cursor-up + line-clear beats alternate-screen-buffer for our use case** — preserves scrollback for demo / CI scenarios.
5. **The differential corpus rewrite is the highest-risk task** — `tests/differential_test.go` glue must be extended carefully so the dryrun path handles lambda kwargs and lambda-built ActionRefs without breaking parse/dryrun agreement.
6. **D-19 free-var lint already protects mutable closures** — synthesized lambdas have no free vars; user-written `action_fn`/`block_fn` flow through the existing path. No new lint code needed.

The planner can confidently use this research to break the phase into 5-7 plans (parser desugarer; AST classifier + block_fn lint; dag/extension type widening; interpreter resolveKwargs + action_fn/block_fn dispatch; cli live block; corpus rewrite + differential test extension).
