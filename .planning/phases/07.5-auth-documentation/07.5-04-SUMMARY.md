## Decisions Made

- **`NewAPIKeyDynamicCredentials` not `Static`** — same rationale as Plans 02/03: the page intro anti-patterns Static for production workers. The Dynamic variant with `GetSecret` re-read on every RPC is the rotation-friendly variant the page demonstrates.
- **`azidentity.NewDefaultAzureCredential(nil)` is the entire WI configuration** — Azure Workload Identity's whole value proposition is that the default credential chain reads `$AZURE_FEDERATED_TOKEN_FILE` automatically when the AKS webhook injects it. No explicit `WorkloadIdentityCredential` import needed; the default chain detects it. This matches D-7.5-08 (medium audience: the IAM plumbing is delegated to the SDK and to the AKS configuration the reader already did).
- **Parameter name `vaultURL` (not `vaultURI` or `keyVaultURL`)** — matches the Azure SDK's own naming for the same input (the `vaultURL` parameter to `azsecrets.NewClient`). Keeps the caller-site env var name `AZURE_VAULT_URL` consistent with the Azure ecosystem convention.
- **Explicit `resp.Value` nil-check** — Azure SDK returns `*string` for the secret Value field (the SDK pattern for distinguishing 'absent' from 'empty string'). The nil-check guards against a misconfigured secret with no value set and returns a descriptive error instead of a nil-pointer panic. Mirrors Plan 03's `SecretString`-nil-check pattern.
- **TLS auto-enabled comment reworded to avoid the literal token `TLSDisabled`** — mirrored Plan 02's and Plan 03's reconciliation verbatim. The phrase "do NOT disable TLS via ConnectionOptions on the returned client.Options" preserves the warning intent AND satisfies the `! grep -q 'TLSDisabled' azure.go` firewall gate. Same reword applied to the markdown fence body so drift-test passes.
- **`go mod tidy` picks the version, not a manual pin** — matches Plans 02/03 stance. Resolved at execution time: azidentity v1.13.1, keyvault/azsecrets v0.12.0, azcore v1.20.0, MSAL v1.6.0. Note: azsecrets is at v0.x (pre-1.0) but is the canonical Azure SDK for Go Key Vault Secrets client — this matches the Azure SDK ecosystem norm where individual service clients ship at v0.x while the SDK core (azcore, azidentity) is at v1.x.
