# Phase 04.2: if_cond as expression with strict-equality result binding - Context

**Gathered:** 2026-05-03
**Status:** Ready for planning

<domain>
## Phase Boundary

Replace today's purely procedural `if_cond` with an EXPRESSION-shaped variant where each branch may end with `result(value={...})` and the `if_cond` itself binds a typed value back into workflow state under a new `output_alias`. Strict structural equality across branches is enforced at parse time — keys must match exactly, per-key value types must match exactly (no LUB / no widening; explicit `float(x)` casts handle widening). A new top-level `fail("msg")` node-builtin is added so a branch can be parse-time-visibly fatal, enabling asymmetric branch shapes (one returns a value, the other terminates).

**Implementation is parser-side.** Runtime semantics of `walkIfCond` remain unchanged: the chosen branch is walked, its result lambda(s) are evaluated, the assembled dict is bound to `ctx[output_alias]` (or the fail message is raised as a NonRetryableErr). No new Temporal history events. No changes to `dag.IfCond`'s zero-event property (INTRP-03).

**Coexistence stance:** ADDITIVE. `output_alias` is opt-in. Existing procedural `if_cond(cond=..., then=[...], else_=[...])` flows continue to compile and run identically. Only when `output_alias` is set does the new expression-mode parse-time validation kick in.

**Required before Phase 5** so the E2E test harness designs against the locked state-propagation shape from the start.

</domain>

<decisions>
## Implementation Decisions

### State binding shape

- **D4.2-01:** `dag.IfCond` gains an optional `OutputAlias string` field (mirrors `Script.OutputAlias`). Setting `if_cond(output_alias="X", ...)` triggers expression mode. Empty string = procedural mode (today's behavior). The corresponding parser builtin `builtinIfCond` accepts an optional `output_alias` kwarg; presence detection mirrors the `hasKwarg` pattern used for `task_queue` (D3-19).

### `result(...)` builtin

- **D4.2-02:** New top-level `result(value={...})` builtin in `parser.newParseTimeGlobals`. Emits a new `*dag.Result` node. Kwarg-only signature (`value=`); positional rejected. The `value=` argument MUST be a Starlark dict-literal at the call site — anything else (a variable reference, a lambda, a function call) is a parse error: `"result.value must be a dict literal"`.

- **D4.2-03:** **Static keys, expression values.** Every dict KEY must be a string literal at parse time (computed keys → parse error). Each dict VALUE is captured as a per-key `*dag.CapturedLambda` via the same synthesized-source desugaring infrastructure as D4.1-01 interpolation. The `*dag.Result` node carries:
  - `Pos syntax.Position`
  - `Keys []string` (insertion order from the source dict-literal — replay determinism is preserved by the parser writing keys in this fixed order; the interpreter assembles the result dict in this exact order)
  - `Values map[string]*CapturedLambda` (per-key value lambdas)
  - `Types map[string]TypeInfo` (per-key inferred type — see D4.2-06)

- **D4.2-04:** `result(...)` is a LEAF — it has no body, no children. It is only legal as the LAST node of a `then` or `else_` body inside an `if_cond` whose `output_alias` is set. The parser rejects `result(...)` everywhere else with a clear hint pointing to the missing `output_alias`.

### `fail(...)` builtin

- **D4.2-05:** New top-level `fail("msg")` builtin in `parser.newParseTimeGlobals`. Emits a new `*dag.Fail` node. **Same NAME as the lambda-time `fail` (D-20)** — the two predeclared environments are mutually exclusive (top-level vs inside-lambda body), so Starlark itself does not collide. Documentation in `pkg/parser/doc.go` and the corpus README must call out the dual semantics:
  - **Top-level** `fail("msg")` → emits `*dag.Fail` node, parse-time-visible, fatal branch.
  - **Inside a lambda body** `fail("msg")` → raises `*starlark.EvalError` at workflow execute time (existing behavior, unchanged).
  Both produce the same observable surface: a NonRetryableErr with the user's message at the .star callsite.

- **D4.2-06:** `*dag.Fail` shape mirrors `Step.Name`/`Step.NameFn` from D4.1-15:
  - `Pos syntax.Position`
  - `Message string` (the literal template — preserves `${...}` markers verbatim)
  - `MessageFn *CapturedLambda` (the synthesized lambda, set when `${...}` interpolation is present in the message; nil otherwise)
  Interpolation is supported (`fail("repo ${ctx.repo} not found")`) — the desugaring path is the existing D4.1-01 infrastructure.

- **D4.2-07:** `fail(...)` is allowed anywhere a body accepts nodes — both in procedural-mode `if_cond` branches (the procedural guard pattern: `if_cond(cond=..., then=[fail("invalid")])`) and as the last node of an expression-mode branch.

### Coexistence with procedural mode

- **D4.2-08:** Additive, opt-in. The presence/absence of `output_alias` on `if_cond` is the mode switch:
  - **Procedural mode** (`output_alias == ""`): TODAY'S behavior preserved exactly. `else_` is optional. Branches contain any procedural nodes. `result(...)` is REJECTED at parse time anywhere in either branch (with hint pointing to the missing `output_alias`). `fail(...)` IS allowed (procedural guard).
  - **Expression mode** (`output_alias != ""`): new parse-time rules in D4.2-09 apply.

### Expression-mode parse-time rules

- **D4.2-09:** When `output_alias` is set, the parser enforces:
  1. Both `then` AND `else_` are present (`else_` cannot be omitted in expression mode).
  2. The LAST node of each branch is either `*dag.Result` or `*dag.Fail` (any other node as the last position is a parse error).
  3. At least ONE branch's last node is `*dag.Result` (otherwise `output_alias` is unreachable — both-fail is rejected with a clear hint that this is procedural-guard territory and `output_alias` should be removed).
  4. Across all branches that end in `*dag.Result`: KEY SETS must be identical (string-literal-equality compared after sorting). Mismatch → `*dag.ValidationError` with both branches' positions and the symmetric-difference of keys in the message.
  5. For each shared key: PER-BRANCH VALUE TYPES are compared best-effort (see D4.2-10).
  Validation lives in a new finalize-pass step (e.g., `validateIfCondExpressionShape`) ordered AFTER `validateLambdaCtxAccesses` so structural state errors surface first.

### Type inference: permissive

- **D4.2-10:** Best-effort static type inference, defer-to-runtime-via-no-check for opaque expressions. The parser walks each `result(value=...)` value-expression and attempts to derive a `TypeInfo`:
  - **Literals** typed directly: int / float / bool / string / None / dict (recursive) / list (homogeneous element type) / tuple (positional element types)
  - **`ctx.X` references** typed via the new typed state schema (D4.2-11)
  - **Operators** (`+`, `-`, `*`, `/`, `//`, `%`, `<`, `>`, `==`, `and`, `or`, `not`) using Starlark's per-operand-type rules
  - **Locked 20-key lambda-time builtins** with their known return-type rules (`len`→int, `str`→string, `bool`→bool, `int`→int, `float`→float, `sorted`/`reversed`→list[T], `enumerate`→list[(int,T)], `zip`→list[tuple], `range`→range, `min`/`max`/`abs`→T, `sum`→int|float, `any`/`all`→bool, etc.)
  - **Conditional expressions** (`a if c else b`) → recursive arm-equality check; if both arms type-equal, use that type; otherwise opaque
  - **Anything else** (comprehensions, calls outside the 20-key vocab, dynamic getattr, string-format methods) → `Opaque`

- **D4.2-11:** Branch equality check (per shared key):
  - Both sides typed → STRICT equality required. No widening — `int` ≠ `float` ≠ `bool`. Mismatch → `*dag.ValidationError` with a clear cast hint (e.g., "branches disagree on key `count`: then=int, else_=float; wrap one side with `float(x)` or `int(x)` to widen explicitly").
  - One side typed, the other Opaque → DEFER (no parse error). Best-effort static; the typed side gives partial guarantee but the parser doesn't claim full static safety.
  - Both sides Opaque → DEFER (no parse error).

- **D4.2-12:** "Strict equality" intentionally means strict — no LUB rules in v1. Explicit casts are the widening mechanism: `result(value={"count": float(ctx.n)})` to align with a `float`-producing sibling branch. This matches the phase trigger paragraph verbatim and is the design discipline; loosening this requires a new ADR.

### State-schema upgrade

- **D4.2-13:** `pkg/parser/state_schema.go`'s `stateSet` (today: `map[string]struct{}`) widens to a TYPED schema. Likely shape: `type stateSchema map[string]TypeInfo`. The existing visibility-only D4-02 ctx-access check continues to work (membership/absence is unchanged); the new type-info field is consulted by the result-inference pass and may also be consulted by future phases. Flow inputs seed the schema from `flow(inputs={"name": "type"})` declared type-hint strings (`int`/`bool`/`string`/`list`/`dict`); script `output_alias` adds entries with the inferred type of the script's `fn=...` body (best-effort same as D4.2-10). When `if_cond(output_alias="X")` is reached, the per-branch result types determine the post-if-cond type for `X` (since branches must agree, the type is unambiguous after the strict-equality check).

- **D4.2-14:** `TypeInfo` is a sealed sum (Go interface with unexported marker, mirroring `dag.Node` and `dag.ActionResult`). Concrete kinds:
  - `TypeScalar{Kind: int|float|bool|string|none}`
  - `TypeDict{Fields map[string]TypeInfo}` (recursive)
  - `TypeList{Element TypeInfo}` (homogeneous; mismatched-element lists collapse to `TypeOpaque`)
  - `TypeTuple{Elements []TypeInfo}` (positional)
  - `TypeOpaque{}` (cannot be statically inferred)

### Renderer / interpreter

- **D4.2-15:** Runtime interpreter changes are minimal. `walkIfCond` (in `pkg/interpreter/walk_ifcond.go`) is extended:
  - When the chosen branch's last node is `*dag.Result` AND `n.OutputAlias != ""`: walk the body normally (renderer indented children unchanged), then evaluate each `Values[k]` lambda in `Keys` order, assemble a Starlark dict, and assign to `ctx[OutputAlias]`. Emit a single `result_bound` event (`event=result_bound`, `alias=<OutputAlias>`, `keys=[...]`, `path=<branch path>`) for renderer visibility.
  - When the chosen branch's last node is `*dag.Fail`: walk preceding nodes, then raise a NonRetryableErr with `n.Message` (or `n.MessageFn` evaluated against state if present). Wraps via `temporal.NewNonRetryableApplicationError` carrying `n.Pos` for callsite preservation. Emit a `step_complete` event with `status=err`, `kind=fail`, `summary=<resolved message>`.
  - Procedural mode: walkBody continues exactly as today; `*dag.Result` and (top-level) `*dag.Fail` nodes are not present in well-formed procedural-mode bodies.

- **D4.2-16:** Renderer shape (live block + static line + verbose modes):
  - `*dag.Result` renders as a leaf row inside the active branch scope: `[depth] ✓ result → ctx.<alias>` with the bound dict's key list visible in `--verbose`. Detail polish is Claude's discretion during planning.
  - `*dag.Fail` renders as a leaf row with the error marker: `[depth] ✗ fail "<resolved message>"`. Mirrors the `flow_failed` red-marker pattern from quick 260502-onc.
  - The pre-existing block-scope rendering (header on `branch` event, indented children, footer on `step_complete`) from quick 260503-rhy is reused without change for the if_cond's outer scope.

### Interaction with existing primitives

- **D4.2-17:** Interpolation (`${ctx.expr}`) extends to fail messages (D4.2-06). It does NOT extend to `result(value={...})` value expressions because those are already first-class Starlark expressions captured as lambdas — there's no string-typed surface to desugar.

- **D4.2-18:** Step kwargs and other interpolation surfaces continue to work unchanged. The new typed state schema (D4.2-13) means interpolation lambdas referencing `ctx.X` after an expression-mode if_cond can be type-checked with the post-if-cond type for `X`. This is forward leverage; no Phase 04.2 plan task is required to exploit it.

- **D4.2-19:** `for_each_parallel` and `call_flow` are unchanged. Nesting an expression-mode `if_cond` inside `for_each_parallel.steps` works mechanically (each iteration binds its own `ctx[output_alias]` in the per-item state); branch-equality validation is per-flow-static and does not depend on iteration.

### Claude's Discretion

- Exact ordering of validation passes within `finalize.go` (only constraint: `validateIfCondExpressionShape` runs AFTER `validateLambdaCtxAccesses`).
- Exact surface of `TypeInfo` constructors and helper APIs in `pkg/parser/state_schema.go` (the hierarchy in D4.2-14 is canonical; the Go API around it is implementation detail).
- The `result_bound` event's exact attribute set and renderer formatting beyond what D4.2-15 / D4.2-16 fixes.
- Test-corpus organization for branch-equality fixtures (where in `pkg/parser/state_schema_test.go` vs a new `result_test.go` they live).
- Exact wording of parse-time error messages (subject to the standard `<file>:<line>:<col> [flow > step]: <msg>` format from D4-04).
- Whether the `Keys`/`Values`/`Types` triple on `dag.Result` becomes a single `[]ResultField` slice or stays as parallel maps — internal shape only, not user-visible.
- Whether `dag.Fail` and `dag.Result` JSON-marshal with custom shapes (as Phase 1 nodes do) or accept the default — golden-test convention applies.

<specifics>
## Specific Ideas

- **Reuse `fail` as a single name across both predeclared scopes.** User's deliberate UX call: "Reuse `fail` (top-level + lambda-time)" over distinct `error`. One vocabulary word; documentation must call out that `fail()` at top-level emits a parse-time-visible node, while `fail()` inside a lambda body raises at runtime. Same observable surface (NonRetryableErr with the message at the .star callsite).
- **Static keys, expression values for `result(value={...})`.** User explicitly chose this shape over (a) fully-literal dicts and (b) kwargs-as-keys. The reasoning: keys must be statically determinable for the parser to verify structural equality across branches; values must be expressions so consultants can propagate runtime data. The parser captures each value as a synthesized per-key lambda, type-infers each.
- **Permissive type inference, defer-to-runtime for opaque expressions.** User's call. Strict equality applies where both sides are inferable; opaque values pass without complaint. Keeps the strict-equality posture for the structural shape (keys) while pragmatically accepting limits on value-expression analysis.
- **Asymmetric branches via `fail()`.** User asked specifically: "else can omit only IF AND ONLY IF the other branch ends in error" — answered by D4.2-09 case 3 (at least one branch must end in `result()`; both-fail rejected with hint). The conventional shape becomes `if_cond(output_alias="X", then=[...result(...)], else_=[fail("msg")])` — both branches present, one binds, the other terminates.

</specifics>

<deferred>
## Deferred Ideas

- **Subtype / LUB rules across branches.** Out of scope for v1. Phase trigger paragraph explicitly rejects them. Explicit casts (`float(x)`, `int(x)`, `str(x)`) are the widening mechanism.
- **Optional fields in result dicts** (some keys present in one branch, absent in another → key-level optional typing). Out of scope for v1; D4.2-09 enforces strict key-set equality. Could land as a separate phase if Phase 6 surfaces the need.
- **Cross-phase state typing exploitation.** The new typed state schema (D4.2-13) opens the door to type-checking `ctx.X` references in step kwargs, interpolation lambdas, and other primitives — but Phase 04.2 only consumes it for result-value inference. Broader exploitation belongs in v1.x or v2 once a customer surface needs it.
- **Pattern matching / `match` primitive.** Adjacent design space (multi-way value-producing branching), explicitly out of scope. v2.
- **`result()` accepting a literal dict (no per-key lambdas) as a fast path.** Could short-circuit lambda capture for fully-static branches. Not enough win in v1; revisit if profiling shows a hotspot.
- **`result_bound` event semantics during replay.** Today's renderer is local-stdout-only; if Phase 6 surfaces a need to replay slog events from history, the alias-bound event might need to ride the history. Out of scope here.
