## Pipeline architecture

The 9-step pipeline is locked in handler.go's doc comment:

1. **defer log emit + panic recovery** — `defer rec.emit(deps.Logger)` + `recover()` panic gate (Pitfall 4). Panics inside lambda/bridge/credential code are caught and mapped to 500 + error_class=lambda_panic. The log line ALWAYS emits, even on panic.
2. **MaxBytesReader cap** — `r.Body = http.MaxBytesReader(w, r.Body, maxBodyBytes)` (D-7.1-12 + Pitfall 9).
3. **io.ReadAll → raw body bytes** — Pitfall 2: HMAC validates against the WIRE bytes, never against re-encoded JSON.
4. **JIT credential resolve** — `deps.CredentialHandler.Resolve` only when `secretCredID != ""`. Unsigned mounts skip entirely.
5. **validateHMAC** — Plan 01's primitive (uses `hmac.Equal`, NOT `bytes.Equal` — verified by grep gate).
6. **Content-Type check** — non-JSON CT → 415 via `writeUnsupportedMediaTypeResponse(w)` (NOT 400 — bug fixed during planning, regression-pinned by `TestHandler_NonJSONContentType`).
7. **json.Unmarshal** — body → `map[string]any`. 400 + `bad_request` + `detail=json_parse_failed` on parse failure (no payload echo in detail — verified by `TestHandler_MalformedJSON`).
8. **Per-trigger fan-out** — for each matching trigger (after ShouldDispatch filter): eval MapLambda → input map; eval IdempotencyLambda → user key string; compose WorkflowID; ExecuteWorkflow with the locked StartWorkflowOptions; classify outcome.
9. **Pick worst status** — order: dispatch_failed > internal > ok > duplicate > event_filtered. Write the matching JSON envelope.

## req struct architectural fix

The plan's `<action>` block sketched a `reqMap := map[string]any{"payload": payload, "headers": flattenHeaders(r.Header)}` shape passed through `bridge.CallLambda`. This was discovered to be incorrect during execution: `bridge.ToStarlarkStruct` (which `bridge.CallLambda` invokes) recursively converts nested maps to `*starlarkstruct.Struct`, which supports only `Attr()` (dot access). Hyphenated names like `X-Github-Delivery` cannot be valid Starlark attribute names, so the test pattern `req.headers["X-Github-Delivery"]` (index access on the headers value) does NOT work when headers is a Struct.

**Fix:** Custom `buildReqStruct(payload, headers)` returns a `*starlarkstruct.Struct` with two fields:
- `payload` → `*starlarkstruct.Struct` from `bridge.ToStarlarkStruct(payload)` (recursive, supports `req.payload.repository.full_name`).
- `headers` → frozen `*starlark.Dict` (supports `req.headers["X-..."]`).

Then `callLambda(ctx, lam, reqStruct)` invokes `starlark.Call` directly on a fresh thread with the step budget pulled from `bridge.DefaultMaxExecutionSteps` — bypassing `bridge.CallLambda` so the custom struct survives the call boundary.

**1. [Rule 1 - Bug] req struct architecture: bridge.CallLambda's recursive ToStarlarkStruct breaks index access on hyphenated header keys**
- **Found during:** Task 1 (initial test run after wiring the plan's sketched code)

Step budget reused from `bridge.DefaultMaxExecutionSteps`.
