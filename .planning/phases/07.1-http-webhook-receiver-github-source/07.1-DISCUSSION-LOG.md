## Source Factory Namespace

### Q1: Where should the generic HTTP webhook source factory live?

| Option | Description | Selected |
|--------|-------------|----------|
| Extend pkg/extension/builtin/http | Adds http.webhook(...) alongside existing http.endpoint outbound; one package, both directions | ✓ |
| New built-in pkg/extension/builtin/inbound | Dedicated inbound.webhook(...); cleaner directional split, more namespace surface | |
| Reuse example webhook extension | Add receiver to example webhook ext; mixes outbound+inbound, demotes inbound to user-land | |
| New built-in pkg/extension/builtin/triggers | Matches original ROADMAP wording but D-07-08 vetoed triggers.* namespace | |

**User's choice:** Extend `pkg/extension/builtin/http` with `http.webhook(...)` alongside existing `http.endpoint(...)`.
**Notes:** Asymmetric naming accepted (endpoint=outbound, webhook=inbound) for a single coherent HTTP package.

### Q2: How configurable should http.webhook's signature scheme be?

| Option | Description | Selected |
|--------|-------------|----------|
| Hardcode HMAC-SHA256, configurable header | Algo locked, header name parameterized for cross-provider use | |
| Fully configurable (algo + header) | signature_algo ∈ {sha256, sha1, sha512} + arbitrary signature_header | ✓ |
| No signature support | Generic webhook never validates; force users to write custom extension | |

**User's choice:** Fully configurable.
**Notes:** Future-proofs for sha512 webhooks; supports cross-provider integrations (Stripe, GitLab, etc.). GitHub's HMAC-SHA256 + X-Hub-Signature-256 stays locked separately for `github.webhook` (TRIG-09).

## Multi-Trigger Routing

### Q1: Two GitHub webhook triggers with different events filters and flow targets — how should routing handle them?

| Option | Description | Selected |
|--------|-------------|----------|
| Single shared handler, fan out by events | One mount; on delivery, dispatch to ALL matching triggers; matches GitHub's "one URL, many subscribers" reality | ✓ |
| Reject duplicate source-kind at parse-finalize | Only one github.webhook trigger per .star corpus; consultants do their own routing inside one flow | |
| Separate path per trigger | Auto-generate /webhook/github/{flow_name}; each trigger owns its URL but breaks GitHub's repo-settings convention | |

**User's choice:** Single shared handler, fan out by events.
**Notes:** Each matching trigger fires its own workflow; idempotency keys disambiguate. Empty `events=[]` matches all events.

### Q2: Two http.webhook triggers binding the same (path, method) — what happens?

| Option | Description | Selected |
|--------|-------------|----------|
| Fan out (consistent with github.webhook) | Both flows fire on every POST /x; idempotency keys disambiguate workflows | ✓ |
| Hard error at parse-finalize | Conflict on (path, method) is a parse error; forces user to disambiguate | |
| Last-write-wins with warning | Boot picks one in file-sort order, warns about others; silent dropped triggers footgun | |

**User's choice:** Fan out — consistent with github.webhook rule.
**Notes:** Universalizes the multi-subscriber pattern across all HTTP-shaped sources.

## Server Lifecycle

### Q1: Boot order — when skytime server starts?

| Option | Description | Selected |
|--------|-------------|----------|
| Worker first, then listener | Connect to Temporal → register workflows → mount listener last; fail-fast on bad config | ✓ |
| Listener first, then worker | Bind :8080 immediately, return 503 until worker ready; nicer for k8s liveness but bound port when broken | |
| Parallel — both come up concurrently | Lowest-latency boot but harder to reason about | |

**User's choice:** Worker first, then listener.
**Notes:** k8s readinessProbe via TCP-connect to --addr is honest: port open ↔ everything ready.

### Q2: Shutdown — on SIGTERM, listener+worker drain order?

| Option | Description | Selected |
|--------|-------------|----------|
| Listener stops accepting, worker drains, both exit | http.Server.Shutdown() refuses new requests immediately; in-flight HTTP finishes; worker drains; both exit | ✓ |
| Listener keeps accepting until budget consumed | Accepts requests until --drain-timeout elapsed; better for unreliable sources but wasteful in k8s | |
| Hard kill listener, drain worker only | Fast close; in-flight HTTP get TCP RST; sources retry but ugly errors mid-drain | |

**User's choice:** Listener-first shutdown.
**Notes:** Matches Phase 7's drain story; clean k8s rolling-deploy semantics.

## Failure Paths + Observability

### Q1: HTTP status code mapping?

| Option | Description | Selected |
|--------|-------------|----------|
| Strawman as proposed | 401 sig mismatch / 400 bad body / 500 lambda panic / 502 dispatch fail / 200 OK on duplicate-skipped + event-filtered + success | ✓ |
| All non-200 errors return 500 | Simple, opaque; fights GitHub webhook delivery view's value | |
| Custom — tweak some | Various provider-specific deviations | |

**User's choice:** Strawman as proposed.
**Notes:** GitHub's webhook delivery view distinguishes 401 from 500 meaningfully; keeping the granularity helps operators debug.

### Q2: What gets logged per request?

| Option | Description | Selected |
|--------|-------------|----------|
| Structured per-request log line | One line per request; method, path, status, duration, source_kind, flow, workflow_id, error_class; redacted | ✓ |
| Errors only | Successful 200s silent; spotting problems easier but no traffic visibility | |
| Verbose (req body+headers, redacted) | Full per-request dump; opt-in via --verbose | |

**User's choice:** Structured per-request log line.
**Notes:** charm-log default for humans; --json-log for structured ingestion. Never logs body, never logs secret, never logs auth headers — only header NAMES if useful. error_class taxonomy: `signature_mismatch | bad_request | lambda_panic | dispatch_failed | event_filtered | duplicate_skipped | ok`.
