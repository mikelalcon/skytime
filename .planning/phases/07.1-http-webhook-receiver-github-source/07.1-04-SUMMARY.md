### TRIG-06 partially satisfied: handler mount per HTTP-shaped trigger

`receiver.Mount(mux *http.ServeMux, w *worker.Worker, deps Deps)` is the boot-time entry point. It walks the worker's frozen TriggerRegistry, type-asserts each trigger's Source against `receiver.HTTPMounter` (Plan 01), groups matching triggers by `mountKey{kind, path, method}`, and registers one HandleFunc per PATH that internally method-dispatches.

```text
worker.Triggers().All() (sorted by Source.Kind, FlowName, Pos.String)
   ↓
groupTriggers — map[mountKey][]*dag.Trigger (HTTP-shaped only; cron skipped)
   ↓
Mount — collapse by path, register dispatchByMethod handler
   ↓
mux: /webhook/github → POST: makeHandler(github,POST) | other: 405
     /hooks/x       → POST: makeHandler(http,POST,/x) |
                      GET:  makeHandler(http,GET,/x)  | other: 405
```

Full satisfaction of TRIG-06 lands in Plan 04b once `makeHandler`'s 501 stub is replaced with the real per-request pipeline.

## Decisions Made

- **Path-level method dispatch over per-method mux registration.** The plan reads "different methods on the same path produce TWO mounts on the same path" but stdlib `http.ServeMux` panics on duplicate path registration (one handler per pattern). The implementation coalesces all (kind, path, method) groups sharing a path into a single HandleFunc that method-dispatches internally via `dispatchByMethod`. Functionally equivalent — POST `/x` and GET `/x` both reach their respective handlers; PUT `/x` returns 405. Documented in Mount's doc comment + tested explicitly by `TestMount_DifferentMethodsSamePath`.

- **groupTriggers as a separate unexported helper, not a closure.** The plan's `TestMount_DoesNotReSort` description suggests "verified by intercepting the slice via a test seam OR by indirect observation that no per-group sort happens". Direct observation via `groupTriggers(...)` is far cleaner and faster than threading the assertion through Mount's mux side-effect. The seam is testing-only — Mount's only public surface remains `func Mount(mux, w, deps)`.

- **Methodology: discard logger in tests, not the real charm-log handler.** Tests don't exercise the per-request log emission (Plan 04b owns that); using `slog.New(slog.NewTextHandler(io.Discard, nil))` keeps test failure messages clean. Plan 04b will swap in the production charm-log + JSON routing for handler-pipeline assertions.

- **Test-only constructor returns `extension.TriggerSource`, not `*httpWebhookSource`.** The interface return type forces test code to either type-assert (which exercises the actual interface plumbing) or treat the value as opaque (which is the intended consumption pattern for downstream `pkg/extension/receiver` code). Mirrors `skygh.NewGithubWebhookSourceForTest` exactly.
