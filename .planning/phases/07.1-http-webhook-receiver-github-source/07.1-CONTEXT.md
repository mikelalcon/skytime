**Gathered:** 2026-05-09

<domain>
## Phase Boundary

Phase 7.1 mounts the actual HTTP receiver on top of Phase 7's plumbing. Five concrete deliverables:

1. **`pkg/extension/builtin/http` extended with `http.webhook(...)`** — the generic inbound HTTP webhook source factory, alongside the existing outbound `http.endpoint(...)`. Asymmetric naming, single coherent package.
2. **`github.webhook(events=, secret_credential=)` source factory** — added to the existing `examples/http-github-webhook/extensions/github/` extension (per Phase 7 D-07-08, source factories live under their owning extension's namespace).
3. **HTTP receiver inside `skytime server`** — listener mounted last in boot order, drained first in shutdown. Each (source_kind, path) tuple maps to ONE handler; fan-out routing dispatches a delivery to ALL matching `trigger(...)` subscribers (each starts its own workflow).
4. **Signature validation + idempotency dispatch pipeline** — validate → map lambda → idempotency_key lambda → `client.ExecuteWorkflow` with `WorkflowIDReusePolicy=REJECT_DUPLICATE`. GitHub uses HMAC-SHA256 against `X-Hub-Signature-256` (TRIG-09 locked). Generic `http.webhook` is fully configurable (`signature_algo` ∈ {sha256, sha1, sha512}, `signature_header` arbitrary).
5. **Crash-recovery demo + walkthrough docs** — new `webhook_demo.star` (comment → sleep 30s → label), quickstart in example README, long-form in `docs/walkthroughs/github-webhook.md`.

**Out of scope (other phases):** Cron triggers (7.2), dashboard + manual trigger UI (7.3), `cli.WithCredfile` lift + extbin consolidation (7.4), production auth integration docs (7.5). The 4 signal-loop tests skipped in Phase 7's `pkg/cli/server_test.go` get unskipped here via the `worker.WithSDKFactory` Option seam.

<key_constraints>
## Load-Bearing Constraints (do not violate)

- **CREDENTIALS NEVER SERIALIZED.** Phase 7 D-07-09 + D-07-10 already locked: `dag.Trigger.Source` JSON only ever contains the credential **ID** string, never the resolved `extension.Secret`. The receiver resolves the secret JIT via `CredentialHandler.Resolve(ctx, id)` ONCE per request inside the request handler — and even there, the resolved Secret stays wrapped in `extension.Secret`'s redacting type. The HMAC comparison runs against the raw byte payload + the unwrapped Secret.Bytes(); the Secret is never logged, never put in the log line's structured fields, and never appears in any error message returned to the caller. Phase 7's credential-redaction firewall (D-07-10 / `tests/firewall_credential_redaction_test.go`) extends to cover this phase's new files.
- **HMAC constant-time comparison.** Use `hmac.Equal()` (NOT `bytes.Equal`) for signature validation to defeat timing attacks. Standard Go pattern; the firewall test should also assert `hmac.Equal` is used (no `bytes.Equal(sig, expected)` slips through).
- **No I/O at parse time.** Source factories register module attributes returning a `TriggerSource` value; they perform no network or filesystem I/O at parse time. HTTP listener mounts at boot time (post-parse), not at parse time.
- **Stdlib HTTP only.** `net/http` for the receiver. No router framework (chi, gorilla/mux). Phase 7.3's dashboard already locked stdlib-only for HTML; the receiver shares the rule for one cohesive HTTP story.
- **Determinism in handler dispatch order.** When multiple triggers match a single delivery (fan-out), iteration order is sorted by `(flow_name, trigger_position)` so logs/tests are stable. Failures in one trigger's `ExecuteWorkflow` do NOT block sibling triggers.
- **Listener stops accepting BEFORE worker drain.** SIGTERM contract: `http.Server.Shutdown(ctx)` runs first; new requests refused immediately; in-flight HTTP requests finish; then worker drains in-flight workflows up to `--drain-timeout`. Second signal at any stage forces `os.Exit(1)` (consistent with Phase 7 D-07-15).

</key_constraints>

<decisions>
## Implementation Decisions

### Source factory namespaces & shapes

- **D-7.1-01: Generic HTTP webhook lives at `http.webhook(...)`.** Extends `pkg/extension/builtin/http` alongside the existing `http.endpoint(...)`. Asymmetric naming (endpoint=outbound, webhook=inbound) but one coherent package with full HTTP both directions. Same Go package, same Starlark namespace `http.*`. `New()` returns the same `Extension`; `Initialize()` adds `webhook` as a second module attribute.
- **D-7.1-02: GitHub webhook lives at `github.webhook(events=, secret_credential=)`.** Already locked in Phase 7 D-07-08. Added to `examples/http-github-webhook/extensions/github/`. The factory is a module attribute returning a `*githubWebhookSource` value satisfying `extension.TriggerSource`.
- **D-7.1-03: `http.webhook` signature scheme is fully configurable.** Kwargs: `path: str` (required), `method: str` (required, e.g. "POST"), `secret_credential: str|None` (optional — `None` mounts unsigned), `signature_algo: str` (optional, default `"sha256"`, allowed: `"sha256"|"sha1"|"sha512"`), `signature_header: str` (optional, default `"X-Signature"`). Algo is rejected at parse time if not in the allowed set. Future-proofs for Stripe, GitLab, generic provider patterns.
- **D-7.1-04: GitHub webhook signature is locked.** HMAC-SHA256 against `X-Hub-Signature-256` (TRIG-09; not user-configurable). Source kwargs: `events: list[str]` (optional, defaults to `[]` meaning "all events"), `secret_credential: str|None` (optional; when omitted, no signature validation — useful for local `gh webhook forward` testing without real secrets).
- **D-7.1-05: `req.payload` and `req.headers` are the only `req` fields HTTP sources expose.** Each `TriggerSource.ReqSchema()` returns `["payload", "headers"]` for `http.webhook` and `github.webhook`. `req.payload` is the JSON-parsed body as a `*starlarkstruct.Struct` (recursive Go-map → Struct conversion already shipped in `pkg/bridge`). `req.headers` is a flat `dict[str, str]` (case-preserving key as received). For non-JSON bodies (form-encoded, raw text), `req.payload` is `None` and the lambda must use `req.headers["Content-Type"]` to dispatch — Phase 7.1 ships JSON-first; broader content-type handling deferred.

### HTTP routing

- **D-7.1-06: Fan-out routing is the universal rule.** Each (source_kind, path, method) tuple maps to exactly ONE HTTP handler mount. When the boot registry walks triggers, it groups them by mount key; the resulting handler dispatches each delivery to ALL matching triggers in deterministic sorted order. Multiple `trigger(...)` calls subscribing to the same mount each fire their own independent workflow — N triggers → 0..N workflows per delivery. Idempotency keys (D-7.1-08) keep them disambiguated. Matches GitHub's reality: one webhook URL, many subscribers.
- **D-7.1-07: GitHub event filtering happens inside the shared handler.** GitHub webhooks all hit `POST /webhook/github`. The handler reads the `X-GitHub-Event` header and dispatches to triggers whose `events=` list contains the event (case-sensitive match against GitHub's documented event names). An empty `events=[]` list means "match all events". Triggers with non-matching events are silently skipped (no log spam — only one structured log line per delivery; see D-7.1-14). If NO triggers match, return 200 OK with body `{"status":"event filtered"}`.
- **D-7.1-08: Idempotency key includes per-trigger identity.** The user-provided `idempotency_key=lambda req: ...` returns a STRING that becomes part of the Temporal `WorkflowID`. The full WorkflowID is composed: `{flow_name}/{trigger_pos_hash}/{user_key}` where `trigger_pos_hash` is a stable short hash of the trigger's `<file>:<line>:<col>` position. Two triggers fanning out from the same delivery with the same user-key produce DIFFERENT WorkflowIDs (won't collide on `REJECT_DUPLICATE`); but two redeliveries of the same webhook (same `X-GitHub-Delivery`) for the same trigger DO collide (correct dedup behavior). Document the composition in `pkg/bridge/doc.go` and surface in Tier-3 test scaffolding.
- **D-7.1-09: Path conflicts are not possible by definition.** Since fan-out collapses (source_kind, path, method) to one mount, two triggers binding the same tuple subscribe to the same mount instead of conflicting. Different tuples mount different paths — also no conflict. The only error worth raising at parse-finalize is method mismatch on the same path: e.g., `http.webhook(path="/x", method="POST")` and `http.webhook(path="/x", method="GET")` — these get different mounts (one per method), no conflict. Document this in the receiver code; no error path needed.

### Server lifecycle

- **D-7.1-10: Boot order is worker-first.** Sequence inside `skytime server`: (1) parse rootdir → flow + trigger registries; (2) `connectClient(cfg)` → Temporal client; (3) register workflows + activities with the SDK worker; (4) start the worker (poll task queue); (5) NOW mount HTTP listener on `--addr`. Steps 2-3 fail-fast on bad config — listener never binds if Temporal unreachable. K8s readinessProbe is a TCP connect to `--addr` and is honest: port open ↔ everything ready. Initial-connect retry is Claude's discretion per Phase 7 D-07-19; recommend bounded exponential backoff (10s total budget by default, configurable later) but the planner can defer if scope pressure.
- **D-7.1-11: Shutdown order is listener-first.** On SIGTERM/SIGINT: (1) call `http.Server.Shutdown(drainCtx)` with `drainCtx` that has `--drain-timeout` deadline; this immediately refuses new requests but lets in-flight HTTP requests finish (which means in-flight `ExecuteWorkflow` dispatch calls finish — the workflow itself is now durable on the Temporal server). (2) After listener.Shutdown returns (or its ctx expires), call `worker.Stop()` which begins the worker drain — Temporal SDK semantics: stop polling new tasks, finish in-flight activity executions. (3) Wait for worker drain or `--drain-timeout`, whichever first. (4) Exit 0 if clean drain, exit 1 + timeout-message if drain budget consumed (consistent with Phase 7 D-07-16). Second signal at any stage forces `os.Exit(1)` immediately (Phase 7 D-07-15).
- **D-7.1-12: Listener uses `net/http.Server` with reasonable defaults.** `ReadHeaderTimeout: 10s`, `ReadTimeout: 30s`, `WriteTimeout: 30s`, `IdleTimeout: 60s`, `MaxHeaderBytes: 64*1024`. Body size limit per request: 25MB (matches GitHub's webhook payload max). Limits enforced via `http.MaxBytesReader`. These are Claude's discretion — adjust during planning if a specific source needs larger payloads, but defaults match the 95% case.
- **D-7.1-13: Phase 7's 4 skipped signal-loop tests get unskipped.** `pkg/cli/server_test.go` has `TestServerCmd_DrainOnSIGTERM`, `TestServerCmd_DrainTimeoutExpiry`, `TestServerCmd_SecondSignalForceExit` (and a fourth) marked `t.Skip("TODO(phase-7.1)")`. Phase 7.1 introduces the `worker.WithSDKFactory` Option (or equivalent test seam) that lets `pkg/cli` black-box tests substitute a fake SDK worker, dropping the skips. The receiver-side tests (signature, idempotency, fan-out, dispatch) live in `pkg/extension/receiver` (or wherever the dispatcher lands) with their own httptest fixtures.

### Failure paths + observability

- **D-7.1-14: HTTP status code mapping is locked.**
  - **200 OK on success** — body: `{"workflow_id":"<composed_id>"}` (single trigger) or `{"workflow_ids":["a","b"]}` (fan-out). Returns ONLY after all dispatched workflows have been started by Temporal — synchronous dispatch confirmation, NOT synchronous workflow completion (webhook semantics: receiver confirms enqueue, not completion).
  - **200 OK on REJECT_DUPLICATE collision** — body: `{"status":"duplicate; skipped","workflow_id":"<existing_id>"}`. Distinct from a brand-new success but same status code so source providers (GitHub) don't retry.
  - **200 OK on event-filter no-match** — body: `{"status":"event filtered"}` (D-7.1-07).
  - **400 Bad Request** — malformed body (JSON parse error when `Content-Type: application/json`). Body: `{"error":"bad_request","detail":"<safe_message>"}`. Never echo the payload.
  - **401 Unauthorized** — signature mismatch OR missing signature header when `secret_credential` is configured. Body: `{"error":"unauthorized"}`. NO detail (don't leak whether the secret is wrong vs missing).
  - **500 Internal Server Error** — `map` lambda panic OR `idempotency_key` lambda panic. Body: `{"error":"internal","detail":"<error_class>"}`. Detail is the error class only (e.g., "starlark eval error") — never the user's payload, never the lambda source, never the resolved Secret.
  - **502 Bad Gateway** — `client.ExecuteWorkflow` returned a network/connection error (Temporal unreachable from receiver). Body: `{"error":"upstream","detail":"temporal_unavailable"}`. Source providers WILL retry on 502, which is correct.
- **D-7.1-15: Structured per-request log line.** One log line per request, emitted after the response is written. Fields: `method`, `path`, `status`, `duration_ms`, `source_kind` (e.g., `"github.webhook"`), `event` (e.g., `"issues"` for GitHub; absent for non-GitHub), `flows_dispatched` (list of flow names that fired, possibly empty), `workflow_ids` (list, possibly empty), `error_class` (string, present iff status ≥ 400). charm-log default: `[skytime] POST /webhook/github 200 12ms source=github.webhook event=issues flows=[issue_triage] workflow_ids=[issue_triage/abc/2026-...]`. `--json-log`: structured JSON record with same fields. NO request body, NO response body, NO header values (only header NAMES if useful), NO secrets. The `error_class` is a stable taxonomy: `signature_mismatch | bad_request | lambda_panic | dispatch_failed | event_filtered | duplicate_skipped | ok`.

### Crash-recovery demo

- **D-7.1-16: New `examples/http-github-webhook/webhook_demo.star`.** Single-trigger flow: `trigger(flow="webhook_demo", source=github.webhook(events=["issues"], secret_credential="github_webhook_secret"), map=lambda req: {"repo": req.payload.repository.full_name, "issue_number": req.payload.issue.number}, idempotency_key=lambda req: req.headers["X-GitHub-Delivery"], credential="github_webhook_secret")`. The `flow("webhook_demo", ...)` body: (1) add comment "received, processing..." via `gh.add_comment`; (2) `workflow.Sleep(30s)` (durable replay-safe sleep); (3) add label "processed" via `gh.add_label`. The reader: webhook delivery → comment appears → kill server with Ctrl-C → restart server → label appears 30s later (counted from original delivery, durable across the kill). Demonstrates Temporal's headline durability story.
- **D-7.1-17: README walkthrough is split across two locations.** Quickstart section in `examples/http-github-webhook/README.md` titled `## GitHub webhook walkthrough (5 minutes)` covering: install gh CLI, run `temporal server start-dev`, run `extbin server`, run `gh webhook forward`, observe comment + label. Detailed walkthrough at `docs/walkthroughs/github-webhook.md` titled `# GitHub webhook walkthrough` covering: prerequisites, secret setup in credfile, full step-by-step including the kill-server crash-recovery demonstration, troubleshooting (signature 401s, event filter mismatches), interpreting the structured log line. Cross-link both ways.

### Claude's Discretion

The planner has flexibility on these (defaults captured during discussion; deviate only if a stronger reason emerges during planning):

- **Receiver code location.** Strawman: `pkg/extension/receiver/` for the HTTP dispatcher (signature validation + lambda eval + dispatch). Alternative: `pkg/server/receiver/` if a top-level `pkg/server` package emerges. Pick consistent with where the listener bind code lives.
- **Receiver Initialize() shape.** When `boot.go` collects triggers, it needs to ask each `TriggerSource` "what HTTP route do you mount?". Strawman: extend `TriggerSource` with an `HTTPRoute() (path, method string, ok bool)` method (HTTP-shaped sources return ok=true; cron sources will return false in 7.2). Alternative: type-assert against an `HTTPMounter` sub-interface in the receiver package. Pick whichever keeps the `extension.TriggerSource` core seal cleaner.
- **Connection retry on initial Temporal connect.** Phase 7 D-07-19 punted this. Strawman for 7.1: bounded exponential backoff, 10s budget, 1s/2s/4s/... Alternative: rely entirely on k8s readinessProbe to retry the pod. Implement-and-test if it fits scope; defer otherwise.
- **`gh webhook forward` flag specifics in walkthrough.** Strawman: `gh webhook forward --repo=user/test-repo --events=issues --url=http://localhost:8080/webhook/github --secret=$GITHUB_WEBHOOK_SECRET`. Verify the exact flag names against current `gh` CLI documentation during planning (the gh webhook subcommand evolved through gh 2.x).
- **Worker drain + listener drain race.** In D-7.1-11 the listener.Shutdown returns BEFORE worker.Stop() is called. But what if `--drain-timeout` is so short the listener.Shutdown itself can't complete? Strawman: `drainCtx` is shared between listener and worker; if it expires during listener.Shutdown, force-kill listener and exit 1 with the timeout message. Edge case; planner finalizes.
- **Body decoder negotiation.** Strawman for non-JSON content-types: if `Content-Type` is `application/json` → parse to `*starlarkstruct.Struct`; else → set `req.payload = None` and let the lambda handle via `req.headers["Content-Type"]`. Alternative: hardcode JSON-only (return 415 Unsupported Media Type otherwise). 415 is cleaner; pick during planning based on which the demo flow needs (GitHub always sends JSON when configured for it).

## Specific Ideas

- **WorkflowID composition format (D-7.1-08).** `{flow_name}/{trigger_pos_hash}/{user_key}` where `trigger_pos_hash = base64url(sha256(trigger.Position.String()))[:8]`. Concrete example: a trigger at `webhook_demo.star:5:1` firing flow `webhook_demo` with `idempotency_key=lambda req: req.headers["X-GitHub-Delivery"]` and an X-GitHub-Delivery of `72c89c70-...` produces WorkflowID `webhook_demo/aGcRb2Q8/72c89c70-...`. Stable across boots, opaque to the user.
- **Test corpus for receiver dispatch.** httptest fixtures under (likely) `pkg/extension/receiver/testdata/`:
  - `github_valid_signature.golden` — sample GitHub `issues` payload + matching X-Hub-Signature-256 against test secret. 200 OK + workflow_id.
  - `github_bad_signature.golden` — same payload, wrong signature. 401.
  - `github_unconfigured_event.golden` — `pull_request` payload against trigger configured for `events=["issues"]`. 200 OK + `event filtered`.
  - `github_redelivery.golden` — same X-GitHub-Delivery posted twice. First → workflow_id; second → 200 OK + `duplicate; skipped`.
  - `http_unsigned_post.golden` — `http.webhook(secret_credential=None)` mount; bare POST → 200 OK.
  - `http_signed_sha512.golden` — `http.webhook(signature_algo="sha512", signature_header="X-Custom-Sig")` mount; matching sha512 sig → 200 OK.
  - `fan_out_two_flows.golden` — two triggers same mount; one delivery → 200 OK + `workflow_ids: [a, b]`.
- **Demo `webhook_demo.star` rough shape (D-7.1-16).**
  ```python
  trigger(
      flow="webhook_demo",
      source=github.webhook(
          events=["issues"],
          secret_credential="github_webhook_secret",
      ),
      map=lambda req: {
          "repo": req.payload.repository.full_name,
          "issue_number": req.payload.issue.number,
      },
      idempotency_key=lambda req: req.headers["X-GitHub-Delivery"],
      credential="github_webhook_secret",
  )

  flow(
      name="webhook_demo",
      steps=[
          step(action=gh.add_comment(
              owner=ctx.repo.split("/")[0],
              repo=ctx.repo.split("/")[1],
              number=ctx.issue_number,
              body="received, processing...",
          )),
          step(sleep="30s"),
          step(action=gh.add_label(
              owner=ctx.repo.split("/")[0],
              repo=ctx.repo.split("/")[1],
              number=ctx.issue_number,
              label="processed",
          )),
      ],
  )
  ```
  Reader runs `gh webhook forward` → opens an issue in their test repo → comment appears immediately → kills server with Ctrl-C → restarts → ~30s after original delivery, label appears. Demonstrates durability.
- **Per-request log line example.** Charm-log default format: `[skytime] POST /webhook/github 200 12ms source=github.webhook event=issues flows=[webhook_demo] workflow_ids=[webhook_demo/aGcRb2Q8/72c89c70]`. JSON: `{"time":"...","level":"INFO","msg":"webhook delivery","method":"POST","path":"/webhook/github","status":200,"duration_ms":12,"source_kind":"github.webhook","event":"issues","flows_dispatched":["webhook_demo"],"workflow_ids":["webhook_demo/aGcRb2Q8/72c89c70"],"error_class":"ok"}`.
- **`gh webhook forward` exact invocation (verify against gh CLI version during planning).** `gh webhook forward --repo=<your-username>/test-repo --events=issues --url=http://localhost:8080/webhook/github --secret="$GITHUB_WEBHOOK_SECRET"` — flags listed left-to-right are required; `--secret` is what gh uses to sign forwarded payloads, must match the credfile's `github_webhook_secret` entry.
