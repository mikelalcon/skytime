## User Constraints (from CONTEXT.md)

### Locked Decisions (verbatim from `<decisions>` block of 07.2-CONTEXT.md)

- **D-7.2-01: `core.cron(...)` is the cron source factory.** SUPERSEDES the roadmap's `triggers.cron(...)`. `core.*` is the reserved namespace for future Skytime-native primitives (`core.signal`, `core.queue`, etc.). Webhook sources stay in their owning extension's namespace (`http.webhook`, `github.webhook`); the asymmetry is intentional.
- **D-7.2-02: `core.cron` lives in `pkg/extension/builtin/core/`** (Claude's discretion on exact path). Built-in extension shipped from the library root; registered via `cli.WithExtensions(core.New(), ...)` by default in `cmd/skytime/main.go` and `examples/http-github-webhook/cmd/extbin/main.go`.
- **D-7.2-03: `core.cron(...)` kwargs.** `schedule: str` (required, 5-field POSIX), `timezone: str|None` (IANA, default UTC), `overlap: str|None` (`"skip"|"allow"|"buffer_one"|"cancel_other"`, default `"skip"`), `catchup_window: duration|None` (default unset → Temporal default 1 minute). All validated at parse time via `*dag.ParseError`.
- **D-7.2-04: Schedule ID format: `skytime/{flow_name}/{trigger_pos_hash}`** where `trigger_pos_hash = base64url(sha256(trigger.Pos.String()))[:8]` — same hash function `pkg/extension/receiver/workflow_id.go::posHash` uses. Example: `skytime/weekly_digest/aGcRb2Q8`.
- **D-7.2-05: `skytime/` ID prefix is the isolation mechanism.** Reconcile lists ALL schedules, filters by prefix, only touches matching ones. User-created schedules NEVER deleted.
- **D-7.2-06: Drift detection → `ScheduleHandle.Update(...)` in place.** Preserves history and in-flight workflows. Delete+recreate REJECTED.
- **D-7.2-07: Orphan deletion is mandatory when `--cron-reconcile` is set.** No `preserve` half-measure. Removing a `core.cron(...)` trigger deletes the corresponding Schedule.
- **D-7.2-08: `skytime server --cron-reconcile` is a boolean opt-in flag.** Default OFF. Replaces the roadmap's `--reconcile=strict|preserve|dry-run` enum.
- **D-7.2-09: `skytime cron-plan` is a separate subcommand** for dry-run. One-shot; reads `--rootdir`; lists Skytime-managed Schedules; prints diff; exits 0. NO cluster mutations.
- **D-7.2-10: Single-flag opt-in.** ONE replica gets `--cron-reconcile`; others run plain `skytime server`. No leader election, no distributed lock.
- **D-7.2-11: Reconcile failure exits non-zero.** No "degrade to plain worker" fallback. K8s CrashLoopBackoff surfaces the misconfig.
- **D-7.2-12: No bounded backoff retry for reconcile.** Single attempt; K8s pod restart provides retry.
- **D-7.2-13: `req` has exactly two fields for cron: `req.scheduled_time` + `req.actual_time`.** `schedule_id` NOT plumbed through (Temporal metadata carries it).
- **D-7.2-14: `ReqSchema()` for `*cronSource` returns `["scheduled_time", "actual_time"]`.** Parser walker validates against this.
- **D-7.2-15: `map=` and `idempotency_key=` are OPTIONAL** on `core.cron(...)`. Defaults: InitState auto-derived as `{"scheduled_time": <iso>, "actual_time": <iso>}`; WorkflowID auto-composes as `{flow_name}/{trigger_pos_hash}/{scheduled_time_unix}`.
- **D-7.2-16: Boot order on cron-reconcile replica.** parse → connectClient → register → **`reconcileCronSchedules` (NEW)** → worker.Start → receiver.Mount → block on signal. Failure at reconcile short-circuits BEFORE listener bind.
- **D-7.2-17: On replicas WITHOUT `--cron-reconcile`,** reconcile step is skipped entirely; zero `ScheduleClient` API calls.
- **D-7.2-18: Schedule action shape.** `ScheduleWorkflowAction` → `"SkytimeWorkflow"` with `Args = dag.WorkflowInput{FlowName, ContentHash, InitState}`.
- **D-7.2-19: TaskQueue on the ScheduleAction matches the worker's task queue** (default `"skytime"`).
- **D-7.2-20: Per-trigger map_lambda evaluation timing.** Claude's discretion. Recommended path: lambda-eval activity as a synthesized first step in `SkytimeWorkflow` when `map` is non-nil. When `map` is omitted, the activity is skipped entirely.
- **D-7.2-21: Test seam for `ScheduleClient`.** Extend `worker.WithSDKFactory` OR add `cli.WithScheduleClientFactory`. Claude's discretion — planner picks.
- **D-7.2-22: Client-side 5-field POSIX cron validation at parse time** via `github.com/robfig/cron/v3` Parser configured for `Minute | Hour | Dom | Month | Dow` only. Reject 6-field explicitly. Position-aware error.
- **D-7.2-23: Timezone validation at parse time** via `time.LoadLocation(name)`. Position-aware error.
- **D-7.2-24: Add `weekly_digest.star`** to `examples/http-github-webhook/` with `core.cron(schedule="0 9 * * 1", timezone="America/New_York")`.
- **D-7.2-25: Add `docs/walkthroughs/cron-schedules.md`** long-form walkthrough mirroring Phase 7.1's `github-webhook.md`.

## Project Constraints (from CLAUDE.md)

- **Tech stack fixed:** Go + Starlark + Temporal. No alternative DSLs, expression languages, or orchestrators.
- **Strict parse/execute separation.** No I/O at parse, no Go escape hatch at execute, no context bleed.
- **Quality > speed.** Foundational infrastructure; correct boundaries are hard to fix retroactively.
- **Determinism.** Parsed DAG must be deterministic (Temporal replay).
- **Credentials never enter workflow state.** Resolver invoked just-in-time inside the activity; state holds only credential IDs. (Trivially honored for cron — `core.cron` has NO `credential=` kwarg.)
- **Temporal Cloud + self-hosted compat.** No cloud-only or self-hosted-only features.
- **No native `go` keyword inside workflows.** Use `workflow.Go`.
- **No `go.temporal.io/sdk/activity` imports inside extensions.** Activity SDK is allow-listed to `{activity, interpreter, worker, cli, testing, extension/receiver}` — Phase 7.2 will add `extension/schedules` (or whatever name) to this allow-list (Rule 3 deviation pattern from Phase 7.1 Plan 04).
- **`logrus` / `gomock` / `viper`** explicitly forbidden.

## Summary

Phase 7.2 has two distinct surfaces. **(1) Parse-time:** a new built-in extension `pkg/extension/builtin/core/` exposing one Starlark namespace `core` with one attribute `cron` that returns a `*cronSource` implementing `extension.TriggerSource` (does NOT implement `receiver.HTTPMounter`, so the existing Phase 7.1 receiver Mount loop skips it cleanly with zero code changes there). **(2) Boot-time:** a `reconcileCronSchedules(ctx, scheduleClient, triggerRegistry, flowRegistry, taskQueue, logger) error` function in a new package `pkg/extension/schedules/` that lists all `skytime/`-prefixed Schedules on the cluster, diffs against the parsed cron triggers, and emits Create / Update / Delete calls via `client.ScheduleClient`. Two CLI surfaces invoke this core: `skytime server --cron-reconcile` (apply mode) and `skytime cron-plan` (dry-run, exits 0).

All four "shapes" needed (`ScheduleClient.Create`, `ScheduleHandle.Update`, `ScheduleHandle.Delete`, `ScheduleClient.List`) are HIGH-confidence verified against `/Users/mikel/go/pkg/mod/go.temporal.io/sdk@v1.42.0/internal/schedule_client.go`. Updates use a `DoUpdate func(ScheduleUpdateInput) (*ScheduleUpdate, error)` callback that receives the current `ScheduleDescription` and returns a `*ScheduleUpdate` carrying a new `*Schedule`. `client.Client` already exposes `ScheduleClient() ScheduleClient` (verified at `internal/client.go:545`).

**Primary recommendation:** Build the parser-side factory mirroring `pkg/extension/builtin/http/webhook.go` verbatim (same `TriggerSourceSeal` embedding, same `{kind, config}` MarshalJSON envelope, same Starlark Value implementation). Build the reconciler in a new package `pkg/extension/schedules/` so both `skytime server --cron-reconcile` and `skytime cron-plan` reuse it; thread a `client.ScheduleClient` via a new option (recommend: `cli.WithScheduleClientFactory` — symmetric to `worker.WithSDKFactory` but cleaner since `cli` already owns the connection lifecycle). Map-lambda eval lands as a synthesized first activity inside `SkytimeWorkflow` (D-7.2-20) — but the planner should consider deferring this synthesis if no demo flow needs it; the default path (D-7.2-15 auto-derived InitState) is the common case.

### Pattern 1: `*cronSource` as `extension.TriggerSource` + `starlark.Value`

**What:** Mirror `pkg/extension/builtin/http/webhook.go::httpWebhookSource` verbatim, swapping HTTP fields for cron fields. Embed `extension.TriggerSourceSeal` for seal satisfaction. Does NOT implement `receiver.HTTPMounter`.

**When to use:** Any trigger source that has no HTTP route (cron is the first; future `core.signal`, `core.queue` follow the same pattern).

**Example** (sketch — planner will detail):
```go
// pkg/extension/builtin/core/cron.go
package core

import (
    "encoding/json"
    "fmt"
    "sort"
    "time"

    "go.starlark.net/starlark"

    "github.com/mikelalcon/skytime/pkg/dag"
    "github.com/mikelalcon/skytime/pkg/extension"
)

const cronKind = "core.cron"

type cronSource struct {
    extension.TriggerSourceSeal // embed for cross-package seal satisfaction

    schedule       string         // required, validated as 5-field POSIX cron at parse time
    timezone       string         // default "UTC"; validated via time.LoadLocation at parse time
    overlap        string         // default "skip"; one of {skip, allow, buffer_one, cancel_other}
    catchupWindow  *time.Duration // optional; nil → Temporal default (1 minute)
}

func (*cronSource) Kind() string         { return cronKind }
func (*cronSource) ReqSchema() []string  { return []string{"actual_time", "scheduled_time"} } // sorted
func (s *cronSource) MarshalJSON() ([]byte, error) {
    cfg := map[string]any{
        "schedule": s.schedule,
        "timezone": s.timezone,
        "overlap":  s.overlap,
    }
    if s.catchupWindow != nil {
        cfg["catchup_window_ns"] = int64(*s.catchupWindow)
    }
    cfgBytes, err := json.Marshal(cfg)
    if err != nil { return nil, err }
    return []byte(fmt.Sprintf(`{"kind":%q,"config":%s}`, cronKind, string(cfgBytes))), nil
}

// starlark.Value contract — identical pattern to httpWebhookSource
func (s *cronSource) String() string         { return fmt.Sprintf("core.cron(schedule=%q, timezone=%q)", s.schedule, s.timezone) }
func (*cronSource) Type() string             { return "core.cron" }
func (*cronSource) Freeze()                  {}
func (*cronSource) Truth() starlark.Bool     { return starlark.True }
func (*cronSource) Hash() (uint32, error)    { return 0, fmt.Errorf("unhashable type: core.cron") }

// Accessors for the reconciler — match pkg/extension/builtin/http/webhook.go's accessor pattern.
func (s *cronSource) Schedule() string                  { return s.schedule }
func (s *cronSource) Timezone() string                  { return s.timezone }
func (s *cronSource) Overlap() string                   { return s.overlap }
func (s *cronSource) CatchupWindow() (time.Duration, bool) {
    if s.catchupWindow == nil { return 0, false }
    return *s.catchupWindow, true
}

var _ extension.TriggerSource = (*cronSource)(nil)
var _ starlark.Value          = (*cronSource)(nil)
```

```go
// pkg/extension/schedules/id.go
package schedules

import (
    "crypto/sha256"
    "encoding/base64"

    "github.com/mikelalcon/skytime/pkg/dag"
)

const SkytimeScheduleIDPrefix = "skytime/"

// ComposeScheduleID per D-7.2-04: "skytime/{flow_name}/{base64url(sha256(Pos.String()))[:8]}"
func ComposeScheduleID(t *dag.Trigger) string {
    sum := sha256.Sum256([]byte(t.Pos.String()))
    return SkytimeScheduleIDPrefix + t.FlowName + "/" + base64.RawURLEncoding.EncodeToString(sum[:])[:8]
}

// IsSkytimeManaged returns true iff id has the SkytimeScheduleIDPrefix.
func IsSkytimeManaged(id string) bool {
    return len(id) >= len(SkytimeScheduleIDPrefix) && id[:len(SkytimeScheduleIDPrefix)] == SkytimeScheduleIDPrefix
}
```

### Pattern 4: Reconciler architecture

**Three-phase pipeline:**
1. **Desired state:** walk `worker.Triggers().All()`, filter by `t.Source.Kind() == "core.cron"`, build `map[scheduleID]*desired{spec, action, policies}`.
2. **Actual state:** call `client.ScheduleClient().List(ctx, ScheduleListOptions{})`, iterate the `ScheduleListIterator`, filter by `IsSkytimeManaged(entry.ID)`, build `map[scheduleID]*actual{spec, ...}`.
3. **Diff:** three buckets — `creates` (in desired, not in actual), `updates` (in both, fields differ), `deletes` (in actual, not in desired). Apply in sorted order by `scheduleID`. Accumulate per-schedule failures; do NOT short-circuit (D-7.2 strawman per `<key_constraints>`); report at end via `errors.Join` (Go 1.20+).

**Drift detection canonical-form comparison:** Marshal each desired schedule to a canonical JSON (cron string, timezone, overlap enum value, catchup_window ns); for each cluster Schedule, normalize the same way from `ScheduleListEntry.Spec` and `entry.Memo` (or call `GetHandle.Describe` for the missing `Overlap` / `CatchupWindow` fields — see Pitfall 2 below). Equal canonical bytes → no diff. Different → emit an Update.

**`List` does NOT return Policy fields.** Verified at `/Users/mikel/go/pkg/mod/go.temporal.io/sdk@v1.42.0/internal/schedule_client.go:649-685`: `ScheduleListEntry` has `ID`, `Spec`, `Note`, `Paused`, `WorkflowType`, `RecentActions`, `NextActionTimes`, `Memo`, `SearchAttributes` — but NO `Policy` field. **So List alone cannot detect overlap-policy or catchup-window drift.**

**Two implementation strategies for the missing fields:**

| Strategy | Pros | Cons |
|----------|------|------|
| **(A) Describe each Skytime-managed schedule** | Authoritative; reads `*Schedule.Policy`. | N round-trips per boot (N = number of cron triggers). For a typical Skytime corpus (≤ 50 cron triggers) this is fine; for hundreds it's slow. |
| **(B) Stash canonical JSON in `ScheduleListEntry.Memo`** at Create/Update time | Single List call detects all drift. | Memo is operator-visible in `temporal schedule list`; the canonical JSON is noise. |

**Recommendation: (A) Describe-per-item for v1.** It's correct, simple, and the volume is bounded by `.star` cron triggers. Promote to (B) if customers hit perf issues at scale.

### Pattern 5: `ScheduleHandle.Update` callback shape

The `DoUpdate` callback receives the current schedule and returns the new one. The simplest correct implementation:

```go
err := handle.Update(ctx, client.ScheduleUpdateOptions{
    DoUpdate: func(input client.ScheduleUpdateInput) (*client.ScheduleUpdate, error) {
        return &client.ScheduleUpdate{
            Schedule: &client.Schedule{
                Action: desired.action,
                Spec:   &desired.spec,
                Policy: &desired.policy,
                State:  input.Description.Schedule.State, // preserve user-set State (paused, etc.)
            },
        }, nil
    },
})
```

**Preserve State.** If a human operator manually paused the schedule via `temporal schedule update`, Skytime should NOT auto-unpause it. The callback reads `input.Description.Schedule.State` and reuses it. This is a load-bearing detail for production safety.

### Pattern 6: Eval-map-lambda activity (D-7.2-20)

**Only needed if a cron trigger declares `map=`.** The default path (D-7.2-15) auto-derives `InitState = {"scheduled_time": <iso>, "actual_time": <iso>}` — no Starlark eval, no activity needed.

When `map` is non-nil, `SkytimeWorkflow` synthesizes a first activity that:
1. Reads `dag.WorkflowInput.InitState` (which contains the raw `{scheduled_time, actual_time}` plus the trigger's `posKey` so the worker can look up the captured lambda).
2. Evaluates the lambda against a `req` struct shaped `{scheduled_time, actual_time}`.
3. Returns the lambda's dict result as the workflow's *real* initial state.

**Risk:** This requires `SkytimeWorkflow` to know "this run came from a cron trigger and has a pending map eval." Plumbing options:

| Plumbing | Trade-off |
|----------|-----------|
| **Sentinel key in `InitState`** (e.g., `__skytime_cron_map_pending__`) | Cheapest; one field. But pollutes the state shape. |
| **Dedicated `*dag.Trigger`-side method** that returns the map-lambda's `LambdaID` and `posKey`, threaded through a new `WorkflowInput.TriggerMeta` field | Cleaner type-wise. Adds a field to `dag.WorkflowInput` (which crosses Temporal history — D3-04 requires stability). |

**Recommendation: planner defers map-lambda support for v1 if no Phase 7.2 example flow uses it.** The walkthrough's `weekly_digest.star` example in D-7.2-24 does NOT use `map=` (auto-derived InitState is sufficient). Punting the synthesized activity to a future phase keeps Phase 7.2 scoped to the durable-Schedule story; revisit when a customer wants `map=lambda req: {"week_of": req.scheduled_time.strftime(...)}`.

### Anti-Patterns to Avoid

- **In-process polling.** Goroutine-driven `time.Ticker` or `robfig/cron` `Cron.Start()` — REJECTED. Phase 7.2's whole point is durability. Schedules survive worker crashes; in-process scheduler does not.
- **Schedule API calls from non-reconcile replicas.** Replicas without `--cron-reconcile` MUST make zero `client.ScheduleClient().*` calls. Easy test: snapshot the fake schedule client's call log and assert empty.
- **Leader election in-process.** Plan said no, mean no. Operator opts in to ONE replica.
- **String-equality on canonical JSON without sorting keys.** `encoding/json` does NOT sort map keys deterministically across Go versions — verify the planner uses `json.MarshalIndent` with a struct (not `map[string]any`) for the canonical form, OR sorts keys explicitly.
- **Re-using `WorkflowID` shape from Phase 7.1.** Phase 7.1's WorkflowID is `{flow_name}/{trigger_pos_hash}/{user_key}`. Phase 7.2's *default* WorkflowID (D-7.2-15) is `{flow_name}/{trigger_pos_hash}/{scheduled_time_unix}`. **Different separator semantics — last segment is unix-timestamp, not arbitrary user key.** The schedule's `ScheduleWorkflowAction.ID` field controls this; the SDK auto-appends a timestamp suffix per docs (`"the workflow ID of the started workflow may not match this exactly, it may have a timestamp appended for uniqueness"`). So setting `ScheduleWorkflowAction.ID = "{flow_name}/{trigger_pos_hash}"` is sufficient — Temporal handles the timestamp. **Verify this during planning** by reading the comment at `internal/schedule_client.go:232-236`.
- **Calling `time.LoadLocation` at boot per trigger.** Cache the result on the parsed `*cronSource` if validation succeeds, OR re-validate in the reconciler (safer; verifies tzdata is available on the target binary not just the parser binary).
- **`go.temporal.io/sdk/activity` import in `pkg/extension/builtin/core/` or `pkg/extension/schedules/`.** Will trip the firewall test (`pkg/activity/firewall_test.go::TestNoTemporalImportsOutsideAllowList`). The reconciler needs `go.temporal.io/sdk/client`, NOT activity. **Add `extension/schedules` to `allowedPkgs` in that firewall test** (Rule 3 deviation pattern from Phase 7.1 Plan 04, where `extension/receiver` was added the same way).

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| 5-field POSIX cron parsing | A regex or manual field-split + range-check | `github.com/robfig/cron/v3` Parser | Standard fields (`MON-FRI`, `*/3`, `1-5,7`), `@`-macro handling, range validation are all subtly wrong if hand-rolled. v3 is one file, zero deps, MIT-licensed. |
| Cron Schedule durability | In-process `time.Ticker` + scheduling state in a JSON file | Temporal Schedules (`ScheduleClient`) | Survives worker crashes (the whole point). Cluster handles missed-fire catchup, overlap, timezone DST, etc. |
| Schedule drift detection | String-compare cron expressions | Canonical-form JSON comparison + `ScheduleHandle.Describe` for non-List fields | Two strings can express the same schedule (`0 9 * * 1` vs `0 9 * * MON`); Temporal normalizes server-side to a calendar form on Create per the SDK comment at `schedule_client.go:128-131`. Either store the *user's* literal cron string in Memo and compare that, or read back the canonical Calendar form and compare. RECOMMEND: store the user's original cron string as a "canonical key" in Memo at Create time; List → Memo gives stable diff without `Describe`. |
| Schedule ID hashing | Custom hash function | Reuse `posHash` from `pkg/extension/receiver/workflow_id.go` | Already verified, already tested (`TestComposeWorkflowID`). Same input → same output; collision risk is negligible at 8 chars of sha256. |
| Timezone validation | A regex against IANA name pattern | `time.LoadLocation(name)` | Validates that the name actually resolves in the binary's zoneinfo source. Catches typos (`Amrica/New_York`) before they hit Temporal. |
| Per-replica leader election | Raft, etcd lease, k8s lease | The `--cron-reconcile` boolean flag itself | D-7.2-10. Operator's deployment topology IS the leader-election mechanism. |
| Cron-trigger map lambda eval at fire time | A "trigger activity" that runs *before* the workflow starts | Synthesized first activity inside `SkytimeWorkflow` (D-7.2-20) | Temporal Schedule actions are static templates — they cannot carry Starlark closures. The workflow itself is the only place lambda eval can happen post-trigger. |

**Key insight:** Phase 7.2 has very little code that's "new" in the sense of custom algorithms. The novelty is in **wiring** — connecting a new Starlark namespace, a new `extension.TriggerSource` shape, and a new boot-time reconciler to the existing Phase 7 / 7.1 registries and CLI subcommands. Every load-bearing piece (parser, registry, worker, receiver, server signal loop) already exists.

## Common Pitfalls

### Pitfall 1: `ScheduleListEntry` does NOT carry the Policy fields

**What goes wrong:** Reconciler diffs `desired.overlap` against `entry.Overlap` (or `entry.Policy.Overlap`) — but `ScheduleListEntry` has no such field. Drift in overlap policy / catchup_window goes undetected; the reconciler reports "no changes" while the cluster actually has stale policy.

**Why it happens:** The Schedule API is asymmetric — `Create` accepts full `ScheduleOptions` (including `Overlap` and `CatchupWindow`); `List` returns a flattened `ScheduleListEntry` that only carries `Spec`, `Note`, `Paused`, `WorkflowType`, recent action history, and Memo/SA. Policy lives only on the full `*Schedule` returned by `Describe`.

**How to avoid:** For each Skytime-managed Schedule found via `List`, call `ScheduleHandle.Describe(ctx)` to read `*ScheduleDescription.Schedule.Policy.{Overlap, CatchupWindow}`. Or, easier: stash the user's canonical cron-config JSON in `ScheduleOptions.Memo` at Create time, then `entry.Memo` is sufficient for diff (no `Describe` round-trips). RECOMMEND the Memo strategy.

**Warning signs:** Reconciler tests that pass `cron-plan` showing no changes when the planner manually edits the overlap kwarg in a `.star` file. If your test corpus doesn't include this case, you'll miss the bug.

### Pitfall 2: `ScheduleWorkflowAction.ID` field semantics

**What goes wrong:** Planner sets `ScheduleWorkflowAction.ID = composeScheduleID(t)` (the Schedule ID), expecting the workflow's ID to be this exact string. Then `temporal workflow list` shows workflows named `skytime/weekly_digest/aGcRb2Q8-2026-05-12T13:00:00Z`, breaking the operator's `client.ListWorkflow` filters that grep for `skytime/weekly_digest/aGcRb2Q8/<unix>`.

**Why it happens:** Per SDK source comment at `schedule_client.go:232-236`: *"The workflow ID of the started workflow may not match this exactly, it may have a timestamp appended for uniqueness."* Schedule actions auto-append a uniqueness suffix.

**How to avoid:** Set `ScheduleWorkflowAction.ID = "{flow_name}/{trigger_pos_hash}"` and let Temporal append the timestamp suffix; verify in a manual smoke test that the resulting WorkflowID format is `{flow_name}/{trigger_pos_hash}-<timestamp>` (note: the SDK uses a `-` separator, not a `/`). Adjust the D-7.2-15 strawman accordingly: the WorkflowID format is `{flow_name}/{trigger_pos_hash}-{scheduled_time_unix}` (SDK-supplied dash, not Skytime-supplied slash).

**Warning signs:** Operators reading the dashboard see WorkflowIDs they didn't expect; `client.GetWorkflow(ctx, id)` calls fail with NotFound because the ID is "wrong."

### Pitfall 3: `time.LoadLocation` works on the parser machine but not in the deployed container

**What goes wrong:** `core.cron(timezone="America/New_York")` validates clean in the developer's `skytime validate` run (macOS has `/usr/share/zoneinfo/America/New_York`). The container build is `FROM scratch` or `FROM gcr.io/distroless/static` — no zoneinfo on the filesystem. Boot fails with `time: unknown zone "America/New_York"` only at reconcile time, not at parse time.

**Why it happens:** Go's `time.LoadLocation` reads `$ZONEINFO`, then `$GOROOT/lib/time/zoneinfo.zip`, then `/usr/share/zoneinfo`. Scratch containers have none. The `time/tzdata` package, when imported with `_`, embeds the zoneinfo zip into the binary.

**How to avoid:** Add `import _ "time/tzdata"` in `pkg/extension/builtin/core/core.go` (or whatever main package guarantees it's pulled in by both `skytime` and `extbin`). Cost: ~450KB binary size; worth it for portability.

**Warning signs:** CI passes on the developer's laptop; production K8s pods CrashLoop on first reconcile-replica boot with `"time: unknown zone ..."`.

### Pitfall 4: `ScheduleClient.List` paginates — silent truncation if you only call `Next()` once per `HasNext()`

**What goes wrong:** The reconciler iterates `for it.HasNext() { entry, err := it.Next(); ... }`. With many schedules, this works. But if the planner accidentally writes `for entry, err := it.Next(); err == nil; entry, err = it.Next() { ... }` they may miss the EOF signaling pattern that `ScheduleListIterator` uses.

**Why it happens:** The SDK's iterator pattern is `HasNext()`/`Next()` and `Next()` returns `(*ScheduleListEntry, error)`. EOF is signaled by `HasNext()` returning false; if you call `Next()` after HasNext returned false, behavior is undefined per Go iterator conventions.

**How to avoid:** Always wrap in `for it.HasNext() { entry, err := it.Next(); if err != nil { return err }; ... }`. Test with `PageSize: 2` on a fake that has 5 entries to force pagination.

**Warning signs:** Reconciler appears to work locally with 2-3 schedules but silently misses some on a cluster with 100+. Cron-plan output is incomplete.

### Pitfall 5: Two replicas hit `--cron-reconcile` at the same time

**What goes wrong:** Operator misconfigures the deployment — both replicas in a `Deployment` have `--cron-reconcile`. Both list, both diff, both Create the same Schedule. The Schedule API is idempotent on ID, so the second Create returns an error rather than silently overwriting.

**Why it happens:** D-7.2-10 explicitly punts coordination to the operator. Temporal's `ScheduleClient.Create` with an existing ID returns `serviceerror.AlreadyExists`.

**How to avoid:** Treat `AlreadyExists` on Create as a non-fatal warning-and-continue (it means another reconciler beat us to it, OR a previous boot succeeded mid-way). DO NOT treat it as fatal. The reconciler's idempotency is a feature, not a bug. Document this in the walkthrough.

**Warning signs:** K8s rolling deploy: old reconcile pod still alive; new reconcile pod starts; both touch Schedules; one pod CrashLoops with `AlreadyExists`. Operator wonders why deploys are flaky.

### Pitfall 6: Cron string parser allowing 6-field by accident

**What goes wrong:** Planner uses `cron.NewParser(cron.Minute | cron.Hour | cron.Dom | cron.Month | cron.Dow | cron.Descriptor)` (with `Descriptor`) — this still accepts macros like `@hourly` but also (per the v3 README's `expandFields` function) translates them to 5-field. A user writes `core.cron(schedule="@hourly")` — accepted. The Phase 7.2 success criterion #4 says: *"a 5-field POSIX cron string is accepted at parse time; a 6-field (with-seconds) string or a malformed string produces a position-aware parse error."* Macros are a gray area: not 5-field literally, but not 6-field either.

**Why it happens:** robfig/cron's standard parser includes `Descriptor` by default. The minimal 5-field-only parser is `cron.NewParser(cron.Minute | cron.Hour | cron.Dom | cron.Month | cron.Dow)` — note NO `Descriptor` flag.

**How to avoid:** Use the exact flag set `cron.Minute | cron.Hour | cron.Dom | cron.Month | cron.Dow` (no Descriptor). 6-field strings will fail with `expected exactly 5 fields, found 6`. Macros will fail with `failed to parse int from <macro_token>`. **Verify by writing tests for both rejection cases in `core_test.go`.**

**Warning signs:** A user's `.star` file with `core.cron(schedule="@hourly")` parses successfully; the planner's tests for "reject 6-field" pass but no test for "reject macros" exists.

### Pitfall 7: `dag.WorkflowInput` content-hash lookup fails for cron-fired runs

**What goes wrong:** Phase 7.1 receiver dispatches with `WorkflowInput{FlowName, ContentHash, InitState}` where `ContentHash` comes from `deps.FlowRegistry.ContentHashFor(t.FlowName)`. The reconciler doesn't have a `FlowRegistry` at hand by default — it has only `worker.Triggers()`. If the cron Schedule is created with a stale ContentHash (e.g., from the previous boot's `.star` file bytes), workflows fired by that Schedule will look up `(FlowName, OldContentHash)` and miss.

**Why it happens:** Temporal Schedules persist their `ScheduleWorkflowAction` config server-side, including the `Args = WorkflowInput{...}` blob. On worker reboot, the worker registry has new ContentHashes; the Schedule's stored Args still have the old one.

**How to avoid:** **Each cron trigger reconcile must Update the schedule's Action whenever the FlowRegistry's ContentHashFor(FlowName) changes** — not just when the cron string changes. Diff algorithm: include `ContentHash` in the canonical form, not just `{schedule, timezone, overlap, catchup_window}`. This means EVERY boot that touches a cron flow's bytes triggers an Update of that flow's Schedule. Acceptable: Update is cheap and preserves history.

**Warning signs:** Edit a cron-fired flow's logic, rebuild, deploy — the reconcile reports "no changes" because the cron config didn't change. Next firing of the Schedule produces a workflow that fails with "flow @ not found." Hard-to-debug because the .star file IS there.

### Example 1: `cronFactory` parse-time validation

```go
// pkg/extension/builtin/core/cron.go

import (
    cronv3 "github.com/robfig/cron/v3"
)

// fiveFieldParser is the locked 5-field POSIX cron parser. No Descriptor
// flag — macros (@hourly, @daily, etc.) are rejected per D-7.2-22.
var fiveFieldParser = cronv3.NewParser(
    cronv3.Minute | cronv3.Hour | cronv3.Dom | cronv3.Month | cronv3.Dow,
)

var allowedOverlaps = map[string]bool{
    "skip":         true,
    "allow":        true,
    "buffer_one":   true,
    "cancel_other": true,
}

func cronFactory(thread *starlark.Thread, fn *starlark.Builtin, args starlark.Tuple, kwargs []starlark.Tuple) (starlark.Value, error) {
    var (
        schedule       string
        timezone       = "UTC"
        overlap        = "skip"
        catchupWindow  string // parsed as time.ParseDuration; nil-sentinel if unset
    )
    if err := starlark.UnpackArgs("core.cron", args, kwargs,
        "schedule", &schedule,
        "timezone?", &timezone,
        "overlap?", &overlap,
        "catchup_window?", &catchupWindow,
    ); err != nil {
        return nil, &dag.ParseError{Pos: callerPosition(thread), Msg: "core.cron: " + err.Error()}
    }

    // 1. Cron string validation (D-7.2-22, success criterion #4)
    if _, err := fiveFieldParser.Parse(schedule); err != nil {
        return nil, &dag.ParseError{
            Pos: callerPosition(thread),
            Msg: fmt.Sprintf("core.cron: invalid 5-field POSIX cron %q: %s", schedule, err.Error()),
        }
    }

    // 2. Timezone validation (D-7.2-23)
    if _, err := time.LoadLocation(timezone); err != nil {
        return nil, &dag.ParseError{
            Pos: callerPosition(thread),
            Msg: fmt.Sprintf("core.cron: invalid timezone %q: %s (use IANA name like \"America/New_York\")", timezone, err.Error()),
        }
    }

    // 3. Overlap validation (D-7.2-03)
    if !allowedOverlaps[overlap] {
        allowed := sortedKeys(allowedOverlaps)
        return nil, &dag.ParseError{
            Pos: callerPosition(thread),
            Msg: fmt.Sprintf("core.cron: overlap %q not allowed; valid: %v", overlap, allowed),
        }
    }

    // 4. Catchup window validation (D-7.2-03)
    src := &cronSource{schedule: schedule, timezone: timezone, overlap: overlap}
    if catchupWindow != "" {
        d, err := time.ParseDuration(catchupWindow)
        if err != nil {
            return nil, &dag.ParseError{
                Pos: callerPosition(thread),
                Msg: fmt.Sprintf("core.cron: catchup_window %q is not a valid duration: %s", catchupWindow, err.Error()),
            }
        }
        if d < 0 {
            return nil, &dag.ParseError{
                Pos: callerPosition(thread),
                Msg: fmt.Sprintf("core.cron: catchup_window must be non-negative; got %s", d),
            }
        }
        src.catchupWindow = &d
    }
    return src, nil
}
```

### Example 2: Reconcile Create / Update / Delete

```go
// pkg/extension/schedules/schedules.go

import (
    "context"
    "errors"
    "log/slog"
    "sort"

    enumspb "go.temporal.io/api/enums/v1"
    "go.temporal.io/sdk/client"

    "github.com/mikelalcon/skytime/pkg/dag"
    skycore "github.com/mikelalcon/skytime/pkg/extension/builtin/core"
    "github.com/mikelalcon/skytime/pkg/interpreter"
)

// Plan describes the diff between desired (parsed .star registry) and
// actual (cluster) Skytime-managed Schedules. Sorted slices for stable
// dry-run output.
type Plan struct {
    Creates []*dag.Trigger        // sorted by ComposeScheduleID
    Updates []*UpdatePlan         // sorted by ScheduleID
    Deletes []string              // sorted Schedule IDs (no Trigger; just the orphaned IDs)
}

type UpdatePlan struct {
    ScheduleID string
    Trigger    *dag.Trigger
    Reason     string // human-readable diff summary for cron-plan output
}

// ReconcileCronSchedules computes the diff and (when apply=true) applies
// Create / Update / Delete via the supplied ScheduleClient. Returns the
// plan + any failures. Per D-7.2-12 there is no internal retry; the
// caller (skytime server --cron-reconcile) exits non-zero on error and
// K8s CrashLoopBackoff provides retry behavior.
func ReconcileCronSchedules(
    ctx context.Context,
    sc client.ScheduleClient,
    triggers []*dag.Trigger,
    flows *interpreter.FlowRegistry,
    taskQueue string,
    apply bool,
    logger *slog.Logger,
) (*Plan, error) {
    desired, err := buildDesired(triggers, flows, taskQueue)
    if err != nil { return nil, err }

    actual, err := listSkytimeManaged(ctx, sc)
    if err != nil { return nil, err }

    plan := diff(desired, actual)

    if !apply {
        return plan, nil
    }

    var errs []error
    for _, t := range plan.Creates {
        opts, err := scheduleOptionsFor(t, flows, taskQueue)
        if err != nil { errs = append(errs, err); continue }
        if _, err := sc.Create(ctx, opts); err != nil {
            // Pitfall 5: AlreadyExists is non-fatal (another reconciler beat us).
            if isAlreadyExists(err) {
                logger.Warn("schedule already exists; another reconciler beat us", "id", opts.ID)
                continue
            }
            errs = append(errs, fmt.Errorf("create %s: %w", opts.ID, err))
        }
    }
    for _, up := range plan.Updates {
        if err := updateSchedule(ctx, sc, up, flows, taskQueue); err != nil {
            errs = append(errs, fmt.Errorf("update %s: %w", up.ScheduleID, err))
        }
    }
    for _, id := range plan.Deletes {
        h := sc.GetHandle(ctx, id)
        if err := h.Delete(ctx); err != nil {
            errs = append(errs, fmt.Errorf("delete %s: %w", id, err))
        }
    }
    return plan, errors.Join(errs...)
}

func updateSchedule(ctx context.Context, sc client.ScheduleClient, up *UpdatePlan, flows *interpreter.FlowRegistry, taskQueue string) error {
    desiredAction, desiredSpec, desiredPolicy, err := scheduleShapeFor(up.Trigger, flows, taskQueue)
    if err != nil { return err }
    return sc.GetHandle(ctx, up.ScheduleID).Update(ctx, client.ScheduleUpdateOptions{
        DoUpdate: func(input client.ScheduleUpdateInput) (*client.ScheduleUpdate, error) {
            return &client.ScheduleUpdate{
                Schedule: &client.Schedule{
                    Action: desiredAction,
                    Spec:   &desiredSpec,
                    Policy: &desiredPolicy,
                    State:  input.Description.Schedule.State, // preserve operator-set paused state
                },
            }, nil
        },
    })
}

func scheduleOptionsFor(t *dag.Trigger, flows *interpreter.FlowRegistry, taskQueue string) (client.ScheduleOptions, error) {
    src, ok := t.Source.(*skycore.CronSource) // accessor exported by core
    if !ok { return client.ScheduleOptions{}, fmt.Errorf("trigger %s is not a *cronSource", t.FlowName) }

    contentHash, ok := flows.ContentHashFor(t.FlowName)
    if !ok { return client.ScheduleOptions{}, fmt.Errorf("flow %q has no resolvable content hash", t.FlowName) }

    overlapEnum := mapOverlapToEnum(src.Overlap()) // see Example 3
    workflowInput := dag.WorkflowInput{
        FlowName:    t.FlowName,
        ContentHash: contentHash,
        // InitState filled in at fire time by the synthesized first activity
        // if MapLambda is non-nil; auto-derived {scheduled_time, actual_time}
        // map otherwise. v1 default-only path: empty map here, the workflow
        // reads workflow.GetInfo(ctx).ScheduledStartTime / Now() at start.
        InitState: nil,
    }
    opts := client.ScheduleOptions{
        ID: ComposeScheduleID(t),
        Spec: client.ScheduleSpec{
            CronExpressions: []string{src.Schedule()},
            TimeZoneName:    src.Timezone(),
        },
        Action: &client.ScheduleWorkflowAction{
            ID:        t.FlowName + "/" + posHash(t), // SDK auto-appends timestamp suffix per Pitfall 2
            Workflow:  "SkytimeWorkflow",
            Args:      []interface{}{workflowInput},
            TaskQueue: taskQueue,
        },
        Overlap: overlapEnum,
        Note:    fmt.Sprintf("Skytime: %s (declared at %s)", t.FlowName, t.Pos.String()),
        Memo: map[string]interface{}{
            // Canonical-form key for List-based drift detection (Pitfall 1 strategy B):
            "skytime_canonical": canonicalConfig(src, contentHash),
        },
    }
    if d, ok := src.CatchupWindow(); ok {
        opts.CatchupWindow = d
    }
    return opts, nil
}
```

## Open Questions

1. **Should we ship the synthesized lambda-eval activity (D-7.2-20) in Phase 7.2?**
   - What we know: D-7.2-15 default path covers the common case; the walkthrough's `weekly_digest.star` doesn't need `map=`. SDK gives us `workflow.GetInfo(ctx).ScheduledStartTime` server-side.
   - What's unclear: whether *any* Phase 7.2 demo flow benefits from `map=`. If yes, the synthesized first activity is load-bearing. If no, defer it.
   - Recommendation: planner reads the example flows; if none use `map=`, **defer to a follow-on quick** and ship Phase 7.2 with the auto-derived default path only. Saves ~150 LOC and one Temporal-history-affecting design change to `dag.WorkflowInput`.

2. **Does the `time.LoadLocation` call need to happen at parse time AND at reconcile time?**
   - What we know: Parse-time validation runs on the parser machine (developer laptop, CI runner); reconcile-time runs on the deployed binary.
   - What's unclear: if a developer parses on macOS (has zoneinfo) but the container has neither system zoneinfo nor `import _ "time/tzdata"`, the parse passes but the reconcile fails late.
   - Recommendation: validate at parse AND at reconcile (cheap; one `time.LoadLocation` call per cron source). Add `import _ "time/tzdata"` to guarantee parity.

3. **Store user's literal cron string in Memo for drift detection, or call `Describe` per item?**
   - What we know: Memo strategy is one List call total; Describe strategy is N calls but more authoritative.
   - What's unclear: At what N does Describe become operationally noticeable? Temporal Cloud lists ~30 schedules/sec; for N=50, that's 1.7s of boot delay — acceptable but visible.
   - Recommendation: ship Memo strategy v1 (no extra Describe calls). Test both strategies in the unit tests; promote to Describe if customer report drift bugs.

4. **Should `--cron-reconcile` accept an environment variable override?**
   - What we know: Phase 7.1 didn't introduce env-var fallbacks for any new flag (verified via `pkg/cli/options.go` and `bindEnvVars`).
   - What's unclear: K8s-native deployments often set boolean flags via env vars; `SKYTIME_CRON_RECONCILE=true` would be idiomatic.
   - Recommendation: Skip for v1; operator can wire `--cron-reconcile` directly in the pod spec. Revisit if 3+ customers want env-var fallback.
