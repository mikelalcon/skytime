# Phase 7.2: Cron triggers via Temporal Schedules — Context

**Gathered:** 2026-05-11
**Status:** Ready for planning

<domain>
## Phase Boundary

Phase 7.2 delivers durable cron triggers backed by Temporal Schedules. Five concrete deliverables:

1. **`core.cron(...)` source factory** — a NEW Skytime-native source factory under the `core` namespace (NOT `triggers.cron` as the roadmap text suggests; superseded during discuss-phase). Lives in a built-in extension shipped from `pkg/extension/builtin/core/` (or equivalent location — Claude's discretion). Kwargs: `schedule: str` (required, 5-field POSIX cron), `timezone: str|None` (IANA tz name, defaults to UTC), `overlap: str|None` (Temporal ScheduleOverlapPolicy enum, default `skip`), `catchup_window: duration|None` (default unset → Temporal default).
2. **`core.cron` is the namespace anchor** — `core.*` is reserved for future Skytime-native trigger primitives (e.g., future `core.signal(...)`, `core.queue(...)`). NOT reserved for general Skytime stdlib code; `core` specifically holds trigger-source primitives that aren't owned by a domain extension.
3. **Boot-time Schedule reconciliation** — opt-in via `--cron-reconcile` boolean flag on `skytime server`. When set on ONE replica in an active-active deployment, that replica performs full CRUD against Temporal's ScheduleClient at boot: create new schedules from parsed registry, update drifted schedules in place (preserving Schedule history), delete orphans whose Schedule IDs are Skytime-managed (prefix `skytime/`) but no longer present in the parsed registry. Other replicas run plain `skytime server` and never touch the Schedule API.
4. **`skytime cron-plan` subcommand** — one-shot dry-run that reads the .star registry, lists Skytime-managed Schedules on the cluster, prints the diff, exits 0. NO cluster mutations. Used out-of-band by operators (CI pre-deploy, manual review, etc.) — invocation pattern is left to the operator.
5. **Cron-triggered workflow dispatch via Temporal Schedules** — Schedules are configured with `ScheduleAction = StartWorkflow` pointing at `SkytimeWorkflow` with the appropriate `dag.WorkflowInput{FlowName, ContentHash, InitState}` shape (matching Phase 7.1's webhook dispatch). When Temporal fires the schedule, the worker (any replica) picks up the workflow task from the task queue normally.

**Out of scope (other phases or deferred):**
- Webhook + cron coexistence is implicit (both are TriggerSource implementations; receiver's Mount loop already skips non-HTTP sources via the HTTPMounter type assertion shipped in Phase 7.1) — no work needed
- Dashboard view of cron schedules: Phase 7.3
- `cli.WithCredfile(path)` Option lift: Phase 7.4
- Production auth docs: Phase 7.5
- Cron-triggered flows that need credentials: flows resolve credentials normally inside their steps via the existing `extension.CredentialHandler` (Phase 2 + Phase 7.1) — no per-trigger `credential=` kwarg on `core.cron(...)`

</domain>

<key_constraints>
## Load-Bearing Constraints (do not violate)

- **Temporal Schedules are the only mechanism.** No in-process polling, no cron library (robfig/cron, etc.), no goroutine-driven tickers. The whole point is durability — Schedules survive worker crashes; an in-process scheduler does not.
- **Schedule ID format is `skytime/{flow_name}/{trigger_pos_hash}`.** This is the load-bearing isolation mechanism: `--cron-reconcile` lists ALL Schedules on the cluster, filters by ID prefix `skytime/`, and only touches those. User-created Schedules without this prefix are NEVER deleted. The `trigger_pos_hash` is the same `posHash(trigger.Pos.String())` Phase 7.1 uses for the webhook WorkflowID composition — base64url(sha256(pos))[:8].
- **Single-replica reconciliation.** `--cron-reconcile` is a boolean flag that opt-in marks ONE replica in an active-active deployment as the reconciler. No leader election, no distributed lock, no in-process coordination. The operator wires the flag via their deployment topology (one StatefulSet replica, one Kubernetes Job, etc.). Setting `--cron-reconcile` on two replicas simultaneously is a self-inflicted footgun; Temporal's idempotent Schedule API makes the outcome correct but the second replica's reconcile call is wasted.
- **Reconcile failure exits non-zero.** No degraded-as-plain-worker fallback. If `--cron-reconcile` is set and the call fails (Temporal unreachable, permission denied, ScheduleClient returns error), `skytime server` exits non-zero. K8s CrashLoopBackoff surfaces the misconfig. Same fail-loud philosophy Phase 7.1 used for the Temporal client connect.
- **`req.scheduled_time` + `req.actual_time` are the only `req` fields for cron triggers.** `schedule_id` is NOT plumbed through; Temporal's own workflow metadata carries it automatically (visible in the Temporal UI without any Skytime plumbing).
- **No I/O at parse time.** `core.cron(...)` returns a `TriggerSource` value; no schedule API calls, no network I/O, no filesystem reads at parse. Reconciliation happens at boot time (post-parse), and only on the designated replica.
- **Deterministic ordering.** Reconciliation iterates schedules in sorted order (by Schedule ID) so logs/tests are stable across boots. Failures on one schedule do NOT block sibling schedules (each is independent; accumulate failures, report at end).
- **Cron string validation is parse-time, position-aware.** Per success criterion #4, a 5-field POSIX cron string is accepted at parse time; a 6-field (with-seconds) string or a malformed string produces a position-aware parse error BEFORE any Schedule API call. The cron string lives inside a `.star` literal, so the position points to the literal's location in the file.

</key_constraints>

<decisions>
## Implementation Decisions

### Source factory namespace + shape

- **D-7.2-01: `core.cron(...)` is the cron source factory.** This SUPERSEDES the roadmap's `triggers.cron(...)` wording. Decision rationale: the roadmap suggested `triggers.*` as the namespace for Skytime-native trigger primitives, but during discussion the user picked `core.*` instead. `core.*` is now the reserved namespace for future Skytime-native primitives (e.g., future `core.signal(name=)`, `core.queue(topic=)`). Webhook sources stay in their owning extension's namespace (`http.webhook` from `pkg/extension/builtin/http`, `github.webhook` from the example github extension) — that asymmetry is intentional: domain extensions own their namespaces; Skytime-built-in trigger primitives live under `core.*`.
- **D-7.2-02: `core.cron` lives in `pkg/extension/builtin/core/` (Claude's discretion on exact path).** Built-in extension shipped from the library root; registered via `cli.WithExtensions(core.New(), ...)` by default in `cmd/skytime/main.go` and `examples/http-github-webhook/cmd/extbin/main.go`. The extension's `Initialize()` registers `core` as a Starlark module with `cron` as a member attribute returning a `*cronSource` value implementing `extension.TriggerSource`.
- **D-7.2-03: `core.cron(...)` kwargs.**
  - `schedule: str` (required) — 5-field POSIX cron string. Parse-time validation: reject 6-field (with-seconds), malformed, or out-of-range fields via `*dag.ParseError` with position.
  - `timezone: str|None` (optional, default UTC) — IANA tz database name (e.g., `"America/New_York"`). Parse-time validation: reject unknown tz names via `*dag.ParseError`.
  - `overlap: str|None` (optional, default `"skip"`) — one of `"skip"`, `"allow"`, `"buffer_one"`, `"cancel_other"`. Maps to Temporal's `ScheduleOverlapPolicy` enum. Parse-time validation: reject values not in the allow-set.
  - `catchup_window: duration|None` (optional, default unset → Temporal default of 1 minute) — Starlark string parsed via Go's `time.ParseDuration` (e.g., `"5m"`, `"1h"`). Reject negative durations.

### Schedule resource identity & lifecycle

- **D-7.2-04: Schedule ID format: `skytime/{flow_name}/{trigger_pos_hash}`.** Where `trigger_pos_hash = base64url(sha256(trigger.Pos.String()))[:8]` — same hash function Phase 7.1's `composeWorkflowID` uses (`pkg/extension/receiver/workflow_id.go::posHash`). Concrete example: a `core.cron(...)` trigger declared at `weekly_digest.star:5:1` for flow `weekly_digest` produces Schedule ID `skytime/weekly_digest/aGcRb2Q8`. Stable across boots; opaque to user.
- **D-7.2-05: Reconciliation tags Skytime-managed schedules via the `skytime/` ID prefix.** `--cron-reconcile` lists ALL Schedules on the cluster (`client.ScheduleClient.List(ctx, ...)`), filters by `id.startswith("skytime/")`, and only operates on those. User-created Schedules without the prefix are NEVER touched. Memo and SearchAttribute tagging were considered and rejected as overkill for v1 — the prefix is sufficient, greppable, and visible in `temporal schedule list` output.
- **D-7.2-06: Drift detection → update in place.** When a parsed `core.cron(...)` config differs from the cluster-side Schedule (different `schedule`, `timezone`, `overlap`, or `catchup_window`), reconcile calls `ScheduleHandle.Update(...)` to mutate the existing Schedule. Preserves Schedule history and any in-flight workflows the Schedule launched. Delete+recreate was considered and rejected — losing history and risking a missed scheduled run during the gap is operationally worse than the slightly more complex diff logic.
- **D-7.2-07: Orphan deletion is mandatory when `--cron-reconcile` is set.** No `preserve` half-measure — if you've opted into managing schedules, removing a `core.cron(...)` trigger from a `.star` file means the corresponding Schedule should be deleted. Otherwise stale Schedules keep firing workflows for code that no longer exists. The `skytime/` ID prefix isolates this to Skytime-managed schedules; user-created Schedules remain untouched. This is a deliberate simplification of the roadmap's original `strict|preserve` enum.

### CLI surface (renamed/scoped from roadmap)

- **D-7.2-08: `skytime server --cron-reconcile` is a boolean opt-in flag.** Default OFF (no flag set → no Schedule API calls; replica is a pure worker). When set, this replica performs full CRUD reconciliation at boot. Replaces the roadmap's `--reconcile=strict|preserve|dry-run` three-value enum (the original framing was unscoped — "reconcile" without qualification implied a broader operation; in practice it's cron-Schedules-only).
- **D-7.2-09: `skytime cron-plan` is a separate subcommand for dry-run.** One-shot: reads `--rootdir` for `.star` files, lists Skytime-managed Schedules on the cluster, prints a structured diff (creates / updates / deletes), exits 0. NO cluster mutations. Replaces the roadmap's `--reconcile=dry-run` value. Invocation is the operator's call — pre-deploy script, manual review, ad-hoc debugging, etc. Subcommand shape keeps it cleanly separated from `skytime server`'s long-running concerns and makes it composable in operator pipelines without server-startup overhead.

### Multi-replica deployment model

- **D-7.2-10: Single-flag opt-in. ONE replica gets `--cron-reconcile`; others run plain `skytime server`.** No leader election, no distributed lock, no in-process coordination logic. The operator wires the flag to one replica via whatever mechanism their deployment topology provides:
  - Kubernetes: a one-replica `Deployment` or a designated `StatefulSet` pod
  - Bare metal: one process invocation has the flag, others don't
  - Local dev: just set the flag once
- **D-7.2-11: Reconcile failure exits non-zero.** If `--cron-reconcile` is set and the reconciliation call fails (Temporal unreachable at boot, permission denied, ScheduleClient.List returns an error, ScheduleClient.Create/Update returns a non-recoverable error), `skytime server` exits non-zero. K8s CrashLoopBackoff surfaces the issue. No "degrade to plain worker" fallback — operator's intent was that this replica manages schedules; silently dropping that intent is worse than failing visibly.
- **D-7.2-12: No bounded backoff retry for reconcile.** A single attempt; on failure, exit non-zero. K8s pod restart already provides retry behavior with backoff (CrashLoopBackoff). Implementing in-process retry would duplicate this and complicate logging.

### `req` shape + lambda support

- **D-7.2-13: `req` has exactly two fields for cron triggers: `req.scheduled_time` + `req.actual_time`.**
  - `req.scheduled_time` — datetime when the Schedule was nominally supposed to fire (e.g., `2026-05-12T09:00:00-04:00`). Use case: "Generate the report for the week of {scheduled_time}".
  - `req.actual_time` — datetime when Temporal actually delivered the trigger (usually within ms of `scheduled_time` in steady state; can be later if the cluster was catching up after downtime). Use case: catchup-aware logic ("am I a backfilled run?").
  - `schedule_id` is NOT plumbed through — Temporal's own workflow metadata carries it (visible via `workflow.GetInfo(ctx)` and in the Temporal UI without any Skytime plumbing).
- **D-7.2-14: `ReqSchema()` for `*cronSource` returns `["scheduled_time", "actual_time"]`.** Parser walker (Phase 7's `findFreeVarAccesses`) validates `req.<attr>` against this schema; `req.payload` or `req.headers` in a cron map_lambda produces a position-aware parse error before any Schedule resource is created.
- **D-7.2-15: `map=` and `idempotency_key=` lambdas are OPTIONAL on `core.cron(...)`.**
  - If `map` is omitted: InitState is auto-derived as `{"scheduled_time": <isoformat>, "actual_time": <isoformat>}`. This is the common case — flows access these via `ctx.scheduled_time` / `ctx.actual_time` in their step lambdas without needing to write a map lambda.
  - If `idempotency_key` is omitted: WorkflowID auto-composes as `{flow_name}/{trigger_pos_hash}/{scheduled_time_unix}` — deterministic, replays-safe across backfills. Two backfill attempts at the same `scheduled_time` produce the same WorkflowID; REJECT_DUPLICATE handles the rest (just like webhook redelivery dedup in Phase 7.1).
  - If either is provided: behaves like webhook triggers (eval at trigger time, result feeds InitState / WorkflowID respectively).

### Boot order + lifecycle

- **D-7.2-16: Boot order on the cron-reconcile replica:**
  1. Parse `--rootdir` → flow + trigger registries (in-memory; same as Phase 7.1)
  2. `connectClient(cfg)` → Temporal client
  3. Register workflows + activities with the SDK worker
  4. **`reconcileCronSchedules(ctx, client, registry)` — NEW step.** Synchronous, fails fast on error.
  5. `worker.Start()`
  6. Mount HTTP listener via `receiver.Mount(mux, w, deps)` (Phase 7.1)
  7. Block on signal
  Failure at step 4 short-circuits BEFORE step 6 — the listener never binds, so K8s TCP readinessProbe on `--addr` correctly reports the pod as not-ready.
- **D-7.2-17: On replicas WITHOUT `--cron-reconcile`, step 4 is skipped entirely.** Sequence is the same as Phase 7.1: parse → connect → register → worker.Start → mount HTTP. Zero ScheduleClient API calls; the binary still imports the SDK's schedule types for the source factory's MarshalJSON shape but does not call any cluster-mutating method.

### Cron-triggered workflow dispatch

- **D-7.2-18: Schedule action shape.** Each Skytime-managed Schedule is configured with `ScheduleAction = client.ScheduleWorkflowAction` pointing at workflow type `"SkytimeWorkflow"` (Phase 3's generic interpreter) with `Args = dag.WorkflowInput{FlowName: <trigger.FlowName>, ContentHash: <FlowRegistry.ContentHashFor(flowName)>, InitState: <map[string]any from map_lambda or auto-derived>}`. Matches Phase 7.1's webhook dispatch shape — same workflow type, same input wrapper, same task queue.
- **D-7.2-19: TaskQueue on the ScheduleAction matches the worker's task queue.** Same `--task-queue` flag value (default `"skytime"`). Schedule fires → workflow task lands on the configured queue → any worker polling that queue picks it up. The reconciler-replica is NOT special at dispatch time; it's only special at boot-time reconciliation.
- **D-7.2-20: Per-trigger map_lambda evaluation timing.** Webhook map_lambdas run at delivery time (inside the receiver handler). Cron map_lambdas — given they only see `scheduled_time` and `actual_time`, both of which Temporal provides at schedule-fire time — can run at fire time inside the Schedule action OR be elided when omitted (D-7.2-15 default path). Implementation: Claude's discretion — easiest path is to evaluate the lambda inside a one-time activity that runs as part of the workflow's first step, NOT inside the Schedule action itself (Temporal's Schedule action templates are static; can't carry Starlark closures). If `map` is omitted, the activity is skipped entirely.

### Test seam

- **D-7.2-21: Test seam for `ScheduleClient`.** Extend the existing `worker.WithSDKFactory` Option pattern (Phase 7.1 D-7.1-13) to allow injecting a fake `ScheduleClient` for tests, OR add a separate `cli.WithScheduleClientFactory` Option. Claude's discretion — the planner picks whichever keeps `pkg/cli`'s Option surface cleanest. Receiver-side tests cover non-HTTP source skip (Phase 7.1 already does); new tests for Phase 7.2 cover reconcile create/update/delete via a fake client that records calls.

### Cron string validation

- **D-7.2-22: Client-side 5-field POSIX cron validation at parse time.** Implementation: Claude's discretion. Recommended path: use `github.com/robfig/cron/v3` Parser with `cron.Minute | cron.Hour | cron.Dom | cron.Month | cron.Dow` (5-field standard parser) to validate the string at parse time. Reject 6-field (with-seconds) explicitly per success criterion #4. Position-aware error: the Starlark literal carrying the cron string has a position; wrap the parser error in `*dag.ParseError` with that position. Pass-through-to-Temporal was rejected because it'd surface the error at boot reconcile time, far from the .star author's edit-test loop.
- **D-7.2-23: Timezone validation at parse time via `time.LoadLocation(name)`.** Same position-aware error wrapping. Unknown tz names rejected before any Schedule API call.

### Walkthrough + example

- **D-7.2-24: Add `weekly_digest.star` to `examples/http-github-webhook/` with `core.cron(...)` trigger.** The existing example project already has the github extension wired and a `weekly_digest.star` declared in Phase 6's roadmap text but never landed as a cron-triggered flow. Phase 7.2 lands it for real: `trigger(flow="weekly_digest", source=core.cron(schedule="0 9 * * 1", timezone="America/New_York"))` firing a flow that lists open PRs and posts a summary comment. Reader can run `gh webhook forward` from Phase 7.1 + Phase 7.2's `skytime cron-plan` against the same example project — both trigger types in one corpus.
- **D-7.2-25: Add `docs/walkthroughs/cron-schedules.md` long-form walkthrough.** Mirror Phase 7.1's `github-webhook.md` structure: prerequisites, secret setup (N/A for cron — no per-trigger credentials), `skytime cron-plan` dry-run review, `skytime server --cron-reconcile` apply, `temporal schedule list` verification, troubleshooting. Cross-link from `examples/http-github-webhook/README.md` quickstart.

### Claude's Discretion

The planner has flexibility on:

- **Built-in extension location.** `pkg/extension/builtin/core/` is the strawman. Alternative: `pkg/extension/core/` (no `builtin/` prefix). Pick consistent with how other Skytime-native built-in extensions get organized (none today; `core` would be the first).
- **`core.New()` registration in default binaries.** `cmd/skytime/main.go` and the example `extbin/main.go` should both include `cli.WithExtensions(core.New(), ...)` by default — but verify there's no harm in the registration when `core.cron(...)` is unused (registration cost is parse-time symbol availability only; zero runtime cost when no cron triggers exist).
- **`reconcileCronSchedules` function placement.** New package `pkg/extension/schedules/` (mirror of `pkg/extension/receiver/`)? Or inside `pkg/cli/server.go`? Decision driven by reusability — if other binaries (`skytime cron-plan`) need the same logic, a shared package wins.
- **Diff output format for `skytime cron-plan`.** Strawman: charm-log default human format (sections per action: creates / updates / deletes), `--json-log` for structured. Match Phase 7.1's pattern.
- **Map lambda eval site for cron.** Inside an activity at workflow first step (recommended for symmetry with webhook lambdas, both eval'd outside the workflow path) vs. inside the Schedule action JSON (impossible — actions are static templates). Recommended: a "lambda-eval" activity that runs as a synthesized step before user-declared steps when `map` lambda is non-nil.
- **Backfill semantics.** Temporal Schedules support `TriggerImmediately()`, `Backfill(start, end, overlap)`. Phase 7.2's reconciler does NOT trigger immediate fires or backfills automatically — it only mutates Schedule resources. Backfill is the operator's call via `temporal CLI`. Worth a documentation note in the walkthrough.
- **Schedule name (Note field on Temporal Schedule).** Strawman: human-readable `"Skytime: {flow_name} (declared at {pos})"`. Helps operators inspecting `temporal schedule list` understand what's running without grepping .star files.

</decisions>

## Specific Ideas

- **Schedule ID composition** (D-7.2-04): `skytime/{flow_name}/{base64url(sha256(trigger.Pos.String()))[:8]}`. Concrete example: a trigger at `weekly_digest.star:5:1` firing flow `weekly_digest` produces Schedule ID `skytime/weekly_digest/aGcRb2Q8`.
- **Cron trigger declaration in `.star`** (D-7.2-24 walkthrough seed):
  ```python
  trigger(
      flow = "weekly_digest",
      source = core.cron(
          schedule = "0 9 * * 1",                # Mondays at 09:00
          timezone = "America/New_York",
          overlap = "skip",                       # default; named here for clarity
      ),
      # map= and idempotency_key= both omitted; defaults apply (D-7.2-15)
  )

  flow(
      name = "weekly_digest",
      inputs = {
          "scheduled_time": "string",             # auto-derived ISO 8601 datetime
          "actual_time": "string",                # auto-derived ISO 8601 datetime
      },
      steps = [
          step(
              name = "List open PRs for the week",
              action_fn = lambda ctx: gh.list_recent_merged_prs(
                  owner = "mikelalcon",
                  repo = "skytime",
                  since = ctx.scheduled_time,
              ),
          ),
          # ... more steps
      ],
  )
  ```
- **WorkflowID for cron-fired runs** (D-7.2-15 default): `{flow_name}/{trigger_pos_hash}/{scheduled_time_unix}`. Concrete: `weekly_digest/aGcRb2Q8/1715515200`. Backfill at the same scheduled_time produces the same WorkflowID → REJECT_DUPLICATE dedup.
- **`skytime cron-plan` output shape** (D-7.2-09, charm-log default):
  ```
  [skytime] cron-plan reading .planning/.../weekly_digest.star
  [skytime] cluster has 2 Skytime-managed schedules
  [skytime] CREATE skytime/issue_triage_cron/qX8Yz1Ab   (cron="0 * * * *" tz=UTC overlap=skip)
  [skytime] UPDATE skytime/weekly_digest/aGcRb2Q8       (cron: "0 9 * * 1" → "0 10 * * 1")
  [skytime] DELETE skytime/legacy_flow/pP7q3RsT         (no matching trigger in registry)
  [skytime] plan: 1 create, 1 update, 1 delete
  [skytime] no changes applied (dry-run)
  ```
- **Reconcile failure log output** (D-7.2-11):
  ```
  [skytime] cron-reconcile starting
  [skytime] ERROR cron-reconcile failed: ScheduleClient.Create: rpc error: code = PermissionDenied
  exit 1
  ```
  K8s readinessProbe (TCP connect to `--addr`) returns connection-refused → pod not ready → CrashLoopBackoff after threshold.
- **No per-trigger credential kwarg on cron** (key constraint): the roadmap's `core.cron(...)` signature has no `credential=` parameter. Flows fired by cron resolve credentials normally inside their own steps via the existing `gh = github.client(credential="github_token")` extension constructor pattern.

## Deferred Ideas

Captured during discussion but belong to other phases or are out of scope:

- **General "labeled worker" abstraction.** User asked whether the cron-reconcile flag should be part of a generic worker-label system (`--label=reconciler`, etc.). Decision: NO — the existing `--cron-reconcile` boolean IS the label. No other v1.43 concerns need this pattern (HTTP receiver runs on every replica, dashboard is read-only, etc.). If a future phase introduces another single-replica-only responsibility, revisit.
- **In-process leader election for cron reconciliation.** Considered to coordinate hundreds of active-active replicas; rejected in favor of single-flag opt-in (D-7.2-10). Revisit if future phases bring more single-replica responsibilities and the coordination logic starts to amortize.
- **Backfill UX.** Temporal Schedules support `TriggerImmediately()` + `Backfill(start, end)`. Phase 7.2 does not surface these in `core.cron(...)`. Reader runs `temporal schedule backfill` manually if needed. Worth a docs note in Phase 7.2's walkthrough; productizing this could be a future phase.
- **Pause/resume schedules from the dashboard.** Phase 7.3's dashboard adds read-only views; pause/resume of cron Schedules is a future enhancement.
- **`core.cron` overlap policy auto-tuning based on flow durations.** If a cron schedule fires every hour and the flow takes 70 minutes, the overlap policy matters. Phase 7.2 ships `overlap="skip"` default + explicit kwarg; auto-tuning is out of scope.
- **Multiple ScheduleSpec calendar forms.** Temporal supports `CronExpressions`, `Calendars` (struct-based), and `Intervals`. Phase 7.2 ships `schedule=` as a 5-field POSIX string ONLY (single CronExpression). Calendar form + intervals are deferred.
- **`PauseOnFailure` policy.** Temporal `SchedulePolicies.PauseOnFailure` can auto-pause a Schedule if a recent workflow fails. Out of scope for Phase 7.2; reader can set this manually via `temporal schedule update`.
