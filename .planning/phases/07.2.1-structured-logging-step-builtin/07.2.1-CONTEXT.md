# Phase 7.2.1: Structured logging step builtin — Context

**Gathered:** 2026-05-11
**Status:** Ready for planning

<domain>
## Phase Boundary

Phase 7.2.1 delivers a first-class `log.<level>(...)` step type that replaces the `print() or {...}` workaround surfaced during Phase 7.2's UAT. Five concrete deliverables:

1. **`log` parser-time global with four attributes**: `log.info`, `log.warn`, `log.error`, `log.debug`. Each is a Starlark builtin that, when called inside a `flow(...)` `steps=[...]` list, returns a new `*dag.LogStep` node. Registration parallels `script`/`flow`/`step` in `newParseTimeGlobals` (`pkg/parser/globals.go`). The `log.fatal` attribute is explicitly out of scope (per roadmap — fatal semantics need workflow-cancellation design first).

2. **`*dag.LogStep` DAG node**: new sealed `Node` carrying `Pos`, `Level` (one of `"info"|"warn"|"error"|"debug"`), `Msg` (literal template), `MsgFn *CapturedLambda` (set when `${ctx.expr}` interpolation present, mirrors `script.IDFn`), and `AttrsLambdaID string` (resolves into `WorkflowInput.Lambdas`). Stable JSON marshaling; participates in the existing `dag.Node` seal.

3. **`pkg/interpreter/walk_log.go` walker**: mirrors `walk_script.go`. Evaluates `MsgFn` (or uses literal `Msg`), evaluates the attrs lambda if non-empty, builds a `[]any` slog-attr slice, routes through `workflow.GetLogger(ctx).<Level>(resolvedMsg, attrs...)` at the matching slog level. Wired into the `case *dag.LogStep:` arm of `i.walkNode` in `pkg/interpreter/workflow.go`.

4. **Human-mode CLI render extension**: the existing Bazel-style render handler (`pkg/cli/render.go`) gains two new behaviors — (a) SUPPRESS `kind=log` `event=step_dispatch`/`step_complete` records (don't draw the dispatch/complete pair) and (b) DECORATE the user-message record with a `[skytime/log]` prefix at render time. The `[N/M]` step counter excludes log steps from `M`.

5. **`weekly_digest.star` migration + broader corpus audit**: the existing `script(id="log_digest", fn=lambda ctx: print(...) or {"logged": True}, output_alias="_log")` block in `examples/http-github-webhook/weekly_digest.star` collapses to a single `log.info("weekly digest complete: scheduled=${ctx.scheduled_time} ...")` step. A grep-driven audit of `examples/`, `docs/`, and `pkg/parser/testdata/` migrates any other surviving `print() or {...}` shapes to `log.info`. `docs/walkthroughs/cron-schedules.md` updates to show the cleaner shape inline. `// skytime:doc` markers on the four `builtinLog*` factories regenerate `docs/reference/builtins.md` via the Phase 04.3 docgen.

**Out of scope (other phases, deferred, or explicitly rejected):**
- `log.fatal(...)` — roadmap-explicit deferral pending workflow-cancellation design.
- Removal or deprecation of `print()` — D3-22 routing (`[skytime/print]` → `workflow.GetLogger.Info`) STAYS as-is (D-7.2.1-09).
- A dedicated `docs/for-flow-authors/logging.md` page — auto-gen entries + walkthrough swap suffice for v1.
- A single `log(level="info", msg=...)` builtin — rejected in favor of attribute-style `log.<level>(...)` matching the roadmap text.
- Slog `Group` attrs for nested-dict attr values — flat `slog.Any` covers v1; revisit when tooling demand surfaces.

</domain>

<key_constraints>
## Load-Bearing Constraints (do not violate)

- **Replay safety is not optional.** `log.<level>` steps must produce IDENTICAL records on workflow replay (same constraint as `workflow.GetLogger` itself). The walker uses `workflow.GetLogger(ctx)`, NEVER `slog.Default()` or a captured logger; the msg lambda and attrs lambda evaluate against `lambdaTimeGlobals` (the locked 20-key set) so they're deterministic. Acceptance criterion #4 is verified via a `TestWorkflowEnvironment` replay test (3× `log.info` → exactly 3 records on replay).
- **No string compilation carve-out is preserved.** `${ctx.expr}` interpolation in the msg literal desugars to a `lambda ctx: ...` via the existing `desugarInterpolation` path (D4.1-22). No new runtime evaluation surface introduced. The attrs lambda is captured at parse time via the existing `captureLambda` machinery (Phase 1) — no special-case eval.
- **No I/O at parse time.** `log.<level>(...)` returns a `*dag.LogStep`; no slog records are emitted, no `workflow.GetLogger` calls happen, no extension `Initialize` runs at this surface (no extension owns `log` — it's a parser-time global, like `script`).
- **First positional msg must be a STRING LITERAL.** The `${ctx.expr}` desugarer operates on string literals (it needs the source bytes for the scan). `log.info(some_var)` or `log.info("a" + "b")` is rejected at parse time with `*dag.ParseError`. This is identical to how `script(id=...)` interpolation works.
- **`log.<level>` only legal as a step inside `flow(...)`.** Calling `log.<level>(...)` at module scope produces a position-aware `*dag.ParseError` mirroring how `step(...)` outside a flow is rejected. (Implementation: the builtin returns a `nodeWrap` value; module-scope evaluation tries to bind it to a name and fails the existing "node value at module scope" check.)
- **Walker emits structured slog events ALWAYS** — `step_dispatch` (kind=log) + the user message at the matching level + `step_complete` (kind=log). The HUMAN renderer suppresses the dispatch/complete pair; JSON-log mode emits everything. This split keeps both audiences happy: operators reading stdout get one extra line per fire; log-aggregator users get the full step graph.
- **`workflow.GetLogger(ctx)` only.** The walker never reaches into `slog.Default()`, never captures the SDK logger at construction time. Workflow replay safety hinges on this.
- **Determinism in attr ordering.** When converting the attrs lambda's returned Starlark dict to slog attrs, iterate via `*starlark.Dict.Items()` (insertion-order, per Phase 04.1 D4.1-14 precedent). This is deterministic by Starlark's language contract — NOT a Go map needing sort.

</key_constraints>

<decisions>
## Implementation Decisions

### Surface shape (Area 1: Argument shape)

- **D-7.2.1-01: Parser-time global `log` exposing four attributes.** `log.info`, `log.warn`, `log.error`, `log.debug` are the four user-facing surfaces. Registration: `newParseTimeGlobals` (`pkg/parser/globals.go`) adds `"log": <module>` where `<module>` is a `*starlarkstruct.Module` (or equivalent attribute-bearing value) carrying four `starlark.NewBuiltin` factories. No `log.fatal` per roadmap.
- **D-7.2.1-02: Call signature `log.<level>(msg, attrs=lambda ctx: dict)`.** First positional arg is the msg string literal (may carry `${ctx.expr}` interpolation). Optional `attrs=` kwarg is a `lambda ctx: dict` evaluated at workflow time against `lambdaTimeGlobals` + ctx (giving access to previous-step outputs via `ctx.<output_alias>`). No other kwargs in v1 (no `retry=`, no `timeout=` — log is a side-channel).
- **D-7.2.1-03: Empty msg ALLOWED.** `log.info("")` is legal; emits an empty slog message. Rationale: rare but occasionally useful for marker events when attrs carry the full payload.
- **D-7.2.1-04: Multi-line msg ALLOWED.** `log.info("""line one\nline two""")` works. The interpolation scanner already rejects multi-line INSIDE a `${...}` expression; the surrounding literal may span lines. No new validation rule needed.
- **D-7.2.1-05: Attrs-dict to slog attrs mapping.** When the attrs lambda returns a Starlark dict, iterate via `.Items()` (insertion order):
  - Scalar values (`starlark.String`, `starlark.Int`, `starlark.Float`, `starlark.Bool`) → typed slog attrs (`slog.String`, `slog.Int64`, `slog.Float64`, `slog.Bool`).
  - `starlark.None` → `slog.Any(key, nil)`.
  - Non-scalar values (lists, dicts, tuples) → `slog.Any(key, goValue)` after `bridge.FromStarlarkValue` conversion. The slog HANDLER decides rendering (JSON for json-log emits the structure natively; human renderer uses `fmt.Sprintf("%+v", v)`).
- **D-7.2.1-06: Reserved attr keys rejected at workflow time.** If the attrs dict contains any key in `{"level", "msg", "time", "source"}`, abort the workflow with `NonRetryableErr` carrying the attrs-lambda position and the offending key name. Prevents corrupting slog's standard fields.
- **D-7.2.1-07: Hard cap of 32 attrs per call.** If the attrs dict has >32 entries, abort with `NonRetryableErr` carrying the attrs-lambda position. Smaller than Phase 2's D2-07 block-size cap of 50 — log records are side-channels, not work primitives, and 32 covers any realistic operational use case while preventing accidental ctx-dumping.
- **D-7.2.1-08: Attr keys must match `^[a-zA-Z_][a-zA-Z0-9_]*$`.** Go-identifier shape. Reject at workflow time with `NonRetryableErr` carrying the offending key. Helps downstream log-analysis tools that expect identifier-shaped field names (Datadog, Loki, GCP Cloud Logging).

### print() builtin fate (Area 2)

- **D-7.2.1-09: `print()` STAYS AS-IS.** D3-22 routing through `workflow.GetLogger.Info` with `[skytime/print]` tag is PRESERVED unchanged. No deprecation, no removal, no warning. Rationale: `print()` is Starlark stdlib; removing it would create a non-portable dialect, and a one-line debug primitive is genuinely useful even when `log.info` exists.
- **D-7.2.1-10: `print()` remains usable INSIDE ANY lambda.** No scoping restriction. Script `fn=lambda ctx: print(...)`, step `action_fn=lambda ctx: print(...)`, etc. all continue to work. Phase 7.2.1 adds a parallel surface; it does not subtract.
- **D-7.2.1-11: Audit corpus + docs for surviving `print() or {...}` shapes.** Grep `examples/`, `docs/`, and `pkg/parser/testdata/` for the workaround. Migrate every occurrence to `log.info(...)`. Beyond `weekly_digest.star` (the known case), the planner identifies and rewrites any others. Pure `print()` calls inside lambdas — without the `or {...}` workaround — are NOT in migration scope (they're legitimate debug uses).

### Walker noise + tag (Area 3)

- **D-7.2.1-12: Walker emits THREE structured slog records per call.** `step_dispatch kind=log label=<id_or_pos>` → user message at matching slog level (Info/Warn/Error/Debug) → `step_complete kind=log status=ok|err duration_ms=N`. Emission happens regardless of human/json mode; the rendering layer decides what to show.
- **D-7.2.1-13: Human-mode CLI renderer SUPPRESSES `kind=log` dispatch/complete frames.** The Bazel-style step counter renderer in `pkg/cli/render.go` (or equivalent path — `buildRoutedSlogLoggerWithHandle` and its handler chain) recognizes `kind=log` events and silently drops dispatch/complete. The user-message record passes through, decorated with a `[skytime/log]` prefix at render time. Step counter `[N/M]` denominator EXCLUDES log steps. Per-fire impact: ONE extra line in stdout per log call.
- **D-7.2.1-14: JSON-log mode emits ALL THREE records verbatim.** The `--json-log` handler does NOT suppress `kind=log` dispatch/complete. Log-analysis tools see the full step graph (dispatch → user message → complete). The `[skytime/log]` prefix is a human-render decoration ONLY; the JSON `msg` field carries the raw user message (post-interpolation, post-attrs-lambda eval).
- **D-7.2.1-15: `kind="log"` on slog events.** Single discriminator, not `kind="log.<level>"` — the slog record's own `level=info/warn/error/debug` carries the level. Avoids redundancy and keeps downstream filter rules simple.
- **D-7.2.1-16: `log.<level>` is a SIDE-CHANNEL step in the author's mental model.** Documented in the auto-gen builtin description: does not advance human `[N/M]`; has its own kind=log slog frame for tooling. Failures inside the attrs lambda (eval error, reserved-key collision, >32 attrs, bad key shape) abort the workflow as `NonRetryableErr` carrying the attrs-lambda position. Msg-interpolation eval failures (rare since `${ctx.expr}` is validated at parse time, but possible if `ctx.x` is missing at runtime) also abort the same way.

### Validation + docs scope (Area 4)

- **D-7.2.1-17: First positional msg arg = STRING LITERAL only.** Reject `log.info(some_var)`, `log.info("a" + "b")`, `log.info(MSG)`, etc., at parse time via `*dag.ParseError`. The `${ctx.expr}` desugarer operates on literal source bytes; non-literals are out of scope. Acceptance criterion #1 reads literal as the expected form.
- **D-7.2.1-18: `log.<level>` at module scope is a parse-time error.** Calling `log.info(...)` outside any `flow(...)` `steps=[...]` produces `*dag.ParseError`: `"log.<level>: only valid as a step inside flow(...)"`. Same shape as `step(...)` outside a flow. Implementation note: the builtin returns a `nodeWrap` value; existing "node at module scope" checks reject it.
- **D-7.2.1-19: Docs = auto-gen markers + `cron-schedules.md` swap.** Add `// skytime:doc` markers (Phase 04.3 pattern) to `builtinLogInfo`, `builtinLogWarn`, `builtinLogError`, `builtinLogDebug` — running `go generate ./...` regenerates `docs/reference/builtins.md` with four new entries automatically. PLUS update `docs/walkthroughs/cron-schedules.md` to show the cleaner `log.info(...)` shape inline in the example fixture excerpt. NO new dedicated `docs/for-flow-authors/logging.md` page in this phase.
- **D-7.2.1-20: Test coverage (minimum acceptable set):**
  - **Parser unit tests** — 4 levels × {literal msg, interpolated msg, with attrs lambda, without attrs lambda} + rejection cases: non-literal msg arg, module-scope call, reserved attr key, >32 attrs, bad key shape (workflow-time rejections need walker tests for the latter three).
  - **Interpreter walker test** — uses `TestWorkflowEnvironment` to capture slog records; asserts each of the 4 levels routes to the matching slog Level; asserts attrs-lambda dict values land as slog attrs in insertion order.
  - **Replay-determinism test** — flow with 3× `log.info` calls; replay produces exactly 3 records (same constraint as `print()` replay test in Phase 3).
  - **`weekly_digest.star` regression smoke** — the existing `docs/walkthroughs/cron-schedules-smoke.sh` (Phase 7.2) continues to render the per-fire log line in `skytime server` stdout after the migration.

### Claude's Discretion

The planner has flexibility on:

- **DAG node name.** `*dag.LogStep` matches the existing naming convention (Script, IfCond, ForEachParallel, CallFlow are all suffix-laden); `*dag.Log` is shorter. Pick whichever reads consistently with the surrounding control.go types.
- **Builtin-factory layout.** Single `builtinLog` factory parameterized by level vs. four separate `builtinLogInfo` / `builtinLogWarn` / `builtinLogError` / `builtinLogDebug` factories. Recommendation: four separate factories — cleaner `// skytime:doc` rendering, simpler error messages (`"log.info: ..."` vs generic `"log: ..."`), no level-string handling at the call site.
- **`log` global construction shape.** `*starlarkstruct.Module` with four builtin attributes vs. a custom `starlark.HasAttrs` type. Recommendation: `*starlarkstruct.Module` for consistency with how extensions register their own namespaces (Phase 1 D-08).
- **Render-side suppression mechanism.** Hard-coded `kind=log` filter in the existing handler vs. a more general "step kinds to suppress" config. Recommendation: hard-coded filter — only one kind today; generalize when a second emerges.
- **Walker file placement.** `pkg/interpreter/walk_log.go` is the obvious mirror of `walk_script.go`. No other reasonable location.
- **Attr key validation site.** Walker-side (workflow time, NonRetryableErr) vs. attrs-lambda-eval boundary (immediately after dict materialization). Walker-side is simpler and matches the "validate at lambda boundary" pattern of script's `bridge.FromStarlarkValue` step. Recommendation: walker-side.
- **Exact slog level attr name.** `level=info` (lowercase) vs `level=INFO` (uppercase, slog's default `String()`). Slog's default works fine; no override needed.
- **`step_complete duration_ms` for log steps.** Always present (will typically be 0-1ms). No special-case.
- **`label` attr on dispatch/complete frames.** If `log.<level>` accepted an optional `id=` kwarg (it does NOT in v1), this would be the label. Without `id=`, use a synthetic label like `log:<level>:<pos_line>` or just the literal `log`. Claude's call; simplest is `log`.

None — no pending todos matched Phase 7.2.1 scope.

### Established Patterns

- **Sealed `dag.Node` types with stable JSON.** `LogStep` joins `Script`, `IfCond`, `ForEachParallel`, `CallFlow`. The `json:"-"` tag on `MsgFn` mirrors `Script.IDFn` (CapturedLambdas don't round-trip).
- **Walker emits `step_dispatch` + (work) + `step_complete` via `workflow.GetLogger(ctx)`.** The named-return + defer pattern in `walk_script.go` guarantees the complete event fires on every return path.
- **Replay-safe logging via `workflow.GetLogger(ctx)` only.** No `slog.Default()` in walker code; no SDK-logger capture at worker construction time.
- **Parse-time literal validation, workflow-time semantic validation.** The msg-must-be-literal check is parse-time (`*dag.ParseError`). The reserved-key / >32-attrs / key-shape checks are workflow-time (`NonRetryableErr`). Mirrors how `for_each_parallel` validates `items` (parse-time literal OR lambda) vs the inner lambda's return value (workflow-time).
- **Insertion-ordered dict iteration.** `*starlark.Dict.Items()` is deterministic by Starlark's language contract (Phase 04.1 D4.1-14 precedent). Walker iterates attrs in this order so slog attr order is stable across replays.

<deferred>
## Deferred Ideas

Captured during discussion but belong to other phases or are explicitly out of scope:

- **`log.fatal(...)` builtin.** Roadmap-explicit deferral — fatal semantics need workflow-cancellation design first. Revisit once a real customer use case lands ("I want this flow to abort hard, not raise NonRetryableErr").
- **Dedicated `docs/for-flow-authors/logging.md` page.** Auto-gen entries in `docs/reference/builtins.md` + cron-schedules walkthrough update suffice for v1. Promote to a dedicated guide if customer feedback shows the auto-gen reference doesn't answer "how do I log effectively in a flow."
- **`print()` deprecation or removal.** D-7.2.1-09 keeps it as-is. Future phase may revisit if customer demand emerges to clean up the surface; for v1.43 the cost (breaking changes, surprising to Starlark users) outweighs the benefit.
- **Level-colored prefix in human render.** `[skytime/log/info]` blue, `[skytime/log/warn]` yellow, `[skytime/log/error]` red, `[skytime/log/debug]` gray. Left to Claude's discretion at implementation time — the existing charm-log handler already does level-aware coloring, so this may come for free; if not, it's a polish item, not load-bearing.
- **Slog `Group` attrs for nested-dict attr values.** Phase 7.2.1 uses flat `slog.Any(key, goValue)` — handler decides rendering. `slog.Group` would be a more idiomatic structure for nested attrs but adds complexity (key flattening rules, group-name validation). Revisit when log-analysis tooling demand surfaces.
- **Single `log()` builtin with level kwarg** (e.g., `log(level="info", msg=...)`). Rejected in favor of attribute-style `log.<level>(...)` per roadmap text and matching the `slog.Info`/`Warn`/`Error`/`Debug` precedent.
- **`id=` kwarg on `log.<level>`** for explicit step labeling (parallel to `script(id=...)`). Not in v1 — log steps are side-channels; the literal msg + position are sufficient labels for tooling. Add if downstream log queries need explicit per-call IDs.
- **Auto-attached attrs from workflow context** (e.g., `workflow_id`, `run_id`, `flow_name` injected automatically into every log record). Out of scope — operators can grep Temporal's own workflow metadata; injecting these into every log would bloat records. Revisit if a customer asks.
- **Retry / timeout kwargs on log steps.** Log is a side-channel; failures are programmer errors (bad attrs lambda), not transient. No `retry=` / `timeout=` kwargs.
- **`*_test.star` integration with log assertions** (e.g., `assert.log_contains("digest complete")` in the Tier-3 test harness). Out of scope for this phase — testing-pattern surface lives in Phase 5; adding log-record assertions is a Phase 5.x follow-up, not 7.2.1.
- **Cross-corpus audit CI gate** (a CI test that fails if any `*.star` still uses `print() or {...}`). Considered as test-coverage option but de-scoped to keep Phase 7.2.1 focused; D-7.2.1-11 covers the audit as a one-time migration task, not an ongoing gate.
