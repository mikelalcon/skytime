## Area 1: Argument shape

### Q1 — What argument shape should `log.<level>(...)` accept in v1?

| Option | Description | Selected |
|--------|-------------|----------|
| Single string only | `log.info("msg ${ctx.x}")`. One positional string with `${ctx.expr}`. Simplest. (Recommended) | |
| String + kwargs as attrs | `log.info("msg", user_id=ctx.user_id, repo=ctx.repo)`. Kwargs become slog attrs. | ✓ |
| Single string + opt attrs dict | `log.info("msg", attrs={...})`. Reserved `attrs=` kwarg. | |

**User's choice:** String + kwargs as attrs
**Notes:** Picked the structured-attrs option; the call site can carry slog-style key/value pairs alongside the message.

### Q2 — If extra kwargs/attrs ARE supported, do their values evaluate against the same `lambdaTimeGlobals` (locked 20-key) env as the message-string interpolation?

| Option | Description | Selected |
|--------|-------------|----------|
| Same env | All values eval against `lambdaTimeGlobals`. Single contract; replay-safe. (Recommended) | |
| Static-only attrs | Attr values must be Starlark literals at parse time (no `ctx.x`). Cheapest; defeats most use cases. | |
| N/A — picked single string | (Skip if Q1 was Single string only.) | |

**User's free-text response:** "they should be able to access previous steps variables"
**Notes:** Clarified to mean: attr values must be evaluable against `ctx` at workflow time so they can read previous-step outputs (i.e., `ctx.<output_alias>`).

### Q3 — Should `log.<level>` require a non-empty literal message string at parse time?

| Option | Description | Selected |
|--------|-------------|----------|
| Require non-empty | Reject `log.info("")` at parse time. Empty messages are almost always bugs. (Recommended) | |
| Allow empty | Accept `log.info("")`. Minimal validation, occasional debug use case. | ✓ |

**User's choice:** Allow empty

### Q4 — Should the message string support multi-line literals (Starlark triple-quoted strings)?

| Option | Description | Selected |
|--------|-------------|----------|
| Allow multi-line | `log.info("""line1\nline2""")` works. Surrounding text can span lines. | ✓ |
| Single-line only | Reject triple-quoted/embedded-newline messages. Cleaner stdout. (Recommended) | |

**User's choice:** Allow multi-line

### Q5 (follow-up) — How should attr values defer evaluation to workflow time?

| Option | Description | Selected |
|--------|-------------|----------|
| Per-attr lambda | `log.info("msg", repo=lambda ctx: ctx.repo, count=lambda ctx: len(ctx.authors))`. Mirrors Phase 04.1 `action_fn=lambda ctx: ...` precedent. (Recommended) | |
| Single attrs= lambda | `log.info("msg", attrs=lambda ctx: {"repo": ctx.repo, "count": len(ctx.authors)})`. One reserved `attrs=` lambda returning a dict. | ✓ |
| All attrs as ${}-strings | `log.info("msg", repo="${ctx.repo}", count="${len(ctx.authors)}")`. Reuses desugarer; loses non-string types. | |

**User's choice:** Single attrs= lambda
**Notes:** Final call signature is `log.<level>(msg, attrs=lambda ctx: dict)`. One lambda per call; the dict carries all dynamic attrs.

### Q6 — How should non-scalar return values from the `attrs` lambda map to slog attrs?

| Option | Description | Selected |
|--------|-------------|----------|
| Auto-flatten / use slog.Any | Scalars become typed attrs; lists/dicts/None get `slog.Any` for native handler rendering. (Recommended) | ✓ |
| Strict scalars only | Reject non-scalar attr values with NonRetryableErr at workflow time. | |
| JSON-stringify non-scalars | Wrap any non-scalar in `json.Marshal` and emit as a string attr. | |

**User's choice:** Auto-flatten / use slog.Any

### Q7 — How should we handle attr-key collisions with slog's built-in fields?

| Option | Description | Selected |
|--------|-------------|----------|
| Reject at workflow time | NonRetryableErr if `attrs` returns a key in `{level, msg, time, source}`. (Recommended) | ✓ |
| Silently rename collisions | Prefix conflicting keys with `user_`. | |
| Allow / passthrough | Let user attrs shadow slog fields. | |

**User's choice:** Reject at workflow time

### Q8 — Should we cap the number of attrs per `log.<level>` call?

| Option | Description | Selected |
|--------|-------------|----------|
| Hard cap at 32 | Reject dicts with >32 keys at workflow time. (Recommended) | ✓ |
| No cap | Trust the author. | |

**User's choice:** Hard cap at 32

### Q9 — Should attr keys be validated as valid identifiers (snake_case, no spaces) at workflow time?

| Option | Description | Selected |
|--------|-------------|----------|
| Loose — any string OK | Slog accepts any string key; we don't add rules. (Recommended) | |
| Strict identifier-shaped | Reject keys that aren't `[a-zA-Z_][a-zA-Z0-9_]*`. | ✓ |

**User's choice:** Strict identifier-shaped

## Area 3: Walker noise + tag

The user requested a reframing of the original four-question batch to focus on operator/author impact rather than implementation choice. Re-presented as three preview-driven questions.

### Q1 — Pick the operator-stdout shape per cron fire of weekly_digest.star (4 work steps + 1 log line)

| Option | Description | Selected |
|--------|-------------|----------|
| Silent walker, no prefix | Walker emits only user's message at level. Counter stays at [N/4]. ~1 extra line per fire. (Recommended) | |
| Silent walker, [skytime/log] prefix | Same as above + prefix. Greppable in mixed stdout. ~1 extra line per fire. | ✓ |
| Full dispatch/complete + prefix | Walker emits dispatch+complete. [N/5] counter. ~3 extra lines per fire. | |

**User's choice:** Silent walker, [skytime/log] prefix

### Q2 — In `--json-log` mode (log aggregators / Datadog / Loki), pick which trade-off matters more

| Option | Description | Selected |
|--------|-------------|----------|
| Minimize record count | Silent walker = 1 JSON record per log call. (Recommended) | |
| Maximize step-graph fidelity | Full dispatch/complete = 3 JSON records per log call. Tools can reconstruct full step graph. | ✓ |

**User's choice:** Maximize step-graph fidelity
**Notes:** Resolves an apparent tension with Q1: the walker emits all three records ALWAYS; the human renderer suppresses dispatch/complete for `kind=log`; the json-log renderer passes everything through. The `[skytime/log]` prefix is human-render-only.

### Q3 — How does the chosen walker shape affect the .star author's mental model of `log.<level>`?

| Option | Description | Selected |
|--------|-------------|----------|
| Log is special: a side-channel | Author thinks: log doesn't show in [N/M], no dispatch/complete frame, failures abort as NonRetryableErr. (Recommended) | ✓ |
| Log is a regular step | Author thinks: log behaves like script. Consistent surface; encourages noisy logging. | |

**User's choice:** Log is special: a side-channel

## Claude's Discretion

The planner has flexibility on:
- DAG node name (`*dag.LogStep` vs `*dag.Log` — recommend the former for consistency).
- Builtin-factory layout (4 separate factories vs 1 parameterized — recommend 4 separate).
- `log` global construction shape (`*starlarkstruct.Module` vs custom `HasAttrs` — recommend Module).
- Render-side suppression mechanism (hard-coded `kind=log` filter — recommend hard-coded for now).
- Walker file placement (`pkg/interpreter/walk_log.go` is the obvious mirror).
- Attr key validation site (walker-side, NonRetryableErr — matches script's `bridge.FromStarlarkValue` pattern).
- Exact slog level attr name (default `String()` is fine).
- `step_complete duration_ms` for log steps (always present, typically 0-1ms).
- `label` attr on dispatch/complete frames (no `id=` kwarg in v1; use literal `"log"` or `log:<level>`).
