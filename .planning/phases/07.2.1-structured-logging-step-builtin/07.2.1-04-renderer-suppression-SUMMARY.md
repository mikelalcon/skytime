## Decisions Made

- **r.Attrs short-circuit over collectAttrs/attrMap allocation.** The decorator inspects records via the canonical `r.Attrs(func(slog.Attr) bool)` callback with a short-circuit boolean — when both `kind` and `event` keys are seen, iteration stops. This avoids allocating an attrMap per record (progressHandler's pattern) and is bounded by the small attr count on Skytime records (~10).
- ***slog.Logger.Handler() extraction over duplicating setupLogging's body.** Wrapping the existing setupLogging return preserves charm-log's debug-level, TTY-detection, ReportCaller, and ASCII-fallback wiring without code duplication; if those settings change in the future, the wrap path picks them up automatically.
- **Re-set slog.Default to the wrapped logger.** setupLogging had already set Default to the inner logger; the wrap re-set is required so indirect slog.Default() callers (parser warnings drained at boot per the legacy comment) flow through the filter — otherwise they'd bypass it.
- **renderStepComplete kind=log early-return BEFORE failureContext capture.** Document D-7.2.1-13's intent: log steps' bookend complete frames are noise, but if a future walker validation rejection (reserved key / >32 attrs) ever produces a complete frame with status=err, that error must NOT populate p.lastErr — the actual workflow-failing step (real script/step) must be the one renderFlowComplete attributes.
- **Synthetic test records over Plan 03 walker import.** Plan 04 is renderer-only and lands BEFORE walker construction in the same wave; tests construct slog records with literal `slog.String("kind", "log")` + `slog.String("event", "step_dispatch")` matching the documented walker contract. When Plan 03's walker ships, its emissions exercise the same code paths via integration tests in higher-level plans.
