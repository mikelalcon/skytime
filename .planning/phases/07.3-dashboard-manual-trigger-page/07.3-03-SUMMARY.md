# Phase 07.3 Plan 03: Events broadcaster + workflow poller Summary

Backend backbone for the dashboard's SSE channel — a single in-process broadcaster that fans out typed events to every connected browser, and a single workflow-status poller that hits Temporal's visibility API every 2s and publishes deltas. Browser count does not multiply Temporal load.

## Public API

```go
// pkg/cli/server/web/events/events.go
type Event struct {
    Name    string  // "snapshot" | "workflow_started" | "workflow_status_changed" | "workflow_replayed" | "delivery_received" | "shutdown"
```

## The Snapshot-Under-Lock Contract (Pitfall 1)

`Subscribe()` builds the Snapshot AND registers the subscriber channel inside the **same** broadcaster mutex acquire. This eliminates the race where a Publish could fire between snapshot-build and channel-attach, dropping an event that the new subscriber would otherwise have missed.

The contract is one-way: the SSE handler (Plan 04) MUST write the returned `Snapshot` as the first SSE frame and MUST NOT call a separate `Snapshot()` method afterward — doing so would reopen the race.

The unsubscribe closure is `sync.Once`-guarded (idempotent) and intentionally does **NOT** `close(ch)` — the fan-out goroutine owns the close, and the SSE handler selects on `<-ch` plus `ctx.Done`. Closing from unsubscribe would race the goroutine's own close on Shutdown.

## Drop-Oldest Fan-Out

| Knob                | Value | Rationale                                                                                                |
| ------------------- | ----- | -------------------------------------------------------------------------------------------------------- |
| `subscriberChanBuf` | 16    | Absorbs ~30 s of 2 s-poll deltas before drop-oldest kicks in (D-7.3-03 + Research Pattern 2)             |
| `publishChanBuf`    | 64    | Generous inbound buffer; Publish blocks only if producer outpaces fan-out for >64 events                 |
| Fan-out goroutines  | 1     | Single goroutine drains `publish` and forwards to all subscribers under broadcaster mutex                |

Drop-oldest semantics: when a subscriber's 16-deep buffer is full, the fan-out goroutine performs a non-blocking receive (drains the oldest queued event) and retries the send. If still full (impossible under normal load), the new event is dropped for that subscriber only — never blocks the goroutine.

`TestBroadcaster_DropOldest` proves the semantics: publish 17 events into a 16-deep buffer; assert the first drained event is `payload=1` (event 0 was dropped) and the last drained is `payload=16` (newest preserved). The test uses the `dispatched` channel barrier (`waitDispatched`) for deterministic fan-out synchronization — no `time.Sleep` (m1 from Phase 7.3 checker).

## The dispatched-Channel Test Seam (m1 fix)

`Broadcaster.dispatched` is a `chan struct{}` field that the fan-out goroutine non-blocking-sends to after each Publish has been forwarded to all subscribers. In production it is `nil` (no allocation cost beyond the field itself). Tests construct via `newTestBroadcaster(t, snap)` which installs the channel with a 64-deep buffer; `waitDispatched(t, b, n, deadline)` blocks until `n` fan-out completions are observed or the deadline fails the test.

This is the **only** synchronization the DropOldest test uses — no wall-clock `time.Sleep`, no race-prone timer reasoning. The signal is precisely "the fan-out goroutine has processed the publish you just made," which is exactly the precondition the test needs.

## Replay-Threshold Knob (Open Question 2)

Research Open Question 2 asked: what HistoryLength delta should trigger the `workflow_replayed` heuristic? Locked answer:

- Default: 50 (`DefaultReplayHistoryThreshold` exported constant)
- Tunable via `PollerConfig.ReplayHistoryThreshold` (`int64`)
- CLI flag `--replay-history-threshold` wires in Plan 04
- Best-effort heuristic (Research Pitfall 5): same workflow still `Status="running"`, HistoryLength delta > threshold ⇒ Publish `workflow_replayed` with `ReplayCount++`
- Replay counts preserved across no-delta and status-change ticks so the dashboard's running total persists

The fundamental difficulty is that `workflow.IsReplaying()` is authoritative but lives inside the workflow goroutine; from outside (via the visibility API) we only see `HistoryLength` snapshots. The threshold approach is documented as best-effort and the knob is exposed so operators can tune for their workflow shapes.
