## Wave 0 Requirements

Wave 0 creates failing-but-compiling test scaffolds for every requirement before any implementation tasks run. Each test imports the to-be-created packages and uses `t.Skip("Wave 0 stub")` so the suite compiles green but execution is gated.

- [ ] `pkg/cli/server/web/handlers_test.go` — integration paths for UI-01 / UI-02 / UI-03 (`TestDashboard_RendersWorkflowList`, `TestSSE_InitialSnapshot`, `TestTrigger_Success`, `TestTrigger_UnknownFlow`, `TestTrigger_BadJSON_DoesNotEchoInput`, `TestDashboard_FlowDropdown`)
- [ ] `pkg/cli/server/web/templates_test.go` — golden-file rendering check for the dashboard template (status badges, anchor `#wf-{id}` links, empty-state row, redacted header markers)
- [ ] `pkg/cli/server/web/events/broadcaster_test.go` — Subscribe/Publish race, drop-oldest semantics on bounded subscriber buffers, shutdown closes subscriber channels
- [ ] `pkg/cli/server/web/events/poller_test.go` — fake `client.Client` driving delta computation (`TestPoller_EmitsDeltas`, `TestPoller_ReplayHeuristic`)
- [ ] `pkg/cli/server/web/deliveries/buffer_test.go` — ring rollover at 100 entries, concurrent Append/Snapshot race-free under `-race`
- [ ] `pkg/cli/server/web/deliveries/redact_test.go` — header redaction matrix covering `Authorization`, `*secret*`, `*token*`, `*key*`, `*signature*` (case-insensitive substring)
- [ ] `pkg/cli/server/web/flowlaunch/launch_test.go` — `executeFlow` error mapping (`StatusOK` / `StatusDuplicate` via `errors.As(*serviceerror.WorkflowExecutionAlreadyStarted)` / `StatusDispatchFailed`)
- [ ] `tests/firewall_execute_workflow_test.go` — AST call-site count test (UI-04 success criterion #5)
- [ ] `tests/firewall_web_stdlib_test.go` — bans non-stdlib HTTP/template imports under `pkg/cli/server/web/`
- [ ] `tests/firewall_source_agnostic_test.go` — bans source-specific header names (`X-GitHub-Event`, `Stripe-Signature`, etc.) outside source-factory packages
- [ ] `docs/walkthroughs/dashboard.md` — manual UAT script: open browser → fire webhook (`gh webhook forward`) → see workflow + delivery rows → click delivery's mapped-workflow link → row flashes → click Run on manual trigger → new row appears within one SSE event

**Framework install:** None — Go stdlib `testing` and `github.com/stretchr/testify` already in `go.mod`.

## Manual-Only Verifications

| Behavior | Requirement | Why Manual | Test Instructions |
|----------|-------------|------------|-------------------|
| Dashboard visual feel (drop shadows, hover/focus, status-dot colors) | UI-01 / UI-02 / UI-03 | Subjective "slightly more polished" assertion (D-7.3-32); no automated visual-regression tool in scope | Open `http://localhost:8080/` after Wave N completes; eyeball status dots (blue/green/red/orange), hover states on table rows, panel drop shadows |
| Browser EventSource auto-reconnect after server restart | UI-01 | Requires real browser + server-restart timing; integration test only validates server-side close | Open dashboard; `pkill skytime`; restart `skytime server`; verify connection indicator returns to `● Connected` and new `snapshot` arrives without manual reload |
| `:target` flash animation when clicking a delivery's mapped-workflow link | UI-02 | CSS `@keyframes` + `:target` selector — no headless verification | Click a delivery row's mapped-workflow ID anchor; observe the matching workflow row scrolls into view and flashes for ~0.5s |
| Replay-detection heuristic (`HistoryLength` jump threshold) with real Temporal | UI-01 | Threshold (default 50) needs dev-test calibration against `temporal server start-dev` + restart-mid-workflow scenarios (Research Open Question 2) | Run a long workflow; restart worker mid-flight; verify dashboard shows `● Running (replayed N times)` once HistoryLength delta exceeds threshold |
