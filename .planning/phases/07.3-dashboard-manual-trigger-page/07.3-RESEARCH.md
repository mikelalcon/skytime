# Phase 7.3: Dashboard + manual trigger page - Research

**Researched:** 2026-05-12
**Domain:** Stdlib Go HTTP/SSE/html-template dashboard + Temporal visibility + receiver refactor
**Confidence:** HIGH (stack pins) / MEDIUM (replay-detection technique) / LOW (none — all uncertainties are flagged explicitly)

## Summary

This phase ships a stdlib-only HTML dashboard at `GET /` served by the existing `skytime server` HTTP mux. Three sections: live workflow list (Temporal `ListOpenWorkflow` + `ListClosedWorkflow`, deduped + sorted server-side), recent webhook deliveries (in-memory ring buffer last 100), and manual trigger form (flow dropdown + JSON textarea → `POST /api/trigger` → `client.ExecuteWorkflow`). Live updates travel over **Server-Sent Events** (`GET /api/events`, `text/event-stream`), driven by a single server-side workflow poller (≈2 s cadence) that fans out via a broadcaster so browser count does not multiply Temporal load. The phase also performs a critical refactor: extract `executeFlow(...)` from `pkg/extension/receiver/handler.go` so webhook ingress, manual trigger POST, and `skytime run` converge on one function (UI-04).

Strict stdlib lock holds end-to-end: `net/http`, `html/template`, `crypto/sha256`, `container/ring`/`sync` for the buffer, `time.Ticker` for the poller, `log/slog` for structured logging. No new third-party HTTP, template, or SSE libraries. A new firewall test bans non-stdlib HTTP/template imports under `pkg/cli/server/web/`.

**Primary recommendation:** Build the dashboard under `pkg/cli/server/web/` as a sibling package tree (`web/templates.go`, `web/handlers.go`, `web/events/`, `web/deliveries/`, `web/flowlaunch/`). Wire all three section data sources into a single `Broadcaster` driven by a single workflow-status poller plus delivery-buffer publish hook. Extract `executeFlow` into `pkg/cli/server/web/flowlaunch/launch.go` (NOT under `pkg/extension/receiver/`) so both the webhook ingress handler and the new `POST /api/trigger` handler import it without circularity. Treat replay detection as nice-to-have — detect via `WorkflowExecutionInfo.HistoryLength` jumps between successive poller snapshots; if the signal is noisy, render plain "Running" and document the fallback.

### Pattern 1: Stdlib SSE Handler (HIGH confidence — verified pattern)

```go
// Source: packagemain.tech canonical SSE pattern + W3C spec
// pkg/cli/server/web/handlers.go
func (h *Handlers) sseHandler(w http.ResponseWriter, r *http.Request) {
    // 1. Headers BEFORE first flush — order matters; status code locks once written.
    w.Header().Set("Content-Type", "text/event-stream")
    w.Header().Set("Cache-Control", "no-cache")
    w.Header().Set("Connection", "keep-alive")
    // Nginx / Cloudflare buffering disable — harmless when no proxy.
    w.Header().Set("X-Accel-Buffering", "no")

    // 2. Subscribe + ensure unsubscribe on return.
    ch, unsubscribe := h.broadcaster.Subscribe()
    defer unsubscribe()

    // 3. Send one snapshot event immediately. Snapshot is captured inside
    //    Subscribe so the broadcaster lock ensures no events are dropped
    //    between snapshot-build and channel-attach.
    snap := h.broadcaster.Snapshot()
    if err := writeEvent(w, "snapshot", snap); err != nil {
        return
    }

    // 4. Flush — required for the browser EventSource to start receiving.
    //    Cast pattern: not all ResponseWriters implement Flusher (e.g., test
    //    httptest.ResponseRecorder doesn't). Guard with type assertion.
    flusher, ok := w.(http.Flusher)
    if !ok {
        http.Error(w, "streaming unsupported", http.StatusInternalServerError)
        return
    }
    flusher.Flush()

    // 5. Stream loop. Two exit paths: client disconnect (r.Context().Done())
    //    and broadcaster shutdown (channel close on the receive side).
    for {
        select {
        case <-r.Context().Done():
            return
        case ev, ok := <-ch:
            if !ok {
                // Broadcaster shut down — write final event and return.
                _ = writeEvent(w, "shutdown", nil)
                flusher.Flush()
                return
            }
            if err := writeEvent(w, ev.Name, ev.Payload); err != nil {
                return // Client likely disconnected mid-write.
            }
            flusher.Flush()
        }
    }
}

// writeEvent writes a single SSE-framed event:
//
//   event: <name>
//   data: <json-encoded payload>
//   <blank line>
//
// W3C spec: each event ends with TWO consecutive newlines (\n\n). Fields
// within an event are separated by single newlines.
func writeEvent(w io.Writer, name string, payload any) error {
    var buf bytes.Buffer
    if name != "" {
        fmt.Fprintf(&buf, "event: %s\n", name)
    }
    body, err := json.Marshal(payload)
    if err != nil {
        return err
    }
    // SSE data: lines must each not contain \n. JSON marshaling of a struct
    // is single-line; if you ever embed pretty-printed JSON, split on \n
    // and prefix each line with "data: ".
    fmt.Fprintf(&buf, "data: %s\n\n", body)
    _, err = w.Write(buf.Bytes())
    return err
}
```

**Pitfalls handled:**
- `http.Flusher` cast — guard or panic; httptest.ResponseRecorder doesn't implement it.
- `X-Accel-Buffering: no` — nginx default-buffers SSE which breaks live updates; this header opts out. Harmless when no proxy is in front.
- Headers set BEFORE first body write — `WriteHeader` is called implicitly on first `Write`; once called, headers freeze.
- Client disconnect: `r.Context().Done()` fires on TCP close; SSE handlers MUST select on it to avoid goroutine leak.
- Browser auto-reconnect: `EventSource` reconnects automatically after error. Server doesn't need to handle this; just expect a fresh subscribe on each connection.

### Pattern 2: Broadcaster Fan-out (HIGH confidence)

```go
// Source: standard Go broker pattern (multiple references confirm)
// pkg/cli/server/web/events/broadcaster.go
package events

type Event struct {
    Name    string // SSE event name: "snapshot", "workflow_started", etc.
    Payload any    // JSON-encodable
}

type Broadcaster struct {
    mu          sync.Mutex
    subscribers map[chan Event]struct{}
    publish     chan Event
    quit        chan struct{}
    snapshot    func() Snapshot // Captured at construction; reads buffer + last workflows.
}

func New(snapshot func() Snapshot) *Broadcaster {
    b := &Broadcaster{
        subscribers: map[chan Event]struct{}{},
        publish:     make(chan Event, 64),
        quit:        make(chan struct{}),
        snapshot:    snapshot,
    }
    go b.run()
    return b
}

func (b *Broadcaster) run() {
    for {
        select {
        case <-b.quit:
            // Drain: close all subscriber channels, exit.
            b.mu.Lock()
            for ch := range b.subscribers {
                close(ch)
            }
            b.subscribers = nil
            b.mu.Unlock()
            return
        case ev := <-b.publish:
            b.mu.Lock()
            for ch := range b.subscribers {
                // Non-blocking send with drop-oldest semantics: if the
                // subscriber's 16-deep buffer is full, drop the oldest
                // (drain one, then send). Slow subscribers don't block
                // the fan-out goroutine.
                select {
                case ch <- ev:
                default:
                    select {
                    case <-ch: // discard oldest
                    default:
                    }
                    select {
                    case ch <- ev:
                    default: // still full — drop this event for this subscriber
                    }
                }
            }
            b.mu.Unlock()
        }
    }
}

func (b *Broadcaster) Subscribe() (<-chan Event, func()) {
    ch := make(chan Event, 16)
    b.mu.Lock()
    b.subscribers[ch] = struct{}{}
    b.mu.Unlock()
    unsubscribe := func() {
        b.mu.Lock()
        if _, ok := b.subscribers[ch]; ok {
            delete(b.subscribers, ch)
            // Don't close ch here — the SSE handler is the receiver;
            // closing would race with its select.
        }
        b.mu.Unlock()
    }
    return ch, unsubscribe
}

func (b *Broadcaster) Snapshot() Snapshot { return b.snapshot() }

func (b *Broadcaster) Publish(ev Event) {
    select {
    case b.publish <- ev:
    case <-b.quit:
    }
}

func (b *Broadcaster) Shutdown() { close(b.quit) }
```

**Why drop-oldest vs drop-newest:** With drop-oldest, the most recent state arrives at slow clients first (they get the fresh `workflow_status_changed` and miss the older transient). Drop-newest leaves stale state stuck in the buffer. Dashboard correctness favors freshness over completeness.

**Snapshot-on-Subscribe race:** Snapshot must be computed under the SAME lock that registers the subscriber. Otherwise an event published between snapshot-build and channel-attach is lost. The pattern above isn't quite right — the planner should either (a) compute snapshot inside `Subscribe()` while holding `mu`, or (b) have the poller publish the snapshot AS a fan-out event on every poll, accepting one ~2 s gap on first connect. **Recommendation:** (a) — atomically build snapshot + register the channel under the lock. Document this in the broadcaster.

### Pattern 3: Workflow-List Poller (HIGH confidence — Temporal SDK shape)

```go
// Source: pkg.go.dev/go.temporal.io/sdk/client + go.temporal.io/api/workflowservice/v1
// pkg/cli/server/web/events/poller.go
package events

func (p *Poller) Run(ctx context.Context) {
    ticker := time.NewTicker(2 * time.Second)
    defer ticker.Stop()
    var lastSnapshot map[string]workflowState // keyed by WorkflowID
    for {
        select {
        case <-ctx.Done():
            return
        case <-ticker.C:
            cur, err := p.fetch(ctx)
            if err != nil {
                p.logger.Warn("workflow poll failed", "err", err)
                continue // Don't crash — next tick retries.
            }
            // Compute deltas vs lastSnapshot.
            for id, w := range cur {
                prev, existed := lastSnapshot[id]
                switch {
                case !existed:
                    p.broadcaster.Publish(Event{Name: "workflow_started", Payload: w})
                case prev.Status != w.Status:
                    p.broadcaster.Publish(Event{Name: "workflow_status_changed", Payload: w})
                case w.Status == "running" && w.HistoryLength > prev.HistoryLength+historyJumpThreshold:
                    // Replay heuristic — see "Replay detection" research below.
                    p.broadcaster.Publish(Event{Name: "workflow_replayed", Payload: w})
                }
            }
            lastSnapshot = cur
        }
    }
}

func (p *Poller) fetch(ctx context.Context) (map[string]workflowState, error) {
    // 1. Open workflows.
    open, err := p.client.ListOpenWorkflow(ctx, &workflowservice.ListOpenWorkflowExecutionsRequest{
        Namespace:       p.namespace, // typically "default"
        MaximumPageSize: 100,         // Tune to expected load.
    })
    if err != nil {
        return nil, fmt.Errorf("list open: %w", err)
    }
    // 2. Closed workflows (last 100). Sorted by CloseTime desc by Temporal.
    closed, err := p.client.ListClosedWorkflow(ctx, &workflowservice.ListClosedWorkflowExecutionsRequest{
        Namespace:       p.namespace,
        MaximumPageSize: 100,
    })
    if err != nil {
        return nil, fmt.Errorf("list closed: %w", err)
    }
    // 3. Merge + dedupe by WorkflowID. A workflow can appear in both if it
    //    closed between the two calls — closed wins because it has the
    //    final Status.
    out := map[string]workflowState{}
    for _, e := range open.Executions {
        out[e.Execution.WorkflowId] = mapToState(e)
    }
    for _, e := range closed.Executions {
        out[e.Execution.WorkflowId] = mapToState(e) // overwrite open if duplicate
    }
    return out, nil
}
```

**Pagination:** `ListOpenWorkflow` / `ListClosedWorkflow` use a `NextPageToken` byte slice. For "last 100 closed + all open", one page each is sufficient (`MaximumPageSize: 100`). We do NOT need to paginate v1 — the buffer is bounded by D-7.3-12.

**Namespace:** Hardcode `"default"` in v1; expose `--temporal-namespace` flag later if customers need it. The Phase 7.1 `pkg/cli/server.go::connectClient` already manages namespace via `client.Options.Namespace`; the poller should read it from `cfg.namespace` (planner to add to `config`).

### Pattern 4: Concurrent Ring Buffer (HIGH confidence)

```go
// pkg/cli/server/web/deliveries/buffer.go
package deliveries

type Delivery struct {
    ID             string            // UUID-ish; assigned at append.
    ReceivedAt     time.Time
    Source         string            // "github.webhook" / "http.webhook" / etc.
    Method         string            // POST
    Path           string            // /webhook/github
    Headers        map[string]string // Already redacted by RedactHeaders helper.
    PayloadSummary string            // Compact ~200 char preview.
    PayloadFull    string            // Full body, also redacted if it ever contains secrets (currently no path leaks).
    Status         int               // HTTP response status.
    WorkflowIDs    []string          // Zero or more dispatched workflow IDs (fan-out).
    ErrorClass     string            // Receiver's errorClass field (matches handler.requestRecord.errorClass).
}

type RingBuffer struct {
    mu      sync.RWMutex
    items   []Delivery // pre-sized to cap.
    head    int        // next-write index, modulo cap.
    count   int        // number of valid entries (0..cap).
    cap     int
}

func NewRingBuffer(cap int) *RingBuffer {
    return &RingBuffer{items: make([]Delivery, cap), cap: cap}
}

func (b *RingBuffer) Append(d Delivery) {
    b.mu.Lock()
    b.items[b.head] = d
    b.head = (b.head + 1) % b.cap
    if b.count < b.cap {
        b.count++
    }
    b.mu.Unlock()
}

// Snapshot returns the last n deliveries (or all, if n > count), newest first.
func (b *RingBuffer) Snapshot(n int) []Delivery {
    b.mu.RLock()
    defer b.mu.RUnlock()
    if n > b.count {
        n = b.count
    }
    out := make([]Delivery, n)
    // Walk backward from head-1.
    idx := b.head - 1
    if idx < 0 {
        idx = b.cap - 1
    }
    for i := 0; i < n; i++ {
        out[i] = b.items[idx]
        idx--
        if idx < 0 {
            idx = b.cap - 1
        }
    }
    return out
}

func (b *RingBuffer) Len() int {
    b.mu.RLock()
    defer b.mu.RUnlock()
    return b.count
}
```

**Why not `container/ring`:** `container/ring` is a doubly-linked list of `*ring.Ring` nodes with `Value any`. Walking it requires repeated type-asserts and the per-node pointer overhead is wasteful for a fixed-size buffer. The slice-with-head-index is ~30 lines, lock-friendly, and amenable to JSON serialization in `Snapshot`.

**Ownership:** The buffer is constructed in `pkg/cli/server.go` boot, then passed BOTH to `receiver.Deps` (for the receiver to append after each delivery) AND to the dashboard handlers / broadcaster (for reads + `delivery_received` publish). This requires adding a `DeliveryBuffer` field to `receiver.Deps`.

### Pattern 5: Source-Agnostic Header Redaction (HIGH confidence — matches Phase 7.1 pattern)

```go
// pkg/cli/server/web/deliveries/redact.go
package deliveries

// Set of substring matchers for header names that MUST be redacted (D-7.3-19).
// Lower-cased lookup; case-insensitive because http.Header.Get already
// canonicalizes.
var redactSubstrings = []string{
    "authorization", "secret", "token", "key", "signature",
}

// RedactHeaders returns a NEW map[string]string with redaction applied.
// Multi-value headers are joined with ", " (rare in practice).
func RedactHeaders(h http.Header) map[string]string {
    out := map[string]string{}
    for name, vals := range h {
        lower := strings.ToLower(name)
        for _, m := range redactSubstrings {
            if strings.Contains(lower, m) {
                out[name] = "<redacted>"
                goto next
            }
        }
        out[name] = strings.Join(vals, ", ")
    next:
    }
    return out
}

// TruncateValue caps a header value at 80 chars with ellipsis (D-7.3-19).
func TruncateValue(v string) string {
    const max = 80
    if len(v) <= max {
        return v
    }
    return v[:max] + "…"
}
```

**Constraint match:** Phase 7.1 has a separate redaction pattern: `pkg/extension/receiver/handler.go::credentialBytes` deals with Secret-wrapped credentials (the `.Reveal()` boundary), and `tests/firewall_credential_redaction_test.go` is a Go-source-level firewall that bans `%+v` / `%#v` format verbs on credential-bearing types in five directories. Phase 7.3's header redaction is **plain string-content redaction at HTTP-receive time**, which is unrelated — but the firewall test should be extended to include `pkg/cli/server/web/deliveries/` so any future code in this dir is also gated against Secret-bearing struct format verbs. (Probably no Secret will ever live in `deliveries/` — but the firewall is cheap.)

**Source-agnostic:** No hardcoded `X-GitHub-Event` / `Stripe-Signature` etc. The matcher is purely substring-based on the header NAME, which generalizes across Slack (`X-Slack-Signature`), Stripe (`Stripe-Signature`), AWS SNS (`x-amz-sns-message-signature`), etc.

### Anti-Patterns to Avoid

- **Polling from the browser** — Defeats the whole point of SSE. Browser opens ONE `EventSource`; server-side single poller fans out.
- **Per-browser server-side poller** — Multiplies Temporal load by N browsers. Single poller, single broadcaster.
- **Snapshot computed outside the subscribe lock** — Race condition: events published between snapshot-build and channel-attach are lost. See "Pattern 2: Snapshot-on-Subscribe race" note above.
- **WriteHeader before subscribe** — If the broadcaster is full at subscribe time, you've already committed to streaming with no way to return 503. Subscribe FIRST, then send headers.
- **Storing `Secret` types in the ring buffer** — The buffer is JSON-serialized into SSE payloads. A Secret with a `String()` returning `<redacted>` is safe; a raw `[]byte` from `.Reveal()` would NOT be. Receiver code MUST NOT pass revealed secrets into the buffer (currently it doesn't; the only `.Reveal()` sites feed `validateHMAC` only).
- **Hardcoded `X-GitHub-Event` in the renderer (D-7.3-17 violation)** — Source-agnostic constraint. The renderer reads `Headers map[string]string` and `Source string`, not source-specific fields.
- **`template.HTML(...)` wrapping for user content** — Bypasses contextual escaping. The dashboard never trusts user content as HTML; payload summaries are inserted as plain text (auto-escaped).
- **Manual ExecuteWorkflow call outside `flowlaunch/`** — Defeats UI-04. The AST test is the firewall; the planner should add a comment to `flowlaunch/launch.go` documenting "the only production ExecuteWorkflow call site".
- **CSS in a separate file served as `/static/`** — Stdlib lock says "no bundler"; serving static assets adds mux complexity. Inline `<style>` block in the template stays under 100 lines per D-7.3-32.

## Common Pitfalls

### Pitfall 1: Snapshot-on-Subscribe Race
**What goes wrong:** A subscriber registers, then computes its snapshot, then sees events. Events published in the window between snapshot-build and registration are lost forever.
**Why it happens:** Naive `Subscribe()` implementations compute snapshot outside the mutex.
**How to avoid:** Hold the broadcaster mutex around BOTH "add channel to subscriber set" AND "build snapshot from current state". The poller's `lastSnapshot` and the buffer's current contents must be read under the same lock.
**Warning signs:** Flaky test where the first event after subscribe is missing; intermittent dashboard rows that "vanish" until next poll cycle.

### Pitfall 2: Nginx/Cloudflare SSE Buffering
**What goes wrong:** Deployed behind a proxy, SSE events accumulate in the proxy buffer and arrive in chunks (or never).
**Why it happens:** Nginx default-buffers responses; Cloudflare's free tier strips SSE compatibility on some plans.
**How to avoid:** Set `X-Accel-Buffering: no` header on the SSE response (nginx-specific opt-out). For Cloudflare, document that SSE works on paid plans + bypass cache. For v1 the dashboard is localhost-only so this is documentation-only.
**Warning signs:** Works on `localhost:8080`, breaks behind any production proxy.

### Pitfall 3: `http.Flusher` Type Assertion in Tests
**What goes wrong:** Unit test with `httptest.NewRecorder()` panics or silently fails — `*httptest.ResponseRecorder` does NOT implement `http.Flusher`.
**Why it happens:** Stdlib `httptest.ResponseRecorder` buffers everything and exposes the result after the handler returns; no streaming.
**How to avoid:** Type-assert with the `, ok :=` form and return a clean 500 if not OK. For tests that need real flushing, use `httptest.NewServer` (real TCP loopback) which gives a real `*http.response`. Most E2E SSE tests use `httptest.NewServer` + an `http.Client.Get` against the server URL.
**Warning signs:** Test panics with `interface conversion: *httptest.ResponseRecorder is not http.Flusher`.

### Pitfall 4: Workflow-List Polling Cost
**What goes wrong:** Every 2s, the dashboard polls Temporal. With many browsers connected (which we won't have, but) or many workflows (which we will eventually), this can spike Temporal visibility load.
**Why it happens:** Visibility APIs hit the secondary visibility store (ES or SQL backed), not the main workflow database. They're cheap but not free.
**How to avoid:** Single server-side poller (D-7.3-02), bounded `MaximumPageSize: 100`. Pin namespace. Don't paginate. If real load surfaces, exponential backoff on errors (start at 2s, double on consecutive failures up to 60s) — not in v1 unless customer feedback demands it.
**Warning signs:** Temporal log shows persistent visibility query traffic correlated with dashboard uptime.

### Pitfall 5: Replay-Detection False Positives (D-7.3-14)
**What goes wrong:** `HistoryLength` increments naturally as a workflow executes — every WorkflowTaskCompleted event adds a few entries. The "jump" heuristic can fire on normal progression.
**Why it happens:** Replay vs normal progression is genuinely hard to distinguish from outside the workflow. The SDK's `workflow.IsReplaying()` is the authoritative answer, but it's INSIDE the workflow goroutine; outside (in the visibility API), all you see is `HistoryLength` snapshots.
**How to avoid:** Treat as nice-to-have (D-7.3-14 already names this). Two viable techniques:
  1. **HistoryLength velocity** — count per-poll-cycle increment. If a single tick adds >50 events (a heuristic threshold for "workflow just resumed from an event-history replay after worker restart"), surface "replayed". Tune threshold via dev testing.
  2. **Worker restart correlation** — track the worker process start time; flag any workflow whose `HistoryLength` was nonzero before restart AND increments after restart. Requires the dashboard to know its own worker's start time, which it does (the poller starts post-worker-start).
**Recommendation:** Implement (1) with a configurable threshold defaulting to 50. If it proves noisy in dev testing, swap to (2) or fall back to plain "Running". **MEDIUM confidence on the technique — DOCUMENT in the plan that this is best-effort.**
**Warning signs:** Workflows oscillating between "Running" and "Replayed" status without an actual worker restart. Tune threshold upward.

### Pitfall 6: Ring Buffer Slot Reuse
**What goes wrong:** A `Delivery` struct stored in the ring buffer holds pointers / maps. Overwriting the slot with `b.items[b.head] = d` leaks the old delivery (GC handles it) — but if `Headers map[string]string` is shared with the caller, mutation post-append corrupts the stored view.
**Why it happens:** `Append(d Delivery)` takes by value but the map field is a reference type.
**How to avoid:** The redaction step `RedactHeaders` already returns a fresh map, so as long as `Append` is called with the redacted output (NOT the raw `r.Header`), there's no aliasing. Document this contract in `Append`'s doc comment.
**Warning signs:** Dashboard shows redacted headers on most rows but unredacted on a few — likely a code path that bypassed `RedactHeaders`.

### Pitfall 7: Manual Trigger Without Idempotency Causes Workflow Collisions
**What goes wrong:** User clicks Run twice rapidly. Both hit `/api/trigger` with the same flow + input. If workflow ID generation is `flow + timestamp(seconds)`, both produce the same ID and the second fails with `WorkflowExecutionAlreadyStarted`.
**Why it happens:** Coarse timestamp resolution.
**How to avoid:** Generate IDs from `crypto/rand` (16 random bytes → 32 hex chars). Format: `manual/<flow>/<hex>`. Collision probability is negligible.
**Warning signs:** Inline feedback shows `✗ workflow already started` on the second click despite no apparent dedup intent.

### Pitfall 8: SSE Long-Lived Connection vs `WriteTimeout`
**What goes wrong:** `pkg/cli/server.go:274` sets `WriteTimeout: 30 * time.Second` on the HTTP server. SSE connections live for hours; the WriteTimeout will close them every 30s.
**Why it happens:** HTTP server WriteTimeout is "max time between request and response" — for streaming, this kills the response after 30s regardless of activity.
**How to avoid:** Either (a) use `http.ResponseController(w).SetWriteDeadline(time.Time{})` inside the SSE handler to disable the deadline for THIS request, or (b) wrap the SSE handler in a `http.HandlerFunc` that calls `SetWriteDeadline` before each `Flush`. **Option (a)** is cleaner — single call at handler start. Requires Go 1.20+ which we have.
**Warning signs:** Browser SSE indicator flips to "Reconnecting" every 30s exactly.

### Pitfall 9: Template Reload During Hot Iteration
**What goes wrong:** Editing the dashboard template requires server restart to see changes. Slow dev loop.
**Why it happens:** `html/template` parses once at startup.
**How to avoid:** Defer — this is dev ergonomics, not a v1 feature. Document the restart-to-iterate workflow. If it becomes painful, add a `--dashboard-reload` debug flag that re-parses on every request (NEVER in production).
**Warning signs:** Slow dev iteration during template tweaks. Acceptable cost in v1.

### Pitfall 10: Secret Leak via JSON Error Messages
**What goes wrong:** `POST /api/trigger` returns `{"error": "invalid JSON: <user-supplied content>"}`. If a user pastes their secret-looking JSON into the textarea, the error response echoes it back. Browser dev tools show it.
**Why it happens:** Naive error formatting.
**How to avoid:** Return generic error strings: `{"error": "input is not valid JSON"}`. Log the detail server-side (slog with `slog.Default()`) but never echo to the client. Matches Phase 7.1's pattern of not leaking detail on 401.
**Warning signs:** Curl `POST /api/trigger` with a malformed body returns the literal body in the error.

package firewall_test

import (
    "go/ast"

    "os"

func TestExecuteWorkflow_CallSiteCount(t *testing.T) {
    moduleRoot := findModuleRootCLI(t)
    // Walk all production .go files under pkg/ and cmd/, count call sites
    // where the callee is "<ident>.ExecuteWorkflow" (a SelectorExpr inside a
    // CallExpr). Allowed sites: pkg/cli/server/web/flowlaunch/launch.go,
    // pkg/cli/run.go. Any other site is a regression.
    allowed := map[string]bool{
        "pkg/cli/server/web/flowlaunch/launch.go": true,
        "pkg/cli/run.go":                          true,
    }
    fset := token.NewFileSet()
    var violations []string
    filepath.Walk(moduleRoot, func(path string, info os.FileInfo, err error) error {
        if err != nil || info.IsDir() {
            return nil
        }
        if !strings.HasSuffix(path, ".go") || strings.HasSuffix(path, "_test.go") {
            return nil
        }
        rel, _ := filepath.Rel(moduleRoot, path)
        // Limit to production source under pkg/ and cmd/.
        if !strings.HasPrefix(rel, "pkg/") && !strings.HasPrefix(rel, "cmd/") {
            return nil
        }
        f, perr := parser.ParseFile(fset, path, nil, 0)
        if perr != nil {
            return perr
        }
        ast.Inspect(f, func(n ast.Node) bool {
            ce, ok := n.(*ast.CallExpr)
            if !ok {
                return true
            }
            sel, ok := ce.Fun.(*ast.SelectorExpr)
            if !ok {
                return true
            }
            if sel.Sel.Name != "ExecuteWorkflow" {
                return true
            }
            if !allowed[rel] {
                violations = append(violations, rel+":"+fset.Position(ce.Pos()).String())
            }
            return true
        })
        return nil
    })
    require.Empty(t, violations,
        "client.ExecuteWorkflow may only be called from %v; found extra call sites: %v",
        allowedKeys(allowed), violations)
}

// pkg/cli/server/web/handlers.go
type triggerReq struct {
    Flow  string         `json:"flow"`
    Input map[string]any `json:"input"`
}

type triggerResp struct {
    WorkflowID string `json:"workflow_id,omitempty"`
    Error      string `json:"error,omitempty"`
}

func (h *Handlers) trigger(w http.ResponseWriter, r *http.Request) {
    w.Header().Set("Content-Type", "application/json")
    if r.Method != http.MethodPost {
        h.writeTrigger(w, http.StatusMethodNotAllowed, triggerResp{Error: "method not allowed"})
        return
    }
    var req triggerReq
    if err := json.NewDecoder(io.LimitReader(r.Body, 1<<20)).Decode(&req); err != nil {
        h.writeTrigger(w, http.StatusBadRequest, triggerResp{Error: "input is not valid JSON"})
        return
    }
    if req.Flow == "" {
        h.writeTrigger(w, http.StatusBadRequest, triggerResp{Error: "flow name required"})
        return
    }
    contentHash, ok := h.flowRegistry.ContentHashFor(req.Flow)
    if !ok {
        h.writeTrigger(w, http.StatusBadRequest, triggerResp{Error: "flow not registered: " + req.Flow})
        return
    }
    // Fresh random workflow ID for manual triggers. crypto/rand is stdlib.
    var buf [16]byte
    if _, err := rand.Read(buf[:]); err != nil {
        h.writeTrigger(w, http.StatusInternalServerError, triggerResp{Error: "internal error"})
        return
    }
    wfid := "manual/" + req.Flow + "/" + hex.EncodeToString(buf[:])
    id, _, err := flowlaunch.Execute(
        r.Context(),
        h.client,
        h.taskQueue,
        req.Flow,
        contentHash,
        req.Input,
        flowlaunch.Options{
            WorkflowID:              wfid,
            ReusePolicy:             enumspb.WORKFLOW_ID_REUSE_POLICY_ALLOW_DUPLICATE,
            ErrorWhenAlreadyStarted: false,
        },
    )
    if err != nil {
        h.logger.Warn("manual trigger failed", "flow", req.Flow, "err", err)
        h.writeTrigger(w, http.StatusInternalServerError, triggerResp{Error: "dispatch failed"})
        return
    }
    h.writeTrigger(w, http.StatusOK, triggerResp{WorkflowID: id})
}

### Open Question 1: The "Third Call Site" for executeFlow (D-7.3-30)

**What we know:**
- D-7.3-30 states "Phase 7.2's cron-schedule callback path... must be updated to call `executeFlow` rather than calling `c.ExecuteWorkflow` directly."
- ROADMAP success criterion #5: "`executeFlow` is invoked from three call sites (webhook ingress, manual trigger POST, and cron via Temporal Schedule callbacks)."
- BUT: cron triggers do NOT use a Go callback. They are configured at reconcile time via `client.ScheduleClient.Create(...)` with `client.ScheduleWorkflowAction{Workflow: "SkytimeWorkflow", Args: []any{dag.WorkflowInput{...}}, TaskQueue: ...}`. Temporal SERVER fires the workflow on schedule — there is no Go process that calls `c.ExecuteWorkflow` for cron.
- Confirmed by reading `pkg/extension/schedules/schedules.go::scheduleOptionsFor` (lines 302-323): the only place where cron meets workflow dispatch is the `ScheduleAction` field on `ScheduleOptions`, and `Args: []interface{}{workflowInput}` — no Go-side ExecuteWorkflow call.

**What's unclear:** The CONTEXT.md decision and ROADMAP success criterion both assert a "third call site" that does not exist in code. There are two ways to reconcile:

1. **Interpret "call site" broadly:** `scheduleOptionsFor` IS the third call site — it's the function that decides "this trigger spawns this workflow with these args". We refactor `scheduleOptionsFor` to share a helper with `flowlaunch.Execute` that builds the `dag.WorkflowInput`. The shared bit is `buildWorkflowInput(flowName, contentHash, initState) dag.WorkflowInput` — trivial today (it's just `{FlowName, ContentHash, InitState}`) but the function exists as the seam.
2. **Add a real third Go call site:** Make `skytime run` also call `flowlaunch.Execute`. This gives three Go-side calls: webhook ingress, manual trigger POST, `skytime run`. Cron still goes through `ScheduleAction` but is documented as "the fourth path that intentionally bypasses `flowlaunch.Execute` because it's server-side". The AST test counts production sites: `flowlaunch.Execute` (1) + `pkg/cli/run.go` (1) = 2, with cron's Schedule registration documented as "out of scope for the call-site test because Temporal server fires those workflows".

**Recommendation:** Option (1) — extract `flowlaunch.BuildWorkflowInput(flowName, contentHash, initState)` as the SHARED seam used by both `flowlaunch.Execute` (for ingress + manual) and `pkg/extension/schedules/schedules.go::scheduleOptionsFor` (for cron). The "three call sites" then map cleanly:
- Webhook ingress → `flowlaunch.Execute(...)` → uses `BuildWorkflowInput`
- Manual trigger POST → `flowlaunch.Execute(...)` → uses `BuildWorkflowInput`
- Cron reconcile → `scheduleOptionsFor(...)` → uses `BuildWorkflowInput`

The AST test counts `c.ExecuteWorkflow(...)` call sites (2: `flowlaunch/launch.go` + `pkg/cli/run.go`) AND `BuildWorkflowInput(...)` call sites (3: `flowlaunch/launch.go`, `pkg/cli/run.go`, `pkg/extension/schedules/schedules.go`). This satisfies the spirit of UI-04 (single source of truth for "spawn a Skytime workflow input shape") without forcing the cron path into a fictitious callback.

**Planner action:** Confirm with the user during discussion-folding or in-plan, then pick (1) or (2). The current `BuildWorkflowInput` is a one-liner so even option (2) is fine if the user prefers "three Go call sites" literally.

### Open Question 3: Per-Browser Authentication & CSRF for `POST /api/trigger`

### Open Question 4: Where Does the Ring Buffer Live in the Dependency Graph?

**What we know:**
- Receiver appends after each delivery (in `pkg/extension/receiver/handler.go`).
- Dashboard handler reads in `pkg/cli/server/web/handlers.go`.
- Broadcaster's `delivery_received` publish hook fires after append.

**What's unclear:** Two viable seams:
- **(A)** Add `DeliveryBuffer *deliveries.RingBuffer` to `receiver.Deps`. Receiver writes; dashboard reads via the same struct passed in `pkg/cli/server.go`. Broadcaster's Publish is a separate handle wired in `pkg/cli/server.go` boot. Cleanest separation but adds a new field to `receiver.Deps`.
- **(B)** Wire the buffer via `cli.Options` (`cli.WithDeliveryBuffer(buf)`). Same plumbing, but adds an option. Useful if a custom binary wants to disable the buffer.

**Recommendation:** **(A)** — extend `receiver.Deps`. Always-on; matches existing pattern. The cost of "no opt-out" is negligible (100 entries × small structs = <100KB). Add a `// Optional — nil disables delivery recording` comment if we want to soften the requirement.

**Planner action:** Add field `DeliveryBuffer *deliveries.RingBuffer` to `receiver.Deps` (optional, nil-checked at append site).
