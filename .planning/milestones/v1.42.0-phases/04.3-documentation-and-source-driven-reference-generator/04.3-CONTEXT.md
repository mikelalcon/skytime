<decisions>
## Implementation Decisions

### Docs format and hosting

- **D-01:** Plain markdown in repo root + `docs/` tree. No static-site infra (mkdocs/docusaurus). GitHub renders out-of-the-box; readers see docs without building.
- **D-02:** README.md is mid-size with embedded tutorial (~500–800 lines target). Includes the full getting-started tutorial inline alongside what-it-is + links to deeper docs. Reader can evaluate the project without clicking through; docs/ owns reference depth.

### Directory structure and audience split

- **D-03:** Two top-level audience guides — `docs/for-flow-authors/` (Starlark consultants writing `.star` files) and `docs/for-extension-developers/` (Go developers building extensions). Reader picks the path on day one.
- **D-04:** No separate "two-tier authoring guide" page — the directory split itself communicates the audience choice. Each guide has its own README pointing into the relevant subset.

### Tutorial scope

- **D-05:** Getting-started tutorial = run-an-example smoke (5–10 min). Walkthrough: `git clone` → `skytime dev-server` (separate terminal) → `skytime run examples/skeleton/expression_if.star --flow check_user --input '{"user_id":"octocat"}'` → explain what just happened (interpolation, expression-mode `if_cond`, result binding, fail interpolation, downstream step). Reader walks away having seen Skytime work end-to-end.
- **D-06:** Tutorial lives at `docs/getting-started.md` (top of docs/ tree) and is also embedded verbatim into README.md (per D-02). Single source: tutorial file is canonical; README reproduces by reference (consider `<!-- include -->` markers if a future docgen phase wants to enforce parity, but for v1 a copy-edit is fine).

### Reference generator (`cmd/skytime-docgen`)

- **D-07:** Build the docgen tool in this phase (in-scope). Copybara-style source-driven generation for the Starlark builtins reference.
- **D-08:** Tool location: `cmd/skytime-docgen/` (sibling to `cmd/skytime/`). Standalone Go binary.
- **D-09:** AST walker targets `pkg/parser/builtins.go` and `pkg/parser/globals.go`. Detects builtin registrations via the canonical `starlark.NewBuiltin("name", p.builtinXxx)` pattern in `globals.go`; recovers each builtin's parameter names, types, and required-vs-optional status by parsing the `starlark.UnpackArgs("name", args, kwargs, "param", &target, ...)` call inside each `builtinXxx` function.
- **D-10:** Coverage v1 = the 8 Starlark builtins only — `flow`, `step`, `script`, `if_cond`, `result`, `fail`, `for_each_parallel`, `call_flow`. (`${ctx.expr}` interpolation is documented as part of the `step`/`flow`/`script` `name`/`id`/string-kwarg sections, not a standalone builtin.)
- **D-11:** Marker syntax = **block with key=value pairs** above each `builtinXxx` function:
  ```go
  // skytime:doc summary="Declares a workflow"
  // skytime:doc returns="none (parse-time DAG node)"
  // skytime:doc since="phase-01"
  // skytime:doc example="flow(name=\"check\", inputs={\"repo\":\"string\"}, steps=[...])"
  // skytime:doc see="step, script, if_cond"
  func (p *Parser) builtinFlow(...) ...
  ```
  Multi-line values supported via repeated `// skytime:doc` lines with the same key (joined with newlines). Quoted strings handle special characters. Easy to grep, parse, and write.
- **D-12:** Output = `docs/reference/builtins.md` — single page with one section per builtin, signature line, parameter table (name | type | required | description), summary prose, runnable example block, "See also" cross-links.
- **D-13:** Generated docs are **checked into the repo**. CI verifies drift: a job runs `skytime-docgen` and `git diff --exit-code docs/reference/`. PRs that change builtin signatures or markers must update generated reference.
- **D-14:** Add a `//go:generate skytime-docgen ./...` directive on the parser package so contributors can refresh via `go generate ./pkg/parser/`. CI runs the same command.

### Hand-written sections (everything docgen does not cover in v1)

- **D-15:** Architecture overview at `docs/architecture.md` — explains the parse/execute split, why Starlark sits at parse time and Temporal at execution time, the absolute boundary, lambda capture model, the registry-based deterministic re-parse on workflow start. Required reading for both audiences.
- **D-16:** CLI reference at `docs/cli.md` (or `docs/reference/cli.md` to keep `docs/reference/` together) — one page covering `skytime run`, `skytime validate`, `skytime info`, `skytime dev-server`. Mirrors `--help` output but with motivation, exit-code semantics, and link-back to relevant builtins/concepts. Hand-written until a future phase teaches docgen to walk cobra.
- **D-17:** Extension I/O reference at `docs/for-flow-authors/extensions/http.md` — bundled HTTP extension's operations, idempotence policy (D4-14: get/head=true; post/put/delete=false), credential handling, common patterns. Hand-written until a future phase teaches docgen to walk extension registrations.
- **D-18:** `examples/README.md` — indexes all skeleton fixtures with what each demonstrates: `simple_check.star` (Phase 4 baseline), `parallel_fanout.star` (Phase 4 for_each_parallel), `expression_if.star` (Phase 04.2 expression-mode if_cond). Each entry: one-line description, what features it exercises, how to run it.

### Phase scope boundary

- **D-19:** This phase covers documentation for what is built today (Phase 1 → 04.2 + quick tasks). Phase 5 (E2E test harness, `temporal_test`, `skytime test`) writes its own docs as part of its phase scope. No stub pages, no scaffolding.

### Claude's Discretion

- Exact prose voice/tone of narrative docs (recommend: pragmatic, code-forward, no marketing speak — match CLAUDE.md's existing tone)
- Choice of `docs/cli.md` vs `docs/reference/cli.md` (recommend: keep all reference under `docs/reference/`)
- Exact column shape of the parameter tables in generated reference (recommend: `Param | Type | Required | Default | Description` — drop Default if data isn't recoverable)
- Decision whether to pin docgen to use `go/parser` + `go/ast` stdlib (recommend yes, no third-party AST lib)
- README emoji density / use of GitHub Alerts blockquotes (recommend: minimal/none unless they meaningfully aid scanability)
- Where to host Mermaid/PlantUML architecture diagrams (recommend: ASCII art in `docs/architecture.md` for v1, no diagram tooling)

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets

- **Existing prose seed:** `pkg/parser/doc.go` already contains a runnable dual-`fail()` example added in Phase 04.2. The docgen tool can either consume it as a `// skytime:doc example=...` source OR leave it as additional prose; either works. Reference page should not duplicate it.
- **Registry pattern:** `pkg/parser/globals.go` uses `starlark.NewBuiltin("name", p.builtinXxx)` consistently — every builtin is reachable through this single map. Walker can enumerate this map deterministically.
- **`UnpackArgs` signature uniformity:** every builtin starts with `if err := starlark.UnpackArgs("<name>", args, kwargs, "<key>", &target, ...)`. Parameter metadata is recoverable purely from this call.
- **Existing CLI patterns:** `pkg/cli/info.go` (lipgloss bordered table) and `pkg/cli/validate.go` show how to wire a new cobra subcommand. `cmd/skytime-docgen` is a separate binary, NOT a `skytime` subcommand — keep it isolated.

### Established Patterns

- **Library-root firewall:** `tests/firewall_cli_test.go` already enforces that `cobra`/`charm-log`/`lipgloss` are reachable only from `{cmd/skytime, pkg/cli}`. The new `cmd/skytime-docgen` binary may need its own allow-list entry (it can use cobra/colored output without leaking to the library root). Plan must extend the firewall.
- **Directory-relative reference resolution:** parser already walks `.git`-ancestor up; docgen should accept either a directory path or a list of files via flags. Match the convention in `validate`/`run` for path handling.
- **No third-party AST/template libs:** the project's `What NOT to Use` list (CLAUDE.md) is strict. Docgen sticks to `go/ast` + `go/doc` + `text/template` stdlib.

### Integration Points

- **`docs/reference/` directory** — new; created by docgen on first run. CI must verify the directory's contents match a fresh run.
- **`go:generate` directive** in `pkg/parser/builtins.go` (or its own file) so `go generate ./pkg/parser/` refreshes docs.
- **README links into `docs/`** — relative links so they work both on GitHub and in `pkg.go.dev` view of the package.

</code_context>

<specifics>
## Specific Ideas

- The `skytime info` subcommand (just shipped in quick task 260504-k9c) is itself a discoverability tool that complements the docs. Reference docs should mention it as the runtime equivalent of the auto-generated reference: "to see what flows a `.star` file declares, run `skytime info <file>`".
- The README's 30-second quickstart should target a reader who has Go installed but no Temporal background. Walk them: install → spin up dev-server → run a demo flow → see the colored progress output.
- Architecture doc should include the boundary diagram (ASCII): user .star file → parser → DAG → Temporal SDK → workflow.Go → activity.GetInfo → extension I/O. Critical to make the parse/execute split visceral.
- The docgen output should look as good as the input source. Generated tables should use the same em-dash convention for empty fields as `skytime info` does (consistency).
- A pleasant DX touch: `skytime info --help` should mention `docs/getting-started.md` so users hitting `--help` get pointed at the tutorial.

</specifics>
