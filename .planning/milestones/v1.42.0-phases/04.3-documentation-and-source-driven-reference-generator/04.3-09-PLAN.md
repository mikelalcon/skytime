> You write `.star` files specialized per customer. You compose
> extensions, write lambdas, define flows. You don't touch Go (mostly).

## Start Here

## Reference Material

- **[CLI Reference](../reference/cli.md)** — `skytime run`, `validate`,
  `info`, `dev-server` flag tables and exit codes
- **[Examples](../../examples/README.md)** — runnable .star fixtures with
  feature checklists
- **[Bundled HTTP Extension](extensions/http.md)** — the one extension
  that ships with `skytime` out of the box

## Common Tasks

- **Run a flow against the dev server** — see [Getting Started](../getting-started.md)
- **Validate without running** — `skytime validate <file.star>` ([cli ref](../reference/cli.md#skytime-validate))
- **Discover what's in a .star file** — `skytime info <file.star>` ([cli ref](../reference/cli.md#skytime-info))
- **Connect to Temporal Cloud / self-hosted** — see [skytime run variants](../reference/cli.md#skytime-run)
- **Build a binary with custom extensions** — that's the OTHER audience; see [docs/cli-binary.md](../cli-binary.md) anyway, or hand it to your Go-side teammate ([for extension developers](../for-extension-developers/README.md))

## What You Cannot Do (and Why)

- **No string-based expressions** (CEL, Jinja, JSONPath) — see [no string compilation](../architecture.md#no-string-compilation)
- **No native goroutines** in lambdas — only Temporal-deterministic primitives; see [no context bleed](../architecture.md#no-context-bleed)
- **No I/O at parse time** — your .star file is pure data; I/O happens through registered extensions

## Building Extensions Yourself?

If you need an extension that doesn't exist yet (Slack, internal API,
AWS, etc.), you'll cross over to the other tier briefly:

→ [For Extension Developers](../for-extension-developers/README.md)

Many flow-author teams pair with a Go-side teammate who builds
extensions; this is the **two-tier authoring model** in action.

```
# For Extension Developers

> You write Go extensions — typed I/O wrappers that wrap real services
> (HTTP, GitHub, Slack, internal APIs). Your work is reusable across
> customers; consultants compose your extensions in `.star` files.

## Start Here

1. **[Skytime Architecture](../architecture.md)** — required reading
   for both audiences. The constraints on extensions (no
   `go.temporal.io/sdk/activity` import, no `workflow.Context` access)
   come from the parse/execute split.
2. **[Extension SDK source](../../pkg/extension/extension.go)** — the
   `Extension` interface (`Name`, `Initialize`, `Operations`) is the
   contract you implement. Read it; it's small and well-commented.
3. **[Bundled HTTP Extension](../../pkg/extension/builtin/http/http.go)**
   — the canonical reference implementation. Read this end-to-end
   before writing your own.

## Reference Material

- **[Custom CLI Guide](../cli-binary.md)** — wiring your extension
  into a standalone `skytime`-compatible binary via
  `cli.NewRootCommand(WithExtensions(...), WithCredentialHandler(...))`
- **[Bundled HTTP Extension Reference](../for-flow-authors/extensions/http.md)**
  — what flow-authors see; useful so you understand the consumer
  perspective before designing your own surface
- **[CLI Reference](../reference/cli.md)** — exit-code semantics,
  Starlark-first error rendering (your extension errors flow through
  this path)

## Hard Rules (architecture firewall)

The library enforces these via AST-walking firewall tests under
[`tests/`](../../tests/) and [`pkg/activity/firewall_test.go`](../../pkg/activity/firewall_test.go):

- **No `import "go.temporal.io/sdk/activity"`** in your extension
  package. Extensions are plain Go; the single generic `ExecuteBatch`
  activity dispatches them.
- **`OperationFunc` takes `context.Context`, not `workflow.Context`**.
  No `workflow.GetInfo`, no `workflow.NewTimer`, none of that.
- **`Idempotent *bool`** is REQUIRED on every `OperationSpec` (a
  `*bool` so you can't forget — `nil` = registration error).
- **`Credential` values come in as parameters**, never returned. The
  resolver runs JIT inside the activity stack frame.

## Building Your First Extension

Mirror the structure of `pkg/extension/builtin/http/http.go`:

1. Define your operation kwargs as Go structs with `star:"name,required?"` tags
2. Implement `Operations() map[string]*extension.OperationSpec`
3. Implement `Initialize(thread, kwargs) starlark.Value` returning a
   `*starlarkstruct.Module` of operation factories
4. Wire into your CLI binary via `cli.WithExtensions(myExt.New())`

See [docs/cli-binary.md](../cli-binary.md) for the full wiring example.

## Writing Flows Against Your Extension?

If you want to use extensions you (or others) have built, that's the
flow-author tier:

→ [For Flow Authors](../for-flow-authors/README.md)

The two tiers are separated by the parse/execute boundary — your Go
code runs at parse time (registering operations) and inside the
single generic activity (executing operations); the Starlark side
never sees Go beyond the typed kwargs/output shapes.
```
