# Phase 04.1 Plan 06: Live Progress Block Renderer Summary

Multi-line live progress block in `pkg/cli` — single render goroutine + 10-frame braille spinner at 100 ms cadence + cursor-up/clear-line ANSI redraw + 10-row truncation; deactivates on `--verbose`, non-TTY, and Windows builds.

## What Was Built

### Task 1 — refactor: extract static path + introduce mode selection (commits `168c5fc`, `41ad5c3`)

Split `pkg/cli/progress.go` into platform-agnostic core + extracted static-path renderers, set up the live-block scaffolding.

- **`pkg/cli/progress_static.go` (new, 241 LOC)** — moved `renderFlowStart` / `renderStepDispatch` / `renderStepComplete` / `renderBranch` / `renderFlowComplete` + helpers (`computeCounter`, `isNestedPath`, `padKind`, `printlnTo`, `println`) + ANSI color helpers (`colorBanner`, `colorCounter`, …). All functions remain methods on `*progressHandler` — pure organizational split, zero behavior change.
- **`pkg/cli/progress.go` (rewritten, 432 LOC)** — handler shape, `progressEvent` value struct (no build tag — shared between platforms per W12), `progressHandlerOptions{Verbose, ForceTTY}` constructor option, `newProgressHandlerWithOptions`, `useLiveBlock()` mode selector, `Close()` lifecycle hook, `Handle()` dispatch, lazy `liveRenderer` construction via `sync.Once`, `buildProgressEvent` translator, `attrMap` + `collectAttrs` + `hasAttr`, cached `isTTY()`. Task 1 left `Handle()` routing through the static path only — Task 3 flips the dispatch to honor `useLiveBlock()`.
- **`pkg/cli/progress_live.go` + `progress_live_windows.go` (new stubs)** — minimal `liveRenderer{out}` shape so the package compiles before Task 2 fills in the real implementation. Build tags `//go:build !windows` and `//go:build windows`.
- **`pkg/cli/render.go`** — `buildRoutedSlogLogger` now uses `newProgressHandlerWithOptions` and threads `cfg.Verbose` so the live block (when wired in Task 3) deactivates per D4.1-20.

Tests added (4): `TestProgress_StaticPath_NonTTY`, `TestProgress_StaticPath_VerboseEvenOnTTY`, `TestProgress_LivePathChosen_TTYNonVerbose` (t.Skip'd, un-skipped in Task 3), `TestNewProgressHandler_AcceptsVerboseFlag`.

### Task 2 — feat: live-block render goroutine + spinner + truncation, Unix only (commits `201f275`, `0912fb7`)

Replaced the `progress_live.go` stub with the real implementation per D4.1-17/18/19 + RESEARCH §Pattern 5.

- **`pkg/cli/progress_live.go` (256 LOC)** — `//go:build !windows`. Locked 10-frame braille spinner (`⠋⠙⠹⠸⠼⠴⠦⠧⠇⠏`); `liveRenderer` with single render goroutine, 100 ms `time.Ticker`, buffered events chan (size 64), `sync.Once` Close idempotency. The goroutine handles `flow_start` / `step_dispatch` / `step_complete` / `branch` / `flow_complete` / `raw` events: dispatches print as **static lines above the redraw region**, dispatches add to the active list, completions remove from active and print the static `[N/M] step ✓ Xms summary` line. The `redraw()` method clears `r.drawnLines` lines (cursor-up + clear-line) then re-emits header + ≤10 active rows + `... and N more` truncation line when applicable. `Close()` drains, restores cursor (`\x1b[?25h`).
- **`pkg/cli/progress_live_windows.go`** — kept as no-op stub.
- **`submit()` close-race handling** — checks `r.closed` first (fast path), then under a `defer recover()` does the send. Recover catches the rare panic when the events channel is closed concurrently with a send. Documented Go idiom for goroutine-isolated state without a global submit mutex.

Tests added (7): `TestLiveBlock_AnsiSequencesEmitted`, `TestLiveBlock_SpinnerCadence` (≥3 distinct frames in 450 ms), `TestLiveBlock_TruncationAtTen` (12 events → "... and 2 more"), `TestLiveBlock_FinalizeRow`, `TestLiveBlock_FlushFinal`, `TestLiveBlock_FailedStepRendersX`, `TestLiveBlock_NoFlickerOnRapidEvents` (cursor-up count ≤ 77 over 5 events). Plus `pkg/cli/progress_testutil_test.go` — `safeBuffer` (mutex-wrapped bytes.Buffer for the test reads concurrent with goroutine writes) and `stripAnsiTest` helpers (no build tag, shared cross-platform).

### Task 3 — feat: wire live renderer into Handle() + cli Close (commits `270f226`, `aeea550`)

Flipped `Handle()` dispatch to honor `useLiveBlock()` and threaded `handler.Close()` through the run subcommand.

- **`pkg/cli/progress.go`** — `Handle()` now branches on `useLiveBlock()`. TTY + non-verbose → lazy-construct `liveRenderer` via `sync.Once` and `submit(buildProgressEvent(r))`. Otherwise → `renderBazelLine(r)` (the static path).
- **`pkg/cli/render.go`** — added `buildRoutedSlogLoggerWithHandle` that returns both `*slog.Logger` AND the underlying `*progressHandler`. The bare `buildRoutedSlogLogger` is preserved for existing tests.
- **`pkg/cli/run.go`** — captures the handler, `defer progHandler.Close()` after the workflow run completes (or is canceled). Static-mode handlers' Close is a no-op (`p.live == nil`).

Tests added (4): un-skipped `TestProgress_LivePathChosen_TTYNonVerbose`; new `TestProgress_LiveBlock_DrainsOnFlowComplete`, `TestProgress_LiveBlock_VerboseRemainsStatic`, `TestProgress_LiveBlock_LifecycleNoLeak` (Close returns within 2 s).

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 — Test bug] Truncation test expectation relaxed**
- **Found during:** Task 2 GREEN.
- **Issue:** `TestLiveBlock_TruncationAtTen` originally asserted `"... and 2 more"` appeared **exactly once**. Reality: the renderer emits `redraw()` after every event AND every 100 ms tick; once the active count saturates at 12, every redraw of the saturated state emits one truncation line. Within the 200 ms test window the test saw 2 occurrences (one from event-driven redraw, one from a tick coincident with the saturation point).
- **Fix:** Changed assertion to `Contains` (≥1 occurrence) and added defensive `NotContains "... and 0 more"` / `... and -` to catch off-by-one regressions. The load-bearing property is "truncation engaged when active > cap" (D4.1-19), not the redraw count — which is intentionally bounded by the spinner ticker, not by deduplication.
- **Files modified:** `pkg/cli/progress_live_test.go`
- **Commit:** `0912fb7`

**2. [Rule 2 — Concurrency safety] safeBuffer wrapper around bytes.Buffer**
- **Found during:** Task 2 GREEN — `bytes.Buffer` is not safe for concurrent use, but tests need to read the buffer between submit() calls while the render goroutine writes.
- **Fix:** Added `safeBuffer{mu sync.Mutex, buf bytes.Buffer}` test helper in `pkg/cli/progress_testutil_test.go` (no build tag — shared between live-only test files and platform-agnostic dispatch tests). All live-block tests use `safeBuffer` instead of raw `bytes.Buffer`.
- **Commit:** included in Task 2 RED commit `201f275`.

**3. [Rule 1 — Test design correction] Verbose+TTY test wording**
- **Found during:** Task 1 GREEN (tests ran).
- **Issue:** First-pass `TestProgress_StaticPath_VerboseEvenOnTTY` asserted no ANSI sequences at all — but the static path on a TTY still wraps `[skytime]`, `[N/M]`, `kind` in color ANSI codes (existing Phase 4 behavior). The verbose preemption rule applies to LIVE-BLOCK ANSI (`\x1b[1A`, `\x1b[2K`, `\x1b[?25l`), not to color escapes.
- **Fix:** Test asserts absence of the load-bearing live-block sequences only, plus presence of plaintext substrings (`flow test_flow`, `1 steps  starting`).
- **Files modified:** `pkg/cli/progress_test.go`
- **Commit:** `41ad5c3`
