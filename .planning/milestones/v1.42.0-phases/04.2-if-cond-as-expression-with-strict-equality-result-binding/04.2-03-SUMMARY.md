## Decisions Made

- **Cases 4-5 implemented in Task 1, not deferred to Task 2 as the plan suggested** — the existing Wave-0 RED tests (TestValidateIfCondExpressionShape_KeysMismatch / TypeMismatch_NoLUB / OneSideOpaqueDefers) require the full implementation. Stubbing `compareResultBranches` in Task 1 would have left those RED at Task 1 commit boundary, violating the test-first contract. Task 2 became pure test-body addition (9 tests + table-driven fixture parses) — appropriate scope split.
- **Defensive Opaque fallback in reinferResultTypes for every failure mode** (missing BodyPos, missing fileBytes entry, parse error, no lambda found) — surfacing internal-state errors as user errors would be a UX regression. Falling back to TypeOpaque means the validator defers, which is the correct semantics when re-inference cannot proceed. Matches plan 02's compile-fallback for opaque value lambdas.
- **Orphan-Result detector folded into walkValidateIfCondExpression's case *dag.Result** — the placement gate (plan 02) catches top-level result() and procedural-mode-branch result(); this validator's walker catches any *dag.Result reaching the orphan case (i.e., not stripped by walkBranchSkippingLastResultOrFail's last-position skip). Two layers, one error message, deterministic.
- **Branch-schema seeding via seedStateSchemaForFlow extracted as shared helper** — both validateLambdaCtxAccesses and validateIfCondExpressionShape need the same seed (flow.Inputs typed via typeFromHint). DRY consolidation; eliminates the inline loop in validateLambdaCtxAccesses; single source of truth for finalize-pass schema seeding.
- **Schema accumulation across nodes (script.OutputAlias addUntyped) intentionally mirrors D4-02 walker exactly** — the validator inherits the same visibility-stacking semantics so the per-branch state schema at the if_cond reflects everything upstream (inputs + script outputs + item-vars). Per-branch fork still uses clone() so branch-local additions don't leak into the sibling.
