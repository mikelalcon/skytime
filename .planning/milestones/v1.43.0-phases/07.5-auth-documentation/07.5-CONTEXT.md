<decisions>
## Implementation Decisions

### Snippet shape

- **D-7.5-01 — Drop-in function snippets.** Each snippet is a complete Go function (e.g., `func newGCPCredentials(ctx context.Context, projectID, secretName string) (client.Credentials, error)`) with full body, error handling, and imports listed at top. Reader pastes into their own package and calls from `main()`. Compilable on its own.

- **D-7.5-02 — Function params take config; calling-site uses env vars.** Function signatures take config values explicitly (e.g., `projectID, secretName string`). The prose around the snippet shows the calling-site pattern: `creds, err := newGCPCredentials(ctx, os.Getenv("GCP_PROJECT_ID"), os.Getenv("TEMPORAL_API_KEY_SECRET"))`. Reader can wire any config layer they want; the snippet itself doesn't lock in env-var-driven config.

- **D-7.5-03 — Full Go-idiomatic error wrapping.** Every error path returns `fmt.Errorf("descriptive context: %w", err)`. Real error chain. Reader sees production-quality code; can paste verbatim.

- **D-7.5-04 — Per-snippet inline preamble (Assumes + Substitute bullet lists).** Each section opens with two short bullet lists immediately before the snippet:

  ```markdown
  **Assumes:**
  - You have a Temporal Cloud namespace with API key auth enabled
  - Your GCP service account has roles/secretmanager.secretAccessor on the secret
  - WIF is configured for your workload (see [GCP docs](...))

  **Substitute:**
  - `projectID` — your GCP project ID
  - `secretName` — the Secret Manager secret holding the Temporal API key
  ```

  Reader sees prerequisites without scrolling.

### CI verification + SDK dependency scope

- **D-7.5-05 — Parallel snippet files are source of truth; markdown excerpts them.** Layout:

  ```
  docs/for-extension-developers/
    temporal-auth.md          # the doc readers see
    snippets/
      go.mod                  # cloud SDK deps live here
      go.sum
      gcp.go                  # newGCPCredentials(...)
      aws.go                  # newAWSCredentials(...)
      azure.go                # newAzureCredentials(...)
      mtls.go                 # newMTLSReloader(...)
      doc.go                  # package comment
  ```

  CI runs `go build ./...` against the snippets module. A small drift-test (Go test in the same module, e.g., `drift_test.go`) reads `temporal-auth.md`, finds each named code fence, and asserts byte-equality (or normalized-whitespace equality, planner picks) against the corresponding `.go` file body. Markdown drift caught immediately.

  Planner's discretion: choice of drift-test mechanism (custom Go test reading both files; embedmd-style tooling; markdown-fence-tag annotations like `<!-- snippet: gcp.go -->`). Pick whatever's simplest and stdlib-only if possible.

- **D-7.5-06 — Separate snippets-only `go.mod`.** Cloud SDK deps (`cloud.google.com/go/secretmanager`, `github.com/aws/aws-sdk-go-v2/...`, `github.com/Azure/azure-sdk-for-go/sdk/...`) live in `docs/for-extension-developers/snippets/go.mod` only. The library's main `go.mod` stays clean — customers don't get cloud-SDK transitives just by importing skytime. Snippets module imports `go.temporal.io/sdk` for `client.Credentials` types but does NOT depend on the local skytime library (it's a Temporal-SDK-only consumer; demonstrates that the patterns work without any Skytime extension surface).

  Planner's discretion: whether the snippets module joins the Go workspace (`go.work`) or stays standalone. Standalone is simpler; workspace inclusion lets `go build ./...` from repo root catch it without a `cd`.

- **D-7.5-07 — New CI step in existing `.github/workflows/ci.yml`.** Add a `snippets-build` job (or step within the existing `ci` job) that runs `cd docs/for-extension-developers/snippets && go build ./... && go vet ./... && go test ./... -count=1` (the test covers the drift-test). Triggered on every push alongside the existing `go test ./...` and walkthrough_smoke. Unified CI surface; one workflow file to maintain.

### Audience + page shape

- **D-7.5-08 — Medium audience.** Reader is a Skytime user with cloud experience (has deployed services to GCP/AWS/Azure) but may not have set up workload identity / IRSA / Azure WI specifically. Each section opens with 2-3 sentences of cloud-IAM context (what WIF is, why it's preferable to long-lived service-account JSON keys, etc.) plus a link out to vendor docs for setup. Then dives into the snippet.

- **D-7.5-09 — Page intro + per-section intros.** Top of `temporal-auth.md`:
  - 2-3 paragraphs on why `client.Credentials` rotation matters (vs one-shot reads): security model (short-lived credentials, periodic refresh, no static API keys in process memory after rotation), how Temporal's `Credentials` interface enables this, how to pick your section based on cluster + cloud.
  - A short "Pick your section" directory: GCP / AWS / Azure / Self-hosted.

  Each section then has its own 2-3 sentence intro to the cloud-IAM flavor before the Assumes/Substitute/snippet block.

- **D-7.5-10 — PROJECT.md "Web UI / dashboard" Out-of-Scope carve-out: verbatim from v1.43-DRAFT-PLAN.md spec.** Drop in:

  > Web UI / dashboard — example dashboard ships under `examples/.../server/web/` as a teaching reference for the customer integration pattern; not a Skytime product feature, no framework dependencies, no roadmap for expansion.

  Goes into the existing `## Out of Scope` section of PROJECT.md. No tonal polish.
