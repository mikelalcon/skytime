## Memo-based Drift Detection Strategy (Pitfall 1 Strategy B)

Steady-state diff requires zero per-Schedule `Describe` calls. The reconciler:

1. At **Create** time, marshals `canonicalConfig{Cron, Timezone, Overlap, CatchupWindowNs, ContentHash}` to JSON and stashes the string in `Memo["skytime_canonical"]` via `client.ScheduleOptions.Memo` (a `map[string]interface{}` that the SDK encodes via the default DataConverter).
2. At **next boot's `List`**, pages through all Schedules; filters by `IsSkytimeManaged(entry.ID)`; for each match, reads `entry.Memo.GetFields()["skytime_canonical"]` and decodes via `converter.GetDefaultDataConverter().FromPayload(pld, &raw)` (symmetric to encode).
3. **Diff** compares the freshly-marshaled `desired.canonical` against `actual.canonical` byte-for-byte. Equal → no-op. Different (including missing/malformed Memo, since that decodes to `""`) → Update.

ContentHash inclusion is the load-bearing detail: a flow's `.star` source change keeps the cron expression the same but bumps ContentHash → Update fires → `Action.Args[0].(dag.WorkflowInput).ContentHash` reflects the new value → fired workflows look up the correct FlowRegistry entry (Pitfall 7).

## ContentHash-in-Canonical Pitfall 7 Mitigation

```go
type canonicalConfig struct {
    Cron            string `json:"cron"`
    Timezone        string `json:"timezone"`
    Overlap         string `json:"overlap"`
    CatchupWindowNs int64  `json:"catchup_window_ns,omitempty"`
    ContentHash     string `json:"content_hash"`  // ← Pitfall 7
}
```

`TestDiff_UpdateOnContentHashChange` pins the behavior: identical cron / timezone / overlap / catchup, only ContentHash drifts → diff emits an Update. Without this, editing a flow file (which changes ContentHash but not necessarily the cron config) would leave the Schedule pointing at the OLD ContentHash; the next Schedule firing would look up `(FlowName, OldContentHash)` and miss the registry — fired workflows would fail with `FlowNotInRegistry`.

## SDK Limitation: Memo Staleness After Update (Documented)

The Go SDK's `ScheduleHandle.Update` does NOT include the Memo field in its outbound `UpdateScheduleRequest` gRPC call. After an Update, the cluster's Memo keeps the OLD `skytime_canonical` value. On the next boot:

1. `listSkytimeManaged` reads the stale Memo.
2. `diff(desired, actual)` sees the same drift the previous boot saw.
3. The reconciler emits the same Update again — byte-identical.

This is **idempotent thrash** bounded to one redundant Update per drifted Schedule per boot. Functionally correct (the Update payload replaces Spec, Action, and Policy correctly, and is byte-identical across boots) but produces extra cluster round trips until the next real change cycles the Memo. `TestReconcile_UpdateMemoStaysStale_DocumentedLimitation` pins the limitation: two simulated boots with the same stale-Memo actual state both emit an Update with the same Reason.

Workarounds rejected:
- **Delete-and-recreate** would lose operator-set State preservation (`Paused=true`, `Note="operator paused"`).
- **In-band Describe-after-Update + push Memo via separate path** isn't possible — the SDK provides no API to update only the Memo.

Fix lives upstream in the Go SDK; revisit when `client.ScheduleUpdate` gains a `Memo` field or `ScheduleHandle.Update` populates `UpdateScheduleRequest.Memo` from `ScheduleUpdateOptions.DoUpdate`'s return value.
