| Option | Description | Selected |
|--------|-------------|----------|

**User's choice:** Free text — "my plan is to run the servers in active-active with hundreds of workers"
**Notes:** Original options sized for typical (single-digit replica) deployments. User's actual scale (hundreds of replicas) changes the math — "last write wins" would cause hundreds of redundant API calls at every rolling deploy. Re-asked with options sized for the actual scale.

### Where should reconciliation actually live in hundreds-of-replicas active-active?

| Option | Description | Selected |
|--------|-------------|----------|
| Separate `skytime reconcile` subcommand (initial recommended framing) | One-shot subcommand from CI/CD. Workers never reconcile. | |
| Server-side flag, opt-in to a 'reconciler' replica | One replica marked with `--reconcile=...`; others run plain server. | |
| Leader election among workers | Self-elect via Temporal-backed lease. | |
| Every replica reconciles, idempotent calls | "Last write wins" at scale. | |

**Aborted question / re-framed:**
User pushed back on the CI/CD framing ("Why are you talking about CI? This is not going to be used for CI"). I had wrongly projected a CI pipeline onto the deployment model. Re-asked with the CI framing removed. The actual options collapsed to three:

1. Every replica reconciles at boot
2. One designated replica reconciles (label/flag-based)
3. Separate binary/subcommand invoked out-of-band (independent of how operator invokes it)

User then proposed a "label for a subset of workers to act as cron reconciler" — equivalent to option 2. Discussion clarified that the existing `--cron-reconcile` flag IS the label (no need for a separate label concept). User confirmed.

**User's choice (locked):** Single-flag opt-in. ONE replica gets `--cron-reconcile`; others run plain `skytime server`. No leader election. No distributed lock. No separate binary. Operator wires the flag via their deployment topology (e.g., one Kubernetes Deployment replica gets the flag).

### Flag naming + simplification

User questioned the `strict|preserve|dry-run` three-value enum: "I think we don't need that. They either are able to create/update/delete or not." Strong point — with the `skytime/` ID prefix already isolating Skytime-managed schedules from everything else on the cluster, the `preserve` half-measure isn't useful. If you've opted into managing schedules, deleting orphans is what you want.

Simplification:
- Boolean `--cron-reconcile` flag (replaces `--reconcile=strict|preserve|dry-run` three-value enum)
- Dry-run handled separately

### How should dry-run be exposed?

| Option | Description | Selected |
|--------|-------------|----------|
| Separate `--dry-run` flag (Recommended) | Two boolean flags; `skytime server --cron-reconcile --dry-run`. | |
| Separate `skytime cron-plan` subcommand | One-shot subcommand; `skytime server` flag stays pure CRUD boolean. | ✓ |

**User's choice:** Separate `skytime cron-plan` subcommand
**Notes:** Cleaner separation — `skytime server` stays purely a long-running worker concern; cron-plan is its own out-of-band concern.

## Cron req-shape + lambda support

### `req.*` shape for cron-triggered workflows

User clarifying question: "Do we need the schedule_id for the steps?"

I walked through the value of `schedule_id`:
- Idempotency: WorkflowID already provides this (composed by Skytime)
- Logging/audit: Temporal attaches Schedule attribution automatically
- Cross-referencing the Schedule resource: extremely rare; workflow context already carries it

Conclusion: drop `schedule_id`; only expose `scheduled_time` + `actual_time`.

**User's choice:** Accepted ("K, sg") — the two-field shape: `req.scheduled_time` + `req.actual_time`.

**Lambda support:** `map=` and `idempotency_key=` lambdas optional on `core.cron(...)`. Sensible defaults when omitted: empty InitState auto-derived from scheduled_time + actual_time; WorkflowID auto-composes deterministically from scheduled_time.

### Reconcile failure mode at boot

| Option | Description | Selected |
|--------|-------------|----------|
| Fail to start, exit non-zero (Recommended) | K8s CrashLoopBackoff surfaces misconfig. | ✓ |
| Log error loudly, continue as plain worker | Warn-and-degrade. | |
| Retry with bounded backoff, then fail | Bounded exponential backoff. | |

**User's choice:** Fail to start, exit non-zero
**Notes:** K8s pod restart provides the retry behavior with backoff implicitly.

## Boot-time reconciliation slot

### Boot order placement

| Option | Description | Selected |
|--------|-------------|----------|
| Before worker.Start (Recommended) | parse → connect → register → cron-reconcile → worker.Start → mount HTTP. | ✓ |
| After worker.Start (parallel to HTTP mount) | Reconcile concurrent with listener bind. | |
| Concurrent with worker.Start (goroutine + WaitGroup) | Parallel boot for speed. | |

**User's choice:** Before worker.Start
**Notes:** Preview accepted with explicit boot sequence. Reconcile failure short-circuits BEFORE listener bind, so K8s TCP readinessProbe stays honest (port-not-open = pod not ready).
