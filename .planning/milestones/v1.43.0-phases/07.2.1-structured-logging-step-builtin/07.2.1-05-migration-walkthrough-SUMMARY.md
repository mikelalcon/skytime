## Decisions Made

- **Extended cmd/skytime-docgen rather than hand-editing builtins.md.** The docgen drift test (`tests/docgen_drift_test.go::TestDocgenDrift`) fails any time the checked-in `docs/reference/builtins.md` doesn't match a fresh `skytime-docgen` run. Hand-editing the file to add the four log entries would have produced a green PR but a red drift gate on the next CI run, and any future docgen run would clobber the hand edits. The correct fix was to extend the docgen pipeline; this lands as a Rule 2 deviation (missing critical functionality — the docgen as shipped couldn't surface the new namespaced builtins).
- **Walk every `builtins*.go` file (lexicographic) instead of hard-coding `builtins.go`.** A switch to e.g. only `builtins.go + builtins_log.go` would have left future split files orphaned. The `builtins*` prefix glob is a natural convention (matches the project's existing file naming for namespaced factories) and `_test.go` exclusion is the standard Go-build convention.
- **Trampoline recovery walks a cross-file FuncDecl registry, not just the current file.** `builtinLogInfo` lives in `builtins_log.go` and calls `buildLogStep` which also lives in `builtins_log.go` — but a future split could see them in different files. The two-pass `WalkBuiltinsMulti` shape (collect all FuncDecls first, then build Builtin records) handles this naturally. Single-pass would have failed any cross-file trampoline.
- **Used `[x]` for LOG-01/LOG-02 bullets, not `[ ]`.** The plan's acceptance-criteria grep pattern (`'^- \[ \] \*\*LOG-01\*\*'`) was a guidance hint, but the plan explicitly said "if the file shape has drifted, adapt the grep to match." Existing TRIG-01..10 / SERVER-01..03 / SCHED-01..03 / CLI-13 / EX-05 entries in REQUIREMENTS.md are all `[x]` — the convention there is `[x]` for shipped requirements, `[ ]` for not-yet-shipped. Phase 07.2.1 ships LOG-01 + LOG-02 in this very plan, so `[x]` is the correct status, and the Traceability `Status` column reads `Complete`.
- **Added a clarifying note below the new walkthrough sample stdout about `step_count=4` excluding log steps.** Without it, a reader walking through the cron tutorial would see a flow with 4 named bodies (seed_authors / fetch_repo_info / for_each_parallel / log.info) report `step_count=4` and wonder if log steps are silently dropped or if there's an off-by-one bug. The note pins D-7.2.1-13 (counter denominator excludes kind=log) inline. ~5-line addition; preserves the rest of the walkthrough verbatim.
- **Inlined trampoline test fixtures rather than reusing existing sample_globals.go.txt / sample_builtins.go.txt.** The existing fixtures don't carry any nested-module shapes; adding the log namespace to them would have polluted the cross-cutting WalkRegistry / WalkBuiltins legacy tests with Phase 07.2.1 specifics. New `sample_log_*.go.txt` fixtures keep concerns separated.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 2 - Missing critical functionality] cmd/skytime-docgen could not surface the four log.<level> builtins**

- **Found during:** Task 1 step 3 (regenerate `docs/reference/builtins.md`).
- **Issue:** Running `go generate ./pkg/parser/` produced ZERO new entries in `docs/reference/builtins.md`. Root cause: `cmd/skytime-docgen/walk.go::WalkRegistry` only recognized direct `starlark.NewBuiltin(name, p.builtin<X>)` registrations in `newParseTimeGlobals`; the `log` namespace is registered as a nested `&starlarkstruct.Module{Members: starlark.StringDict{...}}` (per Plan 02 D-7.2.1-01) and was silently skipped. Compounding issue: `cmd/skytime-docgen/main.go` hard-coded the per-file walk at `builtins.go`, but Plan 02 created the four factories in a NEW file (`builtins_log.go`) so even if WalkRegistry had surfaced the names, WalkBuiltins would not have found the bodies. Third compounding issue: each `builtinLog<Level>` is a one-line trampoline that calls `buildLogStep` — even with the file-discovery fix, `extractUnpackParams` would have found no `starlark.UnpackArgs` call inside the trampoline and fallen back to the alphabetical positional-only path, producing the wrong signature (`log.info(attrs, msg)` instead of `log.info(msg, attrs?)`).
- **Fix:** Three coordinated additions to `cmd/skytime-docgen`:
  1. `WalkRegistry` recurses into `&starlarkstruct.Module{...}` literals via new helper `starlarkstructModuleMembers` and surfaces fully-qualified `<ns>.<member>` registry entries.
  2. New `findBuiltinFiles(pkgDir)` + `WalkBuiltinsMulti(paths, registry, order)` walk every `builtins*.go` (non-test) in the pkg dir; the new two-pass shape collects FuncDecls across all files into a cross-file registry that the trampoline-recovery path uses.
  3. New `extractUnpackParamsWithRegistry` + `extractUnpackParamsRec` recurse through `return p.<helper>(...)` trampolines (via cross-file FuncDecl lookup) until they hit a body with a real `starlark.UnpackArgs` call, then extract from that.
- **Files modified:** `cmd/skytime-docgen/main.go`, `cmd/skytime-docgen/walk.go`, `cmd/skytime-docgen/walk_test.go`; new fixtures `cmd/skytime-docgen/testdata/sample_log_globals.go.txt` + `sample_log_builtins.go.txt`.
