# Phase 7.3: Dashboard + manual trigger page — Context

**Gathered:** 2026-05-12
**Status:** Ready for planning

<domain>
## Phase Boundary

Single-page stdlib-only dashboard at `GET /` served by `skytime server`, showing three sections:

1. **Live workflow list** — workflows from `client.ListWorkflow`; columns: WorkflowID, FlowName, Status, StartTime, **Run Duration**, **Last Updated**. All Running + last 100 Closed (two ListWorkflow calls merged in the server-side poller, deduped by ID). Status visualized as `● running` / `● completed` / `● failed` / `● replayed` colored dot + text.
2. **Recent webhook deliveries** — in-memory ring buffer (last 100; not persistent across restarts), source-agnostic. Each row shows source kind, ALL headers (compact, per-value-truncated to ~80 chars), payload summary (compact JSON when Content-Type indicates JSON; raw-truncated otherwise), HTTP response status (with color badge), and mapped workflow ID (anchor link that scrolls + highlights the matching workflow row).
3. **Manual trigger form** — flow dropdown (registered flows enumerated from `worker.Registry()`) + JSON textarea + `Run` button → `POST /api/trigger` → `client.ExecuteWorkflow`.

**Live updates** travel over **Server-Sent Events** (SSE), not polling, not WebSocket. `GET /api/events` (`Content-Type: text/event-stream`) emits a one-shot `snapshot` event on connect (full workflow list + recent deliveries arrays) followed by curated delta events (`workflow_started`, `workflow_status_changed`, `workflow_replayed`, `delivery_received`). A single server-side poller hits `client.ListWorkflow` every ~2s, computes deltas, and fans out — so N browsers do NOT multiply Temporal load.

**Critical refactor (UI-04):** Webhook ingress, manual trigger POST, and (later) cron Schedule callbacks all converge on a single `executeFlow(...)` function. The ExecuteWorkflow call currently inlined at `pkg/extension/receiver/handler.go:225` extracts into this function; webhook ingress + manual UI + cron callbacks all call it.

**Carried-forward locked decisions** (PROJECT.md / ROADMAP — NOT re-asked):
- Stdlib only: `net/http` + `html/template`; no JS framework, no external CSS, no bundler
- Manual trigger UI is a **JSON textarea**, NOT schema-aware form fields
- Polling **NOT WebSocket** (ROADMAP locked); we landed on SSE during discussion as the stdlib-friendly streaming alternative that satisfies "auto-refresh without manual reload" better than polling and stays inside "no WebSocket"
- Dashboard lives entirely under `pkg/cli/server/web/`
- `executeFlow` has THREE call sites: webhook ingress, manual trigger POST, cron Schedule callbacks
- "Teaching dashboard, not a Skytime product feature" — Out-of-Scope carve-out
- Single binary: worker + HTTP receiver + dashboard in one process

</domain>

<decisions>
## Implementation Decisions

### Live-update mechanism (Server-Sent Events)
- **D-7.3-01:** Use **Server-Sent Events** (SSE), not periodic polling and not WebSocket. SSE is the stdlib-friendly streaming option: `http.Flusher` on the server, native `EventSource` on the browser. Adopting SSE replaces ROADMAP success criterion #1's "auto-refreshes (via polling)" phrasing with "auto-refreshes (via SSE)"; the underlying behaviour ("a workflow that completes appears as 'completed' without manual reload") still holds and is now lower-latency.
- **D-7.3-02:** A **single server-side workflow poller** runs in `pkg/cli/server.go`'s boot sequence, polling `client.ListWorkflow` every ~2s, computing deltas vs last snapshot, and fanning out via the broadcaster. Browser count does NOT multiply Temporal load.
- **D-7.3-03:** New package `pkg/cli/server/web/events` (or sibling under `pkg/cli/server/web/`) exposes a `Broadcaster` with `Subscribe() (ch <-chan Event, unsubscribe func())` and `Publish(Event)`. Each subscriber has a small buffered channel (e.g. 16 entries) with drop-oldest on overflow. Backed by a single fan-out goroutine.
- **D-7.3-04:** SSE endpoint is `GET /api/events`, `Content-Type: text/event-stream`, served on the same `http.ServeMux` that already hosts webhook ingress.
- **D-7.3-05:** Curated v1 event taxonomy (JSON payloads, named SSE events):
  - `snapshot` — sent ONCE on connect; payload `{workflows: [...], deliveries: [...]}` containing the current state so the page loads in one round-trip.
  - `workflow_started` — new workflow seen (any source: webhook, manual, cron); payload `{workflow_id, flow_name, start_time, ...}`.
  - `workflow_status_changed` — running → completed / failed; payload `{workflow_id, status, close_time}`.
  - `workflow_replayed` — `HistoryLength` jumped after a worker restart; payload `{workflow_id, replay_count}`.
  - `delivery_received` — webhook delivery appended to the ring buffer; payload `{delivery_id, source, headers, payload_summary, mapped_workflow_id, status}`.
- **D-7.3-06:** On initial connect the server sends one `snapshot` event, then live deltas. NO event-ID / resume-from-last-id support in v1 — keeps the protocol simple. On reconnect (browser `EventSource` auto-reconnect), client gets a fresh `snapshot`.
- **D-7.3-07:** Shutdown lifecycle: when the server receives SIGINT/SIGTERM and begins draining, the broadcaster emits a final `event: shutdown` to all subscribers, then closes their channels. SSE HTTP handlers detect channel close, write a final event, and return cleanly. Browser `EventSource` auto-reconnects when the new server comes up and replays a fresh `snapshot`.
- **D-7.3-08:** Tiny page-header indicator: `● Connected` (green) when the browser's EventSource `readyState === OPEN`, `○ Reconnecting…` (gray) when `CONNECTING`, `✗ Disconnected` (red) when `CLOSED`. Updated via `addEventListener('open'/'error', ...)` on the EventSource object — ~5 lines of inline JS.

### Workflow list shape
- **D-7.3-09:** **Columns:** WorkflowID · FlowName · Status · StartTime · **Run Duration** · **Last Updated** (Duration = `now - StartTime` for running, `CloseTime - StartTime` for closed; Last Updated = most recent state change timestamp).
- **D-7.3-10:** **Sort:** newest start time first (matches Temporal Web UI convention).
- **D-7.3-11:** **Status visualization:** colored dot + text. Mapping: blue=running, green=completed, red=failed, orange=replayed. Pure CSS background-color on an inline `<span>`.
- **D-7.3-12:** **Row limit:** All currently-Running workflows + last 100 Closed workflows. Implemented as two `ListWorkflow` calls (Open and Closed) merged + deduped by WorkflowID in the server-side poller.
- **D-7.3-13:** **Empty state:** when zero workflows have ever fired, show column headers + a single hint row: "No workflows yet — fire a webhook, click Run below, or wait for cron." Teaches the three ways to launch a workflow.
- **D-7.3-14:** **Replayed status:** detect via `WorkflowExecutionInfo.HistoryLength` jumping unexpectedly after a worker restart (or via SearchAttributes if Temporal exposes a replay-count attribute). Display as `● Running (replayed 3 times)`. Replay detection is best-effort — if Temporal's APIs don't surface enough signal cleanly, fall back to plain `Running` and treat replay detection as nice-to-have rather than blocker. Make the implementation approach a finding the planner pins explicitly.
- **D-7.3-15:** **Temporal Web UI deep-link:** when a `--temporal-web-ui <url>` flag (or `SKYTIME_TEMPORAL_WEB_UI` env var) is set, render the WorkflowID column as `<a href="{TEMPORAL_WEB_UI}/namespaces/default/workflows/{id}">…</a>`. Default for dev = `http://localhost:8233`. Falls back to plain text when the flag is unset (production deploys without a Temporal Web UI co-located).
- **D-7.3-16:** **WorkflowID truncation:** middle-ellipsis (e.g., `weekly_digest/dLKtq…20:51:00Z`) with full text on hover via the `title` attribute. Keeps the table scannable; lossless on inspect.

### Webhook delivery row shape
- **D-7.3-17:** **Source-agnostic rendering — MANDATORY constraint.** The dashboard surfaces webhook deliveries from ANY `TriggerSource` extension (Phase 7.1 ships `github.webhook` and `http.webhook`; future Slack/Stripe/custom extensions must not require template changes). The renderer MUST NOT reference source-specific header names like `X-GitHub-Event` or `Stripe-Signature` directly.
- **D-7.3-18:** **Payload summary:** when the delivery's `Content-Type` indicates JSON (e.g., `application/json`, `application/vnd.github+json`), pretty-print compactly to ~200 chars then truncate with ellipsis. For non-JSON content types, show the first ~200 raw bytes verbatim. For empty body, show `(empty body)`. Full payload available on row click via `<details>`.
- **D-7.3-19:** **Header summary:** show ALL request headers compactly in the row, each value truncated to ~80 chars (long values like `Authorization` get `…` appended). Full untruncated headers in the expanded `<details>`. **`Authorization` and any header whose name contains `secret`/`token`/`key`/`signature` MUST be redacted** (replaced with `<redacted>`) in BOTH the row summary and the expanded view — this is a Phase 7.1 secret-leak-gate constraint that extends naturally to the dashboard surface.
- **D-7.3-20:** **Status badge column:** every delivery shows its HTTP response status (200 / 400 / 401 / 404 / 415 / 500) with a colored badge — distinct colors per class (200 green, 4xx yellow/orange, 5xx red). Failed deliveries appear in the buffer alongside successes, in chronological order — the teaching value of "see why my webhook fails" depends on this.
- **D-7.3-21:** **Mapped workflow ID** column is an anchor link that, when clicked, scrolls the page to the matching row in the workflow list above AND briefly flashes that row (CSS animation — `@keyframes` flash, no JS framework). Implementation hint: each workflow row gets `id="wf-{workflowID}"` and the link is `href="#wf-{workflowID}"`; CSS `:target` selector handles the highlight on its own.
- **D-7.3-22:** **Ring buffer location:** the buffer lives in a new struct accessible from BOTH the receiver (which appends after each delivery) and the dashboard handler / SSE broadcaster. Likely shape: `pkg/cli/server/web/deliveries.RingBuffer` exposed via `cli.Options` or as a field on the receiver's `Deps` struct. Planner to pick the cleanest seam.

### Manual trigger form
- **D-7.3-23:** **Flow dropdown:** enumerates registered flows from `worker.Registry()` (alphabetical by flow name).
- **D-7.3-24:** **Input textarea:** placeholder shows minimal valid JSON `{}`; on submit the form POSTs to `/api/trigger` with `Content-Type: application/json` body `{"flow": "<name>", "input": {...}}`.
- **D-7.3-25:** **POST /api/trigger semantics:** validates that the flow exists and the input parses as JSON, then calls `executeFlow(...)` with no idempotency key and no signature validation (manual triggers always start a fresh workflow). On success: 200 with `{"workflow_id": "..."}`. On validation failure: 400 with `{"error": "..."}`. Server-side error: 500.
- **D-7.3-26:** **Submit feedback:** the form shows the most recent submission's result inline below the Run button: `✓ Started workflow <id>` (green) or `✗ <error>` (red). The user does NOT need to scroll up to the workflow list to confirm it fired — the SSE channel will surface the new row above, but the inline feedback closes the click loop immediately.
- **D-7.3-27:** **Validation:** client-side, the Run button is disabled until the textarea contains *something that parses as JSON*. Inline `JSON.parse(textarea.value)` in a small `<script>` block — ~5 lines.

### executeFlow consolidation (UI-04)
- **D-7.3-28:** **Extract the ExecuteWorkflow call** currently inlined at `pkg/extension/receiver/handler.go:225` (around the workflowInput + StartWorkflowOptions construction) into a new function `executeFlow(...)`. Suggested signature: `func executeFlow(ctx context.Context, c client.Client, taskQueue, flowName string, contentHash string, initState map[string]any, opts ExecuteFlowOptions) (workflowID string, status ExecStatus, err error)` where `ExecuteFlowOptions` carries `{WorkflowIDStrategy (compose-from-trigger / fresh-uuid / cron-suffix), ReusePolicy, ErrorWhenAlreadyStarted}`. Planner to refine.
- **D-7.3-29:** **Location:** `pkg/cli/server/web/flow_launch.go` OR `pkg/cli/server/executor.go` — somewhere shared by webhook ingress, manual trigger POST, and cron Schedule callbacks. Must NOT live under `pkg/extension/receiver/` (that would tie it to webhook ingress).
- **D-7.3-30:** **Cron call site wiring:** Phase 7.2's cron-schedule callback path (Temporal Schedule fires → cron-fired-workflow lifecycle in `pkg/extension/schedules/`) must be updated to call `executeFlow` rather than calling `c.ExecuteWorkflow` directly. Otherwise the ROADMAP success criterion #5 ("three call sites verified by a Go test that asserts call-site count") fails.
- **D-7.3-31:** **Call-site count test:** add a Go test that walks the AST and asserts `c.ExecuteWorkflow(...)` appears at exactly the expected number of call sites (one inside `executeFlow`, plus any callers in `pkg/cli/run.go` if `skytime run` still has its own embedded transient worker path). This is the firewall that prevents future drift.

### Dashboard styling philosophy
- **D-7.3-32:** **Visual feel: "slightly more polished"** — subtle drop shadows on the three main panels, hover/focus states for interactive elements, ~0.2s CSS transitions on color changes. STAYS within "stdlib only + no JS framework + no external CSS" constraints (all inline `<style>` in the template). Pushes against "teaching dashboard, not a Skytime product feature" framing slightly. **MUST NOT** add: animation libraries, transition frameworks, illustration sets, custom icons beyond Unicode symbols (✓ ✗ ● ○), or rebrand into a polished product look. Target inline `<style>` budget: <100 lines.
- **D-7.3-33:** **Typography:** `system-ui, sans-serif` for headers and narrative; `ui-monospace, SFMono-Regular, Menlo, monospace` for workflow IDs, timestamps, JSON payloads, headers in the delivery rows. No external font downloads, no `<link rel=preconnect>`.
- **D-7.3-34:** **Color palette:** semantic only — status dots (blue=running, green=completed, red=failed, orange=replayed) + one accent color (link blue, e.g., `#1a73e8`) for clickable text. Everything else grayscale (background `#ffffff`, table chrome `#f6f8fa`-ish, borders `#d0d7de`-ish, body text `#1f2328`-ish). No theme switcher / no dark mode in v1.
- **D-7.3-35:** **Responsiveness:** desktop-first (min comfortable width ~1024px). On narrow viewports, tables get an `overflow-x: auto` wrapper so columns stay aligned and the page scrolls horizontally inside the table region rather than breaking the layout. NO mobile-specific card layout.
- **D-7.3-36:** **Accessibility floor:** semantic HTML (`<table>`, `<thead>`, `<th scope="col">`, `<button>`, `<form>`, `<label for="...">`), color contrast minimum 4.5:1 for body text. Status dots have an accompanying text label so colorblind operators aren't excluded.

<specifics>
## Specific Ideas

- **Server-Sent Events architecture** per W3C spec + browser-native `EventSource` (no JS framework, no SSE library — stdlib `http.Flusher` is sufficient on the server, ~20 lines including the broadcaster loop).
- **Connection-state indicator UX** inspired by chat apps: `● Connected` / `○ Reconnecting…` / `✗ Disconnected` in the page header, driven by `EventSource.readyState` and `open`/`error` event listeners — ~5 lines of inline JS.
- **Cross-reference scroll + flash** for delivery→workflow linking: pure CSS `:target` + `@keyframes` flash, no JS framework. Each workflow row gets `id="wf-{workflowID}"`; delivery's mapped-workflow-id column links to `#wf-{workflowID}`.
- **Manual-trigger inline feedback** closes the click loop immediately (`✓ Started workflow <id>` next to the Run button) so the operator doesn't have to scroll up to the workflow list to confirm the trigger worked — even though the SSE channel will surface the new row above seconds later.
- **HTMX considered and explicitly rejected** during discussion: HTMX would have made the rendering layer leaner (server pushes HTML fragments, no client JS) but at the cost of relaxing PROJECT.md's "no JS framework" lock AND coupling the event stream to specific HTML targets — which would hurt the "rich future events" story (per-workflow drilldowns, machine-readable subscribers like `skytime tail`). Stdlib JSON events keep the event channel as composable infrastructure rather than tying it to the dashboard's DOM.

</specifics>
