## Live-update mechanism (introduced mid-discussion via user question)

User question: *"aren't there frameworks to make this as stream of events?"*

ROADMAP originally locked "polling" as the mechanism. User question prompted reopening this as a gray area.

| Option | Description | Selected |
|--------|-------------|----------|
| Polling (ROADMAP default) | `<meta refresh>` or fetch loop; 0–2s latency; ~5 lines | |
| **SSE — stdlib streaming** | `http.Flusher` + `EventSource`; instant updates; ~50 lines total; one long-lived conn per browser | ✓ (via "do what you think is best") |
| WebSocket | Bidirectional; protocol upgrade; overkill | |
| HTMX + sse extension | ~14KB CDN script; HTML fragment swaps; relaxes "no JS framework" lock | |

**User's choice:** SSE — stdlib streaming. After user expressed "lets use events" + asked which approach was best from operator POV AND for complex events in the future, Claude recommended stdlib JSON+SSE over HTMX because:
1. From operator POV — identical for current scope (the mechanism is invisible)
2. For complex events in the future — JSON events are more composable than HTMX HTML fragments (per-workflow drill-downs, machine-readable subscribers like `skytime tail`)
3. Keeps every PROJECT.md lock intact (HTMX would require relaxing "no JS framework")

User responded "K do what you think it is best" — Claude proceeded with stdlib SSE design and made the implementation decisions inline (event taxonomy, broadcaster pattern, shutdown lifecycle, connection-state indicator).

**Inline decisions made by Claude (user trusted to decide):**
- Endpoint `GET /api/events`, `text/event-stream`
- Single server-side workflow poller @ ~2s; fan-out via broadcaster (browsers don't multiply Temporal load)
- New `pkg/cli/server/web/events` package with `Broadcaster.Subscribe()/Publish()` pattern; per-subscriber buffered channels (drop-oldest on overflow)
- Curated event taxonomy: `snapshot`, `workflow_started`, `workflow_status_changed`, `workflow_replayed`, `delivery_received`
- On connect: one `snapshot` event with current state, then live deltas; no event-ID/resume in v1
- On drain: broadcaster emits `event: shutdown`, closes channels; EventSource auto-reconnects when new server comes up
- Page-header connection indicator: `● Connected` / `○ Reconnecting…` / `✗ Disconnected` driven by EventSource.readyState
