# Phase 7.4 Plan 01: WithCredfile Option lift + per-subcommand --credfile collapse Summary

**`cli.WithCredfile(path)` Option lifted from extbin's lazyCredfileHandler into pkg/cli with a 4-step resolution chain (flag > env > arg > default), collapsing per-subcommand --credfile boilerplate from ~22 lines per file to a single 3-line `applyCredfileFlag(cfg, credfilePath)` call.**

- **Files modified:** 6 (2 created, 4 modified)

## Accomplishments

- **CLI-08 satisfied:** Custom-binary authors get the dotfile-credfile pattern as a one-line `cli.WithCredfile(path)` Option call instead of needing to copy/maintain ~120 lines of `lazyCredfileHandler` boilerplate per binary.
- **Per-subcommand boilerplate collapsed (D-7.4-03 spirit):** The `--credfile` flag's type-assertion + friendly-error branches that used to be duplicated ~9 lines in BOTH `pkg/cli/server.go` AND `pkg/cli/cron_plan.go` now live ONCE in the package-private `applyCredfileFlag` helper. Each subcommand RunE's credfile section shrinks from a multi-branch block to a 3-line call site.
- **Resolution chain locked into the handler (D-7.4-03):** `--credfile` flag > `SKYTIME_CREDFILE_PATH` env var > `cli.WithCredfile(arg)` > `$HOME/.skytime-credentials` default. All four layers funnel through one `credfileHandler.Resolve()` path; no scattered fallback logic.
- **Lazy-init preserved across the lift (CLI-08 success criterion 1):** `credfile.New()` is NEVER called at `NewRootCommand` construction; the first `Resolve()` under mutex triggers init and caches `(resolver, error)` for stable cross-goroutine error messages. Pinned by `TestWithCredfile_LazyConstruction` via a "file-still-doesn't-exist" assertion after construction.
- **Last-wins semantics with WithCredentialHandler (D-7.4-02):** Both Options mutate `cfg.credHandler`; whichever appears later in the `NewRootCommand` chain wins silently. Pinned by `TestWithCredfile_LastWinsWithWithCredentialHandler` in both directions.
- **All 14 new tests pass + all existing TestServerCmd_*/TestCronPlan tests still pass** — no behavior regression beyond the friendly-error copy consolidation in the helper.

## Decisions Made

- **Declaration in options.go, implementation in credfile.go (D-7.4-04 LOCKED honored verbatim):** The plan was explicit that the user locked this split. Followed exactly — `func WithCredfile` appears once in options.go, zero times in credfile.go. The body is `c.credHandler = newCredfileHandler(path); return nil` — a single delegating line into credfile.go's unexported constructor.
- **applyCredfileFlag is the consolidation seam (D-7.4-03 spirit):** Owns the entire `interface{ SetCredfilePath(string) error }` type-assertion + every friendly-error string. Three error paths covered (nil handler, non-setter handler, setter error) plus the empty-string short-circuit + happy path — all 5 pinned by `TestApplyCredfileFlag_*` tests so server.go/cron_plan.go never need their own duplicate test fixtures for those branches.
- **Friendly-error copy upgrade carried by the helper:** The old server.go message said `cli.WithCredentialHandler`. The helper's nil-handler error now says `cli.WithCredfile or cli.WithCredentialHandler` since CLI-08 ships a second option that also wires a handler. This is a small user-visible copy win shipped as a free byproduct of the consolidation.
- **TestLazyCredfileHandler_SatisfiesServerCmdCapability NOT migrated:** It tested that the lazy handler implements `interface{ SetCredfilePath(string) error }`. The compile-time check `var _ extension.CredentialHandler = (*credfileHandler)(nil)` in credfile.go (and the implicit reachability of `SetCredfilePath` from `applyCredfileFlag`'s type-assertion happy-path test) collectively subsume that test's purpose. Dropping it removes a test that just reproduced what the compiler enforces.
