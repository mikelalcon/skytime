## Critical

### FIX-01: Hand-written lambdas execute against the parse-time predeclared env, not the locked lambda-time env — fail() becomes a no-op and lambdas mutate shared parser state at workflow time

**Location:** `pkg/interpreter/lambda_eval.go:42` — category: correctness, effort: large, verifier confidence: high.

**Current behavior / why it matters.** The project's stated safety model is that lambdas are re-parsed on workflow start ("Option B") and "evaluated inside the workflow against a locked predeclared environment." In reality no such re-parse exists. Hand-written DSL lambdas (script.fn, if_cond.cond, step.action_fn, step.block_fn, for_each_parallel items) are compiled exactly once at parse time by starlark.ExecFileOptions against the FULL parse-time env (p.parseTimeGlobals), and the resulting *starlark.Function is stored in p.lambdas and reused verbatim at execution time. Because a starlark.Function resolves predeclared names from its defining module (starlark interp.go:652 `fn.module.predeclared[name]`), lambda bodies at workflow time see flow/step/if_cond/script/for_each_parallel/call_flow/trigger/result/fail/log and every extension namespace — NOT bridge.LambdaTimeGlobals. Only synthesized interpolation/result-value lambdas ever compile against the locked env. Two confirmed consequences: (1) `fail(...)` inside a lambda resolves to the parser's builtinFail, which RETURNS a *dag.Fail node value instead of raising — so the idiomatic guard `lambda ctx: ctx.x or fail("missing")` never aborts the workflow and the run silently proceeds with a garbage value (in an if_cond cond, the Fail node is truthy and the wrong branch is taken). (2) Any lambda that calls a parse-time builtin performing state mutation runs that mutation at workflow time against the parser maps that boot.go shares into every ParsedFlow: `fail("...${ctx.x}...")` calls p.desugarInterpolation which writes p.lambdas and p.fileBytes (observed 1->2). Under concurrent workflow executions this is `fatal error: concurrent map writes` (unrecoverable Go crash killing the worker and every in-flight workflow), and per-execution mutation is non-deterministic across Temporal replay. Mitigating note: time/random/IO are absent from parseTimeGlobals too, so those specific sources stay unreachable — the sandbox is not fully open — but the locked-env guarantee and fail() semantics are broken.

**Evidence.** pkg/parser/parser.go:403 compiles the whole file (including all hand-written lambdas) against p.parseTimeGlobals: `starlark.ExecFileOptions(opts, thread, filename, execSrc, p.parseTimeGlobals)`. pkg/parser/lambda_capture.go:54 stores the parse-time Fn: `p.lambdas[id] = captured` with no re-compile. pkg/worker/boot.go:144 shares that live map into every flow: `lambdas := p.Lambdas()` then ParsedFlow{Lambdas: lambdas}. pkg/interpreter/lambda_eval.go:24,42 evaluates the parse-time Fn directly: `captured, ok := i.parsed.Lambdas[lambdaID]` -> `bridge.CallLambda(ctx, captured, ...)`; pkg/bridge/lambda_call.go:107 `starlark.Call(thread, captured.Fn, ...)`. starlark interp.go:652 reads predeclared from the defining module: `x := fn.module.predeclared[name]`. Empirically: a script `fn = lambda ctx: str(type(fail))+... type(step)` calls the parse-time builtins at runtime (fail=builtin, log=module, step=builtin); `lambda ctx: fail("boom: "+ctx.x)` returned `Fail(...)` with err=nil (no abort); `lambda ctx: fail("bad ${ctx.x}")` grew p.Lambdas 1->2 and p.FileBytes 1->2 at call time.

**Suggested fix.** Implement the intended re-parse-on-start so hand-written lambdas run against bridge.LambdaTimeGlobals. Concretely: add a boot step (pkg/worker/boot.go, after parsing) that, for each *dag.CapturedLambda whose BodyPos is not synthetic, re-extracts the lambda source from p.FileBytes()[Pos.Filename()] at Pos, wraps it as `_l = <lambda-source>`, and re-compiles via starlark.ExecFileOptions using bridge.LambdaTimeGlobals() as predeclared (adding only the validated module-level FreeVars), then replaces CapturedLambda.Fn with the re-compiled function used at runtime. This makes `fail` resolve to the aborting universe fail and makes `step`/`log`/`flow`/`result`/extension names surface `undefined: <name>` at boot. Add regression tests: a script lambda referencing `step` must be rejected at boot, and `lambda ctx: fail("x")` must return an error (abort) from bridge.CallLambda. Until then do NOT rely on the lambda-time env being locked for user lambdas.

**Verifier note.** Reproduced every claim empirically against the repo's own packages (scratchpad module, no repo edits). (1) Hand-written lambdas are compiled once by starlark.ExecFileOptions against p.parseTimeGlobals (parser.go:394,403), stored verbatim (lambda_capture.go:54), shared live into every ParsedFlow (boot.go:144, Lambdas() returns the live map), and invoked directly at workflow time (lambda_eval.go:42 → lambda_call.go:107). No re-parse-on-start exists for hand-written lambdas; only synthesized interpolation lambdas use bridge.LambdaTimeGlobals (interpolation.go:387). (2) Probe: inside a captured lambda called via bridge.CallLambda, type(fail)=builtin_function_or_method (parser's builtinFail), step resolvable, log=module — the parse-time env. (3) `lambda ctx: ctx.x or fail("missing x")` with falsy x returned a truthy Fail node with err=nil — no abort; walk_ifcond.go takes bool(val.Truth()) so the then-branch is taken silently. This exact pattern is documented in pkg/parser/doc.go:41-56 as raising *starlark.EvalError. (4) `lambda ctx: fail("bad ${ctx.x}")` at call time grew p.Lambdas 3→4 and p.FileBytes 1→2 — runtime writes to unsynchronized maps (parser has no sync at all) concurrently read by every workflow goroutine → Go runtime fatal killing the worker. Not a documented accepted risk: PROJECT.md:18/29/116-117, README.md:43/52, and globals.go:65-72 all promise the opposite ("locked 20-key lambdaTimeGlobals", "Option B: re-parse on workflow start", "predeclared envs are mutually exclusive"). No guard exists: D-19 free-var validation only covers lexical free vars, D4-02 only ctx.<attr>; no firewall test pins the lambda env. Finder's mitigation note is accurate (time/random/IO absent from parseTimeGlobals too, so no direct I/O escape). Severity critical stands: silent wrong-branch on a documented idiomatic guard (data-integrity) plus an unrecoverable whole-worker crash under concurrent executions.

### FIX-02: Webhook destination URL (treated as a secret) leaks into activity error results, Temporal history, and logs on transport/build errors

**Location:** `examples/http-github-webhook/extensions/webhook/webhook.go:176` — category: security, effort: small, verifier confidence: high.

**Current behavior / why it matters.** The webhook extension's design makes the destination URL the secret (D-WEBHOOK-HOST: the URL is resolved from a bearer credential's token, `url := bearer.Token.Reveal()`). But when the outbound POST fails, doPost returns the raw stdlib error, which is a `*url.Error` whose Error() embeds the full URL. On a transport failure (DNS lookup failure, connection refused, TLS error, timeout — all common transient conditions), line 176 returns `fmt.Errorf("webhook.post: transport: %w", err)` where err renders as `Post "http://secret-host.internal/hook?token=abc": dial tcp: ...` — exposing the entire secret URL (host, path, query). The same leak occurs at line 166 (build-request error for a malformed URL). This error becomes a NonRetryableErrResult/RetryableErrResult whose Err is serialized via errString into the ExecuteBatch activity result (pkg/dag/result_marshal.go), which Temporal persists in workflow history, and is also emitted through activity/worker logging. Transport errors are retryable, so each retry re-persists and re-logs the secret. This defeats the entire 'secrets never enter workflow state / activity results / Temporal history' guarantee for exactly the credential this extension protects. Note: this file lives outside the tests/firewall_credential_redaction_test.go coverage set (which does not include examples/.../webhook), and the leak is not a %+v verb, so no existing firewall catches it.

**Evidence.** webhook.go:158 `url := bearer.Token.Reveal()`; line 163 `stdhttp.NewRequestWithContext(ctx, POST, url, ...)`; line 166 `return nil, fmt.Errorf("webhook.post: build request: %w: %s", extension.ErrNonRetryable, err)`; line 176 `return nil, fmt.Errorf("webhook.post: transport: %w", err)`. Verified empirically: a POST to a bad host yields `Post "http://secret-webhook-host.internal:9999/hook?token=abc": dial tcp: lookup ...: no such host`, and a malformed URL yields `parse "http://sec ret/hook": ...` — both embed the full secret URL.

**Suggested fix.** In webhook.go doPost, never surface the raw *url.Error (which contains the URL). Use errors.As to unwrap *url.Error and format only its inner cause plus the credential ID, e.g.: `var ue *url.Error; if errors.As(err, &ue) { return nil, fmt.Errorf("webhook.post: transport error for credential %q: %v", bearer.ID(), ue.Err) }`. Apply the same to the build-request path at line 166 (reference bearer.ID(), not the URL/err). This preserves diagnosability (credential ID + underlying cause like 'no such host') without emitting the secret URL. Consider adding examples/http-github-webhook/extensions/webhook to the redaction firewall's target dirs in tests/firewall_credential_redaction_test.go as defense in depth.

**Verifier note.** Verified end-to-end from code I read and ran.

SECRET NATURE: The webhook destination URL is genuinely a secret — it is stored as extension.NewSecret(url) inside BearerCredential.Token (examples/http-github-webhook/extensions/webhook/webhook_test.go:56; webhook.go:42 "The credential MUST be a BearerCredential whose Token is the destination URL"). webhook.go:158 reveals it via bearer.Token.Reveal().

LEAK PATHS (both empirically reproduced by compiling/running Go against net/http):
- Line 176 (transport, retryable): fmt.Errorf("webhook.post: transport: %w", err) where err is a *url.Error whose Error() = `Post "http://secret-webhook-host.internal:9999/hook?token=abcSECRET": dial tcp: lookup ...: no such host` — full host+path+query leaked.
- Line 166 (build request, non-retryable): malformed URL yields `parse "http://sec ret-host.internal/hook?token=abcSECRET": ...` — also full URL.

PROPAGATION VERIFIED:
- pkg/activity/action_executor.go:100 returns the op error UNWRAPPED.
- Transport error is retryable (execute_batch.go isRetryable: no ErrNonRetryable wrap → default true), so ExecuteBatch returns (nil, err) to Temporal → error recorded in workflow history (ActivityTaskFailed) and emitted via activity logging; re-persisted/re-logged on every retry.
- Build-request error wraps extension.ErrNonRetryable → becomes NonRetryableErrResult{Err: err}, whose Err is serialized via errString(r.Err) = err.Error() in pkg/dag/result_marshal.go → written into the ExecuteBatch result which Temporal persists in history.

NO GUARD CATCHES IT (double miss): tests/firewall_credential_redaction_test.go only matches %+v / %#v string literals (this leak uses %w, not a forbidden verb) AND its targetDirs (lines 46-60) include examples/http-github-webhook/extensions/github but NOT .../webhook. Skytime has no regex error scrubber by design (secret.go D2-09; PROJECT.md:124) — type-level Secret protection is the whole defense, and the secret escapes that protection the moment it is embedded in a plain *url.Error.

NOT AN ACCEPTED RISK — IT VIOLATES A DOCUMENTED INVARIANT: PROJECT.md:59 codifies the receiver-side rule ".Reveal() leak gates (≤3 sites, // SECURITY: comment each, never fed into fmt.Errorf/slog/http.Error)". The webhook .Reveal() site at webhook.go:158 has no // SECURITY: comment and is fed (indirectly, via the %w-wrapped *url.Error) into fmt.Errorf — exactly what that gate forbids. README confirms the webhook extension is shipped, documented Phase-6 example code authors are told to copy.

SEVERITY: Left at high (unchanged). It is example-scoped rather than core-library, but it is shipped/documented/tested demo code and it defeats the project's central, explicitly-documented "secrets never in workflow state / activity results / Temporal history" guarantee for the exact credential this extension exists to protect. The suggested fix (errors.As to unwrap *url.Error, log ue.Err + bearer.ID() only) is correct and sufficient.

### FIX-03: ExecuteBatch reports success with silently skipped actions when the activity context is cancelled (worker drain), and walkStep ignores SkippedResult

**Location:** `pkg/activity/execute_batch.go:88` — category: reliability, effort: small, verifier confidence: high.

**Current behavior / why it matters.** When ctx is cancelled mid-batch, ExecuteBatch emits SkippedResult placeholders for the unrun actions and returns (results, nil). A nil error means Temporal records the activity as COMPLETED. The main way an activity ctx gets cancelled while the workflow is still healthy is worker graceful-stop expiry (baseWorker.Stop cancels the background context after WorkerStopTimeout, SDK internal_worker_base.go:713-714). In that case the completion is ACK'd, the workflow resumes on another worker, and walkStep's only failure check is extractFirstNonRetryable — SkippedResult entries are ignored entirely — so the step is treated as fully successful even though some (or all) of its actions never executed. A routine deploy that hits the drain timeout mid-batch silently drops side effects, directly contradicting the durability story documented in WorkerOptions.WorkerStopTimeout ('uncompleted workflow tasks are NOT ACK'd ... this IS the durability story' — pkg/worker/options.go:119-125), which holds for workflow tasks but not for this activity path.

**Evidence.** execute_batch.go:81-89: `if err := ctx.Err(); err != nil { for j := idx; j < len(batch); j++ { results = append(results, dag.SkippedResult{Idx: j, Reason: "activity cancelled"}) } return results, nil }`. walk_step.go:150-153 only checks `extractFirstNonRetryable(results)`; walk_step.go:294-301 scans solely for `dag.NonRetryableErrResult` — SkippedResult never causes an error.

**Suggested fix.** Two complementary fixes: (1) In ExecuteBatch (pkg/activity/execute_batch.go), on ctx.Err() != nil return (nil, ctx.Err()) (or temporal.NewCanceledError) instead of (results, nil) so the server records the attempt as failed/cancelled and retries it after the deploy — the batch is idempotent by Policy D so re-running is safe. (2) Defense in depth in walkStep (pkg/interpreter/walk_step.go): after decoding results, treat any dag.SkippedResult that is NOT preceded by a NonRetryableErrResult as an error (e.g., return a retryable ApplicationError 'batch cancelled before action N ran') so a completed-with-skips activity can never be walked past as success. Update TestExecuteBatch_CancellationStopsBetweenActions to assert the new contract.

**Verifier note.** CONFIRMED end-to-end from code across three layers.

(1) Activity layer — pkg/activity/execute_batch.go:81-89: on ctx.Err()!=nil mid-loop, ExecuteBatch appends SkippedResult placeholders for unrun indexes and returns (results, nil). Verified.

(2) Temporal SDK v1.42.0 mechanism (go.temporal.io/sdk@v1.42.0). The activity ctx derives from backgroundActivityContext (internal_worker.go:2133, internal_task_handlers.go:2289 rootCtx). baseWorker.Stop() closes stopCh immediately, waits up to WorkerStopTimeout on stopWG, THEN calls backgroundContextCancel(ErrWorkerShutdown) (internal_worker_base.go:703-714). So a batch still executing when the drain timeout expires sees its ctx cancelled mid-loop — exactly the finding's scenario. On return with err==nil, internal_task_handlers.go:2388 calls convertActivityResultToRespondRequest with err=nil, which at internal_task_pollers.go:1619-1628 returns RespondActivityTaskCompletedRequest carrying the partial results — the isActivityCanceled/cancelAllowed branch (1631) is only reached when err!=nil, so it is bypassed. Crucially the completion is reported via reportActivityComplete(context.Background(), ...) (internal_task_pollers.go:1515), NOT the cancelled ctx, so the COMPLETED result reliably reaches the server and is written to history. Line 2364's early-return only triggers on DeadlineExceeded, not Canceled, so it does not intercept.

(3) Interpreter layer — pkg/interpreter/walk_step.go:141-154: after ExecuteActivity(...).Get(&results), the only failure check is extractFirstNonRetryable(results) (line 150), which scans solely for NonRetryableErrResult (line 294-301). SkippedResult is ignored — pinned by TestExtractFirstNonRetryable_SkippedIgnored (walk_step_test.go:377-383). No result-completeness or shutdown check exists anywhere in the interpreter (grep confirmed). On workflow resume the activity is already COMPLETED, so .Get() returns the recorded partial result and the batch is NOT re-run; the step is treated as fully successful and side effects for skipped actions are permanently dropped.

Durability-story contradiction is accurate: WorkerStopTimeout doc (pkg/worker/options.go:119-125) promises uncompleted WORKFLOW tasks are not ACK'd and get redispatched — true for workflow tasks, but this ACTIVITY path ACKs a completed-with-skips result.

Adversarial checks: (a) Not a documented accepted risk — it appears in .planning/FIX-OPPORTUNITIES.md item 6 (a known-bug list), NOT in PROJECT.md Out of Scope or README 'What This Is Not', so documentation corroborates rather than refutes it. (b) Reachability is real: the drain-timeout-expiry case is explicitly implemented by skytime server's --drain-timeout; a slow multi-action idempotent block/block_fn batch straddling the timeout boundary triggers it. (c) The suggested fix's safety claim holds: Policy D (D2-05) makes block batches homogeneously idempotent, so returning an error to force a whole-batch retry is safe.

Severity: leave at high. This is silent side-effect loss on a routine deploy with no error surfaced anywhere and a direct contradiction of the stated durability guarantee. It requires the specific timing of a batch straddling the drain-timeout boundary (not every deploy), which keeps it from being critical, but silent correctness loss on a routine operation fully warrants high. severityOverride=unchanged.

Note: the finding is aware that the current behavior is design-locked (STATE.md line 193, test TestExecuteBatch_CancellationStopsBetweenActions asserts (results,nil)) — the lock was chosen for graceful cancellation but did not account for worker-drain expiry vs user-initiated cancellation being indistinguishable at this layer, which is the actual defect. The finding's two-part fix and test-update note correctly target this.

### FIX-04: Default --addr ":8080" binds all interfaces, exposing the unauthenticated manual-trigger endpoint and webhook payloads, contradicting the documented "localhost-by-default" trust boundary

**Location:** `pkg/cli/flags.go:89` — category: security, effort: small, verifier confidence: high.

**Current behavior / why it matters.** docs/walkthroughs/dashboard.md line 3 states "The dashboard is single-tenant and localhost-by-default" and line 108 accepts no-auth explicitly on that basis ("intended for localhost / internal-network use only"). But defaultAddr is ":8080", which binds 0.0.0.0. POST /api/trigger launches ANY registered flow with attacker-controlled input; its only gate is sameOriginOK, which a non-browser client trivially satisfies by sending `Origin: http://localhost:8080` with Content-Type: application/json (the docs themselves show this curl recipe at dashboard.md:122-124). GET / and GET /api/events have no gate at all and stream recent webhook delivery bodies (PayloadFull up to 64KB each) to any network peer. ### FIX-11: load() cycle crashes the whole process with an unrecoverable stack overflow

**Location:** `pkg/parser/load.go:71` — category: reliability, effort: small, verifier confidence: high.

**Current behavior / why it matters.** makeLoad only commits a loadCache entry AFTER starlark.ExecFileOptions completes (load.go:100). There is no in-progress sentinel, so when file A loads B and B loads A, the recursive load never hits the cache and re-reads/re-executes the file forever. Each iteration consumes Go stack; the result is 'fatal error: stack overflow', which recover() in parse() CANNOT catch — the process dies (verified: exit code 2, 'runtime: goroutine stack exceeds 1000000000-byte limit'). This violates PARSE-05 (every malformed input must surface as *dag.ParseError) and kills the long-running `skytime server` / `skytime validate` on two user-authored .star files that load each other. Worse, parser.go:53-55 explicitly (and wrongly) claims 'Cycles fall through naturally — once we've started loading a file ... the second concurrent load returns whatever globals were committed at the cache-set point' — the code never sets the cache before exec, so the claimed protection does not exist.

**Evidence.** load.go:71-73 `if cached, ok := p.loadCache[resolved]; ok { return cached.globals, cached.err }` — the only cache write paths are line 81 (I/O error) and line 100 `p.loadCache[resolved] = loadCacheEntry{globals: globals, err: execErr}` AFTER ExecFileOptions returns. Reproduced: a.star=`load("./b.star","bsym")`, b.star=`load("./a.star","asym")` → `fatal error: stack overflow`, process exit 2.

**Suggested fix.** In makeLoad (pkg/parser/load.go), before os.ReadFile, insert an in-progress marker: add a `loading map[string]bool` field to Parser (init in NewParser), set `p.loading[resolved]=true` before executing, delete after commit; at the top of the callback, if `p.loading[resolved]` is true, return &dag.ParseError{Pos: callerPos, Msg: fmt.Sprintf("load %q: cycle in load graph", module)}. (This is the standard go.starlark.net load-cycle pattern.) Also fix the false comment at pkg/parser/parser.go:53-55. Add a regression test in pkg/parser/load_test.go asserting a two-file cycle returns a *dag.ParseError containing "cycle".

**Verifier note.** Verified by direct code read and end-to-end reproduction. pkg/parser/load.go: the cycle check at line 71 only consults loadCache, whose sole write paths are line 81 (I/O error) and line 100 (after ExecFileOptions completes); no in-progress sentinel exists, and the root file entered via ParseFile is never cached at all. Each nested load gets a fresh thread with a fresh step budget, so SetMaxExecutionSteps never trips. Reproduced against the real module: a.star loading b.star loading a.star yields 'runtime: goroutine stack exceeds 1000000000-byte limit / fatal error: stack overflow', exit code 2 — a fatal runtime error the recover() in parse() (parser.go:340) cannot catch, violating the PARSE-05 contract that malformed input surfaces as *dag.ParseError. ### FIX-16: SIGTERM delivered during boot (before signal.Notify at step 7 completes... i.e., during Temporal dial or .star parsing) is swallowed — server finishes boot and ignores the shutdown request

### FIX-36: for_each_parallel with item="" shares one mutable state map across all parallel branches

**Location:** `pkg/interpreter/state.go:65` — category: correctness, effort: small, verifier confidence: high.

**Current behavior / why it matters.** state.scoped returns the RECEIVER unchanged when itemVar is empty, so every branch interpreter in walkForEach (walk_foreach.go:127-129) shares the parent's state map. Branch-local script steps then write to the shared map via setOutput, and because branch scheduling order depends on activity completion order, later branches observe earlier branches' outputs non-deterministically — cross-branch contamination and a replay-determinism hazard. The parser's UnpackArgs requires the item kwarg to be present (builtins.go:1194) but accepts item="" without complaint, so a flow author can reach this path.

**Evidence.** state.go:64-66: `func (s *state) scoped(itemVar string, item any) *state { if itemVar == "" { return s } ... }`; walk_foreach.go:127: `scopedState := i.state.scoped(fe.ItemVar, item)` feeds `branchInterp.state = scopedState` for every branch. builtins.go:1193-1195 unpacks `"item", &itemVar` with no non-empty validation.

**Suggested fix.** Two small changes: (1) in builtinForEachParallel (pkg/parser/builtins.go), reject empty item with a position-aware ParseError ('for_each_parallel: item must be a non-empty identifier'); (2) defensively, make state.scoped always copy even when itemVar is empty (drop the early return) so branch isolation never depends on parser validation. Add a parse test for item="".

**Verifier note.** Confirmed real by reading the full chain. (1) state.go:64-66 — scoped("", ...) returns the receiver unchanged (pinned by TestState_ScopedEmptyItemVarReturnsSame, state_test.go:58-62). (2) walk_foreach.go:127-129 — every branch is assigned branchInterp.state = scopedState, so with item=="" all N branches share the SAME *state / same vars map. (3) builtins.go:1192-1201 — UnpackArgs declares "item", &itemVar with no non-empty/identifier validation; I empirically confirmed UnpackArgs accepts item="" (err=nil, itemVar=""), and there is no isValidIdentifier gate anywhere in pkg/parser. So a flow author can reach this path. (4) The write/read plumbing makes contamination observable: walk_script.go:63 writes branch output via i.state.setOutput(alias, ...) into the shared map, and lambda_eval.go:42 reads via i.state.snapshot() from that same shared map. Branches yield at activity dispatch (walkStep), so siblings interleave; a body lambda can therefore observe a sibling's write on a shared alias key.

The "replay-determinism hazard" framing survives adversarial scrutiny. The project's OWN replay model (pkg/testing/replay_diff.go:199-202) states that under the always-on D5-D1 replay — two independent TestWorkflowEnvironment runs, not a true history-driven replay — "sibling completion order is genuine non-determinism." With proper item!="" each branch gets its own copied map (scoped copies at state.go:68-73), so sibling reordering only permutes emitted-event ORDER, which the harness tolerates via canonicalizeParallelOrder + multisetEqual. With item=="" the branches share one map: cross-branch reads yield interleaving-dependent lambda-output PAYLOADS that differ between the two runs, and those payload differences are NOT rescued by multiset equality (the event bag itself differs, not just its order). Post-loop, branch writes also persist into parent state with an interleaving-dependent last-writer-wins value, unlike the isolated item!="" case. This is a genuine correctness/determinism defect distinct from the documented, accepted parallel-ordering tolerance.

Not documented as accepted risk: README "What This Is Not" and .planning/PROJECT.md "Out of Scope" say nothing about for_each_parallel item validation or shared-state branches.

Severity: leaving at low (finder's rating). It is real but reachable only via a degenerate author input (item=""), and only manifests when body steps read/write overlapping aliases and interleave; the fix is small (reject empty item at parse time, and/or drop the scoped early-return so branch isolation never depends on parser validation). The suggested fix and evidence are accurate.

### FIX-37: Empty task_queue passed positionally bypasses the D3-19 rejection (presence detection only inspects kwargs)

Semantic impact is small (empty == inherit), but it is a documented validation (D3-19 'reject empty when supplied') that a legal call shape bypasses, and every DSL builtin is documented/kwarg-styled anyway.

**Evidence.** builtins.go:141 `if hasKwarg(kwargs, "task_queue") && taskQueue == ""` and builtins.go:200-207 hasKwarg iterating only `kwargs []starlark.Tuple`. Repro: `flow("f", {}, [script(...)], "")` → parse err nil, `TaskQueue=""`.

**Suggested fix.** Make the DSL builtins keyword-only, which both closes this gap and matches all documentation/examples: at the top of builtinFlow, builtinStep, builtinIfCond, builtinScript, builtinForEachParallel, builtinCallFlow and builtinTrigger add `if len(args) > 0 { return nil, &dag.ParseError{Pos: callerPosition(thread), Msg: "<name>: keyword arguments only"} }` (fail() and log.* keep their positional msg). **Verifier note.** Reproduced end-to-end against the real parser. starlark.UnpackArgs (verified in vendored source) fills params positionally in pair order regardless of the '?' optional marker, so flow("f", {}, [steps], "") lands "" in task_queue with an empty kwargs slice; hasKwarg (pkg/parser/builtins.go:200-207) inspects only kwargs, so the D3-19 guards at builtins.go:141 (flow), :336 (step), and :595 (if_cond output_alias) are bypassed. ### FIX-38: Interpolation scan/syntax errors report positions computed from the call's Lparen, not the string literal — wrong line and column on multi-line calls

**Location:** `pkg/parser/interpolation.go:89` — category: correctness, effort: medium, verifier confidence: high.

**Current behavior / why it matters.** scanInterpolation's posAt documents openPos as 'the position of the OPENING quote of the user's string literal', but every caller passes callerPosition(thread) — the builtin call's Lparen — because the evaluated kwarg no longer carries a literal position. posAt then advances line/col through the RAW (already unescaped) string content starting from the call position. Verified: for `flow(\n    name = "myflow ${ctx.a",\n ...)` the unterminated-interpolation error is reported at `p.star:1:12` while the `${` actually sits at line 2, col 20 — wrong line AND column (offset lands mid-way through the word 'flow(' line). **Evidence.** interpolation.go:50-55 doc 'openPos is the position of the OPENING quote of the user's string literal' vs builtins.go:382 `p.desugarInterpolation(raw, pos, "")` where `pos := callerPosition(thread)` (call Lparen), same at builtins.go:171, 523, 679, 1136 and builtins_log.go:83. Repro: error `p.star:1:12: unterminated interpolation` for a `${` physically at 2:20.

**Suggested fix.** Recover the true literal position at builtin time using the already-established re-parse pattern (assertLogMsgLiteralAt): re-parse p.fileBytes[pos.Filename()], find the CallExpr whose Lparen positionsEqual(pos), locate the relevant kwarg's *syntax.Literal, and pass its TokenPos advanced past the opening quote(s) as openPos (fall back to the call position when the arg isn't a source literal, e.g. helper-forwarded strings). ### load() sandbox containment is purely lexical (filepath.Rel) and follows symlinks, allowing reads outside the parser root

**Location:** `pkg/parser/load.go:170` (low/security). resolveLoadPath enforces the D-17 sandbox by computing filepath.Rel(rootAbs, abs) on the lexically-cleaned path and rejecting a `..` prefix, then os.ReadFile follows any symlink. A symlink placed inside the root that points outside it is not resolved before the containment check, so `load("/link/x.star")` (where root/link -> /some/outside/dir) reads files outside the sandbox. Confirmed empirically: a load through an in-root symlink read a file in a separate temp dir outside root. The target must be valid Starlark to be usable, and creating the symlink needs write access to the served rootdir, so impact is bounded — but this defeats the load()-containment security control that PROJECT.md lists as delivered ("traversal rejection"). The same gap applies to pkg/worker/boot.go's filepath.WalkDir, which will os.ReadFile a symlinked .star file. A code comment acknowledges symlink hardening is deferred to a possible "Phase 4 os.Root", but there is no PROJECT.md scope decision recording this as accepted, and lexical `..` traversal being covered does not cover the symlink vector. Secondary nit at the same check: `strings.HasPrefix(rel, "..")` also over-rejects a legitimately in-root directory whose name begins with `..` (e.g. `..data`).

**Note.** This overlaps existing `.planning` discussion of `load()` sandbox scope. **Suggested fix:** In resolveLoadPath, resolve symlinks before the containment check: `absResolved, _ := filepath.EvalSymlinks(abs)` and `rootResolved, _ := filepath.EvalSymlinks(rootAbs)`, then run filepath.Rel on the resolved pair (handle not-exist by resolving the deepest existing ancestor). Better, adopt os.Root (Go 1.24+) to open files with the root as a boundary that refuses symlink escape, and apply the same in pkg/worker/boot.go's walk so symlinked .star files outside root are not parsed. Also change the prefix test to `rel == ".." || strings.HasPrefix(rel, ".."+string(os.PathSeparator))` to avoid rejecting legitimate `..`-prefixed directory names. If symlink hardening is truly deferred, record it explicitly in PROJECT.md Out of Scope.
