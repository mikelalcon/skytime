<objective>
Fix Phase 04.1's latent interpolation-lambda-ID collision: when an extension factory call has MULTIPLE `${ctx.expr}` kwargs on the same .star line (e.g., `gh.list_open_issues(owner="${ctx.rp.owner}", repo="${ctx.rp.repo}")`), the parser today synthesizes lambdas that hash to the SAME D-18 ID (because `ar.Pos` is shared across kwargs and the ID is `sha256(fileBytes)[:4]:line:col`). The parser's `p.lambdas[id] = captured` is last-wins, so both kwargs end up pointing at the second kwarg's lambda body. At runtime both kwargs resolve to the same value, breaking `public_repo_check.star` (and CI's walkthrough_smoke).

Purpose:
- Restore correctness for the EX-04 README headline demo and CI's `walkthrough_smoke.sh`.
- Make multi-kwarg interpolation a parser-level invariant, not a flow-author footgun.
- Backstop the regression with TWO tests at TWO tiers (parser-focused + example-smoke) so any future regression fails locally in `go test ./...` without needing Temporal.

Output:
- Surgical signature extension: `desugarInterpolation(raw, openPos, disambiguator string)` + `captureLambdaAtPosition(fn, userPos, bodyPos, disambiguator string)`. When `disambiguator` is non-empty, the synthesized lambda ID becomes `<base-id>:<disambiguator>` — distinct per kwarg key, identical across reparses (deterministic).
- All five OTHER call sites (flow name, step name, script id, fail msg, log msg) pass `""` — their IDs and behavior are unchanged.
- One new parser test file + one new example-package test file. Both fail deterministically if the fix is reverted.
</objective>
