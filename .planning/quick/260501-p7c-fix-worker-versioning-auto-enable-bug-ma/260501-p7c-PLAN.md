<objective>
Fix the worker versioning auto-enable bug. `applyDefaults` currently flips
`UseBuildIDVersioning` to true whenever `BuildID` is non-empty (which is
always, given the "dev" default). Against a freshly-spawned `temporal
server start-dev` task queue with no Build ID compatibility set
registered, Temporal refuses to dispatch tasks to versioned workers — the
workflow sits unscheduled forever and `skytime run` hangs.

The fix makes versioning explicit-only:
  1. Remove the auto-enable if-block from `applyDefaults`.
  2. Update the doc comment on `WorkerOptions.UseBuildIDVersioning` to
     state the opt-in contract (caller must register Build ID
     compatibility on the task queue first).
  3. Update `TestWorkerOptions_Defaults` (currently asserts auto-enable)
     to assert the new opt-in behavior, and add
     `TestWorkerOptions_VersioningOptIn` covering both the default-false
     and explicit-true-preserved cases.
  4. Clarify PROJECT.md D3-20 line: versioning is opt-in.
  5. End-to-end: rebuild `cmd/skytime`, spawn `skytime dev-server` in
     background, run `skytime run examples/skeleton/simple_check.star`,
     assert it completes within 30s.

Purpose: Default UX must be "it works" — a fresh dev server + a fresh
binary should run the example flow without operator-side Build ID
choreography. Production deployers using `pkg/worker.NewWorker`
directly (long-running daemons) explicitly set
`UseBuildIDVersioning: true` AFTER registering a Build ID compatibility
set on their task queue.

Output: Bug fixed. Tests prove opt-in semantics. End-to-end manual
verification confirms no hang.
</objective>
