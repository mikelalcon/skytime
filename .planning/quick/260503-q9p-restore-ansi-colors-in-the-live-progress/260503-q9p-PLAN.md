<objective>
Restore ANSI colors on the live progress block — a regression introduced in Phase 04.1 Plan 06 when the live renderer was added without color wrapping. Today, on the normal user path (TTY + non-verbose), the user gets colorless `[skytime] flow ... starting`, `[N/M] step ... ✓ ...`, `→ branch`, and `[skytime] flow complete/failed` lines, while on every OTHER dispatch branch (non-TTY, --verbose, Windows) the static renderer correctly emits colored output via `p.colorBanner(...)`, `p.colorOk(...)`, etc.

Purpose: Make the most common user-facing path match the static path's color story. The live block is the default UX; the regression makes the binary look broken on first run.

Output: pkg/cli/progress_live.go's `applyEvent` writes color-wrapped static lines (banner / completion marker / arrow / failed marker) using the existing ANSI constants from progress_static.go. New TDD tests in pkg/cli/progress_live_test.go pin the color-presence guarantees; existing tests stay green.

Scope boundary (LOCKED — do NOT exceed):
- Color the FIVE static-line emissions in applyEvent: flow_start banner, step_complete completion row (✓ green / ✗ red), branch arrow, flow_complete success banner, flow_complete failed banner + "failed" word.
- Do NOT color the in-progress redraw region rows (`[skytime] in-progress  N active` and the per-row spinner lines in `redraw()`). Those redraw 10×/sec; coloring them is out of scope for this regression fix and the orchestrator explicitly deferred them.
- Do NOT add new dependencies (firewall_cli_test.go enforces charm-log v2 only).
- Do NOT redefine ANSI constants in progress_live.go — reuse the package-private constants from progress_static.go (same `package cli`).
- Do NOT change structural live-block ANSI (`\x1b[1A`, `\x1b[2K`, `\x1b[?25l`, `\x1b[?25h`).
- Do NOT touch progress_live_windows.go (Windows uses static renderer, already colored).

const (
    ansiReset       = "\x1b[0m"
    ansiDimCyan     = "\x1b[2;36m"  // banner color (used by colorBanner)
    ansiBrightCyan  = "\x1b[1;36m"  // counter color (used by colorCounter)
    ansiBrightWhite = "\x1b[1;37m"  // kind color (used by colorKind)
    ansiGreen       = "\x1b[32m"    // ok marker color (used by colorOk)
    ansiRed         = "\x1b[31m"    // err marker color (used by colorErr)
    ansiYellow      = "\x1b[33m"    // arrow color (used by colorArrow)
)

// Static-path color helpers (progressHandler methods) — color choices
// the live renderer must mirror exactly:
func (p *progressHandler) colorBanner(s string) string  { return p.wrap(s, ansiDimCyan) }
func (p *progressHandler) colorCounter(s string) string { return p.wrap(s, ansiBrightCyan) }
func (p *progressHandler) colorKind(s string) string    { return p.wrap(s, ansiBrightWhite) }
func (p *progressHandler) colorOk(s string) string      { return p.wrap(s, ansiGreen) }
func (p *progressHandler) colorErr(s string) string     { return p.wrap(s, ansiRed) }
func (p *progressHandler) colorArrow(s string) string   { return p.wrap(s, ansiYellow) }
```

type safeBuffer struct { /* mutex + bytes.Buffer; safe for concurrent writer + reader */ }

The new color-presence tests must read the RAW output (`out.String()`) and assert ANSI substring presence — mirroring the pattern in pkg/cli/progress_test.go::TestProgress_StaticPath_NonTTY which uses `require.NotContains(got, "\x1b[")` on the raw buffer.

require.Contains(t, raw, ansiReset, "every wrap is closed by ansiReset")
```

Use `stripAnsiTest(raw)` ONLY when asserting structural content (the words "flow complete", the marker glyph "✓", etc.) without coupling to color.
